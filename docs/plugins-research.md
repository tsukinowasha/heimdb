# Plugin research notes

How the plugins in the [`plugins.md`](plugins.md) list were chosen and checked, the HeimDB differences found along the way, and the verdicts that changed.

## What was checked

| Checked | HeimDB | How chosen | Plugins |
|---|---|---|---|
| 2026-10-16 | 0.2.9 | Plugins that Tsukinowa Inc. supports on the WordPress sites it runs on HeimDB | 24 |
| 2026-10-16 | 0.2.9 | Plugins used on WordPress sites that Tsukinowa Inc. runs (excluding the 24 above) | 52 |
| 2026-10-20 | 0.2.17 | The top 100 popular plugins on wordpress.org (in the order of `https://wordpress.org/plugins/browse/popular/`; `browse=popular` on `api.wordpress.org`), excluding 22 already checked in the two rows above | 78 |
| 2026-11-06 | Stage 107 (after 0.2.36) | The three rows above checked again (except `hello` and `s3-uploads`; the latest version for plugins on wordpress.org, and the newest version at hand for versions obtained). Added `forminator`, which newly entered the top 100 | 155 (1 new) |

The list has 157 plugins. WP Mail SMTP and W3 Total Cache were checked again after the fix in 0.2.10. For the plugins that use `SHOW INDEX ... WHERE` (`seo-by-rank-math`, `duplicator`, `fluent-smtp`, `google-analytics-for-wordpress`, `wp-smushit`, `wpforms-lite`, `sg-security`, `smart-slider-3`), the comparison was run again on 0.2.18, and no statement failed only on HeimDB except for the `wpforms-lite` analytics table (primary key).

For plugins not on wordpress.org (paid plugins, plugins distributed on GitHub), the newest version we could get was checked ("version obtained" in the list). It may not be the latest version. Plugins that the author distributes on their own site were taken from there ("official site").

## Method

The check on 2026-11-06 ran the static check with a fresh cache (`TMPDIR` set to an empty directory), ran activation (`activate.sh`; for each plugin it reports the statements HeimDB rejected, whether the plugin was activated, and HeimDB warnings other than statement errors) in groups of 18, and compared with real MySQL (the `scenarios/activate.sh` scenario of `compare.sh`) only the plugins that had rejected statements. WordPress was 7.1.4 from `wordpress:php8.3-apache`. The 8 comparison scenarios were also run again.

- **Static**: `scripts/plugin-check/check.py <slug or directory>`. It fetches the latest version from wordpress.org (or reads that version if given a directory) and searches the source for the primary key and character set in `CREATE TABLE`, full-text search, stored procedures and the like, and SQL that reads or writes files. It only reads strings in the source, so it cannot see tables built in code (such as Yoast SEO's migrations), nor syntax differences (`ENGINE='InnoDB'`). An uppercase `CREATE TABLE` whose column list cannot be read (the column list is a variable, or the table name is a function call with arguments) is reported as "table definition not readable" and is checked by eye. Columns and primary keys added later with `ALTER TABLE` are not checked.
- **Activation**: `scripts/plugin-check/activate.sh <slug or directory>`. It starts HeimDB from this repository (port 3336) and WordPress (Docker), activates the plugins one at a time, opens the front page and the admin screens, runs the scheduled cron, and reports the statements HeimDB rejected meanwhile. `table not found` for dbDelta's statements that check whether a table exists is not counted, because it is the same on MySQL. Tables not created by activation alone (tables created when a settings screen or a feature is enabled) cannot be seen, so this is combined with the static check. Plugins that need another plugin (add-ons for WooCommerce or Elementor) are checked with that plugin kept active: `REQUIRES=woocommerce scripts/plugin-check/activate.sh <slug>`.
- **Comparison**: for plugins whose main features do not run SQL on activation alone (e-commerce, backups, search and replace, security scans), `scripts/plugin-check/compare.sh <scenario>` runs the same steps (creating products and orders with WP-CLI, taking a backup with `wp eval`, and so on) on WordPress on HeimDB and on real MySQL 8.0 (Docker) one after the other, and compares the statements that failed (on MySQL, `MYSQL_ERRNO` in `performance_schema.events_statements_history_long`; exit code 1 if any statement failed only on HeimDB). The scenarios are in `scripts/plugin-check/scenarios/` (the activation-only `activate.sh` takes slugs in `PLUGINS`; the others are WooCommerce, UpdraftPlus (backup and restore), Better Search Replace, Wordfence, Loginizer and WP Cerber. `keyless-branch.sh` uses HeimDB branches, so run it with `DB=heimdb`).
- **In use**: installed on a WordPress site running on HeimDB and checked by using the admin screens and the main features.
- "Same on MySQL" was confirmed by trying the same statement or the same activation on real MySQL 8.0.

## Details of plugins that do not work

- **WooCommerce** (`woocommerce`, partly works): full-text search of orders (only when enabled in the settings) does not work, because HeimDB rejects full-text indexes. Orders (the HPOS tables), products, attribute filtering and the admin screens worked the same as on MySQL (comparison on 0.2.19; 0 statements failed only on HeimDB).

## Verdicts that changed

- **Tables without a primary key (usable since stage 72)**: HeimDB 0.2.19 and earlier rejected tables without a primary key, and the plugins below did not work. Stage 72 made tables without a primary key possible (stage 72 in docs/plan.md), and on 2026-10-24 they were checked again with comparison scenarios (`scripts/plugin-check/scenarios/loginizer.sh`, `wp-cerber.sh`) (for both, 0 statements failed only on HeimDB, apart from WP Cerber's `OPTIMIZE TABLE`). They were run again after the fixes from the Fable review, with the same result. With `keyless-branch.sh`, both plugins' tables were changed in a branch (adding Loginizer records; adding Cerber ACL entries and adding and deleting log rows) and merged into production. This confirmed that the rows combine with the rows the plugins kept writing in production, and that after the merge, counting failed logins and lockout, logging, traffic logging, `UPDATE` and `DELETE` still work. Searching the source again for tables without a primary key (154 plugins) found one more: the table UpdraftPlus's restore creates to check privileges (below). The 23 plugins that had a new version on wordpress.org at that time (`all-in-one-seo-pack`, `wpforms-lite`, `w3-total-cache` and others) were checked again on the latest version with the static check and the activation comparison (add-ons for WooCommerce and Elementor with those active), and 0 statements failed only on HeimDB (the versions and check dates in the table were updated).
  - **WP Cerber** (`wp-cerber`): it has tables without a primary key (`cerber_acl`, `cerber_lab`, `cerber_qmem`, `wp_cerber_uss`, the log `cerber_log` and the traffic log `cerber_traffic`), and activation stopped. The log and traffic log tables are built in code (`CRB_Schema_Manager`), so the static check cannot see them; activation finds them. It was closed on wordpress.org on 2022-09-22 because of a security issue and is distributed on the official site (`https://downloads.wpcerber.com/plugin/wp-cerber.zip`). The version checked was 9.10 from the official site. The `OPTIMIZE TABLE` run by the maintenance cron is a statement HeimDB did not accept, and it was a syntax error (unrelated to tables without a primary key; the same for any table).
  - **Loginizer** (`loginizer`): the login limiting log table `loginizer_logs` has no primary key (only `UNIQUE KEY ip`), so the table could not be created and all reads and writes for login limiting failed.
  - **UpdraftPlus** (`updraftplus`): before a database restore, it creates a table to check privileges, `CREATE TABLE updraft_tmp_... (test INT)` (no primary key). HeimDB 0.2.19 and earlier could not create it, and the code then treats this as "no privilege to create tables" and restores by emptying the tables and reloading them (this path was not run). Since stage 72, the restore loads into tables with a temporary prefix and then renames them (atomic restore), and `scenarios/updraftplus-restore.sh` restored the same as real MySQL 8.0 (deleted posts come back). The only statements that failed only on HeimDB were the checks for whether stored functions can be created (`CREATE FUNCTION`, `DROP FUNCTION`).
- **Primary keys containing strings, byte strings, dates or `ENUM` (usable since 0.2.19)**: HeimDB 0.2.18 and earlier allowed only integer columns and a single `CHAR` / `VARCHAR` column in a primary key, and the plugins below did not work. 0.2.19 allowed any combination of `CHAR`, `VARCHAR`, `BINARY`, `VARBINARY`, `DATE`, `DATETIME`, `TIMESTAMP` and `ENUM` (stage 70 in docs/plan.md), and they were checked again on 2026-10-21 (WooCommerce and Wordfence with comparison scenarios, WPForms Lite and WP Reviews for Google with the activation comparison, WPML and its add-ons with activation; for all of them, 0 statements failed only on HeimDB).
  - **WPML** (`sitepress-multilingual-cms`): the primary key of `icl_locale_map`, created on activation, is `(code, locale)` (two `VARCHAR` columns); it could not be created and activation stopped. `acfml`, `wpml-media-translation`, `wpml-string-translation` and `wp-seo-multilingual`, which run on top of WPML, can be activated alone but are of no use without WPML. The version checked was 4.6.11, the version obtained (it is paid, so the latest version could not be obtained).
  - **Wordfence** (`wordfence`): the primary key of `wfls_role_counts`, created on activation, is `(serialized_roles VARBINARY(255), two_factor_inactive TINYINT, passkey_inactive TINYINT)`; it could not be created and activation stopped. Past that, tables whose primary key contains an IP as `BINARY(16)` (`wfblockediplog`, `wfcrawlers`, `wflocs`, `wfreversecache`, `wflivetraffichuman`, and `filenameMD5` of `wffilemods`) and `wftrafficrates (eMin, IP, hitType)`, which contains an `ENUM`, also could not be created.
  - **WP Reviews for Google** (`wp-reviews-plugin-for-google`): the primary key of `trustindex_google_views` is a single `DATE` column; it could not be created and activation stopped.
  - **WooCommerce** (`woocommerce`): the primary key of `wc_product_attributes_lookup`, the table for attribute filtering, is `(product_or_parent_id, term_id, product_id, taxonomy VARCHAR(32))`, and it could not be created. A new WooCommerce install has the setting that uses this table (`woocommerce_attribute_lookup_enabled`) enabled, so statements listing products filtered by an attribute (such as color) failed, and writes to this table failed each time a product was saved.
  - **WPForms Lite** (`wpforms-lite`): the primary key of the analytics table `wpforms_analytics_forms` is `(form_id BIGINT, period_date DATE)`; it could not be created, and the analytics of form views and submissions did not work. Creating and submitting forms works.
- WP Mail SMTP (tables for debug events and the email send queue, created with `ENGINE='InnoDB'`) and W3 Total Cache (the table with a `CHARACTER SET ascii` column, created when the CDN is enabled) were partly working on 0.2.9 and work since 0.2.10.

## HeimDB differences found

Behavior that differs from MySQL, found while checking the top 100 popular plugins on wordpress.org. All were confirmed by comparing with real MySQL 8.0.

- **`DESCRIBE` with a column (fixed in stage 107)**: `DESCRIBE table column` (also `DESC` and `EXPLAIN`; the column is a name or a string that can use `%` and `_`) was a syntax error (MySQL returns that column's row in the same form as `SHOW COLUMNS`; empty if there is no such column). `intuitive-custom-post-order` uses it to check whether a column exists when it is deactivated, and the `term_order` column of `wp_terms` was left behind. MySQL does not distinguish upper and lower case of column names in `LIKE` and `WHERE` of `SHOW COLUMNS`, but HeimDB does (an existing difference; plugins check with the same name they created).
- **Comparing an indexed `ENUM` column with a string not in its definition (fixed in stage 107)**: `status = ''` returned error 1105 (`value  is not valid for this Enum`) (columns without an index could already be compared). `forminator` runs it in its migration when upgrading. MySQL stores a value not in the definition as the empty value, and `''` matches that row. HeimDB does not store values not in the definition (it returns an error), so no row matches. When looking up a value not in the definition, HeimDB reads the whole index and filters by the condition (the result is the same; Forminator runs it only once, when upgrading).

- **`OPTIMIZE TABLE`, `CHECK TABLE`, `REPAIR TABLE` (fixed in stage 74)**: HeimDB 0.2.21 and earlier returned a syntax error (MySQL rebuilds the table and returns a result table). WP Cerber's maintenance cron runs them (found in the stage 72 comparison). WP-Optimize, Advanced Database Cleaner, WP-Sweep, WordPress's `wp-admin/maint/repair.php`, and wp-cli's `wp db check` / `optimize` / `repair` (mysqlcheck) also use them. Stage 74 made them do nothing and return a result in the same form as MySQL (stage 74 in docs/plan.md).
- **The `WHERE` of `SHOW INDEX` (`SHOW KEYS`) was ignored (fixed in 0.2.18)**: `SHOW INDEX FROM t WHERE Key_name = 'x'` returned all indexes without filtering (the engine's `buildShowIndex` did not read `WHERE`). Plugins decide "the index exists if a row comes back", so code that adds an index did not add it, and code that drops one ran `DROP INDEX` on an index that did not exist and failed (activation of `smart-slider-3`, `sg-security` and `google-listings-and-ads`). A plugin activated on HeimDB 0.2.17 or earlier may be missing an index it should have added (such as rebuilding indexes when the plugin is upgraded; check with `SHOW INDEX FROM table`). MySQL compares the values of `Key_name` and `Column_name` case-insensitively, but HeimDB is case-sensitive (plugins check with the same name they created, so this causes no trouble). In the top 100, `woocommerce` (6 files, including the index added to `wp_comments`, checking whether the order full-text index exists, and checking the primary key of the tax tables), `seo-by-rank-math`, `wordfence`, `wpforms-lite`, `duplicator`, `fluent-smtp`, `google-analytics-for-wordpress`, `google-listings-and-ads`, `sg-security`, `smart-slider-3` and `wp-smushit` use it. `WHERE` and `LIKE` on the other `SHOW` statements (`COLUMNS`, `TABLES`, `TABLE STATUS`, `VARIABLES`) are correct.
- **`DO 1` was a syntax error (fixed in 0.2.18)**: WordPress core's `wpdb::check_connection()` checks whether the connection is alive with `DO 1`. HeimDB did not accept `DO`, so WordPress decided the connection was lost and reconnected (reconnecting succeeds, so nothing stopped). Core calls it only when the connection is lost (2006), but `updraftplus` and `duplicator` call it for each table during a backup. `DO` prepared through the binary protocol (COM_STMT_PREPARE) is still a syntax error (WordPress does not use it; `internal/backend/do.go`).
- **Primary keys containing strings, dates or byte strings (fixed in 0.2.19)**: `woocommerce`, `wordfence`, `wpforms-lite` and `wp-reviews-plugin-for-google` in the top 100 could not create tables because of this (see "Verdicts that changed" above).
- **The (M,D) and UNSIGNED of `FLOAT(M,D)` and `DOUBLE(M,D)` are dropped (only recorded; counted in stage 119)**: HeimDB does not keep (M,D) or UNSIGNED in the table definition, does not round to D digits on storing, does not check the range, and represents the column as plain FLOAT or DOUBLE (fixing this needed a new data format version; fixed in stage 120 with data format version 8). On 2026-11-16, of the 157 plugins in [`plugins.md`](plugins.md), the source of the latest version of the 151 that could be fetched from wordpress.org and GitHub (`hello` as `hello-dolly`; the paid `advanced-custom-fields-pro`, `acfml`, `otgs-installer-plugin`, `wp-seo-multilingual`, `wpml-media-translation` and `wpml-string-translation` cannot be fetched) was searched for column definitions with `(M,D)` on `FLOAT`, `DOUBLE` (`DOUBLE PRECISION`) or `REAL`, and with UNSIGNED on `FLOAT`, `DOUBLE` or `REAL`. Two plugins use them, and for both, activation and the main features already worked (the verdict does not change).
  - `wordfence` 9.1.1: in `lib/wfSchema.php`, `event_time` of `wfAuditEvents` and `wfSecurityEvents` (DOUBLE(14,4)), `attackLogTime` and `ctime` of `wfHits`, `ctime` of `wfLogins` and `wfStatus` (DOUBLE(17,6) UNSIGNED), and `lat` and `lon` of `wfLocs` (FLOAT(10,7)). The upgrade in `wordfenceClass.php` also adds `attackLogTime` as DOUBLE(17,6) UNSIGNED. The tables are created with `CREATE TABLE IF NOT EXISTS` (not dbDelta). For timestamps (`microtime(true)`), the only effect is that digits beyond 6 decimal places are kept instead of rounded. The latitude and longitude in `wfLocs` come back to PHP with 6 significant digits (on real MySQL, a value of 35.6812363 is 35.6812).
  - `mainwp-child` 6.4.2: `duration` of `changes_logs` in `modules/changes-logs` (FLOAT(11,4)). It is created with dbDelta, so the type in DESCRIBE (`float`) differs from the definition, and each time the table creation code runs it issues `ALTER TABLE ... CHANGE COLUMN` (it runs only when the table version changes). Values with 7 or more digits get 6 significant digits (1234567.12345 is 1234567.1250 on MySQL and 1234570 on HeimDB).
- TLS: the newer MariaDB client (such as `mysqldump` in the official WordPress image) requires TLS by default. HeimDB without `-tls-cert` has its connections refused (`updraftplus` fell back to exporting with PHP). Real MySQL 8.0 talks TLS without any configuration.

## Checking again

When you use a new version of a plugin, or upgrade HeimDB, run the static check and activation again.

```sh
scripts/plugin-check/check.py --quiet redirection wp-mail-smtp ~/sites/x/wp-content/plugins/acfml
scripts/plugin-check/activate.sh redirection wp-mail-smtp ~/sites/x/wp-content/plugins/acfml
```

`activate.sh` needs Docker and Go. It runs HeimDB on port 3336 (`HEIMDB_PORT`) and WordPress on 127.0.0.1:18090 (`WP_PORT`), and removes them when it finishes.
