# SQL engine (fork of go-mysql-server)

In HeimDB, everything after SQL parsing (analysis, query plans, execution, and the MySQL protocol endpoint) is handled by `internal/sqlengine`, a fork of [go-mysql-server](https://github.com/dolthub/go-mysql-server) (stage 40 in [`plan.md`](plan.md)). This document records the source, what was not imported, the list of changes, and the steps for importing upstream fixes.

## Source

| | |
| --- | --- |
| Upstream | `github.com/dolthub/go-mysql-server` |
| Version | v0.20.0 (commit `5d7248826`, 2025-05-13) |
| Imported on | 2026-10-12 |
| License | Apache License 2.0 (`internal/sqlengine/LICENSE`. The original copyright notices stay in the files) |

Why fork: upstream releases rarely (17 months and 3,442 commits between v0.20.0 and main as of 2026-10), and main made a C library (ICU) the default for regular expressions (pure Go needs the build tag `gms_pure_go`). The security and panic problems that HeimDB works around are not fixed in main either. HeimDB needs to change many parts, and wants to specialize further for WordPress.

## Not imported

- `sql/encodings` (character set tables, about 90 MB of generated code): it depends only on the standard library, so it is read as is from the original module `github.com/dolthub/go-mysql-server` v0.20.0 (this is the only reason `go.mod` still depends on go-mysql-server). Collation weights affect index keys, that is, the data format, so it is not upgraded (dependabot does not upgrade it either).
- `_example`, `_integration` (client examples in other languages), `driver` (a `database/sql` driver): HeimDB does not use them.
- Files for running the upstream repository (`README.md`, `CONTRIBUTING.md`, `MAINTAINERS`, `SECURITY.md`, `SUPPORTED_CLIENTS.md`, `Makefile`, `check_repo.sh`, `format_repo.sh`, `mascot.png`, `go.mod`, `go.sum`), and `tools.go`, which only adds development tools as dependencies.

The upstream tests (`enginetest`, `memory`, and each package's `_test.go`) were imported as a regression safety net for engine changes. The tests for removed features (`TestLoadData`, `TestLoadDataErrors`, `TestLoadDataFailing`, `TestSelectIntoFile`) were replaced by `TestServerFilesRemoved`, which checks that the removed features return `sql.ErrServerFiles` (stage 42); their remaining bodies and expected values were deleted in stage 66. vitess (`github.com/dolthub/vitess`), which does parsing and the protocol, stays a dependency pinned to a version (if it needs changes, it will be imported the same way).

## Rules for changing the engine

- For each change, add a short row to the "Change list" in this document (stage, what was changed and where, a short reason), and write the full change and reason in the "Engine changes" section of that stage's record in `docs/stages/` (in English, from stage 130 on; records of earlier stages are in the pre-publication history and not in this repository). Add differences from MySQL that are only recorded to [`differences.md`](differences.md). Add tests (HeimDB-side tests or engine tests).
- In each file whose contents you change, add the line `// Modified by Tsukinowa Inc.: <what was changed> (docs/engine.md)` below the copyright notice at the top.
- When a change makes upstream tests fail, fix the tests too and write the reason (such as removing a feature WordPress does not need).
- At import, the upstream tests passed 53,301 cases in 27 packages and skipped 416 (the same as v0.20.0 as is). After stage 42, 53,208 passed and 414 were skipped (for the tests of removed features). After stage 66, 53,227 pass and 411 are skipped (3 tests that were skipped unconditionally were deleted).

## How to verify

```sh
go test ./internal/sqlengine/...   # upstream tests (packages run in parallel; the slowest takes about 30 seconds)
go vet $(go list ./... | grep -v internal/sqlengine)
```

The `go vet` checks that `go test` runs automatically pass in the engine too (the format strings were fixed in stage 42). Running all of `go vet` still reports 84 findings in the engine, such as struct literal style, so `go vet` is run without the engine.

## Importing upstream fixes

1. In the upstream repository, take the diff from the source commit `5d7248826` to the commit you want to import (`git diff 5d7248826 <commit> -- <path>`).
2. Apply the diff with its paths moved under `internal/sqlengine/` and the import paths rewritten (`git apply --directory=internal/sqlengine`). If it does not apply (files HeimDB changed, or upstream code after a large rewrite), move it by hand. Read HeimDB's fixes in the same place (rows of the change list), and write which one to keep and why.
3. Add it to the change list with the upstream commit. Make one commit per import, and check that reverting the commit makes the tests fail.

All PRs merged upstream after v0.20.0 (up to `c57d5b4c1` on main, 2026-11-09) were reviewed and sorted in stage 110 ([`engine-upstream.md`](engine-upstream.md): candidates to import, skipped, not reproduced, no effect). What happened to the 3 items listed at stage 40 (LIKE escapes, zero datetimes, ENUM quoting) is also there. Next time upstream is reviewed, start after `c57d5b4c1`.

Upstream vulnerability advisories (GitHub's advisories for go-mysql-server and vitess) are fetched every week by the `advisories` job of `vuln` in CI, which fails if any have not been checked (stage 127). How to check them, and how to decide whether to import a fix with the steps above or add it to `.github/known-advisories.txt`, are in "Checking for vulnerabilities" in [`operations.md`](operations.md).
