# WordPress 専用ブランチ型 DB 開発計画

Oct 2, 2026

## 概要と目的

MySQL 互換プロトコルで話し、WordPress のデータを「特定時点に戻せる」「ブランチでステージングを作れる」データベースを作る。実装は Go、SQL 層は go-mysql-server、ストレージは Pebble を使う。

この DB の価値は普通の MySQL にはできない機能に置くため、速度で MySQL を超えることは目標にしない。実用性より、今ないものを作ることを優先する。

看板機能は次の 2 つ。

- **タイムトラベル**: `AS OF` で過去の任意の時点のデータを読める。プラグイン更新で壊れたら更新直前に戻せる。
- **ブランチ**: 本番からコピーなしでステージングを切り、WordPress は `DB_NAME` を `wordpress@staging` のように指定するだけで使える。差分の確認と本番へのマージができる。

ブランチ機能を持つ他の DB との差別化は「WordPress を知っていること」で生む。具体的には URL の上書き、ID 衝突の回避、テーブルの意味に応じたマージで、詳細は「WordPress 特有の課題」に書く。

バージョン: 2026-11 に 0.3.0 でソースを公開した。0.x の間は、データ形式の後方互換をなくすときにマイナーバージョンを上げる（[`operations.md`](operations.md) の「HeimDB のバージョンを上げる」）。1.0.0 は公開から 1 年後（2027 年の終わりごろ）を目標にする。

当面やらないこと: エッジへの分散配置、性能最適化、汎用 MySQL としての完全互換、WordPress で使われない SQL 機能、全文検索（`MATCH ... AGAINST`。FULLTEXT インデックスは定義だけを扱う）。

## これまでの検証結果

go-mysql-server のインメモリバックエンド（`memory` パッケージ）だけで、WordPress のインストーラは修正なしで最後まで通った。wordpress-develop の PHPUnit テストスイートを本物の MySQL 8.0 と比べた結果は次のとおり。

| グループ | 件数 | MySQL 8.0 | 偽 MySQL（インメモリ） |
| --- | --- | --- | --- |
| option | 413 | 全件成功 | 全件成功 |
| meta | 481 | 全件成功 | 全件成功 |
| query | 1,896 | 全件成功 | 失敗 20、エラー 1 |
| wpdb | 651 | 全件成功 | 失敗 66 |

判明している原因は次のとおり。

- **同順位の並び順**: `ORDER BY post_date DESC` で日付が同じ行を、MySQL は ID 降順で返すが、偽 MySQL は ID 昇順で返す。MySQL は `type_status_date (post_type, post_status, post_date, ID)` インデックスを逆向きに走査しているためと考えられる（`EXPLAIN` での裏付けは未確認）。`test_query_sticky_posts_change` は単独実行でこの失敗を再現する。
- **同じ ID の重複**: グループ実行時のみ、期待 `758..754` に対して `754` が 5 回返る。単独では再現せず、前のテストから引き継ぐ状態が絡むと推測。主キーの `IN` 検索単体、およびトランザクション内での `IN` 検索では再現しなかった。未解明。（段階 20 で、インデックスの範囲の重複による同じ行の重複を見つけて直した。おそらくこれ）
- **文字コード**: koi8r、hebrew、big5 などへの `CONVERT ... USING` で接続が切れる（MySQL server has gone away）。テーブルの文字セット取得や `SET NAMES ... COLLATE` も本物と異なる。
- **dbDelta**: FULLTEXT インデックスが `SHOW INDEX FROM` で報告されず、毎回「追加が必要」と判定される。

これらはインメモリ実装の上での結果で、Pebble 実装では並び順の問題をインデックスの逆方向走査で構造的に解決する方針。

## アーキテクチャと設計方針

行を上書きせず、変更のたびに新しいバージョンを追記する MVCC を最初から採用する。タイムトラベルは「ある時刻以前の最新バージョンを読むこと」、ブランチは「分岐時刻までは親を、それ以降は自分の変更を重ねて読むこと」として実現する。後からバージョンを足すとキー設計が作り直しになるため、ブランチが `main` 1 つの段階からバージョンと時刻をキーに含める。

構成は 3 層。

1. **プロトコルと SQL**: go-mysql-server が MySQL ワイヤープロトコル、構文解析、実行計画を担う。
2. **ストレージアダプタ**: 自作部分。`sql.DatabaseProvider`、`sql.Database`、`sql.TableCreator`、`sql.Table`、`sql.InsertableTable`、`sql.UpdatableTable`、`sql.DeletableTable` を実装し、行とインデックスを Pebble のキーに対応づける。インターフェースはバージョンごとに変わるため、使用するバージョンの `memory` パッケージを正とする。
3. **Pebble**: 順序付きキー・バリューストア（`github.com/cockroachdb/pebble/v2`）。範囲走査、アトミックな一括書き込み、スナップショットを使う。

### キー設計

```
m/clock                                   → 最後に発行したコミット時刻
m/seq/<名前>                               → ID の採番器（"branch"、"table"）
m/branch/<ブランチID>                       → ブランチ情報（名前、親ブランチ、分岐時刻）
m/gc                                      → 最後に終わった GC の境界の時刻（これより前は読めない）
m/merge/<ブランチID>/<反転時刻>              → マージの基準（段階 7）
m/resolve/<ブランチID>/<テーブル名>/<id>      → 競合の解決の記録（段階 7b）
m/sync/<ブランチID>/<反転時刻>               → 親の変更をブランチに取り込んだ記録（キーの時刻は取り込みのコミット時刻、値は読んだ親の時刻。段階 94）
m/users                                   → ユーザーと権限（go-mysql-server の mysql_db の直列化。バージョンなし。段階 14）
m/format                                  → データ形式のバージョンの番号（段階 18）
m/logtrim                                 → 最後に消したコミットの記録の時刻（段階 24）
m/rewrite/<ブランチID>/<テーブルID>          → 書き直しの途中の新しいテーブル ID の印（段階 53。GC が消さない。起動時に片付ける）
m/mergeexclude                            → マージから外す表のパターンの一覧（JSON。バージョンなし。段階 60）
l/<時刻>                                   → コミットの記録（そのコミットの Pebble のバッチの中身。段階 24）
l/<時刻>/<番号>                            → 1 MiB を超える記録の続き（番号は 1 から。段階 59）
b/<ブランチID>/c/<テーブル名>/<反転時刻>       → テーブル定義（スキーマ）、または削除の印
b/<ブランチID>/t/<テーブルID>/ai            → AUTO_INCREMENT の次の値
b/<ブランチID>/t/<テーブルID>/r/<主キー...>/<反転時刻>
                                          → 行データ、または削除の印
b/<ブランチID>/t/<テーブルID>/i/<インデックスID>/<列...>/<主キー...>/<反転時刻>
                                          → インデックスの列と主キーの元の値（段階 27）、または削除の印
```

- 表記の `/` は区切りを示すだけで、実際のキーは「1 バイトのタグ（`m`、`b`、`c` など）」と「順序を保つ符号化をした値」をつないだもの。ID と時刻は 8 バイトのビッグエンディアン、名前は後述の文字列の符号化で入れる。
- 時刻はマイクロ秒単位の UNIX 時刻で、`m/clock` を使い「現在時刻と前回の時刻 + 1 の大きい方」として単調に発行する。キーには反転（`math.MaxUint64 - ts`）して入れる。同じ行のバージョンが新しい順に並び、「時刻 T 以前の最新バージョン」が 1 回のシークで得られる。
- 削除はキーを消さず「削除の印」を追記する。消すとブランチで消した行が親から透けて見える。値の先頭 1 バイトを `0x00`（削除の印）か `0x01`（データ）にする。
- `main` ブランチの ID は 1。テーブル ID とブランチ ID は `m/seq/` の採番器で払い出し、再利用しない。
- テーブル定義もバージョンを持つ。`ALTER TABLE` の後でも、`AS OF` やブランチの重ね合わせで「その時点のスキーマ」を引けるようにするため。行の値には、書き込んだときのテーブル定義のバージョン（時刻）を入れ、そのスキーマで復号する。
- テーブル定義のキーは小文字にした名前、行とインデックスのキーはテーブル ID にする。名前の変更は「旧名に削除の印、新名に同じテーブル ID の定義」を同じ時刻で書くだけで済み、行は書き直さない。削除したテーブルと同名で作り直すと、新しいテーブル ID になる。
- テーブル定義は JSON で保存する。列（名前、型の文字列、DEFAULT と ON UPDATE の式の文字列、NULL 可否、AUTO_INCREMENT、主キー、コメント）、主キーの列順、インデックス定義（ID、名前、列とプレフィックス長、一意か、キーの水準）、照合順序、コメントを持つ。型と式は go-mysql-server の文字列表現で保存し（FLOAT と DOUBLE の型の文字列は、段階 120 から MySQL と同じく `float(7,2)`、`double(10,3) unsigned`、`float unsigned` の形で桁と符号なしを持つ。段階 119 までの定義は `float` と `double` だけで、桁のない型として読む）、`planbuilder.ParseColumnTypeString` と `planbuilder.StringToColumnDefaultValue` で復元する。`CREATE TABLE` 文そのものは go-mysql-server から受け取れない（`CreateTable` に渡るのは構造化されたスキーマ）ため保存しない。
- インデックスのエントリの値には、インデックスの列と、含まれていない主キーの列の元の値を、行の値と同じ符号化（バージョンの番号なし）で持たせる（段階 27）。キーの文字列は照合順序の重みで元の値に戻せない（`'Post'` と `'post'` が同じキー）ので、文がこの列だけを使うときに本体の行を引かずに読むために値を持つ。照合順序で等しい値への更新（キーが同じ）でも、値が変わればエントリを書き直す。段階 27 より前に書いたエントリは値を持たず（空）、読むときは本体の行を引く（データ形式のバージョンは変えない）。
- インデックスの定義は、エントリに入れられる型の範囲を示す整数の水準（`key_level`。段階 117）を持つ。0（印なし。段階 117 より前に作った定義）は整数、日時、文字列、バイト列だけ、1 は DECIMAL、FLOAT、DOUBLE、ENUM も入れる、2（段階 120）は SET と BIT も入れる。列のどれかが水準の範囲にない型のインデックスはエントリを持たず、全件を読んで模擬する（段階 117 より前の DECIMAL などのインデックスと同じ）。新しい表、`CREATE INDEX`、マージで足すインデックス、表を書き直す `ALTER TABLE` には今の水準を付け、その時点の行からエントリを作る。前からあるインデックスは水準 0 のまま読み（過去の時点とブランチは、その時点の定義の水準で読むので、エントリのない時点を読まない）、利用者が `CALL heimdb_rebuild_indexes()` で今の水準にして作り直す（そのブランチの今の定義を書き、`CREATE INDEX` と同じ形でエントリを作る）。段階 121 から、本番は起動の後に main のものを裏で 1 つずつ同じ形で作り直す（`-rebuild-indexes`。データ形式のバージョンと記録の水準は変えない）。水準は定義の等しさ（復元、取り込み、マージのインデックスの比較）に含めない。
- セカンダリインデックスは InnoDB と同じく末尾に主キーを含める。逆方向に走査すれば、同順位の行が主キー降順で返り、MySQL の並び順と一致する。ただし go-mysql-server v0.20.0 が逆方向走査を選ぶ条件は限られる（`ORDER BY` をインデックスの走査に置き換えるのは、並べ替えの列がインデックスの先頭の列と一致するときだけ。`internal/sqlengine/sql/analyzer/replace_sort.go` の `isSortFieldsValidPrefix`）。
- 主キーのないテーブル（段階 72）は、エンジンには主キーのない表として見せ、保存のキーを次のどちらかにする（テーブル定義の `keyless`）。`wp_term_relationships` のため、複数列の主キーには最初から対応する。
  - 一意キーで並べる表: すべての列が `NOT NULL` で、前方の長さ付きの列を含まず、主キーにできる型（`rowenc.PKType`）の列だけの一意インデックスのうち、最初のもの（MySQL の InnoDB が暗黙の主キーにするもの）があれば、その列を保存のキーにする（定義の `pk_ordinals` がその列）。キーの形は主キーと同じ。インデックスの定義とエントリは普通の一意インデックスのまま持つ。
  - 行 ID で並べる表: そうでなければ、列の末尾に見えない 2 列 `__heimdb_row_id`（`bigint unsigned`。保存のキー）と `__heimdb_row_hash`（`varbinary(16)`。見える列の値の符号化の SHA-256 の先頭 16 バイト）を足し、`__heimdb_row_hash` に見えないインデックスを足す（列とインデックスの定義の `hidden`）。`__heimdb_row_id` は見えない AUTO_INCREMENT の列で、64 ビットの列と同じブランチの番号帯から、AUTO_INCREMENT のカウンタ（`ai`）で振る（エンジンには AUTO_INCREMENT の列のない表に見せる。そのため、AUTO_INCREMENT の列があり主キーのない表は拒否する）。全件は足した順に読める（MySQL の見えない行 ID と同じ）。エンジンは行を消すときと変えるときに古い行の値を渡すので、ハッシュのインデックスで行 ID を引く（同じ中身が何行もあれば、いちばん小さい ID）。`UPDATE`、マージ、復元、レプリカは行 ID を変えない。
  - 書き直し（`ALTER TABLE`）、一意インデックスの追加と削除、`ADD PRIMARY KEY`、`DROP PRIMARY KEY` のたびに、その時点の定義でどちらにするかを決め直す。変わるときは表を書き直す（空の表は定義だけを変える）。FULLTEXT インデックスは定義だけを持ち、検索のエントリは作らない（段階 10）。
- ブランチの差分は、そのブランチのキー空間を走査するだけで得られる。
- コミットの記録（`l/<時刻>`）は、そのコミットのバッチ（`m/clock` を含む）の中身を、同じバッチで書く。時刻はコミット時刻で、反転しない（古い順に読む）。レプリカは同じ記録を同じ順に適用し、自分も同じ記録を持つ。1 MiB を超える記録は、1 MiB ずつに分けて `l/<時刻>` と `l/<時刻>/<番号>`（4 バイトのビッグエンディアン、1 から）に書き、読むときにつなぐ（段階 59。1 つの大きな値は、Pebble がファイルに書き出すときに丸ごとと圧縮した写しをメモリに持つ）。記録しないのは、そのマシンだけの手入れ（GC とその境界 `m/gc`、データ形式のバージョン `m/format`、記録自身の削除とその時刻 `m/logtrim`、起動時の一時テーブルの片付け）。そのマシンだけのキーは、コミットを通さず Pebble に直接書く。

### データ形式のバージョン

データ形式のバージョンは `m/format` に置く（段階 18）。本番で使い始めたので、段階 36 から、既存のデータを読めることを守る。0.1.0 から 0.1.5 はバージョン 1、0.1.6 からバージョン 2（段階 38。1 列の文字列の主キー。バージョン 1 のデータはそのまま読め、起動時に番号だけを書き換える）、0.2.11 からバージョン 3（段階 59。大きなコミットの記録を分けて書く。バージョン 2 の記録は分けていない記録としてそのまま読め、起動時に番号だけを書き換える）、0.2.19 からバージョン 4（段階 70。バイト列、日付を含む主キーと、文字列を含む複数列の主キー。バージョン 3 のデータはそのまま読め、起動時に番号だけを書き換える）、段階 72 からバージョン 5（主キーのない表。バージョン 4 のデータはそのまま読め、起動時に番号だけを書き換える。記録の中身の形は 2 のまま、レプリカの記録の水準を 3 にする）、段階 94 からバージョン 6（親の変更をブランチに取り込んだ記録 `m/sync`。バージョン 5 のデータはそのまま読め、起動時に番号だけを書き換える。記録の中身の形は 2 のまま、レプリカの記録の水準を 4 にする。古い HeimDB は取り込みの記録を知らず、マージの基準を読み違えるので開かせない）、段階 117 からバージョン 7（DECIMAL、FLOAT、DOUBLE、ENUM の列を含むインデックスのエントリと、インデックスの定義のキーの水準。バージョン 6 のデータはそのまま読め、水準のないインデックスは前と同じくエントリを持たないものとして読む。起動時に番号だけを書き換える。記録の中身の形は 2 のまま、レプリカの記録の水準を 5 にする。古い HeimDB は水準を知らず、そのインデックスのエントリを保守しないので開かせない）、段階 120 からバージョン 8（FLOAT(M,D) と DOUBLE(M,D) と UNSIGNED の型の文字列と、SET と BIT の列を含むインデックスのエントリのキーの水準 2。バージョン 7 のデータはそのまま読め、前からある表の FLOAT と DOUBLE の列は桁のない型のまま、水準 0 と 1 のインデックスは前と同じく SET と BIT の列を含めばエントリを持たないものとして読む。起動時に番号だけを書き換える。記録の中身の形は 2 のまま、レプリカの記録の水準を 6 にする。0.2.39 と 0.2.40 は `float(7,2)` を黙って桁のない `float` として読み、書き込みで丸めず、水準 2 のインデックスのエントリを保守しないので開かせない）。
- 既存のキーの形を変えず、新しい形を足すだけのときもバージョンを上げる（段階 70）。古い HeimDB に、新しい形の表を含むデータを開かせないため（古いバージョンは、その表を開くところで初めて拒否するか、読み違える）。既存のデータは移さず、番号だけを書き換える。

- 変えるときは `store.FormatVersion` を上げ、古いバージョンのデータを起動時に新しいバージョンへ移す処理を入れる。インデックスだけの変更なら、行から作り直せば済む（インデックスは行から求まる）。行、テーブル定義、キーの並びの土台は変える予定がない。
- 変えうる要因: インデックスの文字列のキーは go-mysql-server の照合順序の重み（文字ごと）で並べている（`rowenc/index.go`）ので、go-mysql-server の更新で重みが変わるか、MySQL との差（末尾の空白の比較、複数文字の対応）を直すと、キーを作り直す必要がある。新しい列の型（`JSON` など）は型の印を足すだけで、既存のデータは変わらない。go-mysql-server を上げると、ユーザーと権限の直列化（`m/users`）と型の名前の読み方が変わりうる。
- テーブル定義の列の型の文字列（`internal/schema` の `Column.Type`）で、ENUM と SET の値の `'` と `\` をエスケープするように直した（段階 111）。読む側（vitess の構文解析）は変えず、古い HeimDB も新しい定義を同じ値に読めるので、バージョンは変えない。前に保存した定義はそのまま読む（`\` を含む値は前と同じく退格文字などに読まれる）。
- 古い HeimDB は新しいバージョンのデータの起動を拒否する（段階 18）。レプリケーションは記録（キーと値）をそのまま運ぶので、本番とレプリカのバージョンを確かめ、違えばつながない（段階 36）。確かめるのは記録の中身の形のバージョン（`store.RecordFormat`）で、データ形式のバージョンと分ける（段階 59）。バージョン 3 はコミットの記録の置き方だけを変え、運ぶ記録（つないだもの）はバージョン 2 と同じなので、記録の中身の形は 2 のまま（0.2.10 以前とつながる）。行やインデックスのキーと値を変えるときは両方を上げる。バージョン 4 は既存のキーと値の形を変えず、新しい形の主キーの表を足すだけなので、記録の中身の形は 2 のまま（レプリカを先に上げる間も、0.2.18 以前の本番とつながる）。代わりに、0.2.18 以前のレプリカを 0.2.19 以降の本番につながない（新しい形の主キーの表の記録も受け取ってしまう。docs/operations.md）。

### タイムトラベルの時刻と保持期間

`AS OF` に渡す時刻は、セッションの `time_zone` での日時として解釈する（MySQL の TIMESTAMP 型と同じ感覚）。go-mysql-server は文字列リテラルを文字列のまま、`TIMESTAMP(...)` や `NOW()` を「セッションのタイムゾーンでの日時を UTC と称した `time.Time`」として渡すので、どちらも日時の各欄をセッションのタイムゾーンで読み直して、内部の時刻（UTC のマイクロ秒）に変換する。文字列は `YYYY-MM-DD`、`YYYY-MM-DD HH:MM:SS`、小数秒付きを受け付け、それ以外は明示的なエラーにする。過去の時点のテーブルは読み取り専用で、自分の未コミットの変更は含めない。

古いバージョンを消す保持期間の方針:

- 保持期間は起動時の設定（`-retention`、既定 30 日、0 なら消さない）。GC の間隔も設定（`-gc-interval`、既定 1 時間）。
- 消してよいのは、保持期間の境界より古いバージョンのうち、同じ行に境界以前のより新しいバージョンがあるもの（境界の時点で見えるバージョンは残す）。境界以前のバージョンがすべて削除の印なら、その行のキーはすべて消してよい。
- ブランチの分岐時刻以前のバージョンは、子ブランチが親を通して読むので、分岐時刻の時点で見えるバージョンを残す。
- 保持期間の境界より前を `AS OF` で指定したら、明示的なエラーにする。
- マージの基準の時点（段階 7）で見えるバージョンも残す（次のマージの基準として読むため）。
- 古いバージョンを消す処理（GC）は、ブランチの設計がそろう段階 6 の後に実装する。

### 順序を保つ符号化

値は「バイト列として比較した順序が元の値の順序と一致するよう」符号化する。これにより Pebble の範囲走査がそのまま `ORDER BY` や範囲検索になる。

```go
// 符号なし整数: ビッグエンディアン
func appendUint64(b []byte, v uint64) []byte {
	return binary.BigEndian.AppendUint64(b, v)
}

// 符号付き整数: 符号ビットを反転
func appendInt64(b []byte, v int64) []byte {
	return binary.BigEndian.AppendUint64(b, uint64(v)^(1<<63))
}

// 文字列: 0x00 を 0x00 0xFF にエスケープし、 0x00 0x01 で終端
func appendBytes(b []byte, s []byte) []byte {
	for _, c := range s {
		if c == 0x00 {
			b = append(b, 0x00, 0xFF)
		} else {
			b = append(b, c)
		}
	}
	return append(b, 0x00, 0x01)
}
```

文字列の終端処理がないと、複数列キーで `("ab", "c")` と `("abc", ...)` の順序が狂う（CockroachDB と同じ考え方）。

列の値をキーに入れるときは、先頭に NULL の印を付ける（NULL は `0x00`、値があれば `0x01` の後に値）。MySQL の昇順では NULL が先頭に来るので、それに合わせる。印は文字列にも必要で、ないと空文字列（`0x00 0x01`）と NULL の順序が決まらない。

主キーの列は、NULL の印を付けずに型ごとに次のように入れる（主キーに NULL は入らない）。主キーの昇順がそのままキーの順序になる。

- 整数: 「`0x00` の後に `appendInt64` の 8 バイト」。`int64` に収まらない `uint64` の値だけを「`0x01` の後に `appendUint64` の 8 バイト」で入れる。符号付きと符号なしの値が同じ順序で比べられる。
- 照合順序のある文字列（`CHAR`、`VARCHAR`。段階 38）: セカンダリインデックスと同じ、照合順序の重みの並び。
- バイナリの文字列（`BINARY`、`VARBINARY`。段階 70）: `appendBytes`。`BINARY(n)` の値は、エンジンが書くときに末尾を `0x00` で埋めて n バイトにそろえるので、そろえた値を入れる。
- 日時（`DATE`、`DATETIME`、`TIMESTAMP`。段階 70）: セカンダリインデックスと同じ 12 バイト。
- `ENUM`（段階 70）: エンジンが行に入れる番号（uint16）を、整数と同じ形で入れる。MySQL も `ENUM` を番号の順に並べる。
- 差分と重複のエラーの行の名前では、UTF-8 として読めないか制御文字を含むバイト列を `0x` の 16 進にする（結果の列は utf8mb4 の文字列）。

型はどう組み合わせてもよい（段階 70。それまでは整数の列と、1 列の文字列だけ）。それ以外の型（`TEXT`、`BLOB`、`SET`、`DECIMAL` など）の主キーは、明示的なエラーで拒否する。WordPress コアの主キーはすべて整数で、文字列、バイト列、日付、`ENUM` はプラグインの表（WooCommerce、Wordfence など）が使う。どの型も値の長さが自分で決まる（あるキーが別のキーの先頭部分にならない）ので、列をつないでも順序が崩れない。

行の値は、先頭 1 バイトの印（`0x00` は削除の印、`0x01` はデータ）、テーブル定義のバージョン（8 バイト）、列の数、各列の値の順に並べる。列の値は go-mysql-server が行に入れる Go の値を「型の印 + 中身」でそのまま保存し、列の型を通した変換はしない（`internal/rowenc`）。

セカンダリインデックスのキーの列は、先頭に NULL の印を付けたうえで型ごとに次のように入れ、元の値は行の側から読む。

- 整数: 主キーと同じ形式。
- 照合順序のある文字列: 1 文字ずつの照合順序の重み（go-mysql-server の `CollationID.Sorter()`）を、各文字「`0x01` + 符号を反転した 4 バイト」で並べ、`0x00` で終える。go-mysql-server の文字列比較（重みを順に比べ、同じなら短い方が先）と同じ順序になり、大文字と小文字を区別しない照合順序では `'home'` と `'HOME'` が同じキーになる。プレフィックス長があれば、その文字数で切ってから重みにする。
- バイナリの文字列: `appendBytes`。
- 日時（DATETIME、TIMESTAMP、DATE）: UNIX 秒を `appendInt64`、続けてナノ秒を 4 バイト。`0000-00-00 00:00:00`（Go の時刻のゼロ値）も先頭に並ぶ。
- 以下はキーの水準 1 のインデックスだけ（段階 117）。
  - DECIMAL: 列の桁（スケール）によらない形。符号の 1 バイト（負は `0x01`、0 は `0x02`、正は `0x03`。`-0` は 0）。0 はこれだけ。正は、整数部の桁数の 1 バイト（整数部が 0 なら 0）、整数部の各桁、末尾の 0 を除いた小数部の各桁（1 桁 1 バイトで、数字に 1 を足した `0x01` から `0x0A`）、終端の `0x00`。負は、絶対値の正の形（桁数から終端まで）の全バイトを反転する（終端は `0xFF`）。`1.5` と `1.50` は同じキーになる。終端はほかの位置に現れないので、あるキーが別のキーの前方になることはなく、反転しても順序が逆になるだけで崩れない。
  - FLOAT、DOUBLE: 値を倍精度にした IEEE 754 のビット列を、正（`+0` を含む）は符号ビットを立て、負は全ビットを反転した 8 バイト。`-0` は `+0` にする（MySQL も一意インデックスで 0 と -0 を重複とする）。NaN と無限大は列に入らないので、来たら明示的なエラー。FLOAT（単精度）の値は倍精度に広げて入れる（広げても順序は変わらない）。
  - ENUM: エンジンが行に入れる番号（uint16）を、整数と同じ形で入れる（主キーの ENUM と同じ。MySQL も番号の順に並べる）。
- 以下はキーの水準 2 のインデックスだけ（段階 120）。
  - SET: エンジンが行に入れる番号の組のビット（uint64。定義の 1 番目の値が最下位のビット）を、整数と同じ形（9 バイト）で入れる。MySQL も SET のインデックスをこの数の順に並べる。範囲で引くのは MySQL と同じく `=` と `IN` だけで、大小の比べ（MySQL は文字列で比べる）は全件を読む。
  - BIT: 値（uint64）を、整数と同じ形（9 バイト）で入れる。`appendKeyInt` は 2^63 以上の uint64 も符号なしの数の順に並べるので、BIT(64) の順序も MySQL と同じ。
- 上のいずれでもない型（JSON など）、または水準の範囲にない型を含むインデックスは、キーを持たず、全件走査と並べ替えで模擬する。JSON は MySQL でもそのままではインデックスを作れない（3152）。

プレフィックス長のあるインデックスはキーの順序が値の順序と一致しないので、検索で引いた行を値の順に並べ直す。ほかの型の符号化も同じ原則で、必要になった段階で水準を上げて足す。

## WordPress 特有の課題

この DB の差別化は、汎用のブランチ機能では解けない次の課題を解くことで生む。段階 6、7 で本格的に扱うが、それ以前の設計もこれを妨げないようにする。

**URL の上書き。** WordPress は `wp_options` の `siteurl` と `home` にサイトの URL を持ち、ステージングは別ドメインで動かす必要がある。ブランチごとにこの 2 つの値を上書きできる仕組みを用意し、ブランチを切った瞬間に別 URL で動くようにする。本文中の絶対 URL の扱いは未定。

**ID の衝突。** ステージングと本番がそれぞれ同じ ID を採番するとマージできない。DB が AUTO\_INCREMENT を握っているので、ブランチごとに別の ID 範囲を払い出して衝突を構造的に防ぐ。方式は固定幅のブロックに決めた（段階 6）: ブランチ ID n の 64 ビットの列は (n - 1) × 10^10 から採番し、main（n = 1）は今のままの番号を使う。32 ビットの列は、main が 10^9 未満、ブランチが 10^9 + ((n - 2) mod 100) × 10^7 から 10^7 の幅（段階 61）。JavaScript で安全に扱える整数（約 9 × 10^15）の範囲で約 90 万のブランチを作れる。

**テーブルの意味に応じたマージ。** ステージングから本番へ反映したいのは設定や固定ページで、その間に本番へ入ったコメントや注文は消してはいけない。マージの方針は次のとおり（段階 7 で決めた。テーブルの接頭辞は既定で `wp_`）。

| 対象 | 方針 |
| --- | --- |
| `wp_options` | `option_name` で対応づけた三方向。次は反映しない: `siteurl`、`home`、`blog_public`、`cron`、`rewrite_rules`（マージの後に作り直させる）、`db_version` などの DB のバージョン、トランジェント（`_transient_*`、`_site_transient_*`）、ロック（`*_lock`、`*.lock`）、`recently_activated`、`fresh_site`、`auto_core_update_notified`、`https_*` |
| `wp_posts` | 列単位の三方向。`comment_count` は比べずに、マージの後に数え直す。自動下書き（`auto-draft`）とリビジョンは反映しない。著者が親にいない記事は競合 |
| `wp_postmeta` | 列単位の三方向。`_edit_lock`、`_edit_last` と、反映しない記事のメタは反映しない |
| `wp_term_taxonomy` | 列単位の三方向。`count` は比べずに、マージの後に数え直す |
| `wp_terms`、`wp_termmeta`、`wp_term_relationships`、`wp_links`、プラグインのテーブル | 列単位の三方向 |
| `wp_comments`、`wp_commentmeta`、`wp_users`、`wp_usermeta` | ブランチ側の変更は反映しない（本番の変更を常に残す） |

警告として報告するもの: 同じ記事の同じメタのキーを両側が別々に追加した、ステージングで削除した記事のコメントが本番に残る。

本文中の絶対 URL は扱わない。マージの後に本番で `wp search-replace '<ステージングの URL>' '<本番の URL>' --skip-columns=guid` を実行する（ブロックエディタは本文に絶対 URL を埋めるので、毎回必要）。

**検索は DB の外に任せる。** HeimDB は全文検索（`MATCH ... AGAINST`）に対応しない（段階 10）。WordPress のコアの検索は `LIKE '%語%'` なので HeimDB でもそのまま動く（全件の走査）。関連度の順位や日本語の分かち書きが必要なら、Elasticsearch / OpenSearch（ElasticPress）や Algolia（WP Search with Algolia）などの外部の検索サービスを使う。検索の索引は DB の外にあり、ブランチやタイムトラベルについてこないので、次を運用の手順（製品化の際は組み立て）に入れる。

- これらのプラグインは WordPress のフック（`save_post` など）で変更を索引に送るが、HeimDB のマージ（`heimdb_branch_merge`）と復元（`heimdb_restore`）は DB を直接書き換えるのでフックが走らない。マージと復元の後に索引を作り直す（`wp elasticpress sync`、`wp algolia reindex` など）。
- ステージングは本番と別の索引にする（同じ索引だとステージングの編集が本番の検索結果に混ざる）。索引の名前の接頭辞を `wp-config.php` で切り替える（URL を `WP_HOME` で切り替えるのと同じ）。
- `AS OF` で過去の状態を読めても、検索の索引は今の状態だけを持つ。

**ファイルは DB の外にある。** プラグインやテーマのコード、アップロードされたメディアはこの DB の対象外。DB が受け持つのはコンテンツと設定で、コードは Git、メディアは追記中心として別に扱う。製品化の際に組み合わせ方を設計する。

## 検証方法

物差しは wordpress-develop の PHPUnit テストスイートで、必ず本物の MySQL 8.0 で取ったベースラインと比較する。絶対数ではなく「本物で通って偽で落ちるテスト」だけを調査対象にする。

### 環境

- **偽 MySQL**: ホストの `0.0.0.0:3306` で待ち受ける。logrus を Debug レベルにすると、受信したクエリが `Starting query` 行として接続 ID 付きで出力される。
- **本物の MySQL**: `docker run -d --name realmysql -e MYSQL_ROOT_PASSWORD=root -e MYSQL_DATABASE=wordpress -p 3307:3306 mysql:8.0`
- **WordPress**: Docker Compose の `wordpress:php8.3-apache` と `wordpress:cli`。`WORDPRESS_DB_HOST=host.docker.internal:3306`、`extra_hosts` に `host.docker.internal:host-gateway` を指定。
- **PHPUnit**: `php:8.3-cli` に mysqli、zip、gd（freetype、jpeg、webp 付き）と Composer を入れたイメージ。GD がないとテストが開始されない。
- **wp-tests-config.php**: 接続先を環境変数で切り替える。`localhost` ではなく TCP のホスト名を指定する。

```php
define( 'DB_NAME', 'wordpress' );
define( 'DB_USER', 'root' );
define( 'DB_PASSWORD', getenv( 'WP_TESTS_DB_PASSWORD' ) ?: '' );
define( 'DB_HOST', getenv( 'WP_TESTS_DB_HOST' ) ?: 'host.docker.internal:3306' );
```

### 実行と比較

```bash
# ベースライン（本物の MySQL）
wpphp env WP_TESTS_DB_HOST=host.docker.internal:3307 WP_TESTS_DB_PASSWORD=root \
  vendor/bin/phpunit --group option --log-junit real-option.xml
# 偽 MySQL
wpphp vendor/bin/phpunit --group option --log-junit fake-option.xml
# 件数の確認（--list-tests は --group を反映しないので使わない）
grep -c '<testcase ' fake-option.xml
```

- 対象グループは option、meta、query、wpdb の順。フルスイートは約 29,370 件。
- テストスイートは起動時に DB 内のテーブルをすべて削除する。大事なデータのある DB に向けない。
- 単独で通りグループで落ちるテストは、トランザクションやテスト間で引き継ぐ状態を疑う。

### 検証ツール

- `scripts/wpphp`: wordpress-develop で PHPUnit 用のコンテナを使ってコマンドを実行する（上の `wpphp`）。
- `go run ./cmd/junitdiff real-option.xml heimdb-option.xml`: 本物で成功し HeimDB で失敗したテストだけを一覧にする。
- `scripts/wordpress/docker-compose.yml`: HeimDB（ホストの 3306 番）に接続する WordPress と wp-cli。
- `scripts/wp-login-check.sh`: 管理画面にログインできるかを確かめる。
- `go run ./cmd/replay -log heimdb.log -conn 1,2,3 -mysql ... -heimdb ...`: HeimDB のクエリログ（`-debug`）から接続のクエリを順に取り出し、本物の MySQL と HeimDB に流して、結果が食い違ったクエリを報告する。どちらのデータベースも中のテーブルを削除するので、専用のデータベースに向ける。
- `internal/backend/dml_test.go`: SQL のスクリプトを HeimDB に流し、本物の MySQL 8.0 で作ったゴールデンファイル（`internal/testdata/dml_golden.txt`）と比べる。MySQL への接続先を `-update -mysql` で渡すと作り直す。
- `scripts/compat/run.sh <port> <out.json>` と `go run ./cmd/compatdiff compat/baseline/mysql-8.0.json <out.json>`: MySQL 互換のテスト集（`compat/README.md`。段階 91）。WordPress の接続（wpdb）で文を流して返った値を記録し、本物の MySQL 8.0 の記録と比べる。数秒で終わるので、エンジンを変えたら PHPUnit の全体の前に流す。知っている違いは `compat/known-differences.txt`。

## Claude Code への作業ルール

この節はリポジトリの `CLAUDE.md` にそのまま転記できるように書いている。

- 開発ステップの段階を 1 つずつ進める。完了条件を満たすまで次の段階に手を付けない。各段階の始めに計画を提示し、承認を得てから実装する。
- SQL エンジンは go-mysql-server v0.20.0 を `internal/sqlengine` にフォークしたもの（`docs/engine.md`）。インターフェースは記憶やネット上の解説ではなく、`internal/sqlengine` のコードと `memory` パッケージを正とする。
- エンジンを変えるときは、`docs/engine.md` の変更の一覧に理由とともに書き、テストを足し、中身を変えたファイルの頭に変更の印（`// Modified by Tsukinowa Inc.: ...`）を付ける。上流の修正を取り込むときも記録する。文字コードの表（`sql/encodings`）は元のモジュールから読み、上げない（照合順序の重みがデータ形式に響く）。
- キー設計と符号化を変える場合は、先にこのドキュメント（または `docs/design.md`）を更新してから実装する。既存のデータは読めるようにする（「データ形式のバージョン」）。変えるときはバージョンを上げ、既存のデータを起動時に移す。
- 符号化、MVCC の読み出し、ブランチの重ね合わせには単体テストを書く。順序の性質はプロパティテストで確かめる。
- WordPress の互換性は「検証方法」の手順で、必ずベースラインと比較して判断する。失敗の原因は推測で直さず、ログのクエリで再現してから直す。
- 仕様上は不定でも MySQL が実際にどう振る舞うかを優先して合わせる（例: 同順位の並び順）。合わせるときは、本物の MySQL で `EXPLAIN` などを使って根拠を確認する。
- WordPress 専用として割り切ってよい。WordPress が発行しない SQL は、明示的なエラーを返す形で非対応にする。接続を切ったり panic したりしてはいけない。
- 各段階の終わりに、完了条件の確認結果（テスト件数とベースラインとの差）を報告する。
