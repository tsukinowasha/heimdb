## 段階 121: 古い索引を起動の後に裏で作り直す

- 背景: 0.2.38 以前に作った DECIMAL、FLOAT、DOUBLE、ENUM の列を含む索引（キーの水準 0）と、0.2.40 以前に作った SET と BIT の列を含む索引（水準 0 か 1）はエントリを持たず、引くたびに全件を読む（`docs/differences.md` の「そのほか」。WordPress: はい）。WooCommerce の `wc_product_meta_lookup` の `min_max_price` と `stock_quantity` に当たり、4,000 行どうしの結合が約 7 秒、作り直すと 9 ms（段階 117）。作り直すのは利用者が `CALL heimdb_rebuild_indexes()` を呼ぶときだけで、起動時の警告（`Provider.logStaleIndexes`）が知らせていた。ホスティングではサイトごとに呼ぶ手間があり、呼び忘れると遅いままになる。効く軸は堅牢性と WordPress 特化（上げた後の状態を正しくする。性能の調整ではない）。
- 計画（ユーザー承認、2026-11-17）: 起動の後に 1 本のゴルーチンで、本番の main の古い索引を、手続きと同じ書き込みで作り直す。レプリカでは動かさない。ブランチは作り直さない（ホスティングのブランチは短く生きる）。一意索引の重複（1062）は飛ばして警告にし、残りを続ける（手続きは 1062 で止まるまま）。止めると作りかけは消え、次の起動で続きを作る。始め、索引ごと、終わりにログを出す。データ形式のバージョン（8）と記録の水準（6）は変えない。
- 計画のレビュー（Fable）で変えたこと:
  - 裏の処理の形を `WarmStats`（warm.go）と同じにした（セッションなしの `sql.Context`、動かす単位ごとの `gate.enter/leave`、`Provider.Shutdown` が `stopWarm` と並べて `StopLockWaits` の前に止める）。cmd/heimdb の `WarmStats` と `WatchIdleLocks` の隣で始める。
  - 書き込みのロックの持ち主を `rebuild indexes` にした（`lockDDL` の `"ddl"` 固定を変えられるようにする）。
  - 作り直す単位を表から索引にした（`raiseKeyLevels(ctx, only)`。nil なら手続きと同じく全部）。索引と索引の間でロックを放す。
  - 誤りで全体を止めない: 1062 は表と索引の名前と手続きを添えた警告、ロックの待ちは 5 秒で切って飛ばす（`LockTimeout` の 50 秒を待たない。次の起動でやり直す）、取り消しと `ErrShuttingDown` は静かにやめる、ほかの誤りは警告にして次へ。
  - 見積もった行の数（`rowCounts`）が上限を超える索引は飛ばす（一意でない索引 500 万行、一意の索引 100 万行）。
  - ブランチの作成が親の書き込みロックを取るようにする（前からの競合。分けてコミットする作り直しの途中に分岐点が入ると、ブランチは水準 0 の定義のまま main の作りかけのエントリを見て、後でブランチで作り直すと消した行の main のエントリが残る）。
  - main の復元（`heimdb_restore`）の後に、もう一度動かす（戻した定義に古い索引がありうる）。
  - 昇格の専用の経路はない（`-replicate-from` を外して起動し直す）ので、何も足さずに本番の起動として動く。レプリカの起動時の警告は、本番が作り直してエントリが記録で届く旨にする。
  - フラグは bool の `-rebuild-indexes`（既定 true）と環境変数 `HEIMDB_REBUILD_INDEXES`。heimdb_status の行と指標を足す。
  - 固定データは段階 117 と 120 の `format6_data.tar.gz` と `format7_data.tar.gz` を使い、v0.2.38 はビルドしない。重複のある一意索引はテストの中で作る。
- 方法: 4 コミット。先に `docs/plan.md`、`docs/operations.md`、`docs/procedures.md` を書き（09279d9）、裏の作り直し（7c40913）、ブランチの作成のロック（8cc5e48）、記録の順に入れた。エンジンは変えていない（`docs/engine.md` は触らない）。

  - `Database` に `ddlOp` と `ddlWait` を足し、裏の処理の `lockDDL` は持ち主 `rebuild indexes`、待ち 5 秒、接続 ID 0 で取る（指標の `heimdb_branch_write_lock_holder` は 0）。
  - 状態: heimdb_status に `index_rebuild`（off、running、done）、`index_rebuild_done_at`、`index_rebuild_duration`、`index_rebuild_indexes`（`7 rebuilt, 1 skipped`）、`index_rebuild_error`（最後に飛ばした理由）。指標に `heimdb_index_rebuild_ready`、`heimdb_index_rebuild_seconds`、`heimdb_index_rebuild_skipped`。数と時間は最後の 1 回のもの。停止で途中でやめたときは running のまま。
  - ログ: 始めに `HeimDB: rebuilding N indexes on wordpress made by an older HeimDB in the background, one at a time`、索引ごとに `HeimDB: rebuilt index t.k on wordpress (about N rows) in D`、飛ばしたものは `HeimDB: skipped rebuilding index t.k on wordpress: <理由>` の警告、終わりにまとめ。起動時の警告（`logStaleIndexes`。`NewProvider` から `StartIndexRebuild` に移した）は、動かすときは `wordpress's are rebuilt in the background now`（ブランチにもあれば `; to build the others, run CALL heimdb_rebuild_indexes() ...`）、`-rebuild-indexes=false` のときは前と同じ文、レプリカでは `the primary rebuilds wordpress's in the background after it starts (unless -rebuild-indexes=false), and the entries reach this replica through its commit records`。
  - `heimdb_restore` は main を書いたら `kickIndexRebuild` を呼ぶ（動かしていなければ何もしない）。
  - `createBranch`（internal/backend/branch.go）は、親の書き込みロックを `LockTimeout` まで待って取ってから分ける（持ち主 `create branch`、文の取り消しで待つのをやめる）。呼んだ接続のトランザクションが親のロックを持っていれば取らない（自分を待たない）。
  - テストのため、`buildIndex` が作りかけをコミットするたびに呼ぶ `testHookIndexChunk` を足した（nil なら何もしない）。

## 段階 122: 全件を読む WHERE の比べで行ごとに型を調べない（段階 121 の測りの遅れ）

- 背景: 段階 121 の測り（`docs/bench.md` の「段階 121」）で、72aa902 のページの DB の時間が 0.2.35 より 3〜12% 長かった。長くなったのは wp_comments と wp_posts を全件読んで行ごとに条件を比べる文（ダッシュボードの自分のコメントの数、承認済みのコメントの数、投稿一覧の年と月、トップページの記事の一覧）。手元でバージョンごとに測ると、0.2.38 から 0.2.39 の増えは 3493064（段階 116。`comparison.Compare` が比べるたびに両辺の型と `enumSetAsText` を調べる）で入り、0.2.39 から 0.2.41 の残り（約 0.5 ms）は決められていなかった。
- 計画（ユーザー承認、2026-11-18）: ENUM と SET を値の文字列で比べるかを、行ごとでなく比べの式ごとに一度だけ決める（式の形と型だけで決まる）。`WithChildren` の新しい式は決め直し、並行して評価しても安全にする。結果は変えない。残りの 0.5 ms を、段階 118〜120 のバージョンを交互に測るか CPU のプロファイルで探し、簡単で結果の変わらない直しなら直し、そうでなければ記録する。0.2.35 と 72aa902 と交互に測る。データ形式のバージョンとレプリカの水準は変えない。
- 方法: 3 コミット。先に `docs/plan.md` の行（e0d928f）、直しとテストと `docs/engine.md` の行（ac9319e）、記録の順に入れた。
- 残りの 0.5 ms: 0.2.39（d4dec26）と 72aa902 の両方に 1 つ目の直しを当て、pprof を足したバージョン（作業用の写しだけ。コミットしていない）で自分のコメントの数を 3,000 回ずつ流して CPU のプロファイルを比べると、差は `sql.EvaluateCondition` の下に集まっていた（+0.68 秒。`ConvertToBoolFor` 0.48 秒、`expression.IsTextColumn` 0.20 秒）。b766f06（段階 118）の `EvaluateCondition` と、6ae1072（段階 119）の AND、OR、XOR の `ConvertToBoolFor` が、値によらず行ごとに `IsTextColumnRef` を呼んでいた（条件と、AND と OR の両辺ごとに、型の switch とインターフェースの確かめ）。警告 1292 を出すかを決めるためのもので、要るのは数として読めない文字列のときだけ。比べの結果（真偽）では使わない。
- エンジンの変更:
  - `sql/expression/comparison.go`: `comparison` に `enumSetMode`（0 はまだ、`enumSetNo`、`enumSetYes`）を足し、`useEnumSetText` が最初の `Compare` で `enumSetAsText` を一度だけ呼んで覚える（`sync/atomic` で読み書き。式は並行する反復で共有されうる）。作るとき（`newComparison`）には決めない。解決する前の列（`UnresolvedColumn`）の `Type` は panic するので。`Equals`、`LessThan`、`GreaterThan`、`LessThanOrEqual`、`GreaterThanOrEqual` の `WithChildren` と `SwapParameters` は `New*` で新しい式を作るので、0 から決め直す（値を写す所はない）。`NullSafeEquals` は自分の `Compare` を持ち、ENUM の値の文字列の経路を通らない（前と同じ）。決める材料は両辺の型と、文字列の側が定数か（`constantExpr`）で、どちらも式を作り直さなければ変わらない（`UserVar` と `ProcedureParam` の型は式が持つ値、`BindVar` は実行の前に `Literal` の新しい式に替わる）。
  - `sql/core.go`: `convertToBool` が真偽の代わりに式を受け取り、数として読めない文字列で警告 1292 を出す直前にだけ `IsTextColumnRef` を呼ぶ。`ConvertToBool` は nil を渡し（いつも警告を出す。前と同じ）、`ConvertToBoolFor` と `EvaluateCondition` は式を渡す。
  - `sql/expression/comparison.go` の `quietTextDoubles`: 値が文字列のときだけ `IsTextColumn` を調べる（`quietDouble` は文字列でない値を変えないので、結果は同じ）。`user_id = 1` のような数との比べで行ごとに列の型を見ていた。
  - 理由はどれも性能（段階 116、118、119 の回帰）。結果、警告、計画は変わらない。

- 方法: 先に `docs/plan.md` の行（2fd68fa）、結果の経路と見張りとテストと `docs/engine.md` の行（b2bdaf2）、この記録と測りの順に入れた。小さな候補は 2 つとも残さなかったので、そのコミットはない。GCE のインスタンスは 1 つ（n2-standard-4、Debian 12、pd-balanced）で、終わりに消した。

  - `resultForDefaultIter`: errgroup、チャンネル、行を待つタイマーをやめ、文のゴルーチンで `Next`、`RowToSQL`、128 行ごとの送り（`resetCallback`）を順に行う。組の作り方（128 行で送り、128 の倍数なら最後に空の結果を送らない。0 行なら列の情報だけの結果）は同じ。

## 段階 125: 全件を読む文の行ごとの手間（復号した行の使い回しと、同じバイト列の文字列の比べ）

- 背景: 段階 123 と 124 のプロファイルと調べで、全件を読む文（承認済みのコメントの数、自分のコメントの数、記事の年と月）が 7 ページの DB の時間の約 19% だった。行ごとに、復号で全体のスキーマの幅の行を作り（`scanRowIter.Next` から `rowenc.DecodeRowColumns`）、`projectIter` が文の使う列だけの行をもう 1 つ作って前の行を捨て、WHERE の文字列の等号は当たる行でも文字ごとに照合順序の重みを引いていた。試作（行の使い回しと文字列の早道）では、手元で承認済みのコメントの数が 4.99 ms から 4.05 ms（19%）、自分のコメントの数が 16% 短くなった。
- 計画（ユーザー承認、2026-11-19）: (1) 全件の走査で復号の行を使い回す。使い回すのは、行を受け取る側が写す（`projectIter`）ときだけで、行をそのまま返すとき（列を絞らない）、ALTER の途中（NULL を埋める）、行を集める FULLTEXT の経路、行を持ち続けうるところでは使い回さない。復号と `projectIter` の間に行を持つものがないこと（範囲の条件の評価、DECIMAL の桁のその場の書き換え、数え）と、値が復号のバッファを共有しないことを確かめる。(2) エントリだけで作る行（`coveredRow`）も、安全な所で同じにする。(3) エンジンの `StringType.Compare` で、同じバイト列なら 0 を返す（どの照合順序でも等しい）。(4) `store/layers.go` の `versionCursor.advance` の、行ごとのエントリと値の写しをやめ、イテレータのものを指して返す（要る `last` の写しだけ残す）。持つ期間の決まりが変わるので、見え方と正しさが同じことをテストで示し（逆順、ブランチの層、同時の書き込み、Close）、測って効くときだけ残し、残さなければ理由を記録する。結果、データ形式のバージョン（8）とレプリカの水準（6）は変えない。
- 方法: 先に `docs/plan.md` の行（964a0b6）、行の使い回しとテスト（6dd6f28）、文字列の比べとテストと `docs/engine.md` の行（8e41104）、この記録と測りの順に入れた。カーソルの写しをやめる候補は残さなかったので、そのコードはコミットにない（変更とテストは作業用の場所に残した）。GCE のインスタンスは 1 つ（n2-standard-4、Debian 12、pd-balanced）で、終わりに消した。
- 行の使い回し（`internal/backend`、`internal/rowenc`）:
  - `rowenc.DecodeRowColumnsInto`: `DecodeRowColumns` と同じ行を、容量の足りる行の上に作る（前の値を消してから、使う列だけを復号する）。文字列とバイト列とほかの値は前と同じく行ごとに作るので、使い回す行と値を共有しない（`[]byte` は写し、文字列は `string(payload)`、DECIMAL は `scaleDecimals` が新しい値にする）。
  - `scanRowIter` と `pkRowIter`（エントリだけで作る行。`coveredRowInto`）は、`reuse` のときだけ 1 つの行を使い回す。`reuse` を立てるのは `projectRows` だけで、`projectIter` の子にしたイテレータ（`rowReuser`）に、ALTER の途中でないときに立てる。`projectIter` は子の行から値を写した新しい行を返し、子の行を持たない。
  - 使い回さないもの: 列を絞らない読み出し（`projectRows` は行をそのまま返すか `visibleIter` にする）、ALTER の書き直しの読み出し（`rewriteScan`）と NULL を埋める行、行を集めて返す経路（キーを持たないインデックスと、プレフィックス長の列の並べ替え。`rowIter` に集めてから `projectIter` に渡すので、子は `rowReuser` でない）、`Truncate` の 1 行ずつの削除（`projectRows` を通らない）、主キーの 1 行の読み出しと本体の行を引く経路（行ごとに作ったまま）。範囲の条件（`rangeFilter`）は評価の間だけ行を見る。`CountRest` は行を作らない。

## 段階 128: 2 本の接続で伸びない待ち（文を始めるときに眠った Go のスレッドを起こし、網を見る者を残す）

- 背景: 段階 126 の A で、HeimDB だけ 2 本の接続で伸びなかった（1 接続 18.1、2 接続 28.4 ページ毎秒で 1.57 倍、サーバーの CPU 136%。MySQL は 23.4 から 44.2 で 1.89 倍）。1 ページの CPU は 1 接続と同じで、何かを待っていた。手元（M4）でも、トップページだけで 1 接続 165、2 接続 253、3 接続 447 ページ毎秒と再現し、v0.2.41 でも同じだった（段階 121〜125 より前から）。手元の block と mutex のプロファイルに文の経路の待ちはなく、`GOMAXPROCS=2` でも 3 接続の方が 2 接続より速いので、CPU の不足でもない。実行の記録では、接続のゴルーチンが次の文を待つ（`readEphemeralPacket`）時間が、1 接続 17%、2 接続 39%、3 接続 20% だった。
- 計画（ユーザー承認、2026-11-19）: GCE の 2 つのインスタンス（段階 126 の `gce.sh`。n2-standard-4、asia-northeast1-b）で、HeimDB と MySQL の 1 接続と 2 接続の tcpdump（最後の応答から次の文までの間。40 ms の固まりなら遅れた ACK）、strace の書き込みの数と大きさ、pprof の口を足したビルドの実行の記録を取り、1 つのホストの loopback でも起きるかを見る。原因が HeimDB の送りの経路ならエンジンの変更として直し、Go のランタイムやカーネルの振る舞いなら HeimDB の側で避ける手があれば入れ、なければ記録する。直した後に、段階 126 の A（1、2、4、8 接続、読みだけ）を両方で交互に 2 回ずつ流す。
- 方法: 先に `docs/plan.md` の行（b5446dc）、直しとテストと `docs/engine.md` の行（77098e0）、起こす条件を絞る直し（faf07b0）、この記録と測りの順に入れた。GCE では、main（0.2.44 と同じコード）と直したバージョンを `Dockerfile` と同じ形（`-trimpath -ldflags=-w`）で建て、記録を取るときは pprof の口（127.0.0.1:6360）を足したビルドを使った（そのファイルはコミットしていない）。インスタンスは終わりに 2 つとも消し、残っていないことを `gcloud compute instances list` で確かめた。
- 原因（Go のランタイムのスケジューラ）:
  - 網の読みを待つゴルーチンを起こすのは、仕事のないスレッドが入る止まる netpoll（epoll_wait）か、ゴルーチンを止めたスレッドが次を探すときの止まらない netpoll か、sysmon（10 ms ごと）だけで、止まる netpoll に入るのは 1 度に 1 つのスレッド。止まらない netpoll で見つけたゴルーチンをそのスレッドで走らせるときは、ほかのスレッドを起こさない（`runtime.findRunnable`）。
  - 2 本の接続では、接続 A のゴルーチンが応答を書いて止まると、同じスレッドの止まらない netpoll が、A の文の間に届いていた接続 B の次の文を見つけて B を走らせる。ほかのスレッドは眠ったままで、網を見る者がいないので、B の文の間に届いた A の次の文は B が止まるまで読まれない。こうして 2 本が 1 つのスレッドで交互に走り続け、1 本のときの 1.6 倍ほどにしかならない。3 本以上では、止まらない netpoll が 2 つ以上を見つけ、残りを別のスレッドに渡す（`injectglist`）ので、交互の形が崩れる。MySQL は接続ごとのスレッドが読みで止まるので起きない。
  - 結果の行を送る経路（`resultForDefaultIter`）は、切れた接続の見張りのタイマー（段階 124 の `time.AfterFunc`）を置くときにランタイムがスレッドを起こす（`wakeNetPoller`）ので、そこから後は網を見る者がいる。OK、空、1 行の結果の文と、どの文でも構文解析、計画、組み立ての間は起こさない。v0.2.41 の errgroup のゴルーチンも同じく行を送るときだけだった。
- 確かめたこと（GCE。トップページの 26 文を 2 接続で 40 秒流す途中に取った）:
  - 実行の記録（5 秒）: 2 つの接続のゴルーチンの網の待ち 7,222 回のうち 67%（4,819 回、待ちの時間の 78%）が、もう片方が同じスレッドで止まってから 5 µs の内に終わった。網の待ちは 1 接続ごとに 5 秒のうち 2,290 ms（46%。1 接続では 1,034 ms、21%）、中央値 379 µs（1 接続 219 µs）。
  - tcpdump（3 秒、DB の側）: 文が届いてから最初の応答のパケットまでの中央値は、1 接続 604 µs、2 接続 993 µs（MySQL は 220 µs と 216 µs）。負荷の側が最後の応答から次の文を送るまでは、どれも中央値 160〜210 µs で、35 ms を超える間は 0（遅れた ACK や Nagle ではない）。1 文の応答のパケットは平均 1.6（MySQL 1.7）。
  - strace（3 秒）: 1 文あたりの書き込みは約 2.1 回（16 KiB の書き込みが半分。大きな結果は vitess の 16 KiB の書き込みのバッファごとに書く）で、1 接続と 2 接続で同じ。送りの経路は 2 本で伸びない理由ではない（MySQL は約 1.05 回。後の候補）。
  - 1 つのホストの loopback（DB のインスタンスで loadgen を 127.0.0.1 に）でも起きる: トップページで 1 接続 40.9 と 42.2、2 接続 59.7 と 62.6（1.47 倍）。
- エンジンの変更（`server/handler.go`、新しい `server/netpoll_heimdb.go`）:
  - `Handler` に開いた接続の数（`openConns`。`NewConnection` で足し、`ConnectionClosed` で引く）と、文を処理している接続の数（`busyConns`）を持たせる。`errorWrappedDoQuery`（COM_QUERY と複数の文）と `errorWrappedComExec`（バイナリプロトコルの実行）の始めに `commandStarted`、終わりに `commandDone` を呼ぶ。
  - `commandStarted` は、文を処理している接続がこれだけになり（`busyConns` が 1）、ほかに開いた接続があれば、空のゴルーチンを起こす（`wakeIdleThread`）。go 文は、空いた P があり探しているスレッドがいなければ眠ったスレッドを 1 つ起こし（`wakep`）、そのスレッドは空のゴルーチンを走らせた後に仕事がなく、止まる netpoll に入る。P が全部ふさがっていれば何もしない。接続が 1 本だけなら起こさない（ゴルーチンを止めたスレッドがそのまま止まる netpoll に入るので要らず、スレッドの切り替えだけが増える）。ほかの接続が文の途中なら起こさない（どれかが止まるときのスレッドの止まる netpoll か `injectglist` が網を見る）。
  - 初めのバージョン（77098e0）は、ほかに文を処理していない接続があれば文のたびに起こした。実行の記録では、1 回起こすたびにスレッドが約 2 つ起き（空のゴルーチンを見つけたスレッドが、もう 1 つ起こす）、1,000 文あたりの CPU が 4 接続で 10%、決まった速さで 9% 増えたので、起こすのを文の途中の接続がほかにないときに絞った（faf07b0）。タイマーで起こす案は、実際のページでは効かなかった（2 接続 28.0 ページ毎秒）。
  - 理由は性能。結果、エラー、警告は変わらない。Go のランタイムの設定（GODEBUG など）で避ける手はない。
- テスト（`server/netpoll_heimdb_test.go`）:
  - `TestStage128WakeWhenOthersWait`: 起こす関数を数えるものに替え、1 本だけなら起こさない、2 本目を開くと起こす、ほかが文の途中なら起こさない（2 本と 3 本）、エラーの文も数えを戻す、閉じた接続は数えないことを確かめる。
  - `TestStage128IdleConnectionReadDuringStatement`: このテストのバイナリを別のプロセスの接続の相手として起こし（同じプロセスだと相手のゴルーチンが待つたびにスレッドが空く）、スレッドを手放さない 100 ms の文の途中に、もう片方の接続が流した `SELECT 1` が返るまでの時間を 9 回測って、中央値が 2 ms より短いことを確かめる。結果の行の見張りのタイマーでスレッドが起きないよう、接続を `*net.TCPConn` でない型に包む。手元で 100〜430 µs（-race で 280〜600 µs）。直しを外すと 5〜17 ms で落ちる（長い文が 10 ms で横取りされるか sysmon が見るまで読まれない）。
