# 段階 51〜60

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 51: カテゴリとタグの一覧の LEFT JOIN（外部結合の単純化）

- 背景: WordPress のタクソノミーの絞り込み（カテゴリ、タグのページ）は `wp_posts LEFT JOIN wp_term_relationships ON (wp_posts.ID = object_id) WHERE term_taxonomy_id IN (5) AND ...` を出す。WHERE が右の表の列を条件にするので結果は INNER JOIN と同じで、MySQL は INNER JOIN に直して記事の少ないカテゴリでは `term_taxonomy_id` のインデックスから読む。go-mysql-server はこの直しをしないので、どのカテゴリでも記事の全件を読み、記事ごとに `wp_term_relationships` を引く（手元の `wpbench` で、記事 50 件のカテゴリが 27.3 ms、MySQL 0.23 ms。INNER JOIN に書き換えると 0.48 ms）。記事の多いカテゴリ（5,000 件）は、`IN (1)` のままだと JOIN で引くキーに定数が入らず範囲で読む（30.5 ms。`= 1` なら主キーの点で引き 12.9 ms、MySQL 3.0 ms）。
- 方針: `internal/backend` の解析ルールで、JOIN の順を決める前に、(1) WHERE の AND の項に、右の表（1 つの表か別名）の列と NULL でない定数の比較（`=`、`<>`、`<`、`>`、`<=`、`>=`、`IN`）があれば、その LEFT JOIN を INNER JOIN にする（右に行がなければ列は NULL で、その項は真にならない）。`IS NULL`、`<=>`、`IFNULL`、`COALESCE`、`OR` の中の項、HAVING は見ない。(2) 要素が 1 つの `列 IN (定数)` を `列 = 定数` にする（MySQL では同じ意味）。エンジンは変えない。データ形式は変えない。
- 完了条件: 書き換える形と書き換えない形で結果が変わらない（右に行がない記事、複数のタクソノミー、別名を含む）。`TestWordPressJoinsMatchMySQL` に少ないカテゴリ、多いカテゴリ、タグ、複数のタクソノミーの文を足し、本物の MySQL と結果と並び順が同じ。`TestCategoryQueryPlans` で、少ないカテゴリは `term_taxonomy_id` のインデックスから読み、多いカテゴリは引くキーに定数が入る。直しを 1 つずつ外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で、カテゴリの一覧の文（少ないカテゴリを足す）とページが速くなったことを数字で示す。CI が通る。
- 結果: `outerjoin.go` の、解析の前のルール `simplifyOuterJoins`。(1) WHERE の AND の項のうち、比較（=、<>、<、<=、>、>=、IN）の辺が列そのものなら、その列の表を右に持つ LEFT JOIN（右が 1 つの表か別名）を INNER JOIN にする。(2) INNER JOIN にした表の列の、値が 1 つの `列 IN (定数)` を `列 = 定数` にする（文字列の列は同じ文字セットの文字列、整数の列はそのまま入る整数だけ。go-mysql-server の IN は定数を列の型に変換して比べ、等号は数として比べるので、どちらでも同じになる形に限る）。初めはどの表の IN も等号にしたが、GCE の計測で 1 件の記事の term の読み込み（`tr.object_id IN (5003)`）が遅くなった（1.95 ms から 2.51 ms。等号から、go-mysql-server が term_taxonomy の全件から引く順を選んだ）ので、INNER JOIN にした表に絞った。手元の `wpbench` で、記事 50 件のカテゴリの一覧が 27.3 ms から 0.33 ms（MySQL 0.23 ms）、記事 5,000 件のカテゴリが 30.5 ms から 12.7 ms（MySQL 3.0 ms）、ほかの文は前と同じ。`TestWordPressJoinsMatchMySQL` に、タグ、複数のカテゴリ、2 つのタクソノミーの AND、メタの値の `<>`、値が 1 つの IN、INNER JOIN にしない形（meta_query の NOT EXISTS、IS NULL と OR、`<=>`、COALESCE）を足し、本物の MySQL と結果と並び順が同じ。`TestCategoryQueryPlans` に、記事 30 件のカテゴリが `term_taxonomy_id` のインデックスから読むこと、多いカテゴリで記事ごとに引くキーに定数が入る（`keys: wp_posts.ID, 1`）こと、1 件の記事の term の読み込みが `wp_term_relationships` の `object_id` から読むことを足した。直しを 1 つずつ外す（INNER JOIN にしない、IN を替えない、どの表の IN も替える、IS NULL と `<=>` も NULL を拒むと見る、OR や関数の中まで見る）と、対応するテストが落ちる。Go のテストは 306 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト（直したバージョンで流した）。接続の切断と panic は 0。GCE（`docs/bench.md` の「段階 51 の後」。測ったのはどの表の IN も替えるバージョン）: カテゴリのページの DB の時間が、記事の多いカテゴリで 89 ms から 49 ms、少ないカテゴリで 82 ms から 19 ms（MySQL 15 ms と 8 ms）。ほかのページ、同時アクセス、書き込みは同じ。GCE のインスタンスは消した。データ形式は変えていない。
- レビュー（Fable）: 約 75 通りの文を、段階 51 のバージョン、前のバージョン、本物の MySQL で比べ、差は 1 つ。符号なしの BIGINT の列で `b.v IN (9007199254740993)` を等号にすると、go-mysql-server の等号が符号つきの定数と符号なしの列を小数に直して比べるので、9007199254740992 の行も一致した（MySQL と前のバージョンは 1 行）。等号にするとき、定数を列の型にした（`exactLiteral` の値で作る）。ゴールデンに、2^53 を超える値と最大の値の IN、入れ子の LEFT JOIN、RIGHT JOIN、USING、JOIN を含む UPDATE と DELETE を足した（定数の型を戻すと落ちる）。前からある差（この段階で変わらない）は記録だけ: 符号なしの列と 2^53 を超える定数の `=`（エンジンの比較）、PAD SPACE の照合順序の末尾の空白、同じ日付の記事のカテゴリのアーカイブの並び（MySQL も選ぶ計画で変わる。ゴールデンのデータには、1 つのカテゴリの中に同じ日付の記事がない）。Go のテストは 306 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。

## 段階 52: 整数の型の確かめを軽くする

- 背景: 段階 51 の後、記事の多いカテゴリの記事の一覧（手元 12.6 ms、MySQL 3.0 ms）は記事ごとに `wp_term_relationships` を主キーの 1 点で引き（`RowReader` で Pebble の走査を使い回す）、その 17% が整数の型の確かめ（`types.IsInteger`、`IsSigned`、`IsUnsigned`）だった。go-mysql-server は `t == Int8 || t == Int16 || ...` と型をインターフェースの比較で 10 回調べ、そのたびに構造体を比べる。エンジンのほかの多くの場所（比較など）でも呼ぶ。
- 方針: `sql/types/typecheck.go` の `IsSigned` と `IsUnsigned` を、`NumberTypeImpl_` への型の判定 1 回と元の型の種類（`baseType`）の switch にする（エンジンの変更。`docs/engine.md` に記録する）。数の型を作るのは `CreateNumberTypeWithDisplayWidth` だけで、表示幅は 0 か `TINYINT(1)`（`Boolean`）の 1 なので、結果は今と同じ。`SystemVariableType` の中身を取り出すのは残す。手元で、記事の多いカテゴリの一覧が 12.6 ms から 9.9 ms。データ形式は変えない。
- 完了条件: すべての数の型と数でない型（`SystemVariableType` で包んだものも）で、元の比較と結果が同じことをテストで確かめる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で、0.2.7 と比べて数字で示す。CI が通る。
- 結果: `IsSigned` と `IsUnsigned` を、型の判定 1 回と `baseType` の switch にした。`TestIsSignedUnsignedMatchEquality`（すべての数の型、`TINYINT(1)`、数でない型、システム変数の型で、元の比較と同じ。整数の型が真になる数も確かめる）。中身を取り出す処理を外す、`Int24` を落とすと落ちる。手元の `wpbench` で、記事の多いカテゴリの記事の一覧が 12.6 ms から 9.9 ms、自分のコメントの数が 10.9 ms から 10.1 ms。Go のテストは 306 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。データ形式は変えていない。
- レビュー（Fable）: 実行中にありうるどの型でも、元の比較と結果が同じ（数の型を作るのは 1 か所で、表示幅は 0 か `TINYINT(1)` の 1。システム変数の型、YEAR、BIT、DECIMAL、ENUM、SET、nil、空の値、ポインタも同じ。WordPress の `bigint(20) unsigned` や `int(11)` は、保存した型の文字列から読み直すと表示幅 0 の型になり、インデックスのキーとデータ形式に響かない）。`IsBoolean` は `TINYINT(1)` と `TINYINT` を見分けるので、今の比較のままにする。指摘されたテストの抜けを足した: `TestIsSignedUnsignedMatchEquality` に nil、空の値、ポインタ、システム変数の ENUM と SET。`internal/schema` の `TestNumberTypeDisplayWidths`（WordPress の DDL の数の型を保存して読み直すと、表示幅が 0、`TINYINT(1)` と BOOL だけ 1）。Go のテストは 307 件。
- GCE（`docs/bench.md` の「段階 52 の後」）: 0.2.7 と比べて、記事の多いカテゴリの記事の一覧が 70.9 ms から 25.0 ms（段階 51 の計測では 31.1 ms）、カテゴリのページの DB の時間が 88 ms から 43 ms と 82 ms から 19 ms。段階 51 で遅くなった 1 件の記事の term の読み込みは 1.92 ms から 1.76 ms。ほかは揺れの範囲。GCE のインスタンスは消した。
- CI の `TestCrashRecovery` が 1 度だけ `Access denied for user 'root'` で落ちた（流し直すと通った）。HeimDB のログは空で、テストが空いたポートを選んでから HeimDB が使うまでの間に、並行して走るほかのパッケージのテストのサーバーが同じポートを取り、そちらにつながっていた。テストの起動（`startArgs`）を、HeimDB が受け付けを始めたと出力して接続できるまで待ち、ポートを使えずに終わったら別のポートで起動し直すようにした（HeimDB 本体は変えていない）。

## 段階 53: 大きな表の ALTER TABLE のメモリ（ホスティング側からの報告）

- 背景: ホスティング側から、311 万行の `wp_postmeta` に `ALTER TABLE ... ADD COLUMN` を流すと、メモリを使い切ってプロセスが落ちる（OOMKilled、上限 7.7GB。120 万行は通り、160 万行で落ちる）と報告があった。WordPress の更新（dbDelta）が流すので、本番が止まる。手元でも、20 万行で 890 MiB、80 万行で 2.0 GiB、160 万行で 2.8 GiB（0.2 秒おきの RSS。下限）と行数に比例した。書き直し（`rewriter`）が、(1) 全件の走査で全行をメモリに集め（`scanPK`）、(2) 新しい形の行も全部集め（`rewriter.rows`）、(3) 主キーの重複を map で確かめ（`seen`）、(4) 全行とインデックスのエントリを 1 つの Pebble のバッチに書き、(5) 記録を残す設定ではバッチの中身を複製して同じバッチに書き足す。
- 方針: (1) 書き直しのための全件の読み出しを、1 つのスナップショットのまま千行ずつ読む（`RewriteInserter` の後の `PartitionRows` だけ。ほかの文の全件の走査は、同じ文の書き込みが後のページに見える（INSERT ... SELECT で同じ表を読むなど）ので、この段階では変えない）。(2) 新しい形の行は集めず、符号化して数 MB ごとに新しいテーブル ID へコミットする。新しい ID はテーブル定義が指すまでどこからも見えない。最後のコミットでテーブル定義を新しい ID に向ける。書き込みのロックは今と同じく ALTER の間持つ。(3) 書きかけの新しいテーブル ID に印 `m/rewrite/<ブランチID>/<テーブルID>` を付け（最初のコミットで ID の払い出しと一緒に。最後のコミットで外す）、GC は印の付いた ID を消さない（レプリカも自分で GC を回すので、印は記録でレプリカに写る）。文が失敗したら、書いたデータと印を消す。プロセスが途中で落ちたら、本番の起動時に印の付いたデータと印を消す（レプリカを本番に切り替えたときも起動時に消える）。古いバージョンの HeimDB は印を読まない（GC が使われていない表として消す）ので、データ形式のバージョンは上げない。(4) 主キーの重複は、主キーの列を変える書き直しでだけ、書いた分（コミット済みの新しい ID と、まだコミットしていない分）を引いて確かめる。一意インデックスは、変える列（消す列を含む）を含むものだけ、INSERT と同じ確かめ（`checkUnique`）を新しい ID で行う。
- 完了条件: 160 万行の ALTER の最大メモリが行数によらずほぼ一定になる。書き直した表の行とインデックスが今と同じ。途中で失敗した文と、途中で落としたプロセスのデータが片付く。書き直しの途中の GC が書きかけを消さない。レプリカに正しく写る。主キーと一意インデックスの重複が今と同じエラーになる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で、ホスティング側と同じ形のデータ（160 万行と 311 万行）の ALTER の時間と最大メモリを測り、目安としてホスティング側に渡す。CI が通る。
- 追加（承認済み）: GCE の計測で、`CREATE INDEX` も行数に比例してメモリを使う（311 万行で 4.5 GiB。全エントリを 1 つのバッチに書き、一意インデックスは全行を集めて並べ替える）ことが分かったので、同じ形に直した。また、起動し直した直後の書き直しは、AUTO_INCREMENT の次の値を求めるために全行をメモリに読んでいた（`maxAutoIncrementValue`）ので、AUTO_INCREMENT の列だけを 1 行ずつ読むようにした。
- 結果: (1) `rewriter`（`alter.go`）: 古い行は `rewriteScan` で千行ずつ読み、新しい形の行とインデックスのエントリは 4 MB ごとに新しいテーブル ID へコミットする。最初のコミットで ID の払い出しと印 `m/rewrite/<ブランチ>/<テーブル>` を書き、最後のコミットで印を外してテーブル定義を書く。書き込みのロックは最初に 1 回取り（`lockDDL`）、最後まで持つ。主キーの重複は主キーの列を変える書き直しだけ、一意インデックスは変える列（消す列を含む）を含むものだけ、コミット済みの分（新しい ID を引く）とまだコミットしていない分（メモリの表）で確かめる。(2) `CREATE INDEX`（`table.go`、`indexes.go` の `buildIndex`）: エントリを 4 MB ごとにコミットし、最初のコミットで前に途中で終わった作成のエントリを消して印 `m/rewrite/<ブランチ>/<テーブル>/<インデックス>` を付け、最後のコミットで印を外して定義にインデックスを足す。エントリを書かなかったとき（行がない、FULLTEXT）も、最後のコミットで同じ ID の残りを消す。(3) GC は印の付いたテーブル ID とインデックス ID を消さない（印はテーブル定義より先に読む）。本番の起動時に、印の付いたデータと印を消す（レプリカは消さない。本番の片付けが記録で写る）。(4) 文が失敗したら書きかけと印を消す。エンジンが取り消しも Close も呼ばずに返す経路（ENUM を狭めて値が入らないなど）は、文の終わり（`CommandEnd`）で取り消す。(5) 主キーの列の数が変わる書き直し（複数の列の主キーから列を消す）は `HeimDB: changing the primary key is not supported` で拒否する（前は panic した）。コミットの単位は GCE で 1、4、16 MB を比べて 4 MB にした（小さいとコミットのたびの同期書き込みで遅く、Pebble のメモリ上の表を大きく超えると別扱いの書き出しでメモリが増える）。GCE（`docs/bench.md` の「段階 53」、起動し直した直後）: 311 万行の `ADD COLUMN` が 7,806 MiB から 745 MiB（31.5 秒から 24.9 秒）、`CREATE INDEX` が 4,525 MiB から 629 MiB。160 万行と 311 万行でほぼ同じで、行数によらない。テスト: `TestChunkedRewriteKeepsRowsAndIndexes`、`TestChunkedRewriteDuplicates`、`TestAlterMatchesMySQLInSmallChunks`（行ごとにコミットし 2 行ずつ読んでも本物の MySQL と同じ）、`TestChunkedCreateIndex`、`TestChunkedCreateUniqueIndexDuplicate`、`TestRewriteDiscardedAtCommandEnd`、`TestRewriteRejectsPrimaryKeyChange`、`TestStaleIndexEntriesDroppedForFulltext`、store の `TestGCKeepsRewritingTable`、`TestGCKeepsIndexBeingBuilt`（子ブランチの作成中のインデックスを GC が消さない。レビューで見つけた）、`TestDropAndCleanupRewrites`、`TestReplicaKeepsRewritingTable`。直しを 1 つずつ外すと、対応するテストが落ちる。`TestBranchTimeLimit` は、10 万行の ALTER が 30 ms より早く終わるようになったので、ALTER だけ上限を 1 ms にした。Go のテストは 320 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。データ形式のバージョンは上げない（古いバージョンは印を読まず、使われていない表として GC が消す）。ただし 0.2.7 以前のレプリカに 0.2.8 以降の本番をつながない（古いレプリカの GC が書きかけを消す。`docs/operations.md` に書いた）。GCE のインスタンスは消した。
- レビュー（Fable）で見つけて直したもの: 子ブランチの `CREATE INDEX` の途中に GC が作りかけのエントリを消す（インデックスの印を足した）、エンジンが後始末を呼ばない経路で書きかけと読み出しのスナップショットが残り GC の境界が止まる（`CommandEnd` で取り消す）、キーを持たないインデックスが前の作りかけのエントリを引き取る、複合主キーの列を消す `DROP COLUMN` の panic。この段階で直さず記録したもの（同じく表の大きさに比例するメモリ）: 列の変更を含むブランチのマージ（`coldiff.go`）、復元でのインデックスの作り直し（`restore.go`）、条件のない DELETE を Truncate にしない経路（`scanAll`）、インデックスを使えない全件の読み出し（`scanPK`）。

## 段階 54: 検索の LIKE の照合を速くする

- 背景: 検索のページの DB の時間は 235 ms（MySQL 65 ms）で、ほとんどが記事の全件への `LIKE '%語%'` の照合（`LikeMatcher`）。ベンチマークの本文（約 1.9 KB）1 件の照合が手元で 32 µs、記事と固定ページ約 5,200 件の本文だけで約 170 ms になる。照合はパターンの 1 文字ごとのノードをインターフェースで呼び、一致しない位置ごとに後戻りする。ASCII 以外の文字（日本語など）は重みを 1 文字ごとに map で引く（段階 48 の表は ASCII だけ）。
- 方針: (1) パターンが `%` と普通の文字（エスケープした文字を含む）だけで、文字セットが utf8mb4 なら、`%` で区切った区間ごとの重みの列を前もって作り、区間を左から順に最初に一致する位置で探す（`%` だけのワイルドカードなら、この貪欲な探し方で後戻りと同じ結果になる）。今の照合は壊れた UTF-8 と U+FFFD を含む文字列を偽にするので合わせる。`_` を含むパターンと utf8mb4 以外は今の照合のまま。(2) 重みの関数の表を ASCII から U+0000〜U+FFFF に広げる。照合順序ごとに最初に使ったときに作る（256 KB、約 2 ms）。表は元の関数から作るので、重み（インデックスのキーを含む）は変わらず、データ形式も変わらない。
- 完了条件: 今の照合をテストに残し、新しい照合とランダムな文字列とパターンで一致することをプロパティテストで確かめる（照合順序は unicode_520_ci、0900_ai_ci、general_ci、bin など。大小、アクセント、全角と半角、日本語、U+FFFD、壊れた UTF-8、エスケープ、空のパターン）。U+0000〜U+FFFF のすべての文字で表と元の関数の重みが一致する。直しを外すと対応するテストが落ちる。本物の MySQL との LIKE のゴールデンテストと Go のテストが通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で検索の DB の時間が減ったことを示す（`docs/bench.md`）。CI が通る。その後 0.2.8 として公開する（公開の前に確認を取る）。
- 結果: (1) `likeSegments`（`sql/expression/like.go`）。真ん中の区間は最初の文字の重みで位置を探してから残りを比べ、最後の区間は末尾から逆に読んで比べる。元の照合は `matchNodes` に名前を変えて残した。(2) `tableSorter`（`sql/collations.go`）。ASCII の表は起動時に作り（`CollationID.ASCIIWeights()` で照合が関数を呼ばずに引く）、U+0080〜U+FFFF の表は照合順序ごとに最初に使ったときに作る。テスト: `TestLikeSegmentsMatchNodes`（重みの関数を持つ utf8mb4 のすべての照合順序（76 個）、エスケープの文字 3 つ（`\`、`|`、`あ`）、約 6 万のパターンと 120 万の文字列で元の照合と同じ）、`TestLikeSegmentsExamples`、`TestLikeSegmentsOnlyForPercent`、`TestTableSorterMatchesBase`（段階 48 の `TestASCIISorterMatchesBase` を広げた。すべての照合順序の U+FFFF までの全文字）、`TestTableSorterCachesBMP`。直しを 1 つずつ外すと（区間の照合、文字列の確かめ、区間の重なりの確かめ、`_` の除外、U+FFFF までの表）、対応するテストが落ちる。手元の照合のベンチマーク（本文 1 件）は英語で 32 µs から 1.8 µs、日本語で 34 µs から 7.5 µs。Go のテストは 320 件（エンジンのテストは別に 4 件足した。-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。GCE（`docs/bench.md` の「段階 54」）: 検索のページの DB の時間が 238 ms から 50 ms（MySQL 66 ms）、検索の文が 215 ms から 24 ms（MySQL 54 ms）。ほかのページは同じ。GCE のインスタンスは消した。データ形式は変えていない。
- レビュー（Fable）: 新旧の照合の違いは見つからなかった（utf8mb4 のすべての照合順序、8 つのエスケープの文字、結合文字、合字、BMP の外の文字、壊れた UTF-8 で約 550 万の組を比べて 0 件）。直したもの: 一致したときの確かめから `utf8.ValidString` を外した（`strings.ContainsRune(s, utf8.RuneError)` が壊れたバイト列も見つける）、プロパティテストを広げた（すべての utf8mb4 の照合順序、`\` 以外のエスケープの文字、BMP の外の文字、トルコ語の i、NUL。`_` を使うかの判定をノードで行う）、`docs/engine.md` に表のメモリの上限（181 個で約 45 MB）を書いた。記録だけ（前からの MySQL との差）: 本文に U+FFFD か壊れた UTF-8 を含む行は LIKE に一致しない（MySQL は U+FFFD を普通の文字として照合する。WordPress では文字コードの変換に失敗した本文に入ることがある）。
- バージョンを 0.2.8 にした（データ形式は 0.2.7 と同じ。段階 51 から 54 を含む）。

## 段階 55: 大きな表でメモリを使い切らない（ホスティング側のお願いの 2）

- 背景: 段階 53 の後、ホスティング側と同じ形の表（手元、40 万行と 80 万行）で文ごとの最大のメモリを測ると、どの文も行数に比例した（80 万行で、`SELECT COUNT(*)` 311 MiB、インデックスを使わない読み出し 401 MiB、主キーの範囲と `LIMIT 10` 451 MiB、半分の行の `DELETE` 1,551 MiB、全行の `UPDATE` 1,252 MiB、`DELETE FROM m` 2,373 MiB）。読み出しは、インデックスを使わない走査と範囲の検索が、当たる行をすべて集めてから返す（`scanPK`）。書き込みは、変更をトランザクションのバッチ（と索引）、文の取り消しのための記録（`tx.log`）、コミットで作るバッチに重ねて持つ。ホスティング側は、プロセスが落ちるより、上限を超えたらエラーを返すほうが運用として重要だとしている。
- 方針: (1) インデックスを使わない走査、主キーの範囲、インデックスの範囲（エントリ）を、集めずに 1 行ずつ返す。store に、層を重ねた走査を 1 件ずつ進める形（`scanLayered` を引き出し型にする）と、トランザクションが持つ走査を足す。Pebble のバッチのイテレータは作った時点の変更だけを見る（v2.1.7 の `Batch.NewIter` の文書）ので、文の始めに作れば同じ文の書き込みは見えず、今の見え方と同じ。走査はトランザクションの終わりと文の終わり（`CommandEnd`）で閉じる。条件のない `DELETE` を 1 行ずつ消す経路も集めずに読む。(2) メモリの上限 `-memory-limit`（`HEIMDB_MEMORY_LIMIT`）を足す。指定がなければ cgroup の `memory.max` を使う（なければ上限なし）。上限は `debug.SetMemoryLimit` に渡し、行を読む、書く、コミットするところで、ときどき生きているヒープの量を調べ、上限の一定の割合を超えたら文をエラー 1041（`HeimDB: ` で始まる）で止める（文は取り消され、プロセスは落ちない）。メモリはプロセス全体で数えるので、止まる文が使っている当の文とは限らない。(3) 書き込みの重複（バッチ、記録、コミットのバッチ）はこの段階では直さず記録する（上限でエラーになる）。
- 完了条件: 手元の 40 万行と 80 万行で、読み出しの文の最大のメモリがほぼ同じになる。上限を設定すると、大きな `DELETE` が落ちずにエラー 1041 を返して取り消され、その後もほかの文が動く。1 行ずつ読む経路で、同じ文の書き込みが見えない（`INSERT ... SELECT` で同じ表、主キーを変える `UPDATE`）、前の文の変更が見える、文の取り消しの後、ブランチの層の重ね合わせ、`AS OF` が今と同じ。エンジンが途中でやめても走査が閉じ、GC の境界が止まらない。直しを外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で 311 万行の読み出しの最大のメモリと、上限のある大きな `DELETE` を測る。CI が通る。
- 結果: (1) store に引き出し型の走査 `Scan`（`Next`、区間を移す `Reset`、`Close`）を足し、`scanLayered` もこれで書き直した。トランザクションの `RowScan`、`IndexScan` は開いた走査を覚えてトランザクションの終わりに閉じ、`RowScanAsOf`、`IndexScanAsOf` は AS OF で開く。backend は、全件の走査と主キーの範囲を `scanRowIter`、インデックスの範囲を `pkRowIter`（エントリを 4,096 件ずつ読み、主キーで行を引く）で 1 行ずつ返す。文の間だけ開いておくものは `stmtCloser` で `CommandEnd` に閉じる。条件のない `DELETE` の 1 行ずつの経路も集めない。(2) `-memory-limit`（`HEIMDB_MEMORY_LIMIT`）。指定がなければ cgroup の上限の 8 割（手元の 80 万行の `UPDATE` で RSS が上限を 1〜2 割超えたため）。生きているヒープ（`/gc/heap/live:bytes`）が上限の 75% を超えたら、GC を回して確かめ直し（100 ms に 1 回まで）、エラー 1041 で止めてトランザクションごと取り消す（`TranslateQueryError`）。調べるのは、行を 1,024 行読むごとと、コミットで 1,024 件書くごと（`Store.CommitCheck`）。取り消した後の最初の確認では必ず GC を回し直す（GCE で、止めた直後の文が古い値で止まったのを直した）。テスト: `TestRowScanIgnoresLaterWrites`、`TestScanMatchesScanRows`、`TestOpenScanClosedWithTransaction`、`TestCommitCheckStopsCommit`、`TestStreamingScanSkipsOwnWrites`、`TestStreamingScanStopsAtLimit`、`TestStreamingScanClosedAtCommandEnd`、`TestMemoryLimitStopsStatement`、`TestParseMemoryLimit`。直しを 1 つずつ外すと（全件の走査、主キーの範囲、インデックスのエントリを集める形に戻す、バッチの見え方の更新、トランザクションの終わりと文の終わりの後始末、メモリの確認、トランザクションの取り消し、コミットの確認、取り消し後の GC）、対応するテストが落ちる。GCE（`docs/bench.md` の「段階 55」）: 310 万行の読み出しの最大のメモリは 485〜512 MiB（0.2.8 は 836〜1,592 MiB。`ORDER BY ... LIMIT` だけ 868 MiB）。`LIMIT` の付いた範囲は 100 倍以上速い。310 万行の `DELETE` は 0.2.8 で 9.4 GiB、上限 4 GiB の段階 55 は 3.9 GiB でエラー 1041 を返して行を残し、次の文も動く。ページの表示は 0.2.8 と同じか少し短い。Go のテストは 329 件（-race も通る）。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 29 と同じテスト（panic 0、接続 1,303 本をすべて閉じた）。書き込みの重複（1 行あたり約 3 KB）は直していない。
- レビュー（Fable）の後: (1) 明示的なトランザクションの `COMMIT` がコミットの途中の確認で 1041 になると、`CommitTransaction` が先にトランザクションを外していたので取り消しが何もせず、明示的なトランザクションの状態が残って、続く文が自動コミットされなかった。トランザクションがなくても状態を終えるようにした（`TestMemoryLimitStopsCommit`）。(2) コミットの途中の確認は書き込みの鍵を持っているので、GC を回さず直前の GC の値で判断する（`checkCommitMemory`、`TestCommitMemoryCheckSkipsGC`）。(3) `-memory-limit` の桁あふれをエラーにした。直しを外すと、それぞれのテストが落ちる。(4) 実行時間の上限のテスト（`TestBranchTimeLimit`）が時々落ちた。1 行ずつ読むので 10 万行の `COUNT(*)` が 30 ms より早く終わり、`DELETE` も読んで消す部分は 30 ms の内に終わる（残りは止めないコミット）。上限を 1 ms にした。記録だけにしたもの: 大きな変更を持ったまま何もしていないトランザクションがあると、止まるのはほかのセッションの文で、その間は GC が 100 ms に 1 回まで回る（トランザクションの大きさの上限は別の段階で考える）。cgroup v2 の入れ子で親だけに上限があるとき（Kubernetes の pod だけの上限など）は上限なしになる（`-memory-limit` を指定する）。`heimdb_restore` やマージが自分のコミットで 1041 になると、セッションのトランザクションも取り消す。
- バージョンを 0.2.9 にした（データ形式は 0.2.8 と同じ。段階 55 を含む）。

## 段階 57: MySQL が受け付ける ascii の列と、引用符で囲んだエンジン名を受け付ける

- 背景: 段階 56 のカタログで、MySQL が受け付ける書き方を HeimDB が拒否するために、WP Mail SMTP（5 サイト。`ENGINE='InnoDB'`）のデバッグイベントとメールの送信キュー、W3 Total Cache の CDN（`CHARACTER SET ascii`）が使えなかった。手元で確かめると、`ENGINE='InnoDB'`、`ENGINE="InnoDB"`、`ENGINE 'InnoDB'`、`ALTER TABLE ... ENGINE='InnoDB'` が構文エラーになる（バッククォートと `CHARSET='utf8mb4'` は通る）。本物の MySQL 8.0 では、ASCII の 128 文字について `ascii_general_ci` と `utf8mb4_general_ci`、`ascii_bin` と `utf8mb4_bin` の並び順と等しい組が同じで、どれも PAD SPACE。
- 方針: (1) 構文解析の前の書き換え（`parser.go`）で、`CREATE TABLE` と `ALTER TABLE` の表のオプションの位置にある引用符で囲んだエンジン名を、バッククォートにする。`SELECT ... WHERE engine = '...'`、文字列とコメントの中、列の名前は変えない。vitess は変えない。(2) ascii の表と列（表の既定、列、`ALTER TABLE`、`CONVERT TO`）を、段階 37 の utf8mb3 と同じく、utf8mb4 の照合順序（`ascii_general_ci` は `utf8mb4_general_ci`、`ascii_bin` は `utf8mb4_bin`）として保存し、警告を出す。データ形式とキーの符号化は変わらない。(3) 記録だけ: `SHOW CREATE TABLE` には utf8mb4 と出る。ascii の列に ASCII 以外の文字を入れると、MySQL は WordPress の sql_mode（strict なし）では `?` にし、既定の strict ではエラー 1366 にするが、HeimDB はそのまま保存する（元の文字セットを覚えるとデータ形式が変わる）。
- 完了条件: 書き換えるもの（`CREATE TABLE` と `ALTER TABLE` の引用符で囲んだエンジン名）と変えないもの（`WHERE engine = '...'`、文字列とコメントの中、列の名前の `engine`）のテスト。ascii の表と列の作成、インデックス、並び順、等しさが utf8mb4 の照合順序と同じで、警告が出るテスト。WP Mail SMTP と W3 Total Cache の実際の `CREATE TABLE` が通る。直しを外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。`scripts/plugin-check` で 2 本を確かめ直し、`docs/plugins.md` を直す。CI が通る。

ENGINE='InnoDB'`、`WHERE engine = 'InnoDB'` の件数）、`TestASCIIStoredAsUTF8MB4`（W3 Total Cache の表、大小だけ違う主キーの重複と検索、`ascii_bin`、表の既定、`ALTER`、`CONVERT TO`、`SHOW CREATE TABLE`、utf8mb3 と混ざったときの警告）。ascii を拒否することを確かめていた 2 つのテストは utf16 で確かめる形にした。直しを 1 つずつ外すと（書き換えをつながない、SELECT で止めない、括弧の深さ、CREATE / ALTER の判定、ascii の置き換え、ascii の受け入れ、主キーの型の置き換え、文字コードごとの警告）、対応するテストが落ちる。Go のテストは 334 件（本物の MySQL が要る 1 件を含む。-race でも成功）。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 55 と同じテスト（panic 0、接続 1,303 本をすべて閉じた）。1 回目は、並行して `activate.sh`（Docker の WordPress）を動かした間にフォントのテストが 13 件落ちた（そのテストだけを HeimDB と MySQL で流すとどちらも通る）。並行の作業なしで流し直して 43 件。`scripts/plugin-check`: `check.py` は ascii を指摘しない。有効化で WP Mail SMTP と W3 Total Cache に拒否した文がない。`docs/plugins.md` で 2 本を「使える」にし、`docs/status.md` の文字コードの差を直した。
- レビュー（Fable）: エンジン名の書き換えは、パーティションの前後、複数の文、ANSI_QUOTES、`ENGINE_ATTRIBUTE`、`engine` という列への変更など約 30 の入力で意味が変わらず、長さも変わらなかった。ascii の置き換えの根拠（128 文字の並びと等しい組、PAD SPACE）は本物の MySQL で確かめ直された。直したもの: `check.py` が主キーの前方の長さ（長さを捨ててから判定していた）と生成列を見落とし、列の一覧が読めない `CREATE TABLE` を数えずに飛ばしていた。前方の長さと生成列を調べ、大文字の `CREATE TABLE` で読めないものは「表の定義が読めない」として出す（顧客のサイトの 52 本では、WPML の `create_table` と WP Cerber 9.10 の表の組み立ての 2 か所が新しく出た）。`docs/plugins.md` の判定の基準に 2 つを足した。`activate.sh` の HeimDB は、WordPress のコンテナから届くアドレスだけで待ち受ける（macOS は 127.0.0.1、Linux は Docker の既定のブリッジのアドレス。Linux では試していない）。ログの panic は、行頭の `panic:` と回復のログだけを数える。文書の誤り（`docs/status.md` の段階、`?` になるのは strict でないときだけ、`CONVERT TO` の説明）を直した。記録だけ: プリペアドステートメント（バイナリプロトコルの COM_STMT_PREPARE）では、vitess がハンドラより前に構文解析するので、エンジン名の書き換えも段階 11 の `\_` の書き換えも効かない（WordPress の wpdb はテキストプロトコルだけ。直すには vitess のフォークが要る）。`/*!50100 CREATE TABLE ... ENGINE='InnoDB' */` の中は書き換えない（バージョンの数字を最初の語と数える）。列に `COLLATE ascii_general_ci` を付けた比較は、HeimDB では照合順序が utf8mb4 の列に合わないエラーになる（MySQL は通る）。`information_schema.columns` の `CHARACTER_OCTET_LENGTH` は ascii の `CHAR(3)` で 12（MySQL は 3）。
- バージョンを 0.2.10 にした（データ形式は 0.2.9 と同じ。段階 56、57 を含む）。

## 段階 58: メモリの上限で、サイトが止まらないようにする（ホスティング側のお願いの続き）

- 背景: ホスティング側が 0.2.9 を本番に入れ、50 万行の表（`wp_postmeta` と同じ形）を `-memory-limit 256M` で開くと、1 行だけ読む文も索引を使う文もエラー 1041 になり、起動し直しても直らなかった（64M でも同じ）。その間も `heimdb_status()` は通るので、SQL で見る監視では気づけない。手元で確かめると、生きているヒープは起動直後に 42 MiB（大半は照合順序の重みの表 36 MiB）、読んだ後に 178 MiB で、増えた分はほぼすべて Pebble のブロックキャッシュ（134 MiB）だった。本番のイメージは cgo なしで建てるので、Pebble はキャッシュを Go のヒープに取り（`manual.New` が `make`）、上限の判定に数えられる。キャッシュは読めば満ちて GC でも減らないので、上限の 75% が「起動直後の分 + キャッシュ」より小さいと、どの文も拒否され続ける。常駐は行数にはほぼよらない。ホスティング側は、ほかに (a) `heimdb_status()` に生きているヒープと上限を出す、(b) 上限が小さすぎることを起動時に知らせる、(c) 行数とともにまだ増える経路を知りたい（311 万行の `ORDER BY meta_value DESC LIMIT 10` の 868 MiB が最大か。列の変更を含むマージと復元）、(d) 禁じられているバージョンの組み合わせ（0.2.7 以前のレプリカと 0.2.8 以降の本番）をソフトで拒否する、を求めている。
- 方針: (1) `-cache-size` を指定しないときは、ブロックキャッシュを上限の 8 分の 1（16 MiB から 128 MiB の間。上限なしなら 128 MiB）にする。(2) 起動時に、表を開いた後で GC を回し、生きているヒープ + キャッシュの大きさ + 文の余裕（32 MiB）が上限の 75% を超えるなら、必要な上限を添えたエラーで起動を拒否する。(3) `heimdb_status()` に `memory_limit_bytes`、`memory_abort_bytes`（文を止める境目）、`memory_live_bytes`（直前の GC で生きていたヒープ）、`memory_aborted_statements`、`cache_size_bytes`、`cache_used_bytes` を足す。(4) レプリカは同期の要求に、自分が分かる記録の水準（`level`）を付ける。本番は水準の足りないレプリカ（付けない 0.2.10 以前を含む）を、データ形式のバージョンの違いと同じく 409 で拒否し、本番の `heimdb_status` に理由を出す。レプリカを先に上げる手順のとおりなら困らない。(6) GCE で測ると、マージ（列を足したブランチ、全行を変えたブランチ）と復元（全行を変えた後）は、変わる行をすべてメモリに集めて計画を作る間に上限を確かめず、上限 3,276 MiB でも 1041 にならずに OOM で落ちた（上限なしでは、列を足したマージが 11.9 GiB、復元は cgroup の 12 GiB を超えた）。計画づくりと適用の繰り返しで、ときどき（行を読む経路と同じ間隔で）メモリを確かめ、1041 で止めて取り消す。行数に比例しない形にすること（計画を集めずに流す）と、列を変えたマージが遅い（881 秒）ことは、次の段階にする。(7) ホスティング側の 2 通目の報告（`mariadb-dump` の既定の出力は表ごとに 1 つのトランザクションになり、311 万行の取り込みが 7.7 GiB で落ちた）を受けて、`docs/operations.md` に `--skip-no-autocommit` を書く。コミットしていない書き込みを行数に比例しない形にすることと、1 行あたりのメモリ（ホスティングの取り込みで 2.4 KB 以上、元のデータは 74 バイト）を縮めることは、次の段階の候補にする。(5) 行数とともに増える経路（索引を使わない `ORDER BY`、表全体の `UPDATE` と `DELETE`、列の変更を含むマージ、復元）を 311 万行で測り、`docs/operations.md` に常駐と文ごとの目安を書く。データ形式は変えない。
- 完了条件: 256M の上限で 50 万行を開き、全件を読んだ後も 1 行の文が通る。小さすぎる上限で起動が拒否され、エラーに必要な上限が出る。`heimdb_status()` に 6 項目が出て、1041 の後に回数が増える。水準のないレプリカと足りないレプリカが拒否され、同じバージョンなら同期する。上限を付けると、大きなマージと復元が落ちずに 1041 を返して取り消され、その後もほかの文が動く。直しを外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で、311 万行の経路ごとの最大のメモリを測る。CI が通る。
- 結果: (1) `-cache-size` の既定を 0（上限の 8 分の 1 を 16〜128 MiB に収める。`AutoCacheSize`）にした。(2) `CheckStartupMemory`（`main.go` で store を開いた後）。足りる上限は、キャッシュが上限から決まるときはそれも含めて求める。(3) `heimdb_status()` に `memory_limit_bytes`、`memory_abort_bytes`、`memory_live_bytes`、`memory_aborted_statements`、`cache_size_bytes`、`cache_used_bytes`（store の `Status` にキャッシュの大きさと Pebble の `BlockCache.Size`）。(4) レプリカは `level`（`replicaLevel` 1）を付け、本番は `minReplicaLevel` より低いレプリカを 409 で拒否する。(6) マージと復元の計画づくり（`differ` の `getRow` と `scanRows`、store の変わった行の一覧に `Store.ReadCheck`）、列を変えたマージの親の書き直し（`rewriteParentTable`）、復元のインデックスの作り直し（`rebuildIndexes`）、自分のトランザクションに書く editor（`e.tx`。それまでセッションのトランザクションのときだけ確かめていた）で、メモリの上限を確かめる。マージは 1041 を包んで返していたので、接続先には 1105 で届いていた。メモリの上限のエラーは包みを外して 1041 で返す（`TranslateQueryError`）。テスト: `TestAutoCacheSize`、`TestCheckStartupMemory`、`TestStatusMemory`、`TestMemoryLimitStartup`（実行ファイルを起動して、64M で起動を拒否し、256M でキャッシュが 32 MiB）、`TestReplicaLevel`、`TestMergeMemoryLimit`、`TestRestoreMemoryLimit`、`TestChangedRowsReadCheck`、`TestOwnTxnEditorMemoryLimit`。直しを 1 つずつ外すと、対応するテストが落ちる。ただし親の書き直しとインデックスの作り直しの読み出しの確かめは、手元の小さな表ではその前の計画づくりで止まるのでテストで切り分けられず、GCE の 310 万行で確かめた。手元（cgo なし、50 万行、`meta_value` 200 バイト）: 256M で全件を読んだ後も 1 行の文が通る（生きているヒープ 88 MiB、キャッシュ 32 MiB）。64M は「at least 118 MiB」を添えて起動しない。GCE（`docs/bench.md` の「段階 58」）: 常駐は 310 万行で RSS 約 500 MiB、生きているヒープ約 200 MiB（キャッシュ 127 MiB を含む）。行数とともに増えるのは、`ORDER BY ... LIMIT` 866 MiB、値がすべて違う列の `GROUP BY` 1,728 MiB、表全体の `UPDATE` 4,042 MiB、`DELETE` 9,344 MiB、全行を変えたブランチのマージ 7,871 MiB、列を足したブランチのマージ 11,869 MiB（881 秒）、全行を変えた後の復元（12 GiB を超えて落ちた）。上限 3,276 MiB で、直す前は列を足したマージと復元が OOM で落ち、直した後は 3 つとも 1041 を返し（最大 3,266〜3,399 MiB）、データは変わらず、次の文も動いた。`docs/operations.md` に常駐と経路ごとの目安、上限に数える常駐の分、ダンプの取り込み（`--skip-no-autocommit`）、レプリカの水準、`docs/procedures.md` に `heimdb_status()` の 6 項目を書いた。Go のテストは 343 件（-race も通る）。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 57 と同じテスト（panic 0、接続 1,303 本をすべて閉じた。マージと復元の直しの前と、計画づくりの直しの後の 2 回。editor の直しは上限のないときは何もしない）。記録だけ: `SUM(LENGTH(...))` が HeimDB では `1e+08` と浮動小数点の形で返る（MySQL は `100000000`）。

## 段階 59: 大きな書き込み、マージ、復元のメモリを縮める（ホスティング側の 2 通目のお願い）

- 背景: ホスティング側が `mariadb-dump` の既定の出力（表ごとに 1 つのトランザクション）で 311 万行を取り込むと、7.7 GiB で落ちた（RSS で 1 行 2.4 KB 以上。元のデータは 74 バイト）。手元の 20 万行（`autocommit=0` の INSERT）のコミット前の生きているヒープは約 235 MiB（1 行約 1.2 KB）で、RSS はその約 2 倍（上限がなければ GC がヒープの 2 倍まで伸ばす）。内訳は、文の取り消しのための記録 `tx.log`（キー、値、記録の構造体を Pebble のバッチとは別に持つ）が約 130 MiB、バッチの本体 64 MiB、バッチの並びの索引 32 MiB。Fable のレビューで、本当の山はコミットの最中にあることが分かった。コミットはバッチ（大きさ D）を別のバッチに 1 件ずつキーを作り直して写し、コミットの記録を残すとき（既定）は `bytes.Clone(Repr())` でもう一度同じバッチに入れるので、一瞬 4〜6D が要る。Pebble のバッチは 4 GiB で panic する（`batch.go` の `grow`）が、いまは何も確かめていない。段階 58 の GCE の測定では、マージ（列を足したブランチで 11.9 GiB、881 秒）と復元（12 GiB 超）は、変わった行の主キーをすべて一覧にし、主キーごとに AS OF の点読み（層ごとにイテレータを作る）を 4 回し、変わる行の値をすべて持つ。
- 方針: (1) コミット: 写し先のバッチを要る大きさで確保し、キーは `SetDeferred` で直接書いて時刻を付け直す。記録は `Repr()` を `SetDeferred` で写し、`bytes.Clone` をなくす。(2) `tx.log` をやめ、バッチを正にする。`DropMergeBasesAfter` の削除はバッチに入れ、位置（文の始め、`Mark`、印）はバッチの件数で数え、文の取り消しは古いバッチの先頭から読み直して作る。古いバッチはトランザクションの終わりまで閉じない。データ形式は変えない。(3) コミットしていない書き込みに上限を設ける（バッチが 1 GiB を超えたら 1197 で文を取り消す。メッセージで `--skip-no-autocommit` を案内する）。(4) 復元とマージ: 変わった行の一覧と主キーごとの点読みをやめ、時点ごとの走査を主キーの順に並べて進める。復元は変わる行の値を持たずに流し、復元の書き込みでは一意の確かめを省く（戻した後は T の時点の状態）。マージは確かめと適用の 2 回を同じ関数で流し、食い違えば書かずに止める。列を変えたマージの親の書き直しと、復元のインデックスの作り直しも行を集めない。先にプロファイルで確かめる。(5) コミットしていない書き込みをディスクに逃がすことはしない（コミット前のバージョンを見えなくする仕組み、データ形式、レプリケーションの記録が変わる）。
- 計画から変えたこと: (3) の上限は 1536 MiB にした（上限 3,276 MiB の環境でどちらが先に効くかは GCE で測る）。マージと復元のトランザクション（`BeginInternal`）は分けて書けないので、Pebble が受け付ける限り（記録を残すとコミットのバッチは 2 倍になる）の 1900 MiB を上限にし、超えたら 1197 でその操作の案内（復元は「表を分けて戻す」）を返す。包んだエラーも接続先には 1197 で返す。(2) の古いバッチは、次のコマンドの始めに走査が残っていなければ閉じる（Fable のレビュー: 1197 で止まった文を同じトランザクションで繰り返すと、上限に近いバッチが 1 本ずつ溜まった）。取り消しの写し先は要る大きさで確保する。(4) のマージは 2 回流さず、行が多ければ（5 万行以上）差分では主キーと親にあるかだけを持ち、適用のときに同じ時点の走査で読み直す（同じロックの中で同じ時点を読むので食い違わない）。走査は主キーの昇順にしか引けないので、逆に引いたらエラーにする（変わった行の一覧は層をまたいで主キーの順に返る）。復元の一意の確かめは省かなかった（通常の書き込みのまま。測ってから決める）。列を変えたマージの親の書き直しで行を集めないのは、一意インデックスのないテーブルだけ（あるテーブルは重複を確かめてから書くので集める）。完了条件のコミット中の山（3.5 倍）は 4.5 倍にした。トランザクションのバッチは倍々に伸びるので最大でその 2 倍を確保し、コミットのバッチは記録を残すと中身を 2 回持つので、合わせて 4 倍を超えることがある（20 万行で 4.1 倍。テストは 4.5 倍まで）。コミットのバッチは、保存していない AUTO_INCREMENT のカウンタ（すべてのテーブルの分）の大きさも足して先に確保する（Fable の 2 回目のレビュー: 余白の 64 KiB を超えると倍々に伸び、上限に近い大きさでは約 7.6 GiB を確保した）。GCE の測定（310 万行）で、2 つ見つけて直した。(a) コミットのバッチを先に確保するようにしたため、メモリの上限の確かめ（1024 件ごと）より前に一度に確保し、上限 3,276 MiB の復元が 1041 にならずに cgroup に落とされた。コミットのバッチを確保する前と、トランザクションのバッチが倍に伸びる前に、確保する大きさを足して境目を超えないか確かめる（`Store.AllocCheck`）。(b) コミットの記録は中身全体で 1 つの値なので、コミットの後に Pebble がファイルに書き出すとき、その値と圧縮した写し（100 万行の復元で約 1.6 GB）をメモリに持つ（0.2.10 からある。コミットの後なのでメモリの上限の確かめが効かず、上限なしの復元はコミットの後に 12.5 GiB で落ちた）。記録を 1 MiB ずつに分けて書く（データ形式のバージョン 3）。
- 完了条件: 20 万行の取り込みのコミット前の生きているヒープが 1 行 0.7 KB 未満、コミット中の山がバッチの 3.5 倍以下。上限を超えた書き込みが 1197 で取り消され、接続が生きている。文の取り消し（同じキーの 2 回書き、削除の記録との組み合わせ、取り消しをまたぐ走査）と、ランダムな操作列のモデルとの比較のテスト。一意の値の入れ替えの復元、2 回のマージの食い違いを止めるテスト。直しを外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で 310 万行の取り込み、`UPDATE`、`DELETE`、マージ、復元の最大のメモリと時間を測り、`docs/operations.md` に RSS と生きているヒープの違いと目安を書く。CI が通る。
- 結果: (1) `tx.log` をやめ、書き込みはバッチだけに持つ。位置はバッチの件数で数え、文の取り消しとセーブポイントへの取り消しは、古いバッチの先頭から要る大きさのバッチに写して作る（`truncate`）。古いバッチは次のコマンドの始めに、走査が残っていなければ閉じる。`DropMergeBasesAfter` の削除もバッチに入れる。コミットはバッチを順に読み、`SetDeferred` で時刻を付け直して、要る大きさで確保したコミットのバッチに写す。記録は `Repr()` を写さずに書く。(2) 上限: 接続のトランザクションは 1,536 MiB、マージと復元（`BeginInternal`）は 1,900 MiB で 1197。包んだエラーも 1197 で返す。(3) 大きな確保の前の確かめ（`Store.AllocCheck`）: トランザクションのバッチが倍に伸びる前、文の取り消しで写す前、コミットのバッチを確保する前に、確保する大きさを足してメモリの境目を超えないか確かめ、超えれば 1041。取り消しで写す分が拒否されたら、トランザクションごと取り消し、元のエラー（重複など）の代わりに 1041 を返す（go-mysql-server は取り消しのエラーを捨てるので、セッションが覚えて返す）。(4) コミットの記録を 1 MiB ずつに分けて書き（`l/<時刻>/<番号>`、データ形式のバージョン 3、運ぶ記録の形はバージョン 2 のまま）、64 MiB 以上のコミットの後は書き出しを 2 回促す。レプリカは記録を写さずに適用し、書くバッチを先に確保する。(5) マージと復元: 5 万行以上は時点ごとの走査を主キーの順に進めて読む（`rowCursor`。逆順に引けばエラー）。マージは行の値を持たずに主キーと親にあるかだけを持ち、適用で読み直す。既定値は表ごとに一度求め、変換の文脈を使い回す（列を足したマージの 881 秒の大半）。一意インデックスのない表の親の書き直しと、復元のインデックスの作り直しは流し込む。復元は計画、削除、挿入の 3 回を同じ関数で流し、計画との件数の食い違いで止める。テスト: `txnbatch_test.go`（同じキーの 2 回書き、マージの記録の削除、取り消しをまたぐ走査、モデルとの比較、1 行あたりのメモリとコミットの山、1197 とその繰り返し、AUTO_INCREMENT の分の確保、確保の前の確かめ、取り消しの確かめ、大きなコミットの後に手放す）、`TestChunkedRecords`、`TestUnchunkedRecord`、`TestApplyRecordsPresized`、`TestFormatVersion`、`TestUncommittedWritesLimit`、`TestInternalWritesLimit`、`TestCheckAlloc`、`TestDiscardOutOfMemory`、`TestMergeAndRestoreWithCursors`（しきい値を 1 にしてマージと復元のテストを流す。`HEIMDB_TEST_CURSOR_MIN_ROWS=1` で backend 全体も通る）、`TestRestoreBranchAcrossLayersWithCursors`、`TestRowCursorRejectsOutOfOrder`、`TestRestoreRebuildRemovesStaleEntries`。`HEIMDB_TEST_LOG_CHUNK_BYTES=64` で store と replication の全体も通る。直しを 1 ## 段階 60: マージから外す表と、マージの結果を機械が読める形にする（ホスティング側のお願い）

- 背景: ホスティング側から、Yoast SEO の索引の表（`yoast_indexable` など）は、ステージングのものをマージしたい場面がなく、マージの後に本番で作り直せばよいという意見があった。マージに含めたくない表はほかにもありうる。Yoast の索引の表は `int` の AUTO_INCREMENT で、記事の保存やページの表示のたびに行が増え、別の表がその ID を指すので、両側で足すとマージが競合で止まるか、参照が黙ってずれる（段階 61 の背景）。作り直しのきっかけにするフック（`heimdb_after_merge` のようなもの）も欲しいが、HeimDB は PHP を呼べないので、フックはプラグインが出す。HeimDB に要るのは、マージが何をしたか（変えた表、外した表、解決した件数、拒否の理由）を機械が読める形で返すこと。ホスティング側の要望: (1) 外した表は「本番をそのまま残す」（空にしたり、ブランチの側で置き換えたりしない。索引の表が一瞬でも空になると、公開側のメタタグとサイトマップが欠ける）。(2) 外した表はスキーマの差も無視する（ブランチが Yoast の更新をまたぐと、`yoast_migrations` と索引の表の定義が片側だけ変わる）。(3) 除外を変えられるのは管理者だけ、読むのはサイトのユーザーでもよい（プラグインが状態の表示に読む。顧客の側から除外を外せないように）。(4) WordPress 本体の表をどう見分けるかを文書に書く（接頭辞はサイトごとに違う）。(5) undo（マージを戻す復元）も、何を戻したかを同じように返す（マージ → 再索引 → undo のとき、再索引をやり直すため）。(6) 拒否の理由の語は英語で固定し、翻訳せず、足すだけで消さない。できれば語ごとにエラー番号を分ける。ホスティング側は 1 サイト 1 プロセス（サイトごとに `-db`、ポート、データ）なので、サーバの設定はそのサイトだけに効く。払い出しのときに、`catalog/plugins.yaml` のプラグインごとの「マージから外す表」に接頭辞を付けて登録する（ホスティング側の作業）。
- 方針: (1) マージから外す表の設定を、バージョンのないメタデータ（`m/mergeexclude`）に持つ。コミットを通して書くので、レプリカとバックアップに付いていく。手続きは `heimdb_merge_exclude(パターン)`（足す）、`heimdb_merge_include(パターン)`（外す）、`heimdb_merge_excludes()`（一覧）。パターンは表の名前で、`%` と `_` を `LIKE` と同じ意味で使える（大小を区別しない）。足すと外すは管理者（SUPER）だけ。一覧は、接続中のデータベース（ブランチを含む）の EXECUTE 権限を持つユーザー（サイトのユーザーとブランチだけの権限のユーザー）なら読める。(2) 外した表には、マージで何もしない（行、列の定義、インデックスを比べず、書かない。ブランチで作った表も親に作らない。ブランチで消した表も消さない）。差分の要約とマージの結果には `status` が `excluded` の行を出し、件数の列にはブランチの側の変更（反映しなかったもの）の件数を出す。`detail` に当たったパターンを出す。マージの `undo` の行の表の一覧には入らない（戻すときにも触らない）。(3) WordPress 本体の表は外せない。本体の表は、マージが使う接頭辞（`detectPrefix`。`option_name` 列を持つ `<接頭辞>options` と `<接頭辞>posts` の組から求める。見つからなければ `wp_`）に、`posts`、`postmeta`、`options`、`comments`、`commentmeta`、`terms`、`term_taxonomy`、`term_relationships`、`termmeta`、`links`、`users`、`usermeta` を付けた名前と（大小を区別せず）完全に一致する表。名前の終わりだけでは見ない（`wp_foo_posts` は本体ではない）。判定は足すときとマージのときの両方でする。足すときは、接頭辞が決まれば本体の表に当たるパターンをエラーにし、決まらなければ（WordPress のインストールの前）受け付ける。マージのときは毎回判定し、パターンに当たった本体の表も外さずにマージして、差分とマージの結果に `status` が `not excluded` の行（`detail` に当たったパターンと理由）を出す（設定の順番によらず本体の表を守る）。組が 2 つ以上あるとき（古いインストールの表が残っている `wp_` と `wp_old_` など）は、今は最も短いものを黙って選び、マージの規則（記事とメタの関係、件数の数え直し）も取り違えうる。接頭辞が決まらないので、除外の有無によらず差分とマージを `ambiguous_prefix` で拒否し、見つかった接頭辞をエラーに出す（古い表を消すか名前を変えてからマージする。足すときは、本体の表の判定ができないので受け付ける）。ホスティングの移行済みの 3 サイト（2026-10-18）は、どれも組が 1 つ（`wp_`）で、止まるサイトはない。ホスティング側はダンプの受け入れ検査に「組が 2 つ以上ないか」を足す。組を数える問い合わせ（`information_schema` の `columns` と `tables` の結合）は HeimDB でもそのまま通ったので、`docs/procedures.md` に載せる。マルチサイトの表（`wp_2_posts` など）は、もともとマージの規則の外。(4) マージを拒否するエラーに、英語の理由の語と、語ごとの HeimDB のエラー番号を付ける。形は `HeimDB: merge refused (<語>): ...`。番号は本物の MySQL が使わない範囲から取り、SQLSTATE は `HY000`。今ある拒否と、この段階で足す `ambiguous_prefix`（解決していない競合、`db_version` の違い、トランザクションの途中、ブランチがない、親がない、親の行がマージの間に変わった、メモリの上限 1041、大きさの上限 1197、レプリカ）を洗い出して一覧にする。1041、1197、レプリカのように既に番号の決まったものは番号を変えず、語だけを付ける。語と番号は足すだけで、消さず、翻訳しない（`docs/procedures.md` に書く）。(5) 復元（マージの `undo` を含む）は、今も戻した表ごとの行（`restore rows` と件数）を返す。形をマージの結果とともに `docs/procedures.md` にまとめ、プラグインが同じ規則で読めるようにする（列の名前は変えない）。(6) 文書: `docs/procedures.md`（3 つの手続き、結果の形、本体の表の見分け方、理由の語と番号の表）、`docs/plugins.md`（Yoast を外すときの手順。Yoast はマイグレーションをどこまで済ませたかを `wp_options` の
