## 段階 71: 主キーの等号の文を含む `UNION`

- 背景: 段階 70 のコードレビューの修正を確かめる途中で、`SELECT b FROM q WHERE id = 1 UNION ALL SELECT b FROM q WHERE id > 1` が `result max1Row iterator returned more than one row`（1105）になると分かった。`UNION`、`UNION ALL`、`EXCEPT` の左右どちらかに主キーの等号の文があると起き、定数との `UNION`、3 つ以上つなぐもの、`ORDER BY` や `LIMIT` の付いたものも同じ。派生テーブルの中の `UNION`、集計どうしの `UNION`、`INTERSECT` は通る。エンジンは主キーの等号で 1 点を引く文に「最大 1 行」の印（`QFlagMax1Row`）を付け、結合と副問い合わせでは付けないが、集合演算を確かめていない。印は文全体に効き、結果を返す処理が 2 行目でエラーにする（上流の v0.20.0 も同じ）。WordPress のコアは使わないが、`UNION` を使うプラグインで起きうる。
- 方針: 段階 48（`EXPLAIN` の同じエラー）と同じ場所（`engine.go` の `analyzeNode`）で、解析する文に集合演算（`plan.SetOp`）があれば印を外す。印は結果を返す処理の近道にだけ使うので、外しても結果は変わらない。印を付ける 3 か所は変えない。
- 完了条件: 上の書き方がエラーにならず、MySQL と同じ行を返す（準備した文でも）。主キーの等号だけの文は 1 行で返る。印を外す処理を消すとテストが落ちる。Go のテスト（-race、カーソルで読む設定、記録を分ける設定）が通る。PHPUnit の全テストで差が増えない。
- 結果: `analyzeNode` で、束縛した文の木に `plan.SetOp` があれば `QFlagMax1Row` を外した。テスト `TestSetOpWithPointLookup`（`UNION ALL` の左右、`UNION`、定数との `UNION`、`EXCEPT`、3 つつなぐもの、`ORDER BY` と `LIMIT`、準備した文、等号だけの文）。enginetest は結果を返すサーバの処理を通らず、印を外す処理を消しても落ちないので、段階 48 と同じく HeimDB のテストで確かめる（足した enginetest は外した）。印を外す処理を消すと、普通の文でも準備した文でもテストが落ちる。Go のテストは 398 件から 399 件（-race、`HEIMDB_TEST_CURSOR_MIN_ROWS=1`、`HEIMDB_TEST_LOG_CHUNK_BYTES=64` でも成功）。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 70 と同じテスト（panic 0、接続 1,302 本をすべて閉じた。3336 で流した）。

## 段階 72: 主キーのない表

- 背景: 主キーのない表を拒否していたので、WP Cerber（ログ、通信の記録、`cerber_acl` など）と Loginizer（`loginizer_logs`。主キーがなく `UNIQUE KEY ip` だけ）が使えず、移行するサイトのダンプも、使われていないプラグインの置き忘れの表（段階 39 の `wp_yoast_seo_meta`、`wp_xsg_sitemap_meta`）で止まった。PHPUnit の 43 件の差のうち 3 件もこれ。ブランチのマージは主キーで行を対応づけるので、主キーのない表の行の対応づけが要る。
- 方針: エンジンには主キーのない表として見せ、保存のキーを 2 通りにする（「キー設計」）。すべての列が `NOT NULL` の一意インデックス（前方の長さなし、主キーにできる型）があれば、MySQL の InnoDB と同じく最初のものの列で並べる（ブランチの差分とマージは、その列で今の主キーの表と同じに対応づく）。なければ見えない行 ID（AUTO_INCREMENT と同じブランチの番号帯）で足した順に並べ、エンジンが消す・変える行として渡す値は、見える列のハッシュの見えないインデックスで行 ID に戻す（同じ中身が何行もあれば行 ID の小さいもの）。ブランチの差分とマージは行 ID のまま今の仕組みで比べる（両側で足した行は ID がぶつからずに両方残り、分岐の前からある行は行 ID で対応づく）。`UPDATE`、マージ、復元、レプリカ、書き直しは行 ID を変えない。書き直し、一意インデックスの追加と削除、`ADD PRIMARY KEY`、`DROP PRIMARY KEY` のたびに、どちらで並べるかを決め直し、変わるなら表を書き直す（空の表は定義だけ）。データ形式のバージョンを 5（番号だけ）、レプリカの記録の水準を 3 に上げる。Fable の計画レビューで、行 ID の表のマージを中身の数で比べる案から今の仕組みに変え（全部を消して入れ直すと重複するのは記録だけ）、並べる一意インデックスの規則を MySQL に合わせ（`NOT NULL`、前方の長さなし）、一意インデックスの追加でも書き直すことにした。
- 完了条件: 2 つの種類の表の `INSERT`、`SELECT`（`ORDER BY` なしの順も）、`UPDATE`、`DELETE`、同じ中身の行、`UPDATE` / `DELETE ... LIMIT 1`、`ON DUPLICATE KEY UPDATE`、`REPLACE`、`INSERT IGNORE`、`SHOW CREATE TABLE`、`SHOW COLUMNS`、一意インデックスの追加と削除、主キーの追加と削除が、本物の MySQL 8.0 と同じ。AS OF、ブランチの差分とマージ、変更の一覧と復元、TRUNCATE、ALTER の書き直し、GC、レプリカと昇格、mysqldump の往復が動く。判定を外すとテストが落ちる。Go のテスト（-race、カーソル、記録を分ける設定）が通る。PHPUnit の全テストで主キーのない表の差が減り、ほかの差が増えない。`compare.sh` で Loginizer と WP Cerber が HeimDB でだけエラーになる文 0。
- 結果: テーブル定義に `keyless` と、見えない列とインデックスの `hidden` を足した（`schema.Table.SettleKey`、`EngineSchema`、`RowHash`）。`backend.Table` は、HeimDB の中で使うスキーマ（見えない列と保存のキーを含む）と、エンジンに見せるスキーマ（`esch`）を分け、行を返すときに見えない列を除く。エンジンからの行は見える列だけなので、書く前に見えない列を入れ（`completeRow`）、消す・変える行はハッシュで引く（`locateRow`）。マージと復元からの行は見えない列を含み、行 ID をそのまま使う。書き直しは、古い表を読む走査が最後に返した行の行 ID を引き継ぐ（エンジンは 1 行ずつ読んで変換して書く）。一意インデックスの追加はエンジンがその後で呼ぶ書き直しで、削除は HeimDB が自分で書き直す（`rewriteWithout`）。`ADD PRIMARY KEY`、`DROP PRIMARY KEY` は `PrimaryKeyAlterableTable` を実装し、エンジンの書き直しを通す（主キーを足すときは重複を確かめる）。差分とマージは行のハッシュの列を比べない（書くときに求め直す）。行 ID は、見えない列を AUTO_INCREMENT の列にして、既存の番号帯、カウンタの保存、書き直しと復元の引き継ぎをそのまま使う（エンジンには AUTO_INCREMENT の列のない表に見せる）。そのため、AUTO_INCREMENT の列があり主キーのない表は明示的なエラーにした（MySQL でも AUTO_INCREMENT の列はインデックスが要り、WordPress のプラグインは主キーにする）。`__heimdb_row_` で始まる列名もエラー。計画から変えたもの: 計画では採番器を別のキー（`rid`）にするとしたが、AUTO_INCREMENT の仕組みで足りたので足していない。並べる一意インデックスの名前を定義に持つ案は、名前の変更で古くなるので、保存のキーの列の位置で比べる形にした（`SameKey`）。書くときの値を 1 度復号してからハッシュを求める処理、見えないインデックスを消させない判定（エンジンが `GetIndexes` INDEX`、主キーの追加と削除、TRUNCATE）、`TestKeylessAllTypes`（23 の型で値から行を引く）、`TestKeylessBranchAlter`（ブランチの書き直しの後のマージ）、`TestKeylessIndexes`（SHOW INDEX、見えないインデックス）。GC の試験、レプリカと昇格の試験、段階 39 の古いダンプ（主キーのない 2 件（-race、`HEIMDB_TEST_CURSOR_MIN_ROWS=1`、`HEIMDB_TEST_LOG_CHUNK_BYTES=64` でも成功）。PHPUnit の全テストで、本物の MySQL との差は 43 件から 35 件（主キーのない表の 2 件と、主キーのない utf8 の表を作る文字セットのテスト 6 件が通った。新しく失敗したテストはない。panic 0、接続 1,302 本をすべて閉じた。3336 で流した）。`compare.sh` に Loginizer と WP Cerber のシナリオを足し、Loginizer（ログインの失敗とロックアウト。数え上げも同じ）は HeimDB でだけエラーになった文が 0、WP Cerber（有効化、ログイン、ログと通信の記録、cron）は `OPTIMIZE TABLE` のほかに JOIN` はエンジンが拒否する。行 ID の表の差分と変更の一覧の行の名前は `__heimdb_row_id=N`。一意インデックスの重複のエラーの文は、主キーのある表の一意インデックスと同じく `duplicate unique key given: [値]`（MySQL は `Duplicate entry '値' for key '表.名前'`）。確かめる途中で見つかった、主キーのない表に限らない差: `OPTIMIZE TABLE` は構文エラー（WP Cerber の手入れの cron が流す。直していない）。`CONCAT` に `DECIMAL` の列を渡すと末尾の 0 を落とす（`3.5000` が `3.5`。エンジン）。一意キーで並べる表は、保存のキーと同じ列の一意インデックスのエントリも持つ（減らせるが、今の仕組みのままにした）。

## 段階 73: 指標の口（Prometheus の `/metrics`）

- 背景: HeimDB の状態は `CALL heimdb_status()` を SQL で呼んだときにしか見えず、値の移り変わりを見張って知らせる手段がない（段階 59 では、メモリの上限で文が拒否され続けても SQL で見る監視では気づけなかった）。New Relic、Prometheus と Grafana、Grafana Cloud、Google Cloud Managed Service for Prometheus などは、どれも Prometheus の形式を読める（New Relic は、同じ VM かネットワークの中のインフラのエージェント（nri-prometheus）か OpenTelemetry Collector が読んで送る）。OpenTelemetry の環境も、Collector の prometheus receiver で読める。段階 19 で「HTTP の口は今は作らない」とした部分を作る。
- 方針: `-metrics-addr`（例: `127.0.0.1:9104`）を指定したときだけ、HTTP で `GET /metrics` を開く（既定は閉じている。ほかのパスは 404。レプリケーションの口とは別で、同じアドレスは起動時のエラー）。本番でもレプリカでも開ける。認証と TLS は付けない（取り込み役は同じ VM かネットワークの中から読むので、外に開けない。別のネットワークから読ませる必要が出たら、Bearer トークンと TLS を足す）。形式は Prometheus のテキスト形式 0.0.4 で、標準ライブラリだけで書き出す（`client_golang` は依存が増え、出す値は gauge と counter と 1 つのヒストグラムだけ）。出す値（接頭辞 `heimdb_`）は、全体（`build_info{version}`、`start_time_seconds`、`replica`）、接続（`connections`、`connections_total`）、文（`statements_total{type}`、`statement_errors_total{code}`、`statement_duration_seconds` のヒストグラム、`running_statements`、`slow_statements_total`）、メモリ（`memory_limit_bytes`、`memory_abort_bytes`、`memory_live_bytes`、`memory_aborted_statements_total`、`cache_size_bytes`、`cache_used_bytes`、`go_goroutines`）、ストア（`disk_bytes`、`branches`、`branch_size_bytes{branch}`、`last_commit_timestamp_seconds`）、トランザクションと GC（`open_transactions`、`oldest_snapshot_age_seconds`、`pinned_times`、`gc_boundary_age_seconds`、`gc_last_run_timestamp_seconds`、`gc_last_duration_seconds`、`gc_last_failed`）、レプリケーション（本番は `replication_sync`、`replication_async_switches_total`、`replica_behind_seconds{replica}`、`replica_last_seen_seconds{replica}`、レプリカは `replication_behind_seconds`、`replication_last_contact_seconds`、`replication_failing`）、そのほか（`tls_cert_expiry_timestamp_seconds`、`watch_changes_total`）。`type` は文の先頭の語で決まった組（`select`、`insert`、`update`、`delete`、`replace`、`call`、`ddl`、`transaction`、`set`、`show`、`other`）、`code` は MySQL のエラー番号、`branch` はブランチ名、`replica` は `-replica-name`。文の中身、ユーザー名、データベース名、表の名前は出さない。文の数、エラー、時間は、文の終わり（遅い文のログと同じところ）で原子的な加算で数える。エラーは、接続先に返すエラー（`TranslateQueryError` の後）の番号。値を読む処理は書き込みのロックを取らない。
- 完了条件: Go のテストで、閉じているときは開かず、同じアドレスはエラー、`/metrics` 以外は 404。出力が Prometheus の解析器（`prometheus/common` の `expfmt`）を通り、値が実際の状態と合う（トランザクションを開くと `open_transactions`、文の種類ごとの数と時間、ない表の文で `code="1146"`、ブランチの数と大きさ、メモリで止めた文、遅い文、レプリカの遅れと最後の連絡）。出力に文の中身、ユーザー名、表の名前が出ない。長い文の実行中とバックアップの間にも返る。数える処理を外すと落ちる。-race、カーソル、記録を分ける設定でも通る。PHPUnit の全テストを `-metrics-addr` を開いて 1 秒ごとに読みながら流し、差が 35 から増えず、panic と接続の切断が 0。compose で、同じネットワークの Prometheus が値を読める（ポートはホストに公開しない）。New Relic（nri-prometheus と OpenTelemetry Collector）と Prometheus の設定、知らせる規則の例を文書に書く。

## 段階 74: `OPTIMIZE TABLE`、`CHECK TABLE`、`REPAIR TABLE` を受け付ける

- 背景: vitess の構文解析がこの 3 つを知らず、構文エラー（1105）になっていた。WordPress の `wp-admin/maint/repair.php`（`WP_ALLOW_REPAIR`。`CHECK TABLE` の `Msg_text` が `OK` か、「修復と最適化」では `ANALYZE` の後に `OPTIMIZE` の先頭の行を見る）、WP-Optimize 4.7.0（最適化）、Advanced Database Cleaner 4.2.0（最適化、壊れた表の確認、修復）、WP-Sweep 2.0.1（全部の表を並べた `OPTIMIZE`）、WP Cerber（手入れの cron）、wp-cli の `wp db check` / `optimize` / `repair`（mysqlcheck）が使う。効く軸は WordPress 特化と堅牢性。
- 方針: 何もせずに MySQL と同じ 4 列（`Table`、`Op`、`Msg_type`、`Msg_text`）を返す。古いバージョンは GC が消し、ディスクは Pebble が詰め、壊れは Pebble のブロックのチェックサムで確かめるので、作り直しと表ごとの確かめは作らない。構文解析の前に `ANALYZE TABLE 表の並び` に書き換え（`DO` の段階 69 と同じ考え方。表の並びは vitess の字句解析で切り出し、後ろの選択肢は除く）、表の名前、データベース、権限はエンジンの `ANALYZE` の処理で決める。文の種類はセッションに覚え、実行の直前に `ANALYZE` の節を結果を返す節にする。
- 本物の MySQL 8.0 で確かめたこと（realmysql に確かめ用のデータベースを作り、終わった後に消した）: `OPTIMIZE` は InnoDB の表ごとに `note`（`Table does not support optimize, doing recreate + analyze instead`）と `status` の `OK`、`CHECK` は `status` の `OK`、`REPAIR` は `note`（`The storage engine for the table doesn't support repair`）。`NO_WRITE_TO_BINLOG`、`LOCAL`、`TABLES`、後ろの選択肢（`QUICK`、`FAST`、`MEDIUM`、`EXTENDED`、`CHANGED`、`FOR UPGRADE`、`USE_FRM`）、末尾の `;` は結果を変えない。ない表は SQL のエラーにせず、`Error`（`Table 'db.t' doesn't exist`）と `status` の `Operation failed` の行（`ANALYZE` も同じ）。`Table` の列はいつも `データベース.表`。
- 計画のレビュー（Fable）で変えたこと: (1) `OPTIMIZE` は `status` の `OK` の 1 行だけ返す（MyISAM と同じ形）。repair.php は `OPTIMIZE` の先頭の行の `Msg_text` で成否を出すので、InnoDB の `note` の行を先に返すと、本物の MySQL と同じく「Failed to optimize」になる（ユーザーが 1 行だけにすると決めた）。(2) ない表は、エンジンの `ANALYZE` の解析が先にエラー 1146 にするので、MySQL の行の形には合わせず差として記録する（使うものはどれも、ある表にしか流さない）。(3) `ANALYZE TABLE` も同じ節で返す（エンジンの `ANALYZE` は表を全件読んで統計を作るが、HeimDB は自分の統計を使うので無駄だった。`Table` の列も `データベース.表` になった）。(4) `Msg_type` は MySQL と同じ小文字（WP-Optimize は大文字小文字を区別して比べる）。(5) 権限で確かめるのは、そのデータベースに入れるかだけ（MySQL の SELECT と INSERT までは見ない）。
- 結果: `internal/backend/maintenance.go`（`rewriteMaintenance`、`maintenanceNode`）。字句解析の位置は、`FOR` の後で先読みのため字句の始めを指さないので、名前を読んだ直後の位置で表の並びの終わりを決め、後ろの選択肢は確かめずに `;` か終わりまで捨てる（`;` は残りの文字列から探す）。`Table` の列のデータベースは表の属するデータベース（ブランチなら `wordpress@staging.wp_posts`、別のデータベースを指定すればそのデータベース）。テスト: `TestMaintenanceStatements`（3 つの文と `ANALYZE` のさまざまな形、バッククォートの中の `;`、ない表と `CHECKSUM TABLE` はエラー）、`TestMaintenanceMultiStatements`（複数の文を送る接続で、文ごとに種類が決まり、残りの文が実行される）、`TestMaintenancePrivilegesAndBranches`（サイト用のユーザー、ブランチのユーザー、一時テーブル、ブランチにつないだ root からの本番の表、ほかのデータベースは拒否される、コミットしない）、`TestReplicaCatchesUpAndPromotes`（レプリカでも通る）。書き換え、節の差し替え、種類の記録、`REPAIR` の結果、表のデータベース、`db.表` の終わり、`FOR` の後の終わり、`NO_WRITE_TO_BINLOG`、`;` の探し方を 1 つずつ外すと、対応するテストが落ちる。Go のテストは 416 件（-race、`HEIMDB_TEST_CURSOR_MIN_ROWS=1`、`HEIMDB_TEST_LOG_CHUNK_BYTES=64` でも成功。下のレビューの後は 417 件）。PHPUnit の全テスト（26,475 件）で、本物の MySQL との差は 35 件で段階 73 と同じテスト（panic 0、接続 1,302 本をすべて閉じた）。compose（ローカルで作ったイメージ、サイト用のユーザー）で WordPress を入れ、repair.php の「修復」で 12 の表がすべて OK、「修復と最適化」ですべて「Successfully optimized」になり、WP-Optimize の最適化（`OPTIMIZE TABLE` を表ごとに）と `check_table`（`CHECK TABLE \`a\`,\`b\`;` が `OK`）、Advanced Database Cleaner の最適化（最適化できなかった表なし）、壊れた表の確認（なし）、修復、WP-Sweep の「Optimize Tables」（15 表を 1 文で）、`wp db check` / `optimize` / `repair` が動いた。ログの panic とエラーは 0。
- 記録だけ: wp-cli の `wp db check` / `optimize` / `repair` は MariaDB の `mariadb-check` を使い、既定で TLS を求めるので、TLS なしの HeimDB では `--skip-ssl` が要る（段階 74 と関係なく前から。`wp db query` は wp-cli が扱うので要らない）。WP-Optimize の修復の画面は MyISAM などの表だけを確かめるので、HeimDB（InnoDB と見せる）では `CHECK TABLE` を流さない。バイナリプロトコルの準備（COM_STMT_PREPARE）は vitess が先に解析するので構文エラーのまま。`PREPARE` と `EXECUTE` では種類が落ちて `analyze` の結果になる。複数の文を送る接続では、エンジンのログに残る文が `ANALYZE TABLE` になる。表の並びの後ろは `;` まで確かめずに捨てるので、`CHECK TABLE t u` のように MySQL では構文エラーの書き方も通り、コメントの中の `;` で文が切れて構文エラーになる。表の並びを `/*! */` で包むと構文エラー。MySQL と違い、開いているトランザクションを暗黙にコミットしない。HeimDB の表でないもの（`information_schema` など）の `Table` の列は今のデータベースの名前になる。
- コードのレビュー（Fable）で直したこと（重大はなし。panic する入力は見つからなかった）: (1) 文の種類を使った後も消していなかったので、バイナリプロトコルで準備した `ANALYZE TABLE` を、文字列の `OPTIMIZE TABLE` の後に実行すると `optimize` になった（準備した文の実行は構文解析を通らない）。コマンドの始め（`CommandBegin`）で消す（`TestMaintenancePreparedStatement`）。(2) 字句解析は文を丸ごと写すので、すべての文で写していた。先頭の語が OPTIMIZE、CHECK、REPAIR のときだけ字句解析を作る。(3) 予約語でない語（`status`、`data` など）の表とデータベースの名前を拒否していた。識別子のほかに予約語でない語も受け付け、予約語は後の `ANALYZE` の解析に拒否させる。(4) 選択肢を確かめずに捨てること、暗黙のコミットをしないことなどを記録に足した。直しを 1 つずつ外すと対応するテストが落ちる。Go のテストは 417 件（-race などの 4 通りで成功）。

## 段階 75: 性能の今を Linux（GCE）で測り、次に直すところを決める

- 完了条件: MySQL、0.2.11、0.2.22 の数字が `docs/bench.md` にある。遅くなったところがあれば原因がわかっている。差の大きい操作の内訳がわかっている。GCE のインスタンスを消した。

## 段階 76: クラッシュの試験を、ブランチの操作と新しい種類の表に広げる

- 背景: `kill -9` の試験（`cmd/heimdb/durability_test.go`、段階 18）は、整数の主キーの表での残高の移動、記録の追加、ALTER、バックアップ、GC しか流していない。ホスティングの本番で使うブランチの作成、マージ、復元（`heimdb_restore`）と、段階 70 と 72 で入った文字列や日付を含む主キーの表、主キーのない表は、途中で落ちたときを確かめていない。効く軸は堅牢性。
- 方針: (1) 試験の表に、文字列と日付の複合の主キーの表と主キーのない表を足す。(2) 書き込みを流しながら、別の接続でブランチの作成、ブランチへの書き込み、マージ、復元、ブランチの削除を繰り返し、`kill -9` で落とす。(3) 起動し直すたびに、応答を返した書き込みとマージが残ること、途中のマージと復元は全部入ったか全く入っていないかのどちらかであること、主キーのない表の行数と合計が保たれること、そのまま書き込みとマージを続けられることを確かめる。(4) 壊れ方が見つかったら、ログで再現してから直す（直し方はその時点で計画を出す）。
- 完了条件: 広げた試験が 3 回繰り返して安定して通る（`-race` でも）。見つかった問題は直して試験で確かめたか、記録した。Go のテストが通る。PHPUnit の全テストで差が 35 から増えない。
- 結果: `cmd/heimdb/crashbranch_test.go` の `TestCrashRecoveryBranches`。主キーのない表 `logs` と、文字列と日付の複合の主キーの表 `kv` に、本番の書き込み（2 つの接続）と、ブランチの係（作成、ブランチへの 200 行の書き込み、時刻を覚えて 200 行の書き込み、覚えた時刻への `heimdb_restore`、マージ、削除の繰り返し）を流しながら、`kill -9` で 8 回落として起動し直す（GC は 200 ミリ秒ごと）。起動し直すたびに、本番で応答を返した書き込みと、応答を返したマージの行がすべてあること、マージの行は全部か無か（途中で落ちたマージも）、マージを試みていないブランチの行と、復元で消した行が本番にないこと、どの行も 1 つだけ（主キーのない表で重ならない）ことを確かめる。残ったブランチは、書き込みと復元が全部か無かで、応答を返した書き込みが残り、応答を返した復元の後に消した行がないことを確かめてから消し、最後にブランチを作って書いてマージできることを確かめる。1 回の試験で、ブランチ 52〜57 本、応答を返したマージ 46〜50 回、マージの途中で落ちたもの 0〜3 回。壊れ方は見つからなかった（直したものはない）。試験が壊れ方を捕まえることは、コミットのバッチを 2 つに分けて間を空けて書く変更（マージの 200 行のうち 100 行だけが入って落ちる）と、復元を書かない変更（復元の後のブランチに 2 回目の行が残って落ちる）で確かめた。3 回ずつ流して、通常も `-race` も通った。製品のコードは変えていないので、PHPUnit の全テストは流していない。

## 段階 80: 性能の直し（定数のキーで引く JOIN と、起動し直した後の表ごとの最初の文）

- 背景: ホスティング側の計測（HeimDB 0.2.23、`wp_postmeta` 311 万行、同時数 1）で、テーマが 1 ページに 8 回流す `ID NOT IN (SELECT post_id FROM wp_postmeta WHERE meta_key = 'bzb_include_rss' AND meta_value = 'none')` が 1 回 330〜380 ms かかり、起動し直した直後のページでは、その文が 4.9 秒、続く `UPDATE wp_postmeta ... WHERE post_id = 1 AND meta_key = 'views'` が 2.7 秒かかった。手元（記事 31,000 件、メタ 310 万行）で確かめると、(A) 反結合の右を、`ID = post_id` ではなく右の条件の定数（`meta_key = 'bzb_include_rss'`）だけで引き、左の行ごとに同じ範囲を読み直していた（go-mysql-server は右の定数の条件だけでも lookup のキーを作り、コストは読み直す分を数えない）。そのキーの行が 3.1 万行なら 2 分を超え、MySQL は 0.17 秒（サブクエリを 1 回だけ実体化して引く）。`IN (SELECT ...)`、`NOT EXISTS`、WordPress 本体の meta_query の `'compare' => 'NOT EXISTS'`（`LEFT JOIN ... IS NULL`）も同じ形。(B) 起動し直した後、表ごとの最初の文が、統計を作るために表を 2〜3 回全部読み（`rowCounts.get` と `buildStats`）、表への最初の書き込み（UPDATE でも INSERT でも）が、AUTO_INCREMENT の最大値を求めるために全行を読んでいた（`maxAutoIncrementValue`）。レプリカは関係ない（手元はレプリカなしで同じ形）。効く軸は性能。
- 方針: (1) 引くキーが左の列を含まない lookup JOIN を、入れ子のループと同じく高く見積もる。(2) 相関のないサブクエリから作る反結合（`LeftOuterExcludeNulls`）と半結合の lookup JOIN だけ、引くたびに読む行の数（右の表の行数 ÷ 引くインデックスの先頭の列の値の種類）をコストに足し、サブクエリを 1 回読むハッシュ JOIN を選ばせる（MySQL の実体化に当たる）。普通の LEFT JOIN と INNER JOIN のコストは変えない（LIMIT のある記事の一覧で、作る側を全部読むハッシュ JOIN に替わると遅くなる）。値の種類の数は、表全体の値だけを、間引いた標本から Chao1 で見積もる（一意なインデックスは行数）。バケットの値の種類は変えない。(3) AUTO_INCREMENT の列が主キーのただ 1 つの列なら、最大値は主キーの帯の中の最後の 1 行だけを逆に読んで求める（ほかの形は今のまま全行を読む）。(4) 統計は表を 1 回だけ読んで作る（行数も同じ走査で数え、標本はハッシュの上位のビットで残す行を段階的に絞るので、走査の順によらず同じデータなら同じ標本）。行数のキャッシュも同じ走査の値を使う。(5) 起動したら、main のすべての表の統計を裏で作り始める（同じ表を同時に作らない）。データ形式は変えない。エンジンは変えない。
- 計画のレビュー（Fable）で変えたこと: 引くたびに読む行の数を lookup JOIN 全般に足す案は、LIMIT のある記事の一覧などで計画が揺れ、値の種類の見積もり（バケット）を直すと JOIN の行数の見積もりも変わるので、サブクエリから作る形に絞った。meta_query の NOT EXISTS は MySQL も `post_id` で引くので、(1) だけで同じ形になる。統計を主キーの範囲を区切って読む案は、行数を数える走査が残り、主キーの空間が疎（ブランチの帯）で、挿入の時期の偏りを拾うのでやめ、1 回の走査と裏での作成にした。AUTO_INCREMENT の全行の読み出しは INSERT でも起きるので、UPDATE で求めないだけでは足りない。
- 完了条件: 上の 4 つの形の結果と並びが本物の MySQL のゴールデンと同じ（`NOT IN` の右に NULL がありうるときを含む）。`NOT IN` と `IN (SELECT ...)` はサブクエリを 1 回読む形、meta_query の NOT EXISTS は `post_id` で引く形（MySQL の `EXPLAIN` で確かめる）。ページが流す 219 種類の文の計画と結果を段階 79 と比べ、変わった文の一覧と理由がある。AUTO_INCREMENT の値が今と同じ（最後の行が削除済み、帯の上に行がある、層のあるブランチ、主キーが複合の表）。統計は同じデータなら同じ。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。起動し直した後の表ごとの最初の文（`wp_postmeta` の SELECT、INSERT、UPDATE）の時間を、段階 79 と並べて示す。
- 結果: (1)(2) 手元（macOS。記事 31,000 件、`wp_postmeta` 310 万行、`bzb_include_rss` 310 行。サーバの側の時間）で、`NOT IN` が 8.2〜8.6 秒から 50〜61 ms、`NOT EXISTS` が 9.8 秒から 31 ms、meta_query の NOT EXISTS が 5.8 秒から 0.84〜0.91 秒（`post_id` で引く。そのキーの行が 3.1 万行のデータで MySQL は 4.6 秒）。`IN` はこのデータでは段階 79 も 2 ms（メタから記事を引く形）。そのキーの行が 3.1 万行のデータでは、段階 79 はどの形も 15 秒を超え（`NOT IN` は 2 分超）、MySQL は `NOT IN` 0.17 秒、`IN` 0.45 秒。結果と並びは本物の MySQL 8.0.46 のゴールデン（`internal/testdata/subquery_golden.txt`。サブクエリが NULL を返す `NOT IN` を含む）と同じで、MySQL の `EXPLAIN` も `NOT IN` と `NOT EXISTS` はサブクエリを実体化して引き、`IN` はメタから記事を主キーで引き、meta_query の NOT EXISTS は `post_id` で引く。(3)(4)(5) 起動し直した直後の表ごとの最初の文（同じデータ、サーバの側の時間）は、段階 79 で SELECT 0.86〜0.95 秒、INSERT 0.57〜0.61 秒、UPDATE 1.39〜1.46 秒、段階 80 は統計を裏で作り終えた後（310 万行の表を含めて起動から約 0.5 秒。ログに `statistics: built for N tables`）で 1 ms、10〜11 ms、7〜10 ms、作り終える前に来た文でも 0.39〜0.44 秒、5〜6 ms、0.32〜0.35 秒（作っている統計を待つ）。ページが流す 219 種類の文は、ベンチのデータで計画も結果も段階 79 と同じ。リビジョンを足したデータ（`wprev`。`wp_posts` 5.5 万行）では、カテゴリの 2 ページ目の文の計画が 1 つ変わり（記事の範囲を読むハッシュ JOIN から、カテゴリの関係から記事を主キーで引く lookup JOIN へ。結果は同じ）、手元で 6.6 ms から 9.0 ms になった。統計の標本が 3 行に 1 行から 4 行に 1 行になり、ほぼ同点（どちらも約 5,000 行）の 2 つの計画の順位が入れ替わった。標本の上限を 2 倍にすると計画の変わる文が 6 つになったので、上限は変えない。Go のテストは 433 件で、-race でも通った。直しを 1 つずつ外すと、対応するテストが落ちる（定数のキーの割り増し、サブクエリの lookup のコスト、最後の 1 行の読み出し、裏での作成、Chao1、標本のビットの絞り方）。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 79 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。
- 記録だけ: 並べ替えのない文で、MySQL が文の列をすべて持つインデックス（`type_status_author`）を全部読むと、行の並びが HeimDB（主キーの順）と違う（`post_type` の条件のない `NOT EXISTS` の文で見つけた。段階 80 より前から。WordPress はこの形の文を出さない）。meta_query の NOT EXISTS の、同じ日時の行の並びも段階 80 より前から MySQL と違う（MySQL は GROUP BY の後の並べ替えで決まった順にならない）。反結合の右の Filter に同じ条件が 2 組並ぶ（ホスティング側の指摘。結果は同じ。原因は調べていない）。ホスティング側の計測の 0.2.23 では、`SELECT 1 FROM <表> LIMIT 1` は統計を作らず（インデックスを選ばないので）、`SHOW TABLE STATUS` は AUTO_INCREMENT を準備しない。0.2.23 で読むだけで温めるなら、表ごとに `SELECT <主キー> FROM <表> WHERE <主キー> = 0` と `SHOW CREATE TABLE <表>`。次の候補: ホスティング側の依頼（`SET GLOBAL long_query_time` を効かせる、遅い文のログのリテラルを畳む、読んだ行数と使ったインデックス、止まった時間の内訳）。
- レビュー（Fable）で直した: 裏で統計を作る処理が、表の一覧を停止の待ちの外で読んでいた（起動直後に止めると、閉じたストアを読みうる）。その処理のセッションを接続として数えていた（`heimdb_status` の接続数と指標が 1 多いまま）。表ごとの統計を作るロックの表が、表やブランチを消しても縮まなかった。テストに、符号付きの 64 ビットを超える ID と、接続の数を足した。ヘッドレスの API の検証（記事 2 万件、メタ 32 万行）で、WP_Query の meta_query の INNER JOIN（`meta_key = 'category' AND meta_value = 'cat3'`、`meta_key = 'priority'` で並べ替え、`event_date` の範囲の JOIN 3 本、条件 2 つと並べ替えの JOIN 3 本）も、段階 79 は右の定数だけで引いて記事ごとに 2 万行を読み直していた（返らない）。段階 80 で手元のサーバの側の時間が 38〜54 ms、306〜346 ms、487〜497 ms、66〜70 ms（ホスティング側の測った MySQL は 59〜91 ms、188〜221 ms、294〜417 ms、51〜68 ms）。この 4 つの形を本物の MySQL のゴールデン（`internal/testdata/metaquery_golden.txt`）と計画のテストに足した。
- レビューの記録: 表全体の値の種類の数（Chao1）は、エンジンの JOIN の出力の行数の見積もり（`memo/rel_props.go` の JOIN の distinct と `expandRatio`）にも効く（`wp_postmeta.post_id` は行数に近い値から約 100 分の 1 になる）。219 種類の文で計画が変わらないことは確かめた。一意なインデックスのすべての列を定数で引く lookup JOIN は、`uniqueLookup` の見積もりが先に効き、段階 80 の割り増しを受けない（左の行ごとに高々 1 行なので害は小さい）。統計を作っている表を使い始めた文は、作り終えるまで待ち、その間は KILL で抜けない（手元で 0.3〜0.4 秒）。`max_execution_time` は接続ごとの設定として読んでいない（ブランチの実行時間の上限 `heimdb_branch_limit` だけ。`long_query_time` と同じく、`SET` はエラーにならず効かない）。クライアントが切れたときの文の取り消しは、Linux で TCP の接続が閉じれば約 5 秒で止まる（0.2.23 のイメージで確かめた。macOS はエンジンの見張りが実装されていない）。
