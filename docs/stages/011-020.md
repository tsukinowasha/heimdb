# 段階 11〜20

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 11: 小さな互換性の差

- これまでに見つけた、本物の MySQL との小さな差を直す。
- 完了条件: 各項目を本物の MySQL とのゴールデンテスト（B、C は並行実行のテスト）で確かめる。PHPUnit の option、meta、query はベースラインとの差 0 件のまま、wpdb の `test_set_charset_changes_the_connection_collation` が通る。
- 項目:
  - A: `SET NAMES <文字セット> COLLATE <照合順序>` の COLLATE を `collation_connection` に反映する（go-mysql-server は構文解析の後で COLLATE を捨てる。WordPress は接続のたびに `SET NAMES utf8mb4 COLLATE utf8mb4_unicode_520_ci` を送る）。文を構文解析し直して設定を足す。
  - B: `SET autocommit=1` で、未コミットのトランザクションをコミットする。
  - C: 一時テーブルにだけ書くトランザクションは、ブランチの書き込みロックを取らない。
  - D: 照合順序を指定しないテーブルの既定を、MySQL と同じ `utf8mb4_0900_ai_ci` にする（既存のテーブルの定義は変えない）。
  - E: 末尾が単独の `\` の LIKE のパターンを、`\` そのものとして扱う。
  - F: 非 STRICT の sql_mode で、NULL を含む列を `NOT NULL` に変える ALTER は、型の既定値（'' や 0）に置き換えて警告にする。
  - G: 1 つの ALTER で FULLTEXT を 2 つ作ると、エラー 1795 にする。
  - H: `information_schema.STATISTICS` の `SUB_PART` を、プレフィックス長がなければ NULL にする（差し替えられなければ記録だけ）。
  - I: `'\_'`、`'\%'` のような 1 つの `\` の文字列で `\` を残す（構文解析の前に手を入れられなければ記録だけ）。
  - J: 並べ替えのルール（ORDER BY をインデックスの走査に置き換える）を、別名と `IN` の条件に対応させる。
- 結果:
  - A: 文を構文解析し直して照合順序を取り出し、`collation_connection` の設定を足す。照合順序の名前は MySQL と同じ正式な名前にし（`utf8_general_ci` は `utf8mb3_general_ci`）、文字セットに合わなければエラー 1253。
  - B: すでに MySQL と同じだった（段階 5 の後のどこかで直っていた）。ゴールデンテストで確かめた。
  - C: 書き込む文の対象のテーブルがすべてセッションの一時テーブルなら、文の前にブランチのロックを取らない（一時テーブルがあるときだけ文を構文解析する）。
  - D: `Database` が `sql.CollatedDatabase` を実装し、`utf8mb4_0900_ai_ci` を返す（go-mysql-server は照合順序のない CREATE TABLE で `plan.GetDatabaseCollation` を使う）。`ALTER DATABASE ... COLLATE` はエラー。
  - E: 定数のパターンが単独のエスケープ文字で終わるなら、そのエスケープ文字をエスケープする（ESCAPE を指定した場合も）。
  - F: 見送り。go-mysql-server の列の変更の書き直し（`modifyColumnIter`）が sql_mode を見ずに NULL を拒否するので、HeimDB の `ModifyColumn` で NULL を持つ行とインデックスを書き直す必要があり、小さな差の範囲を超える。（段階 15 で対応した）
  - G: 1 つの ALTER で 2 つ目の FULLTEXT を作るとエラー 1795。あわせて `SHOW INDEX` の並びを MySQL と同じく FULLTEXT を最後にした。
  - H: どの列にもプレフィックス長のないインデックスは `PrefixLengths` を空にして、`SUB_PART` を NULL にする。プレフィックス長のある列とない列が混ざる複合インデックスでは、ない列が 0 のまま（go-mysql-server の `PrefixLengths` で列ごとの「なし」を表せない）。
  - I: go-mysql-server の構文解析器（`Engine.Parser`）を包み、構文解析の前に文字列の中の `\_` と `\%` を `\\_` と `\\%` にする（識別子とコメントは変えない、何度通しても同じ）。
  - J: 別名の付いたテーブルと、値が 1 つの `IN`（go-mysql-server は `HashInTuple` にする）に対応した。値が複数の `IN` は対象外。
  - 記録だけ（見つけたが直していない）: 明示した ID の複数行の INSERT で、接続に返る insert_id が MySQL（最後の行）と違う（最初の行）。`SHOW CREATE TABLE` は NULL を許す列の `DEFAULT NULL` と、列の `COLLATE` の前の `CHARACTER SET` を書かない。
- 対象外（wpdb グループで残る差）: 主キーのないテーブルを使うテスト、UTF-8 以外の古い文字コード（HeimDB は utf8mb4 だけを扱う。古い文字コードのサイトは移す前に utf8mb4 に変換する）、`CREATE PROCEDURE`。

## 段階 12: インデックスの違いのマージ

- これまでのマージは列だけでテーブル定義を比べ、インデックスの違いを無視していた（ステージングでプラグインを更新して dbDelta が `ADD INDEX` しても、本番に入らない）。
- 完了条件: ブランチで足した、消した、変えたインデックスが、マージで親に反映される。両側の食い違いは競合として報告され、解決できる。本物の WordPress で、ステージングのインデックスの追加をマージし、本番の `SHOW INDEX` が MySQL と同じ形になる。
- 実装の方針:
  - インデックスは名前で対応づけ、定義（列、プレフィックス長、一意、FULLTEXT、コメント）を、ブランチと親それぞれの基準の時点と比べる（三方向）。ブランチだけが足した、消した、変えたものを親に反映し、親だけの変更は残す。両側が同じ名前を違う定義にしたら、またはブランチが消して親が変えたら競合。名前の変更は削除と追加。
  - 差分の要約の `detail` にインデックスの変更を出し、行ごとの表示では id を `INDEX <名前>` とする。競合は行と同じく `heimdb_branch_resolve` で解決し、記録には両側の定義のハッシュを持たせる。
  - マージでは、親のロックを持ったまま、行の反映の前にインデックスの定義を書き、親の今の行からエントリを作る。一意インデックスで親の行が重複していれば、マージ全体をエラーにする。
  - 列が違うテーブルは、これまでどおりテーブル単位の競合（列の変更のマージは別の課題）。
  - 結果（実装済み）: インデックスの定義を 1 つの値（`種類(列(長さ),...) comment=...`）にして `merge.Decide` にかける（`indexdiff.go`）。行の反映の前に書き、その後の行の反映は新しい定義で書く（エディタが新しいインデックスのエントリも書く）。本物の WordPress で、プラグインの更新を模した dbDelta がステージングで足したインデックスを本番にマージし、本番で同じ dbDelta を流すと変更なし（`Array()`）になった。
  - 段階 11、12 のレビューで直したこと:
    - マージは 1 つのコミットにした。新しいテーブルの定義（`store.Txn.PutTable`）、インデックスの定義とエントリ、行をすべてマージのトランザクションに書く（新しいテーブル ID だけは先に払い出す）。ブランチの行が、ブランチで足した一意インデックスで本番の行と重複して失敗しても、本番には何も残らない。
    - `SET NAMES ... COLLATE` のルールは、go-mysql-server が SET NAMES を展開した SET 文（character_set_client を設定する）だけに当て、文字列とコメントの中は見ない（`SET @msg = '... NAMES x COLLATE y'` に反応していた）。
    - 一時テーブルにだけ書くかの判定で、`DELETE t FROM wp_options AS t` の対象を FROM 句のテーブルに解決する（別名が一時テーブルと同じ名前だと、本物のテーブルへの DELETE が文の前にロックを取らず、同時に書く接続があるとエラー 1213 になっていた）。
    - 記録だけ: `SET NAMES utf8mb4 COLLATE DEFAULT` は構文エラー（vitess。MySQL は文字セットの既定の照合順序）。構文解析の前処理（`\_` → `\\_`）の後の文がビュー、トリガー、ストアドプロシージャの定義として保存されるので、`SHOW CREATE VIEW` などの表示が MySQL と違う（意味は同じ）。

## 段階 13: 列の変更のマージ

- これまで列が違うテーブルはテーブル単位の競合で、親の側（そのテーブルをマージしない）にしか解決できなかった。プラグインの更新で列が増えたり型が変わったりしたテーブルは、列も行もマージできなかった。
- 完了条件: ブランチで足した、変えた、消した列が、マージで親に反映され、その後の行の差分も反映される。両側の食い違いは競合として報告され、解決できる。本物の WordPress で、ステージングの dbDelta（列の追加と型の変更）をマージし、その間に本番に入った行が残り、本番で同じ dbDelta を流すと変更なしになる。
- 実装の方針:
  - 列は名前で対応づけ、定義（型、NULL の可否、既定値、ON UPDATE、コメント、Extra）を、インデックスと同じ三方向で比べる。両側の食い違いは `COLUMN <名前>` の競合として `heimdb_branch_resolve` で解決する。名前の変更は削除と追加。主キーの列と AUTO_INCREMENT の変更は明示的なエラー。
  - 親のテーブルを新しい列の形で、新しいテーブル ID に書き直す（マージのトランザクションの中。既存の行の足した列には既定値、型を変えた列は新しい型に変換、インデックスは作り直す）。足した列の位置は、ブランチでその前にある列の後ろ。その後、行の差分を新しい列の形で反映する。
  - NULL を含む列を NOT NULL にするときは、NULL を型の既定値（'' や 0）にする（WordPress の非 STRICT の sql_mode で dbDelta を流したときと同じ）。型を狭める変更で親の値が収まらなければ、マージを拒否し、行と値をエラーに出す（黙って切り詰めない）。
  - 結果（実装済み、`coldiff.go`）:
    - 主キーの列が違うテーブルだけが、これまでどおりテーブル単位の競合（`schema differs`）。それ以外は列ごとにマージする。
    - 行の比較は、マージの後の親の定義（`tableDiff.Merged`）の列と型にそろえて行う（`conformRow`）。型を変えた列で、どの行も変わったと見なさない。後から足した列で既定値が式（`CURRENT_TIMESTAMP` など）のものは、基準の行に値がないので、今の行の値を基準とする（列を足したときに入った値は変更と見なさない）。
    - マージでは、親を新しいテーブル ID に書き直し（`rewriteParentTable`。マージのトランザクションの中）、その後でインデックスの変更と行の差分を反映する。ブランチの行は親の定義にそろえてから書く（親だけにある列は既定値）。親の行を使う更新と削除は、書き直した後の形に変換する。
    - 式の既定値は `SELECT <式>` として評価する（`planbuilder.StringToColumnDefaultValue` は v0.20.0 で壊れている。カタログなしで評価すると関数の参照で panic するので、セッションのプロバイダからカタログを作る）。
    - 本物の WordPress で、プラグインの更新を模した dbDelta（列の型の変更 2 つ、列の追加 2 つ、インデックスの追加）と移行処理の UPDATE をステージングで行い、その間に本番に行を足してマージした。本番の列はステージングと同じになり、本番で同じ dbDelta を流すと変更なし、本番の行と変更は残り、足した列は既定値になった。
    - 列の並びだけの変更（`MODIFY ... AFTER`）はマージしない。
  - 段階 13 のレビューで直したこと:
    - 【以前からの不具合】1 つの ALTER TABLE で列を 2 つ以上変える（`ADD COLUMN a ..., ADD COLUMN b ...` など）と、テーブルの全行が消えていた。go-mysql-server は操作ごとにテーブルを書き直すが、2 回目の書き直しが、1 回目の前のスナップショットで行を読んでいた。DDL の操作ごとにスナップショットを取り直す（`store.Txn.RefreshSnapshot`）。
    - 基準の行にない列は、その側の今の定義の既定値で埋めてから、マージの後の定義にそろえる（`differ.sideRows`）。両側で同じ列を違う既定値で足すと、もう一方の側の既定値で埋めて、全行を変更と見なしていた。式の既定値の列を今の行の値で埋めるのも、列の変更の有無にかかわらず行う（同じ dbDelta を両側で流すと、全行が競合になっていた）。
    - ENUM と SET の型の変更は、値の文字列で変換する（`convertValue`。内部の番号のまま変換すると、値の並びを変えたときに別の値になる）。
    - 同じ自然なキーの行（記事、ターム）をブランチの側に解決して親の行に写すとき、親だけにある列は親の値のままにする。
    - 制限（記録だけ）: 既定値が式（`CURRENT_TIMESTAMP` など）の列をブランチで足した後、移行処理がその列を書き換えても、その書き換えはマージされない（列を足したときの値が残っていないので、書き換えと区別できない）。

## 段階 14: 認証

- これまではパスワードがなく、ポートに届けば誰でも本番とすべてのブランチを読み書きでき、マージや復元もできた。
- 完了条件: 正しいユーザー名とパスワードでないと接続できない（エラー 1045）。ステージング用のユーザーは本番のデータベースに接続できない（エラー 1044）。HeimDB の手続きは管理者だけが実行できる。再起動してもユーザーと権限が残る。権限を絞ったユーザーで PHPUnit を流し、ベースラインとの差が変わらない。本物の WordPress で、本番とステージングを別々のユーザーで動かせる。
- 実装の方針:
  - go-mysql-server のユーザーと権限の仕組み（`mysql_db`）をそのまま使う。管理は MySQL と同じ `CREATE USER`、`GRANT`、`ALTER USER`、`DROP USER`。認証方式は `mysql_native_password`。
  - ユーザーと権限は `m/users` に保存する（go-mysql-server の直列化をそのまま入れる。ブランチにもタイムトラベルにも属さないので、ブランチを切っても復元しても変わらない）。起動時に読み込む。
  - ユーザーがまだいなければ、`-root-password`（または環境変数 `HEIMDB_ROOT_PASSWORD`）で `root@'%'`（全権限）を作る。どちらもなければ起動を拒否する。`-no-auth` を明示すれば、これまでどおり認証なしで動く（開発用）。
  - ブランチは `wordpress@staging` という名前のデータベースに見えるので、ブランチごとの権限は普通の GRANT で与える（例: ``GRANT ALL ON `wordpress@staging`.* TO 'staging'@'%'``）。ステージングのサイトが乗っ取られても本番のデータに届かない。
    - ブランチのデータベース名の区切りは、これまでの `/` から `@` に変える。go-mysql-server の権限の判定（`planbuilder/auth_default.go` の `authDatabaseName`）は、Dolt の `db/revision` の名残でデータベース名を `/` で切って前半だけで判定するので、`wordpress/staging` では `wordpress` の権限ですべてのブランチに入れてしまい、ブランチだけの権限も効かない。`@` は GRANT のワイルドカード（`_`、`%`）でもない。
  - 結果（実装済み、`auth.go`、`routines.go`）:
    - 認証を有効にすると、go-mysql-server はデータベースを `mysql_db.PrivilegedDatabase` で包み、ビュー、トリガー、ストアドプロシージャ、イベントのインターフェースをすべて HeimDB に転送する（実装がないとエラーになり、CREATE TABLE が同じ名前のビューを確かめるところで失敗した）。HeimDB の `Database` にこれらを実装し、読む側は「ない」、作る側は明示的なエラーにした（認証の有無で振る舞いが同じになる）。
    - テスト用のサーバも本番と同じく認証を有効にした（root、パスワードなし）。既存のテストはすべてこの包みを通る。
    - MySQL との差（記録だけ。WordPress はエラー番号を見ずに「データベース接続確立エラー」を出す）: データベースへのアクセスの拒否は 1044 ではなく 1105（メッセージは同じ）、存在しないユーザーは 1045 ではなく 2012。どちらも go-mysql-server のサーバの部分で決まる。
    - 本物の WordPress で、本番を `wordpress`（本番だけの権限）、ステージングを `staging`（`wordpress@staging` だけの権限）で動かした。それぞれのサイトが動き、互いの資格情報では相手のデータベースに接続できず（WordPress のデータベース接続エラー）、ステージングのユーザーはマージを実行できなかった。root でマージすると本番に反映され、root のパスワードなしで再起動しても両方のサイトが動いた。
  - 段階 14 のレビューで直したこと:
    - 【以前からの不具合】引数のない HeimDB の手続きを引数つきで呼ぶと（`CALL heimdb_gc(1)` など）、接続が切れていた。go-mysql-server の登録簿は、引数の数が合わず引数のない登録しかないとゼロ値を返し、planbuilder が panic する。`Provider.ExternalStoredProcedure` で引数の数のエラーにする。
    - ユーザーがいるのに root のパスワードを指定したら、無視したことを警告する（変えるには `ALTER USER`）。ユーザーがいるのに `-no-auth` で起動したら、全ブランチがパスワードなしで開いていることを警告する。
    - 記録だけ（go-mysql-server の限界。WordPress は使わない）: `information_schema.processlist` は、権限のないユーザーにも他のユーザーの実行中の文を見せる（`SHOW PROCESSLIST` は正しく拒否する）。`SET GLOBAL` に権限の確認がない（ステージングのユーザーでも全体の設定を変えられる。WordPress は接続ごとに `sql_mode` を設定し直す）。この 2 つは段階 35 で直した。`CREATE VIEW` などは、これまで接続の間だけ動いていた（再起動で消える）が、明示的なエラーになった。
  - HeimDB の手続き（`heimdb_branch_*`、`heimdb_restore*`、`heimdb_gc`）は `AdminOnly` にする（SUPER 権限、つまり `root` か `GRANT ALL ON *.*` のユーザーだけ）。
  - 対応しない: TLS、`caching_sha2_password`（go-mysql-server v0.20.0 の実装はパスワードのキャッシュがなく、TLS か Unix ソケットの接続でないと拒否する）、ロール、列単位の権限。`mysql_native_password` は MySQL 8.4 で既定で無効、9.0 で削除されたが、HeimDB がサーバなので影響しない（PHP の mysqlnd は対応を続けている。MariaDB の標準の方式でもある）。WordPress と HeimDB を別のネットワーク越しにつなぐ必要が出たら、TLS を足す段階を設け、そのときに `caching_sha2_password` も使えるようにする。

## 段階 15: 非 STRICT の sql_mode での NOT NULL の ALTER（段階 11 で見送った F）

- NULL を含む列を `NOT NULL` に変える ALTER は、MySQL では非 STRICT の sql_mode（WordPress の既定）なら NULL を型の既定値にして通るが、HeimDB はエラー 1048 で止まっていた。プラグインの dbDelta が列を NOT NULL に変えると、本番の MySQL では通るのに HeimDB では失敗する。
- 完了条件: 非 STRICT では NULL が型の既定値になり、警告の番号と件数が MySQL と同じ。STRICT ではエラー（MySQL と同じ 1138）。本物の MySQL 8.0 のゴールデンと一致する。PHPUnit の option、meta、query の差は 0 件のまま。
- MySQL 8.0.46 で確かめた振る舞い: 置き換える値は列の既定値ではなく型の既定値（`DEFAULT 'x'` の列でも ''、数値は 0、datetime は `0000-00-00 00:00:00`、ENUM は ''）。置き換えた行ごとに警告 1265（`Data truncated for column '<列>' at row <行>`。行は主キーの順の 1 から）。STRICT ではエラー 1138（`Invalid use of NULL value`）で何も変えない。
- 結果（実装済み、`alter.go` の `nullFill`）:
  - go-mysql-server は列の変更の書き直しで、行を変換した直後に NULL を拒否する（`modifyColumnIter.validateNullability`）。書き直しの入口（`RewriteInserter`）は行を読む前に呼ばれ、行は HeimDB のテーブルから読まれるので、NULL を許す列を NOT NULL に変える書き直しの間だけテーブルに印を付け、行を読むところ（`Table.PartitionRows`）で NULL を型の既定値にして警告を出す（STRICT ならエラー 1138）。印は書き直しの終わりと取り消しで外す。go-mysql-server は改変しない。
  - あわせて、`SHOW WARNINGS` の並びを MySQL と同じく出た順にした（go-mysql-server の `BaseSession.Warnings` は新しい順に返す。`Session.Warnings` で上書き）。実行中に出る警告に効く（構文解析の段階の警告は下の記録を参照）。
  - 記録だけ: 1 つの ALTER で複数の列を NOT NULL にすると、MySQL は警告を行の順（行ごとに列を並べる）に出すが、HeimDB は列ごとに出す（go-mysql-server が操作ごとに書き直すため）。件数と内容は同じ。
  - 段階 15 のレビューで直したこと:
    - TIMESTAMP の列は、MySQL と同じく NULL を文の時刻（`NOW()` と同じ値。go-mysql-server の日時はセッションのタイムゾーンでの値）にして、警告を出さない（DATETIME は型の既定値と警告 1265 のまま）。
    - `sql_mode` の `TRADITIONAL` を STRICT とみなす（MySQL では STRICT_TRANS_TABLES と STRICT_ALL_TABLES を含むが、go-mysql-server は展開しない）。
    - 記録だけ: 構文解析の段階で出る警告（`DROP TABLE IF EXISTS a, b` の Note 1051 など）が 2 つ以上だと、MySQL と逆の順になる。go-mysql-server（engine.go）が構文解析の警告を新しい順の前提で取り出して入れ直すため（段階 15 の前も逆だった。段階 93 で直した）。新しい ENUM に元の値がない書き直しは、go-mysql-server が取り消しを呼ばずにエラーを返すので印が残るが、テーブルのオブジェクトは文ごとに作り直すので、ほかの読み取りには効かない。以前からの go-mysql-server の差: 文字列の列を数値の列にする ALTER で数値でない値があるとエラー（MySQL は 0 と警告 1366）、`@@warning_count` と `SHOW COUNT(*) WARNINGS` は未対応。

## 段階 16: バックアップ

- これまでは、動いたままの HeimDB のデータを安全に写す方法がなかった（データディレクトリをそのままコピーすると書き込みの途中を拾いうる）。タイムトラベルと復元は同じディスクの中にあるので、ディスクが壊れると何も残らない。
- 完了条件: 管理者が `CALL heimdb_backup([名前])` で、動いたまま、ある時点の整合したバックアップ（全ブランチ、保持期間内の履歴、ユーザーと権限）を作れる。書き込みが続いている最中に取っても整合している（テスト）。そのバックアップから起動すると取った時点の状態に戻る（本物の WordPress で、バックアップの後に変更し、戻すと、サイトがバックアップの時点で動き、ログインでき、ブランチ、`AS OF`、ユーザーが残る）。テスト用のサイトで、バックアップと復元の時間と大きさを記録する。
- 実装の方針:
  - Pebble の Checkpoint で、整合したスナップショットをハードリンクで作る（同じファイルシステムなら一瞬で、ほとんど容量を使わない）。作ったディレクトリはそのまま HeimDB のデータディレクトリとして開けるので、復元は「HeimDB を止めて差し替える」か「`-data` でそのディレクトリを指す」だけにする（専用の復元の仕組みは作らない）。
  - 置き場所は起動時の `-backup-dir` に限り、手続きからは名前だけを指定する（省略すれば時刻）。SQL から任意のパスに書けないようにする（MySQL の `secure_file_priv` と同じ考え方）。`-backup-dir` がなければエラー。手続きは管理者だけ（段階 14 の `AdminOnly`）。
  - 結果に、バックアップのパス、時刻（その時点の最後のコミット）、大きさを返す。
  - 整合性: コミットはすべて `Store.Update` の書き込みのロックの中で 1 つの Pebble のバッチとして同期書き込みする。Checkpoint をこのロックの中で取るので、ある時点までのコミットがすべて入り、それより後は 1 つも入らない。未コミットのトランザクションは入らない。一時テーブルの残りは起動時に片付ける（`dropUnregisteredBranches`）。AUTO_INCREMENT のカウンタは起動時に「保存した値」と「行の最大値 + 1」の大きい方から始めるので、戻した後も重複しない。
  - 外部への持ち出し（S3 など）と世代の管理は作らない。手順の例を書く（tar で固めて送り、送ったら消す）。ハードリンクの Checkpoint は、Pebble の圧縮が進むと元のデータと共有しなくなって容量を使うので、置いたままにしない。
- 結果（実装済み、`store/backup.go`、`backend/backup.go`）:
  - `CALL heimdb_backup([名前])` は、パス、時刻（UTC のオフセット付き。`AS OF` と復元にそのまま渡せる）、大きさ（ハードリンクで共有している分も数える）を返す。空の名前は省略と同じ。
  - テスト: 4 つの接続が残高の移動（合計が変わらない）を続ける間に 5 回バックアップを取り、それぞれを開くと、合計が保たれ、元のサーバの `AS OF <バックアップの時刻>` と同じ内容だった。バックアップから起動すると、ブランチ、ユーザーと権限（ブランチだけの権限を含む）、`AS OF` の履歴が戻り、その後の書き込み（AUTO_INCREMENT を含む）もできた。
  - 本物の WordPress（記事 300 件）で、バックアップは 0.09 秒、大きさ 0.7 MB（ハードリンクなので、データディレクトリに足した容量は 0.2 MB）。バックアップの後に題名と記事を変え、HeimDB を止めてバックアップのディレクトリで起動すると（0.3 秒で接続を受け付けた）、サイトはバックアップの時点で動き、管理画面にログインでき、ステージングのユーザーとブランチ、`AS OF` も残っていた。
  - 運用の手順の例（外部への持ち出し）:
    ```
    name=$(date -u +%Y%m%dT%H%M%SZ)
    mysql -uroot -p -e "CALL heimdb_backup('$name')"
    tar -C /var/lib/heimdb-backups -czf - "$name" | aws s3 cp - "s3://example-backups/heimdb/$name.tar.gz"
    rm -rf "/var/lib/heimdb-backups/$name"   # 置いたままにすると、圧縮が進むにつれて容量を使う
    ```
    戻すときは、HeimDB を止め、展開したディレクトリを `-data` に指定して起動する（`-backup-dir` は同じファイルシステムに置くとハードリンクで速い）。
- 段階 16 のレビューで直したこと:
    - 名前を省略したときの名前をマイクロ秒まで含める（秒の粒度で、同じ秒の 2 回目が「already exists」になっていた）。
    - HeimDB が作る `-backup-dir` を 0700 にする（バックアップには `m/users` のパスワードのハッシュが入る）。`-backup-dir` は絶対パスにしてから使う（結果のパスを接続元でも意味のあるものにする）。`-data` と同じ場所なら起動を拒否する（バックアップの名前によっては、Pebble が自分のファイルと読み違える）。
    - バックアップを取る間は、コミットのロックを持つのですべての書き込みが止まる（返す時刻と中身を一致させるため。ロックの範囲を狭めると、Pebble が WAL を写すまでの間のコミットが入ってしまう）。`-backup-dir` が別のファイルシステムだとハードリンクできずに全ファイルを写すので、フラグの説明に同じファイルシステムに置くことを書き、1 秒以上かかったら警告のログを出す。
    - 記録だけ: ユーザーと権限（`m/users`）はバージョンを持たず、コミットのロックの外で書くので、バックアップと同時の `CREATE USER` や `GRANT` は、入ることも入らないこともある（中途半端には入らない）。
    - 記録だけ（以前からの問題。段階 18 で直した）: 停止（SIGTERM）のとき、サーバは接続の受け付けを止めるだけで実行中の文を待たずに Pebble を閉じるので、実行中の書き込み（バックアップを含む）が閉じた Pebble に書こうとして panic しうる。

## 段階 17: mysqldump での出し入れ

- MySQL のサイトを HeimDB に移す道と、HeimDB から MySQL に戻す道（やめたくなったら戻れる）を確かめる。事前の調査（MySQL 8.0 と、mysqldump 9.6）では、既定の指定なら往復がすでに動いた（記事 5 万件、メタ 20 万件、66 MB で、全テーブルのチェックサム、`CREATE TABLE`、AUTO_INCREMENT が一致。HeimDB からのダンプ 0.7 秒、HeimDB への取り込み 5.4 秒）。止まるのは `--single-transaction`（動いているサイトを止めずに整合したダンプを取る普通の指定）だけで、mysqldump がテーブルごとに使うセーブポイントを HeimDB が非対応にしていた。
- 完了条件: `mysqldump --single-transaction` で、書き込みが続いている最中でも整合したダンプが取れる。本物の MySQL 8.0 と HeimDB の間で往復しても、全テーブルのチェックサム、スキーマ、AUTO_INCREMENT が一致する（絵文字、NULL、`0000-00-00` の日時、バイナリ、大きな本文を含む）。本物の WordPress で、wp-cli の `wp db export` / `wp db import` で本番のサイトを別の HeimDB に移すと動き、ログインできる。MySQL で動いていたサイトを HeimDB に移しても動く。本番だけの権限のユーザーでもダンプが取れ、ブランチ（`wordpress@staging`）のダンプも取れる。対応しないテーブル（主キーのないもの、utf8mb4 以外の文字コード）を含むダンプは、取り込みの途中で、どのテーブルかが分かる明示的なエラーになる。
- 実装の方針:
  - セーブポイントに対応する。文の失敗の取り消し（書き込みの記録をある位置まで切り詰めてバッチを作り直す）と同じ仕組みで、セーブポイントは記録の位置を名前で覚える。`ROLLBACK TO SAVEPOINT` で切り詰め、それより後のセーブポイントを忘れる。`RELEASE SAVEPOINT` はそれと後のものを忘れる。同じ名前は置き換える。MySQL と同じく、AUTO_INCREMENT の払い出しとロックは戻さない。振る舞いは本物の MySQL のゴールデンで確かめる。
  - ほかは確かめて、差が見つかったときだけ直す（ログのクエリで再現してから）。
  - ダンプはそのブランチの今の状態だけで、履歴（`AS OF`）やほかのブランチは入らない。全体を写すなら段階 16 のバックアップを使う。
  - 対象外: UpdraftPlus などの PHP で作るバックアッププラグインの確認、古い文字コードのテーブルの自動変換。
- 結果（実装済み）:
  - セーブポイント（`session.go`、`store.Txn.Mark` / `RollbackTo`）。入れ子、名前の大文字と小文字、同じ名前の置き換え、`RELEASE` の後と自動コミットの中での `ROLLBACK TO`（エラー 1305）、AUTO_INCREMENT の欠番、mysqldump と同じ一連の文が、本物の MySQL のゴールデン（`savepoint_golden.txt`）と一致する。
  - 確かめる途中で見つけて直したこと:
    - `SHOW CREATE TABLE` が ENUM と SET の既定値を内部の番号で書いていた（`DEFAULT '2'`。go-mysql-server の `convertColumnDefaultToString` が既定値を列の型に変換してから書く）。HeimDB のダンプを MySQL に入れるとエラー 1067 になる。FULLTEXT のために差し替えていた `SHOW CREATE TABLE` で、値の文字列に直す。
    - latin1 と utf8mb3 のテーブルは、go-mysql-server がその文字コードで表せない文字をそのまま入れ、MySQL（`?` にして警告 1366）と違う値になり、`HEX()` などがエラーになる。utf8mb4 以外の文字コードのテーブルと列は、作る時点と照合順序を変える ALTER で、テーブル名と変換の方法を出す明示的なエラーにする（WordPress は 4.2 からテーブルを utf8mb4 に変換している）。utf8mb3 は段階 37 から、utf8mb4 の同じ名前の照合順序として受け入れる。主キーのないテーブルのエラーにもテーブル名を出す（go-mysql-server は CREATE TABLE の構文解析では列にテーブル名を入れないので、HeimDB の `createTable` で名前を付けて確かめる）。PHPUnit の wpdb グループの結果は変わらなかった。
  - 確かめたこと（mysqldump 9.6 と MySQL 8.0.46）: 絵文字、NULL、`0000-00-00` の日時、バイナリ（`0x00` を含む）、1 MB の本文、decimal、double、ENUM、SET、TIMESTAMP の表を MySQL → HeimDB → MySQL で往復し、チェックサム、スキーマ、AUTO_INCREMENT が一致。2 つの接続が残高の移動を続ける間に `--single-transaction` で 3 回ダンプを取り、どれも合計が保たれていた。本番だけの権限のユーザーとブランチだけの権限のユーザーでもダンプが取れ、ブランチに取り込める。
  - 本物の WordPress: HeimDB のサイトを wp-cli の `wp db export` / `wp db import`（コンテナの中は MariaDB の `mariadb-dump` 11.8）で空の HeimDB に移すと、題名、記事数、絵文字の記事、ログインがそのまま。MySQL で動いていたサイト（記事 32、カテゴリ）を MySQL の mysqldump で書き出して `wp db import` で HeimDB に入れると、サイトが動き、ログインできた。取り込んだ直後に MySQL に戻すと、全テーブルのチェックサムと AUTO_INCREMENT が元と一致した。
  - 記録だけ: wp-cli のコンテナの MariaDB のクライアントは、MySQL 8 の `caching_sha2_password` で認証できない（HeimDB の問題ではない。MySQL からの書き出しは MySQL の mysqldump を使う）。値にクォートを含む ENUM（`enum('it''s')`）は、go-mysql-server が型の文字列でクォートをエスケープしないので作れない（エラーになる）。`CONCAT` と `CONCAT_WS` は ENUM と SET を内部の番号で連結する（go-mysql-server の以前からの差。WordPress のコアには ENUM の列がない）。
  - 運用の手順の例:
    ```
    # MySQL から HeimDB へ
    mysqldump --single-transaction --set-gtid-purged=OFF -h mysql-host -u root -p wordpress > site.sql
    mysql -h heimdb-host -u root -p wordpress < site.sql
    # HeimDB から MySQL へ（main ブランチ。ブランチは wordpress@<名前>）
    mysqldump --single-transaction -h heimdb-host -u root -p wordpress > site.sql
    ```
- 段階 17 のレビューで直したこと:
    - HeimDB は UTC で動く（起動時に `time.Local` と `system_time_zone` を UTC にする。RDS などの MySQL の既定と同じ）。go-mysql-server は TIMESTAMP の値をセッションの `time_zone` で変換せずにそのまま持つので、日本時間のマシンで動かすと、`NOW()` で入った値や、mysqldump（`SET TIME_ZONE='+00:00'` で書き出す）で移した TIMESTAMP が 9 時間ずれていた。UTC で動かせば、`time_zone` を変えない接続（WordPress）の値は UTC の値として MySQL と往復できる。`AS OF` と復元の時刻も、`time_zone` を指定しなければ UTC で解釈する。
    - 【以前からの不具合】トランザクションの途中の DDL の暗黙のコミットが、明示的なトランザクションを終わらせていなかった（go-mysql-server は COMMIT と ROLLBACK のときだけ印を外す）。DDL の後の書き込みがコミットされずに残り、後の ROLLBACK で消えていた（MySQL ではコミット済み）。`beginDDL` で印を外す。
    - 記録だけ: 接続が `time_zone` を UTC 以外にして TIMESTAMP を読み書きすると、MySQL と値が違う（変換しない）。列のコメントにクォートがあると、`SHOW CREATE TABLE` がエスケープせずに書き、そのダンプは取り込めない（go-mysql-server。テーブルのコメントは正しい。WordPress のコアには列のコメントがない。段階 114 で直した）。複数行の INSERT で AUTO_INCREMENT の値を明示したときの insert_id は、MySQL が最後の値、HeimDB が最初の値（以前からの差）。

## 段階 18: 耐久性（クラッシュからの回復、停止の手順、データ形式のバージョン）

- 停止（SIGTERM）のとき、go-mysql-server は新しい接続の受け付けを止めるだけで、実行中の文やつながったままの接続の次の文を待たずに Pebble を閉じていたので、書き込み、バックアップ、裏の GC、切断時の後片付けが閉じた Pebble に触って panic しえた（段階 16 のレビュー）。`kill -9` の後に正しく戻るかは試していなかった。データディレクトリに形式のバージョンがなく、将来形式を変えたときに古いデータを黙って読み違えるおそれがあった。
- 完了条件: SIGTERM を受けたら新しい文を MySQL と同じエラー 1053（`Server shutdown in progress`）で拒否し、実行中の文と GC が終わるのを待ってから Pebble を閉じる。書き込みが続いている最中に何度止めても panic しない。書き込み（残高の移動、記録の追加）、GC、バックアップが続いている最中に `kill -9` で何度も落として起動し直し、応答を返した書き込みがすべて残り、途中までのトランザクションが 1 つも残らず（合計が保たれる）、そのまま書き込みを続けられる（自動のテスト）。データディレクトリに形式のバージョンを記録し、今の HeimDB より新しい形式のデータは理由を書いたエラーで起動を拒否する。
- 実装の方針:
  - 接続ごとのコマンドの始まりと終わり（`CommandBegin` / `CommandEnd`）で実行中の文を数え、停止が始まったら新しいコマンドを拒否する。切断時の後片付け（`SessionEnd`）と裏の GC も同じ仕組みに入れる。止めるときは、受け付けを止め、実行中のものが終わるのを待ってから Pebble を閉じる。待つ時間の上限（`-shutdown-timeout`、既定 30 秒）を過ぎたら、Pebble を閉じずにプロセスを終える（コミット済みのデータは同期書き込み済みなので、クラッシュと同じで安全。閉じて panic させるよりよい）。
  - クラッシュの試験は、テストの中で HeimDB をビルドして別のプロセスで動かし、書き込みの最中に `kill -9` を繰り返す。電源断そのものは試せないので、Pebble の同期書き込み（`pebble.Sync`）を信頼する。
  - 形式のバージョンは `m/format` に置く（今は 1）。バージョンのない既存のデータはバージョン 1 とみなして書き込む。新しい形式のデータは起動を拒否する。形式を変えるときは番号を上げて移行の処理を足し、HeimDB を更新する前にバックアップ（段階 16）を取る手順にする。
- 結果（実装済み、`backend/shutdown.go`、`store` の `checkFormat` と `StopLockWaits`、`cmd/heimdb/durability_test.go`）:
  - 停止: `CommandBegin` で実行中の文を数え、停止の後は新しい文をエラー 1053 で拒否する（`CommandEnd` で数を戻す。`SessionEnd` の後片付けは停止の後は何もしない）。停止が始まったら、書き込みロックを待っている文もエラー 1053 にする（次の文を拒否された接続のトランザクションがロックを持ったまま残るので、それを待つ文が最大 50 秒終わらず、停止が進まなかった。試験で見つけた）。実行中の文が終わったら Pebble を閉じ、`stopped` とログに出す。`-shutdown-timeout`（既定 30 秒）を過ぎたら閉じずに終える。
  - 形式のバージョン: `m/format` に 1 を書く。バージョンのないデータはバージョン 1 として開いて書き、今より新しいバージョンのデータは「newer HeimDB」のエラーで開かない。
  - 試験（`go test ./cmd/heimdb`、`-short` で飛ばす）: HeimDB をビルドして別のプロセスで動かし、4 つの接続の残高の移動と記録の追加（1 つのトランザクション）、列の追加と削除の ALTER（テーブルの書き直し）、バックアップ、短い保持期間で 200 ミリ秒ごとの GC を続けながら、`kill -9` で 6 回落として起動し直した。毎回、応答を返したコミット（合計 250 件ほど）がすべて残り、試みていない記録はなく、合計が保たれ、ALTER の途中で落ちたテーブルも行数が変わらず、そのまま書けた。SIGTERM で 4 回止めると、毎回 panic せずに閉じ（終了コード 0）、開いたままのトランザクションの次の文は拒否され、起動し直して同じ確認が通った。3 回繰り返して安定していた（`-race` でも通る）。
  - 記録だけ: 電源断そのものは試せないので、Pebble の同期書き込みを信頼する。バックアップの途中で落ちると、作りかけのバックアップのディレクトリが残る（開けないことがあるので消す）。PHPUnit の wpdb グループで、go-mysql-server が対応していない文字セットへの `CONVERT(... USING ujis)` などが、結果の列の型が空のまま panic していた（段階 18 のレビューで直した。下を参照）。
- 段階 18 のレビューで直したこと:
  - 【以前からの不具合】go-mysql-server が変換を実装していない文字セット（ujis、koi8r、big5、cp1251、tis620、hebrew など）への `CONVERT(... USING ...)` は、結果の型が空のまま panic し、WHERE の定数（解析のときに評価する）や UPDATE / INSERT では回復されずに接続が切れていた。構文解析の直後（`likeEscapeParser`）に構文木を歩いて、明示的なエラー（1235。知らない文字セットは MySQL と同じ「Unknown character set」。go-mysql-server が構文解析のエラーを 1105 で包むので、番号は本文に入る）にする。解析のルールでは、単純な INSERT と UPDATE が通らない（`sql/analyzer/node_batches.go`）。WordPress がこれを使うのは utf8mb4 以外のテーブルのための `wpdb::strip_invalid_text` だけで、HeimDB はそのテーブルを作らせない（段階 17）。
  - 停止の後でも、空いている書き込みロックは取れるようにする（`select` が準備のできた道を無作為に選ぶので、停止の前に始まった文が、競合していないのに 1053 で失敗することがあった）。
  - 2 回目の SIGTERM（Ctrl-C）ですぐに終える（長い文があっても、`-shutdown-timeout` を待たずに止められる。コミット済みのデータは同期書き込み済みなので安全）。
  - 停止の試験で、プロセスが生きている間（実行中の `SLEEP` を待っている間）に、開いたままのトランザクションの次の文がエラー 1053 になり、実行中の文が最後まで終わることを確かめる（以前はプロセスが終わった後に確かめていたので、どのエラーでも通っていた）。

## 段階 19: 見える化

- これまでは、GC で消えた量と、GC の境界が開いたトランザクションで止められていることがログに出るだけで、ディスクの使用量、ブランチごとの大きさ、最後の GC、開いたままのトランザクション、実行中の文の数、遅い文が外から見えなかった。バージョンを追記するので使用量は増え続け、放置したブランチは分岐の時点のバージョンを残すので、気づく手段が要る。
- 完了条件: 管理者が `CALL heimdb_status()` で、データ全体のディスク使用量、最後の GC（時刻、境界、消した数、かかった時間、エラー）、GC の境界の遅れとそれを止めているもの（最も古い開いたトランザクションと使用中の時刻の経過時間）、接続数、実行中の文の数、開いたトランザクションの数を 1 回で見られる。`CALL heimdb_branch_list()` にブランチごとの大きさ（推定のディスク使用量）を足す（分岐からの経過は既存の `forked_at` で分かる）。`-slow-query` で指定した時間を超えた文を、接続 ID、ユーザー、時間とともにログに出す。値が実際の状態と合うことをテストで確かめる。
- 実装の方針: ディスク使用量は Pebble の実際の使用量（`Metrics().DiskSpaceUsage()`）、ブランチの大きさはブランチのキーの範囲の推定（`EstimateDiskUsage`。推定なので、小さいブランチや書いた直後はメモリ上の分が数えられず 0 に近いことがある）。最後の GC はストアが覚える（起動してからのもの）。実行中の文の数は段階 18 の仕組みの数、接続数はセッションの始まりと終わりで数える。遅い文は段階 18 の文の始まりと終わりで測る。HTTP の口（Prometheus の `/metrics` など）は今は作らない。
- 結果（実装済み、`backend/status.go`、`store/status.go`）:
  - `CALL heimdb_status()`（管理者だけ）は、項目と値の行を返す: `disk_bytes`、`branches`、`connections`、`running_statements`（この呼び出しを含む）、`open_transactions`、`oldest_snapshot_age_seconds`、`pinned_times`、`oldest_pinned_time_age_seconds`、`gc_retention`、`gc_boundary`、`gc_boundary_age_seconds`、`gc_last_run_at`、`gc_last_duration`、`gc_last_removed`、`gc_last_error`。`oldest_snapshot_age_seconds` は、最も古い開いたトランザクションを開いてからの時間ではなく、そのスナップショット（開いた時点の最後のコミット）の古さで、GC の境界をどこまで止めているかを表す（しばらく書き込みがなければ、開いたばかりでも大きい）。`gc_last_*` は、まだ GC をしていなければ NULL（行はいつも出る）。
  - `CALL heimdb_branch_list()` の最後の列に `size_bytes`（推定）を足した。
  - `-slow-query 2s` のように指定すると、それを超えた文を `slow query: <文>`（1000 文字まで）として、接続 ID、ユーザー、データベース、時間とともに警告のログに出す。ユーザーの管理の文（`CREATE USER`、`ALTER USER`、`SET PASSWORD`、`GRANT`、`IDENTIFIED` を含む文）は、パスワードを出さないよう先頭の 2 語だけにする。
  - 限界（記録だけ）: 1 回の送信に複数の文をつなげる接続（multiStatements）では、遅い文のログに残りの文もつながって出る。WordPress はこの送り方を使わない。
  - `-no-auth` で `CREATE USER` や `GRANT` を実行すると、go-mysql-server がユーザーの保存先がないため panic して接続が切れていた（段階 14 からの問題）。保存先を必ず設定し、`-no-auth` ではユーザーの変更をエラーにする。
  - 本物の WordPress のデータ（記事 300 件、ステージングのブランチ）で、全体の使用量、本番とステージングの大きさ、遅い文のログが期待どおりに見えた。
  - 限界: ブランチの大きさの推定は、ディスク上のファイル（sstable）になった分だけを数える。書いたばかりでメモリと WAL にある分は入らないので、PHPUnit の直後は全体の使用量が 1.3 MB でも main が 0 と出た。Pebble がメモリの分をファイルに書き出すと（既定では数 MB ごと）数えられる。全体の `disk_bytes` は WAL を含む実際の使用量。最後の GC は起動してからのもので、起動の直後は NULL（既定では 1 時間ごとに動く）。
  - あわせて、名乗るバージョンと製品名をそろえた。接続のときに名乗るバージョン、`@@version`、`VERSION()` を MySQL 8.0.33（互換の目標。WordPress の `has_cap` や mysqldump の `/*!40101 ... */` がこの番号で判断する）にし、`@@version_comment` を `HeimDB` にする（mysql コマンドの表示は `Server version: 8.0.33 HeimDB`）。go-mysql-server の既定は、接続のときのバージョン（vitess の 8.0.33）と `@@version`（8.0.31）が食い違い、製品名が `Dolt` だった。

## 段階 20: PHPUnit の全テストでの互換性

- これまでは option、meta、query、wpdb の 4 グループ（約 3,400 件）だけで確かめていた。全テスト（約 29,370 件）の残り（投稿の一覧、タクソノミー、ユーザー、コメント、REST API、cron など）が出す SQL は HeimDB で流したことがない。
- 完了条件: 全テストを本物の MySQL と HeimDB で流し、本物で成功し HeimDB で失敗するテストを原因ごとに一覧にする。接続が切れる、panic するものは 0 にする。残りの差は原因ごとに、直す、明示的なエラーで非対応にする、記録だけにする、のどれかに決める。直したものには、ログのクエリで再現するテストを付ける。4 グループのベースラインとの差は増やさない。
- 実装の方針: まず両方で流して差の一覧と原因の分類を作り、直す範囲を決める（多ければ段階を分ける）。接続の切断と panic を最優先にし、次に失敗の件数の多い原因から直す。原因は `cmd/replay` とログのクエリで再現してから直す。HeimDB は専用のポート（3316）と使い捨てのデータディレクトリで動かす。
- 結果（実装済み）:
  - 全テスト 26,475 件。本物の MySQL は失敗 1（環境の open_basedir）、所要約 6 分。HeimDB は直す前が失敗とエラー 82、本物で成功し HeimDB で失敗するもの 80（うち 42 は既知の wpdb グループの差と同じ。新しい差は 38）、接続の切断と panic は 0。
  - 直したもの（38 件のうち 26 件）:
    - `FOUND_ROWS()` と `LIMIT` の offset（23 件。REST API の総数のヘッダ、2 ページ目以降、「前の投稿」のリンク、コメントのページ分け）: go-mysql-server の Limit は子から受け取った行を数えるので、子が Offset だと読み飛ばした分が数えられない（5 件のうち `LIMIT 2, 2` で 3）。解析ルールで `Limit(n, Offset(k, 子))` を `Offset(k, Limit(n + k, 子))` に組み替える（`backend/foundrows.go`。プリペアドステートメントの引数でもよい）。
    - 同じ行の重複（1 件）: インデックスの先頭の列に条件がなく後ろの列に `IN` があると、範囲ごとにインデックス全体を走査して同じ行を範囲の数だけ返していた（コメントの `post_status IN ('publish','future')`）。範囲をキーの区間に変換した後、重なる区間をまとめてから走査する（`rows.go` の `mergeIntervals`）。「これまでの検証結果」の未解明の「同じ ID の重複」は、おそらくこれ。
    - 大文字と小文字だけを変える `UPDATE`（1 件。メールアドレス）: go-mysql-server は古い行と新しい行を対象のテーブルの `Schema()` の型（照合順序）で比べ、等しければ書き込まない。実行の直前に対象のテーブルを包み、比較に使うスキーマの文字列の列を `utf8mb4_bin` にする（`backend/updatecase.go`）。単一のテーブルの `UPDATE` は HeimDB が足した解析ルールを通らないので、`Analyzer.ExecBuilder` を包んで書き換える。
    - `information_schema.TABLES` の `TABLE_ROWS`（1 件。サイトヘルスのオブジェクトキャッシュの推奨）: いつも 0 だった。`sql.StatisticsTable` の `RowCount` は実行計画のコストや `COUNT(*)` の置き換えにも使われ、計画と並びが変わりうるので実装しない。`information_schema.TABLES` を読むときだけ、HeimDB のテーブルの行数を数えて入れる（`backend/tablerows.go`。数えるので大きなテーブルでは遅い）。
  - 直した後: 本物で成功し HeimDB で失敗するものは 54（既知の 42 と、下の 12）。接続の切断と panic は 0。
  - 段階 21 に回すもの（11 件）: WordPress の非 STRICT の sql_mode で、MySQL は値を直して警告にするが HeimDB はエラーにする。NOT NULL の列への NULL（`UPDATE` と複数行の `INSERT`。暗黙の既定値と警告 1048）、不正な日時（ゼロの日時と警告 1265。`'2012-01-01 0'` は日付の部分）、既定値のない NOT NULL の列の省略（暗黙の既定値と警告 1364）。単一の `INSERT ... VALUES` も HeimDB の解析ルールを通らない（go-mysql-server の node_batches.go）。
  - 記録だけ（1 件）: `GROUP BY` と `NOT IN` のある文の同じ日時の行の並び（REST API の `tags_exclude`）。MySQL は一時テーブルとソートを使い、同順位の並びに決まった規則がない（4 行なら昇順、32 行ならほぼ降順で一部が入れ替わる）ので合わせない。
  - レビューで直したもの: `SQL_CALC_FOUND_ROWS` と「offset から最後まで」の `LIMIT k, 18446744073709551615` で行が返らなかった（組み替えた `n + k` が溢れて負になった。上限で止める）。
  - 記録だけ（レビューで見つけた。WordPress は使わない）:
    - `SQL_CALC_FOUND_ROWS` のない `SELECT` の後の `FOUND_ROWS()` は、MySQL では offset で読み飛ばした行も数える（`LIMIT 3, 2` で 6 行なら 5）。HeimDB は返した行の数。
    - `UNION` と `SQL_CALC_FOUND_ROWS` の `FOUND_ROWS()` は、MySQL は `UNION` 全体の行数、HeimDB は返した行の数（`UNION` の `LIMIT` は Limit ノードにならないので組み替えの対象外）。
    - `WHERE id IN (SELECT ...)` と `UPDATE ... JOIN` の形の `UPDATE` では、大文字と小文字だけの変更が書き込まれない（go-mysql-server が Update Join にするので、対象のテーブルを包めない）。スカラーサブクエリと `EXISTS` の形は直っている。`UPDATE ... WHERE EXISTS (相関サブクエリ)` は go-mysql-server のエラー（段階 20 とは無関係。接続は切れない）。
    - `information_schema.TABLES` を読むと、条件に関係なくすべてのブランチの全テーブルの行を数える（サイトヘルスはまれにしか呼ばないので許容）。読めないテーブルの `TABLE_ROWS` は 0（テーブル名が見えるのは go-mysql-server の以前からの挙動）。`SHOW TABLE STATUS` の `Rows` は 0 のまま。
