# Stage 132: sync leaves out comments and users, and patterns cannot be removed while branches exist

## Background

- `heimdb_branch_sync` copied `wp_comments`, `wp_commentmeta`, `wp_users` and `wp_usermeta` like any other table, while a merge never applies them. Logging in on both sides changes `session_tokens` on both sides, which is a conflict, and `'parent'` overwrote the branch's users.
- A merge and a sync move a branch's base forward for all tables, including excluded tables whose rows they did not touch. If the pattern was removed later, the table was compared against a base it never had. Reproduced on 0.3.1:

| Order | Result |
| --- | --- |
| exclude, sync, include, merge | A column changed on production went back to the old value, and a row deleted on production came back |
| the same, with an `ALTER TABLE` on the branch | Production's update went back to the old value although the branch changed no row |
| exclude, merge, include, sync | The branch's unmerged value was overwritten with production's |
| exclude, merge, include, merge | Only columns changed later were merged (a row with old and new values mixed) |
| the same, for a table created on the branch | `dropped on parent`; never created on production |
| exclude, include, merge | Correct (no merge or sync in between) |

None of them was a conflict or an error.

## Plan

1. A sync does not write the rows of the four tables, with no option to include them (the base is per branch, so a later sync with the option would miss what an earlier one skipped). To get them, recreate the branch.
2. `heimdb_merge_include` is refused while there is a branch other than `main` (the base is recorded per branch, so with no branches it is safe). Adding patterns stays allowed.

## Changes

- `syncBranch` (`internal/backend/sync.go`): rows of `merge.KindParentOnly` tables are skipped; a `not synced` row is returned if the parent changed them. A table the branch does not have at all is still copied whole.
- The planned skip of the definition check for these tables was dropped: a merge compares their columns, and after a sync with different definitions it removed a column that only production had. They are refused with 51010 as before.
- `mergeExclude` (`internal/backend/mergeexclude.go`): 51011 `branches_exist`, checked inside the write that changes the setting.

## Engine changes

None. The data format does not change.

## Tests

- `TestBranchSyncKeepsUsersAndComments`: conflicting rows and the same IDs on both sides, a sync with `'parent'`, undo, a merge, comment counts, and different definitions.
- `TestMergeExcludedTables`: `heimdb_merge_include` with and without a branch.
- The existing sync tests that expected comments to be copied now expect `not synced`, and use post meta to check that rows are copied.

## Only recorded

- A `RENAME TABLE` that takes a table out of a pattern has the same effect as removing it (noted in `procedures.md`).
- Branches for which a pattern was already removed after a merge or a sync are not repaired; recreate them.
