# 段階 31〜40

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 31: SQL からサーバのファイルを読み書きできないようにする

- 背景: go-mysql-server は FILE 権限を確かめず（`LoadFile.Eval` に TODO）、`secure_file_priv` が空なので、どのファイルでも読み書きできる。`GRANT ALL ON wordpress.*` だけのユーザーでも、`SELECT LOAD_FILE('/etc/hosts')` で読め、`SELECT ... INTO OUTFILE` で書けた（`LOAD DATA INFILE` は root だけができた）。プラグインに SQL インジェクションの穴が 1 つあれば、`/proc/self/environ`（`HEIMDB_ROOT_PASSWORD`、レプリケーションの合言葉）、TLS の鍵、データのファイルを読め、書き込める場所にファイルを書ける。
- 方針: WordPress はこれらを使わないので、常に明示的なエラー（`HeimDB: reading or writing server files is not supported`）にする。FILE 権限は実装しない。構文解析の直後に文の木をたどり（`checkConvertUsing` と同じ場所。単純な INSERT は解析のルールを通らないため）、`LOAD_FILE()`（副問い合わせや INSERT の値の中も）、`INTO OUTFILE`、`INTO DUMPFILE`、`LOAD DATA`（`LOCAL` も）を拒否する。`INTO @変数` は使える。プリペアドステートメント（`PREPARE ... FROM` とバイナリプロトコル）も同じく止まるようにする。二重の守りとして、起動時に `secure_file_priv` をファイルを置けない場所にする（起動のたびの「insecure」の警告も消える）。
- 完了条件: 3 種類の文がどこに書いても（副問い合わせ、INSERT の値、プリペア）エラーになり、ファイルを読めず、作れない。接続は切れず、次の文が使える。`SELECT ... INTO @変数` は使える。Go のテストが通る。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（compose）で、インストール、記事の作成、wp-cli の `db export` と `db import` が動く。
- 実装: `parser.go` の `checkServerFiles`。`checkConvertUsing` とまとめて `checkStatement` から呼ぶ。`secure_file_priv` は `/dev/null/heimdb`（ディレクトリになりえないので、go-mysql-server の `stat` が必ず失敗する）。
- 見つけて直したこと: 複数の文を送れる接続（mysql クライアントは有効にする。Go のドライバと mysqli は既定で無効）では、go-mysql-server の handler が `Parse` のエラーを見ずに、返った文をそのまま実行していた（`doQuery` で、後の `queryExec` が err を上書きする）。HeimDB の確認は文とエラーを両方返していたので、この経路では効いていなかった（段階 18 の `CONVERT ... USING` も同じ）。エラーのときは文を返さないようにした。文がなければ、エンジンが同じ Parser で解析し直してエラーを返す。
- 結果: `TestServerFilesRejected` で、13 の形（`LOAD_FILE` を SELECT、副問い合わせ、FROM の副問い合わせ、INSERT の値、UPDATE に。`INTO OUTFILE`、`INTO DUMPFILE`、UNION の `INTO`、`LOAD DATA`、`LOAD DATA LOCAL`）が、テキスト、`PREPARE ... FROM '...'`、`PREPARE ... FROM @変数`、バイナリプロトコルのプリペア、複数の文の接続のどれでもエラーになり、ファイルが作られず、行も入らず、接続が切れないことを確かめた（確認を外すと 48 か所、文を返さない直しを外すと複数の文の経路で 15 か所落ちる）。`INTO @変数` と、文字列の中の `LOAD_FILE` は使える。Go のテストは 322 件（-race でも成功）。PHPUnit の全テストで、本物で成功し HeimDB で失敗するものは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。本物の WordPress（compose）で、インストール、記事の作成、`wp db export` と `wp db import`（消した記事が戻る）が動き、`LOAD_FILE('/proc/self/environ')` はエラーになり、起動の `secure_file_priv` の警告が消えた。
- 段階 31 のレビュー（Fable）で直したこと: vitess の `ast.Walk` は、DDL の列の定義と既定値（`(*DDL).walkSubtree` は表の名前とビューの式しかたどらない）と `EXPLAIN` の中の文に降りないので、`ALTER TABLE ... ADD COLUMN w TEXT DEFAULT (LOAD_FILE(...))`、`CREATE TABLE ... DEFAULT (LOAD_FILE(...))`、`EXPLAIN SELECT LOAD_FILE(...)` が確認を通っていた。行のある表に列を足すと、その場で既定値を計算してファイルを読む（テストのサーバで中身が読めた。本番は `secure_file_priv` で止まる）。確認は `reflect` で文の木をすべてたどる形に替えた（行 5,000 件の INSERT で、構文解析 4.3 ms に対して 0.5 ms、メモリの確保なし。木に循環があってもサーバが落ちないよう、深さ 65,536 を超えたら拒否する）。`TestServerFilesRejected` に DDL の既定値、`EXPLAIN`、`DESCRIBE`、バッククォートと `mysql.` の付いた名前を足した（前の確認に戻すと落ちる）。backend のテストのサーバは main を通らず `secure_file_priv` が空なので、バイナリを起動して `@@secure_file_priv` と起動の警告がないことを確かめる `TestSecureFilePriv`（cmd/heimdb）を足した。レビューは Fable の安全の仕組みで途中で止まり、最初の指摘の後は届かなかった。直した後、Go のテストは 323 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。バージョンを 0.1.1 にした（データ形式は 0.1.0 と同じ）。
- 記録だけ: バイナリプロトコルで `LOAD DATA` をプリペアすると、vitess が HeimDB の確認より前に、プレースホルダを数えるために文の木をたどって panic し（`IGNORE n LINES` がないと nil の `*SQLVal` を読む）、接続が切れる。ファイルは読まれない。WordPress はバイナリプロトコルのプリペアを使わない。複数の文の接続では、vitess はエラーの後も残りの文を実行する（MySQL は止める。どのエラーでも同じ）。WordPress は複数の文を一度に送らない。

## 段階 32: WordPress を root で動かさない（最小権限の既定）

- 背景: compose と文書の例は WordPress を root（すべての権限）でつないでいた。プラグインに SQL インジェクションの穴が 1 つあれば、HeimDB の手続き（`heimdb_restore`、`heimdb_branch_delete`）、`CREATE USER` と `GRANT`、本番とステージングの両方のデータに届く。これから作る「管理者以外は拒否する」仕組み（変更の見張り、設定の鍵）も、WordPress が root のままでは効かない。データベースだけの権限で WordPress、wp-cli、dbDelta、mysqldump が動くことは段階 14 で確かめた。
- 方針: 起動のフラグ `-site-user`（既定 `wordpress`）と `-site-password`（または環境変数 `HEIMDB_SITE_PASSWORD`）で、サイト用のユーザー `'<名前>'@'%'` を作り、`GRANT ALL ON <-db>.*` を与える。ユーザーがまだいないときだけ作る（いれば何もしない。パスワードと権限を変えない）。root と違い最初の起動に限らない（後から環境変数を足して起動し直せば作られる）。レプリカでは作らない（本番から写る）。パスワードがなければ何もしない。compose は、`wordpress` をサイト用のユーザー（`HEIMDB_SITE_PASSWORD` を必須に）、`staging` をそのブランチだけの権限のユーザー `staging`（`STAGING_DB_PASSWORD` を必須に。ブランチを作る手順の中で wp-cli から `CREATE USER` と `GRANT` をする）でつなぐ。`cli`（wp-cli）は管理者の道具として root のまま。文書の「簡単のため root で接続する」をなくす。ステージングのユーザーは自動で作らない（ブランチを作る時期を HeimDB は決めない）。
- 完了条件: Go のテストで、パスワードがあればデータベースだけの権限のユーザーができ、すでにいれば変えず、そのユーザーからは `CALL heimdb_*`、`CREATE USER`、ほかのブランチへの接続が拒否される。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（compose）で、サイト用のユーザーでのインストール、記事の作成、テーブルを作るプラグインの有効化、wp-cli の `db export` と `db import`、ステージングのユーザーで動くステージング、マージが動き、サイト用のユーザーからは `CALL heimdb_branch_list()` が拒否される。0.1.2 として公開する。
- 実装: `backend.EnsureSiteUser`（auth.go）。ユーザーがいるかは `mysql_db` の Reader で '<名前>'@'%' を引いて確かめ、いなければ root としてエンジンで `CREATE USER` と `GRANT ALL ON <db>.*` を実行する（`mysql_db` の API で権限を組み立てるより、普通の GRANT と確実に同じ権限になる）。名前は英数字、`_`、`-` だけ。compose の `${...:?}` はプロファイルを使わなくても効くので、`STAGING_DB_PASSWORD` は必須にせず、`staging-files` の中で空ならメッセージを出して止める（`staging` はその成功を待つので起動しない）。
- 結果: `TestSiteUser`（cmd/heimdb。バイナリを起動する）で、サイト用のユーザーが表を作り、読み書きし、列を足せること、`CALL heimdb_branch_list()`、`heimdb_restore`、`CREATE USER`、`GRANT ... ON *.*`、ステージングの表の読み出しと `wordpress@staging` への接続が拒否されること、権限が `USAGE ON *.*` と本番のデータベースだけであること、2 回目の起動で別のパスワードを渡しても変わらないこと、パスワードがなければ作らないこと、名前の誤りが起動のエラーになることを確かめた（`GRANT` を `*.*` にすると落ちる）。Go のテストは 324 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト（PHPUnit は root でつなぐ）。接続の切断と panic は 0。本物の WordPress（compose、ローカルで作ったイメージ）で、サイト用のユーザーでのインストール、記事の作成、テーブルを作るプラグイン（dbDelta）の有効化、wp-cli（root）の `db export` と `db import` が動き、サイト用のユーザーからの `CALL heimdb_branch_list()`、`CREATE USER`、`wordpress@staging` の読み出しは拒否された。`STAGING_DB_PASSWORD` がないとステージングは「set STAGING_DB_PASSWORD」で止まり、あればステージングのユーザーで動いた（本番のデータベースと `heimdb_branch_merge` は拒否）。ステージングで書いた記事は、wp-cli からのマージで本番に出た。

## 段階 33: 危ない変更の見張り

- 背景: WordPress が乗っ取られるとき（プラグインの穴、盗まれた管理者のパスワード）には、決まった行が変わる。管理者の追加、`default_role` を administrator にして登録を開く、`siteurl` の書き換え、プラグインの有効化など。HeimDB は書き込みをすべて見ているので、それを知らせられる。
- 方針: コミットのときに、トランザクションが書いた行のうち見張るテーブルの行を、コミット前の値と比べ、変わっていればログ（警告、`HeimDB: watch: ...`）に出し、`heimdb_status` の `watch_changes`（起動からの件数）、`watch_last_change`、`watch_last_change_at` に出す。止めはしない。見張るもの: `*options` の `siteurl`、`home`、`admin_email`、`users_can_register`、`default_role`、`template`、`stylesheet`（前と後の値）、`active_plugins`（足したものと外したもの）、`*user_roles`（変わったことだけ）。`*users` の追加と削除（ログイン名と ID）、`user_pass` の変更（ログイン名だけ。ハッシュは出さない）、`user_email` の変更。`*usermeta` の `*capabilities` に administrator が新しく付いたこと。`*sitemeta` の `site_admins`。テーブルは名前の終わりと列の名前で見分ける（接頭辞とマルチサイトの `wp_2_options` に効く）。すべてのブランチで、ブランチ名とつないだユーザーを出す（root も）。ロールバック、失敗した文、セーブポイントで取り消した変更は出ない（コミットで比べるため）。セッションのコミットとマージを見張る。復元は次の段階。レプリカでは見張らない。フラグは足さない。1 つの文で多くの行を変えたときの警告は採らない（一時データの掃除などで誤検知が多い）。
- 完了条件: Go のテストで、上の各変更がログと `heimdb_status` に出て、ロールバック、失敗した文、セーブポイントで取り消した変更、見張らない行では出ず、パスワードのハッシュが出ず、マージで本番に入った変更で出る。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（compose）で、管理画面の設定の変更、wp-cli での管理者の追加、プラグインの有効化がログに出る。
- 実装: `internal/backend/watch.go`。エディタ（`editor.Insert`、`Update`、`Delete`）が、見張るテーブルの行を書いたら、書く前の位置（`Txn.Mark`）とともに印を `store.Txn.Note` で添える。`Txn.truncate`（文の取り消し、`ROLLBACK TO SAVEPOINT`）は、その位置より後の印を消す。コミットは `Provider.commitWatched` を通し（セッションのコミット、DDL の前の暗黙のコミット、マージ）、コミットが成功したら印を行ごとにまとめ、最初の前の値と最後の後の値を比べる。復元のエディタは印を付けない。ログのユーザーは、権限のホスト（`%`）ではなく接続してきた相手のアドレス（`wordpress@172.18.0.4`）。オプションは名前で絞ってから印を付けるので、一時データなどの書き込みは比べない。`siteurl` と `home` はマージの規則で親に入らないので、マージでは出ない。
- 結果: `TestWatch` で、表の各変更（インストールの形の挿入、`INSERT ... ON DUPLICATE KEY UPDATE`、更新、削除、プラグインの有効化と無効化、役割の定義、ユーザーの追加と削除、パスワードとメールアドレスの変更、administrator の付与、`site_admins`、`wp_` 以外の接頭辞の `shop_2_options`）がログと `heimdb_status` に出ること、見張らない行、値の変わらない更新、ロールバック、セーブポイントへのロールバック、トランザクションの中と自動コミットの失敗した文、同じ行を書いて元に戻した変更、名前だけ似たテーブルでは出ないこと、ブランチの変更がブランチ名で出て、マージで入った変更が `(merge of branch staging)` 付きで出ること、パスワードのハッシュが出ないことを確かめた（印を取り消しで消さないと、行ごとにまとめないと落ちる）。Go のテストは 325 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。見張りのログは全テストで 1,812 行（テストはユーザーとオプションをよく作る）。本物の WordPress（compose、ローカルで作ったイメージ）で、インストール（root）、wp-cli のプラグインの有効化と管理者の追加（`plugins activated: hello.php`、`user added`、`administrator role given`）、管理画面の一般設定での `users_can_register` と `default_role` の変更（`wordpress@<WordPress のコンテナのアドレス>`）がログに出て、管理画面の表示、`wp-cron.php`、記事の作成では出ず、`heimdb_status` の件数と最後の 1 件がログと合った。
- 段階 33 のレビュー（Fable）で直したこと: 同じトランザクションで足して消したユーザーが、前も後もない行として `user added: "" (ID )` と出ていた。前も後もない行は出さない。マルチサイトのネットワークでの有効化（`wp_sitemeta` の `active_sitewide_plugins`）を見張っていなかったので足した。オプション名（`*user_roles`）、メタのキー（`*capabilities`）、プラグインのファイル名を引用符なしで出していたので、空白、制御文字、`"`、`\` を含むものは引用符で囲んでエスケープする（端末に出すときに、改行でログの行を偽れた。Docker のログは logrus が `msg` を引用するので元から安全）。`wp_usermeta` と `wp_sitemeta` は、見張るキーの行だけに印を付ける（前は全行に付け、コミットまで行を持っていた）。テーブルの種類はエディタで 1 回だけ調べる（前は行を書くたびに列の対応を作っていた）。テストに、足して消したユーザー、DDL の前の暗黙のコミット（後の ROLLBACK で消えない）、ネットワークでの有効化、名前のエスケープ、ブランチで足したユーザー（マージの規則で親に入らないので、マージでは出ない）、復元で戻した行（出ない）、サイト用のユーザーの接続元のアドレスを足し、期待値を末尾の一致から完全な一致にした（足して消した行の直し、エスケープを外すと落ちる）。直した後、Go のテストは 325 件（-race でも成功。PHPUnit と同時に流した 1 回だけ 1 件落ち、名前を残せなかった。その後の 3 回はすべて成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。バージョンを 0.1.3 にした（データ形式は 0.1.2 と同じ）。公開したイメージを取り込んで動かし、サイト用のユーザーの変更が見張りのログと `heimdb_status` に出ることを確かめた。
- 記録だけ: オプションの行の名前を変える `UPDATE`（`siteurl` から別の名前へ）は出ない（新しい名前で判断する。WordPress はしない）。`REPLACE INTO wp_options` で `option_id` が変わると、削除と追加の 2 行になる。`TRUNCATE`、`DROP TABLE`、`RENAME TABLE` は見張らない。運用で出るもの（インストール、客の登録、WordPress 6.8 のパスワードのハッシュの作り直し、`wp search-replace`）は `operations.md` に書いた。

## 段階 34: 変更の一覧と、復元のときの警告

- 背景: 見張りのログで気づいた後、ある時刻から後に何が変わったかを調べる手段がない（`heimdb_restore_preview` はテーブルごとの数だけ）。既定の復元はユーザー（`wp_users`、`wp_usermeta`）を戻さないので、乗っ取られた後に復元しても、後から足された管理者が残り、それに気づけない。
- 方針: `CALL heimdb_changes(ブランチ, 時刻[, テーブル])` は、時刻から今までに変わった行を、`table_name`、`id`（`heimdb_branch_diff` と同じ書き方。`wp_options` は `option_name`）、`change`（`insert`、`update`、`delete`）、`columns`（変わった列）、`changed_at`（行が最後に変わった時刻）、`watch`（見張りの対象なら段階 33 と同じ説明）で返す。`changed_at` の順。何も書かない。テーブルは `heimdb_restore` と同じ指定（省くとすべて）。時刻からの間にテーブル ID が変わったテーブル（作った、消した、`ALTER` や `TRUNCATE` で書き直した）は、行ではなくテーブルの 1 行（`table created`、`table dropped`、`table rewritten`）にする。毎分のように変わる行（`_transient_*`、`_site_transient_*`、`cron`、記事の `_edit_lock`）は除き、その数を最後の行（`table_name` が `*`）に出す。時刻は保持期間の中だけ。既定の `heimdb_restore` と `heimdb_restore_preview` は、戻さないユーザーのテーブルについて、時刻から後に見張りの対象の変化（ユーザーの追加、パスワードとメールアドレスの変更、administrator の付与）があれば、`action` が `not restored` の行を足し、`detail` に中身とユーザーも戻す呼び出しを出す。復元したときはログにも警告で出す。値の前と後は出さない（`AS OF` で読む）。記事 1 件をメタごと戻す手続きは作らない（表を指定して記事とメタの片方だけを戻すときの警告は段階 62）。
- 完了条件: Go のテストで、一覧が追加、更新、削除を正しい列と時刻の順で返し、除く行がその数とともに除かれ、見張りの説明が入り、テーブルで絞れ、期間の外の時刻はエラーになり、ブランチで使え、テーブルの書き直しが 1 行になる。既定の復元で、後から足された管理者が `not restored` として結果とログに出て、`'*'` では出ない。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（compose）で、管理者の追加と `default_role` の変更の後、`heimdb_changes` にその 2 つが見え、既定の復元で警告が出て、`'*'` での復元で管理者が消える。
- 実装: `internal/backend/changes.go`（`heimdb_changes`）。行の候補は `Store.ChangedRowTimesSince`（`ChangedRowsSince` に、見えるバージョンを書いた時刻を足したもの。ブランチの層ごとに上の層の時刻）で求め、時刻の時点と今の行を比べる。見張りの説明は `watchDescribe`（段階 33 の `watchNote.changes` を、テーブル定義から使えるようにした）。テーブルの選び方は `restoreSelection`（省くと `'*'`）。結果の列は、計画の `watch` を `detail` にした（最後の要約の行にも使うため）。復元の警告は `warnRestoreUsers`（restore.go）。既定の復元で選ばなかったテーブルのうち、見張りの種類がユーザーとユーザーのメタのものについて、変わった行を見張りの比べ方で調べ、`not restored` の行にする（件数はその変化の行の数）。復元はその行を書かず、ログに警告で出す。書いたテーブルがなければ取り消しの行を出さない。
- 結果: `TestChanges` で、一覧が乗っ取りの再現（`default_role`、ユーザーと administrator の付与）と普段の変更（記事の更新と削除、メタの追加）を、変わった列と時刻の順で返し、変えて戻した行は出ず、一時データ、`cron`、`_edit_lock` の 3 行は除いて数だけ出し、テーブルで絞れ、時刻の後に作ったテーブル、`ALTER` したテーブル、消したテーブルが 1 行になり、ブランチでは分岐の後のブランチの変更だけが見え、ブランチがない、今より先、ないテーブル、GC の境界より前の時刻はエラーになることを確かめた。既定の `heimdb_restore_preview` と `heimdb_restore` は、後から足された管理者を `not restored` として結果とログに出し、ユーザーは残す。`'*'` とテーブルの指定では出ない（除く処理と警告を外すと落ちる）。Go のテストは 326 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。本物の WordPress（compose、ローカルで作ったイメージ）で、管理画面での `users_can_register` と `default_role` の変更、wp-cli での管理者の追加、記事の作成の後、`heimdb_changes` がその流れを時刻の順に示し（見張りの説明付き、一時データなど 10 行は除外）、既定の復元で `default_role` が戻り、`wp_users` と `wp_usermeta` の `not restored` の行とログの警告が出て、管理者は残り、`'*'` での復元で管理者が消えた。バージョンを 0.1.4 にした（データ形式は 0.1.3 と同じ）。公開したイメージを取り込んで動かし、`heimdb_changes` が見張りの説明付きで変更を返し、サイト用のユーザーからは拒否されることを確かめた。

## 段階 35: WordPress が使わない全体の操作を塞ぐ（`SET GLOBAL` と processlist）

- 背景: 段階 14 で記録だけにした 2 つの go-mysql-server の穴を、サイト用のユーザー（段階 32）で確かめた。`SET GLOBAL`（`SET @@GLOBAL.x` も）は、読み取り専用の値（`secure_file_priv` など）以外すべて通り、その後に始まるすべての接続の既定になった。`autocommit=0` では新しい接続の書き込みがコミットされず（WordPress は `COMMIT` を送らないので、黙って失われる）、`sql_select_limit=1` では新しい接続の `SELECT` が 1 行しか返さず、`time_zone` では時刻の読み方が変わった（再起動で戻る。`SET PERSIST` はもともと使えない）。プラグインに SQL インジェクションの穴が 1 つあれば、サイトを壊し、データを黙って失わせられ、見張り（段階 33）にも出ない。`information_schema.processlist` は、権限のないユーザーにも root の実行中の文を見せた（ユーザーの列は、データベースを選ばずにつないだ接続では `unauthenticated user` のまま。go-mysql-server の `ProcessList.ConnectionReady` はデータベースを選んだときしか呼ばれない）。`SHOW PROCESSLIST` と `performance_schema` は拒否する。
- 本物の MySQL 8.0.46 で確かめた振る舞い: 権限のないユーザーの `SET GLOBAL`、`SET @@GLOBAL.x`、`SET PERSIST`、`SET @@PERSIST.x`、`SET SESSION a = …, GLOBAL b = …` はエラー 1227（`Access denied; you need (at least one of) the SUPER or SYSTEM_VARIABLES_ADMIN privilege(s) for this operation`）、`SET PERSIST_ONLY` はエラー 3630。読み取り専用の値（1238）とない名前（1193）は、権限より先にそのエラー。`PREPARE` は通り、実行で確かめる。processlist（`information_schema`、`SHOW PROCESSLIST`、`performance_schema`）は、PROCESS 権限がなければ自分のユーザーの接続だけが見える。
- 方針: MySQL に合わせる。解析のルールで、`SET` の全体の値（`GLOBAL`、`PERSIST`、`PERSIST_ONLY`）を、SUPER 権限のないユーザーならエラー 1227（`PERSIST_ONLY` は 3630）にする（ない名前と読み取り専用の値は、今のまま go-mysql-server のエラー）。`-no-auth` と root は今のまま。`information_schema.processlist` は、PROCESS 権限がなければ自分のユーザーの接続の行だけにし、ユーザーの列を HeimDB が覚えた接続のユーザーにする。`SHOW PROCESSLIST` は今のまま拒否する（WordPress は使わない）。
- 完了条件: Go のテストで、サイト用のユーザーの `SET GLOBAL` の各形（`PREPARE` の経路、1 つの `SET` に並べた形を含む）がエラー 1227 になって全体の値が変わらず、接続が切れず、`SET SESSION` と WordPress の接続の初めの文は通り、root は変えられる。processlist で、サイト用のユーザーには root の文が見えず、自分の接続は見え、root にはすべて見える。確認を外すと落ちる。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（compose）で、サイト用のユーザーでのインストール、記事の作成、プラグインの有効化が動く。
- 実装: `internal/backend/globals.go`。`setGlobalPrivilege`（解析の前のルール。`PREPARE` した文も実行のときに通る）は、`plan.Set` の `SetField` の左辺の `SystemVar` の範囲が `GLOBAL`、`PERSIST`、`PERSIST_ONLY` で、値があり読み取り専用でなければ、SUPER 権限（`MySQLDb.UserHasPrivileges`。認証が無効なら真）を確かめる。`processListPrivilege`（解析の後のルール。`information_schema.tables` の `tableRows` と同じ形）は、`information_schema.processlist` の表を包み、PROCESS 権限がなければ自分のユーザーの行だけを返し、ユーザーの列を `Provider.users`（`NewSession` で接続 ID とユーザーを覚え、`SessionEnd` で消す）の名前にする。
- 結果: `TestGlobalOperationsNeedPrivileges` で、サイト用のユーザーの `SET GLOBAL autocommit`、`SET @@GLOBAL.sql_select_limit`、`SET @@global.time_zone`、`SET PERSIST`、`SET @@PERSIST.x`、`SET SESSION … , GLOBAL …` がエラー 1227、`SET PERSIST_ONLY` が 3630 になり（文は MySQL と同じ）、ない名前と読み取り専用の値はそのエラーのまま、`PREPARE` は通って `EXECUTE` で 1227 になり、全体の値が変わらず、接続は切れず、`SET NAMES`、`SET SESSION sql_mode`、`SET time_zone` は使え、root は全体の値を変えられることを確かめた。processlist では、サイト用のユーザーには root の実行中の文が見えず自分の接続が見え、root にはデータベースを選ばずにつないだ接続も `root` の名前で見える（2 つのルールを外すと 11 か所で落ちる）。段階 14 の `TestReview14PrivilegeGaps`（穴があることを記録していた）は、ステージングのユーザーでも塞がっていることを確かめる形に直した。Go のテストは 327 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト（root でつなぐので主に退行の確認）。接続の切断と panic は 0。バージョンを 0.1.5 にした（データ形式は 0.1.4 と同じ）。公開したイメージを取り込んで動かし、サイト用のユーザーの `SET GLOBAL` がエラー 1227 になり、processlist にほかのユーザーの接続が出ず、root は全体の値を変えられることを確かめた。本物の WordPress（compose、ローカルで作ったイメージ）で、サイト用のユーザーでの画面からのインストール、ログイン、記事の作成の画面、プラグインの有効化（`hello.php`）、wp-cli での記事の作成が動いた。

## 段階 36: データ形式のバージョンの固定と、レプリケーションでのバージョンの確認

- 背景: ホスティングで本番に使い始めるにあたり、同期のレプリカを別のゾーンに置き、障害時は手動で昇格させる方針になった。レプリカは本番のコミットの中身（キーと値）をそのまま適用するが、本番とレプリカのデータ形式のバージョン（`m/format`、段階 18）を確かめていない。バージョンの違う HeimDB をつなぐと、黙って食い違う。また、文書は「開発中はデータ形式が予告なく変わる」としていて、本番に使う前提と合わない。
- 方針: レプリカは要求に自分の形式のバージョン（`format`）を付け、本番は違えば `409 Conflict`（`HeimDB: data format version differs (primary N, replica M)`）を返す。本番は応答のヘッダ `X-HeimDB-Format` に自分のバージョンを入れ、レプリカは違えば記録を適用せずに止まる（合言葉の誤りと同じく、やり直さず、エラーをログと `heimdb_status` に出す）。バージョンの印のない相手（0.1.5 以前）はバージョン 1 とみなす（それまでの形式はすべてバージョン 1）。形式はバージョン 1 で固定すると決め、変えうる要因（照合順序の重み、新しい型、go-mysql-server の更新）と、変えるときの決まり（バージョンを上げ、起動時の移行を入れる。インデックスだけなら行から作り直す）を「キーの設計」に書く。`operations.md` に HeimDB のバージョンを上げる手順（レプリカの有無、形式が同じか違うか、戻し方）を足し、README、`operations.md`、Docker Hub の説明文の「形式が予告なく変わる」を改める。
- 完了条件: Go のテストで、バージョンの違う本番とレプリカが両方の向きで止まって 1 件も適用せず、バージョンの印のない相手とはバージョン 1 として動き、確認を外すと落ちる。本物のバイナリで、今のバージョンどうしの同期のレプリカ、公開済みの 0.1.5 との新旧両方の向きの接続、バージョンを変えたバイナリでの停止を確かめる。PHPUnit はレプリケーションだけの変更なので流さない。
- 実装: `internal/replication/replication.go`。レプリカは要求の `format` に `store.FormatVersion` を付け、本番は合言葉と位置を確かめた後にバージョンを比べ、違えば `409` を返して `replica <名前>` の行にエラーを残す。本番はすべての応答に `X-HeimDB-Format` を付け、レプリカは記録を読む前に比べる（`409` とバージョンの違いは、合言葉の誤りと同じく、やり直さない停止）。示さない相手は `peerFormat` でバージョン 1 にする。テストのため、比べるバージョンはパッケージの変数 `formatVersion`。「キーの設計」に「データ形式のバージョン」の節を足し、作業ルールの「互換性は当面気にしない」を改めた。`operations.md` に「HeimDB のバージョンを上げる」を足し、README、`operations.md`、Docker Hub の説明文の「形式が予告なく変わる」を改めた。
- 結果: `TestFormatVersion` で、バージョン 2 のレプリカの要求を本番が `409`（`data format version differs (primary 1, replica 2)`）で拒否して本番の状態にそのエラーを出し、バージョンを示さない要求は受け付け、バージョン 2 を示す本番からはレプリカが 1 件も適用せずに止まって `replication_last_error` にエラーを出し、バージョンを示さない本番からは受け取ることを確かめた（本番の確認を外すと落ち、レプリカの確認を外すとレプリカが止まらずテストが終わらない）。Go のテストは 328 件（-race でも成功）。本物のバイナリで、今のバージョンどうしの同期のレプリカが動き（`replication_sync` が `sync`）、`FormatVersion` を 2 にしたバイナリは、レプリカでも本番でも相手が止まって行を適用しなかった。公開済みの 0.1.5 のイメージとは、0.1.5 の本番と新しいレプリカ、新しい本番と 0.1.5 のレプリカのどちらも同期で動いた。

## 段階 37: utf8mb3 の表を utf8mb4 として受け入れる

- 背景: ホスティングで許可リストの 24 のプラグインを HeimDB で動かしたところ、Yoast SEO（`wordpress-seo`）だけが落ちた。Yoast の移行の仕組み（Ruckusing）は `CREATE TABLE ... DEFAULT CHARSET=utf8`（utf8mb3）を固定で出し、段階 17 の確認（utf8mb4 以外を拒否）で表が作られず、Yoast がそのエラーを飲み込むので、後で `table not found` としてだけ出る。段階 17 の確認は、go-mysql-server が utf8mb3 や latin1 の列に表せない文字をそのまま入れてしまう事故を防ぐためのもので、utf8mb3 を utf8mb4 として持てば、その事故は起きない（utf8mb4 は utf8mb3 を含む）。
- 方針: utf8mb3（別名 `utf8`）の照合順序は、名前の文字コードの部分だけを utf8mb4 に替えた照合順序（`utf8mb3_general_ci` は `utf8mb4_general_ci`、`utf8mb3_bin` は `utf8mb4_bin`、`utf8mb3_unicode_ci` は `utf8mb4_unicode_ci`）として保存する。比較の意味は MySQL の utf8mb3 と同じ（基本多言語面の文字の重みが同じ）。対応する utf8mb4 の照合順序がないもの（`utf8mb3_general_mysql500_ci`、`utf8mb3_tolower_ci`）と、latin1 などほかの文字コードは、これまでどおり拒否する（バイトの意味が変わる）。読み替えは `schema.MapUTF8MB3` に置き、テーブルの定義を作るところ（`FromSQL` と `ColumnFromSQL`。テーブルの作成、列の追加と変更の書き直し）と、既定の照合順序の変更（`ModifyDefaultCollation`）から呼ぶ。読み替えたら警告（`SHOW WARNINGS`）とログに出す。`SHOW CREATE TABLE` とダンプには utf8mb4 の照合順序が出る（MySQL は utf8mb3。意図した差）。依頼は Yoast が後で出す `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_520_ci` のため `utf8mb4_unicode_520_ci` に寄せることを勧めていたが、go-mysql-server v0.20.0 の `CONVERT TO` は既定の照合順序の変更（`ModifyDefaultCollation`）になり、列の照合順序を確かめる `ModifyStoredCollation` は呼ばれないので、どの読み替えでも通る（レビュー（Fable）で確かめた）。`unicode_520_ci` に寄せると、既存のサイトの utf8mb3 のプラグインの表をダンプから取り込んだときに比較の意味が黙って変わる（`は` と `ば` が等しくなる）ので、名前どおりにする。
- 完了条件: Go のテストで、Yoast の 6 本の `CREATE TABLE` と後の `CONVERT TO`、utf8mb3 の各照合順序の列（`general_ci`、`bin`、`unicode_ci`）、utf8mb4 の表の中の `CHARACTER SET utf8` の列、`ALTER ... DEFAULT CHARSET=utf8` の後に文字コードを書かずに足した列、`ALTER ... MODIFY ... CHARACTER SET utf8`、MySQL のダンプの形（`DEFAULT CHARSET=utf8mb3 COLLATE=utf8mb3_general_ci`、データ付き）が通って utf8mb4 の照合順序になり、警告が出る。latin1、ascii、対応のない utf8mb3 の照合順序は拒否のまま。
- 実装: `schema.MapUTF8MB3`（名前の `utf8mb3` を `utf8mb4` に替えて `sql.ParseCollation` で引く）を、`FromSQL`（テーブルの既定）、`ColumnFromSQL`（文字列、ENUM、SET の列。`WithNewCollation` で型を作り直してから文字列にする）、`ModifyDefaultCollation` から呼ぶ。`checkCharset` は、対応のある utf8mb3 を通す。警告は `warnUTF8MB3`（3719。テーブルの作成、列の追加と変更の書き直し、`ModifyColumn`、`ModifyDefaultCollation` の成功の後）で、ログにも出す。
- 結果: ホスティング側の `verify-plugin.sh` を、このバージョンのイメージと `-debug` で Yoast に回し、Yoast が出す 6 本の `CREATE TABLE` を取った。文字列の主キーの `wp_yoast_expiring_store`（段階 38）を除く 5 本が通って移行が 27 件まで進み、後で Yoast が出す `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_520_ci`（4 本）も通った。`TestUTF8MB3StoredAsUTF8MB4` で、その 5 本が警告付きで `utf8mb4_general_ci` になり、`CONVERT TO` と挿入が通り、`utf8mb3_general_ci`、`utf8_bin`、`utf8mb3_unicode_ci` の列が名前どおりの utf8mb4 になって比較の意味（`は` と `ば` を区別する、`bin` は大小を区別する）が変わらず、列の追加と変更、既定の照合順序の変更（直後の `TABLE_COLLATION` も確かめる）、その後に文字コードを書かずに足した列が utf8mb4 になり、書き直しの後も値が残り、mysqldump の形（`DEFAULT CHARSET=utf8mb3 COLLATE=utf8mb3_general_ci`、一意キー、データ付き）が取り込めて大小だけ違う値が重複のエラーになり、`SHOW CREATE TABLE` に utf8mb3 が出ず、latin1、ascii、`utf8mb3_tolower_ci`、`utf8_general_mysql500_ci` は拒否されることを確かめた（列の読み替えを外すと 4 か所、既定の照合順序の読み替えを外すと 1 か所で落ちる）。段階 17 の拒否のテスト（`dump_test.go`、`review17_test.go`）から utf8mb3 を外し、対応のない utf8mb3 の照合順序を拒否の例にした。Go のテストは 329 件（-race でも成功）。PHPUnit は段階 38 と合わせて流す。
- 記録だけ: `ALTER TABLE ... CONVERT TO CHARACTER SET` は、go-mysql-server v0.20.0 では既定の照合順序だけを変え、列の照合順序を変えない（MySQL は列も変える）。前からの差（`ModifyStoredCollation` は呼ばれない）。

## 段階 38: 1 列の文字列の主キー

- 背景: Yoast SEO の `wp_yoast_expiring_store`（2026-03-25 の移行で作る）は `key_name varchar(255)` を主キーにする。HeimDB は整数の主キーだけに対応していたので、表が作られず、Yoast を使うサイトは本番のダンプの取り込みでも落ちる。
- 方針: 主キーが 1 列の `CHAR` か `VARCHAR`（utf8mb4 の照合順序。utf8mb3 は段階 37 で utf8mb4 になる）なら受け入れる。複数列の文字列の主キー、`TEXT`、`ENUM`、前方の長さを付けた主キーは、これまでどおり明示的なエラー。キーは、インデックスの文字列のキーと同じく、文字ごとの照合順序の重み（`0x01` と 4 バイト）を並べて `0x00` で終える（主キーは NULL にならないので NULL の印は付けない）。キーのバイト順は照合順序の順と一致し、前方の一致で取り違えない。元の値は行に持つ。照合順序で等しい値（`_ci` の大小の違い）は同じ主キーで、重複のエラーになる（MySQL と同じ）。インデックスのエントリのキーから主キーを取り出すところ（`pkOfEntry`）は、整数の主キーを 1 列 9 バイトとしていたので、文字列の主キーのときはインデックスの列を前から読み飛ばして残りを主キーにする（後ろからは、前の列のバイトと区別できない）。値から主キーを作る `AppendPKValue` は型を受け取る。差分、マージ、復元、変更の一覧、GC、ブランチの重ね合わせ、レプリケーションは、主キーをバイト列として扱うので変えない。データ形式のバージョンを 2 にする（段階 36 の決まりの最初の適用）。0.1.5 以前は、文字列の主キーの表のインデックスで主キーを 9 バイトと読み違えるため。バージョン 1 のデータは変換なしでバージョン 2 として読め、起動時に `m/format` を 2 に書き換える（書き換えないと、古い HeimDB に戻したときに開けてしまう。バージョンの番号はマシンごとでレプリカに送られないので、表があるときだけバージョン 2 にする方法はとらない）。レプリカは段階 36 の確認で、0.1.5 以前（バージョンを示さない＝バージョン 1）とはつながらない。残る差: PAD SPACE の照合順序（`utf8mb4_unicode_520_ci`、`utf8mb4_general_ci`）では、MySQL は `'a'` と `'a '` を同じ主キーとみなすが、HeimDB は区別する（インデックスと同じ既知の差。HeimDB の既定の `utf8mb4_0900_ai_ci` は NO PAD で MySQL と同じ）。
- 完了条件: 並び順の性質のテストで、ランダムな文字列のキーのバイト順と照合順序の比較が `utf8mb4_0900_ai_ci`、`utf8mb4_unicode_520_ci`、`utf8mb4_general_ci`、`utf8mb4_bin` で一致し、前方が一致しない。Go のテストで、Yoast の `wp_yoast_expiring_store` の形の作成、挿入、主キーでの読み出し（大小の違う値でも見つかる）、`IN`、範囲、`LIKE 'abc%'`、`ORDER BY ... DESC LIMIT`、結合、大小だけを変える更新、削除、大小だけ違う値の重複のエラー、空文字列の主キー、二次インデックスのある表の読み出し、`AS OF` と GC、統計、ブランチの変更の差分とマージ、復元、`heimdb_changes`、mysqldump の往復、レプリケーション、バージョン 1 のデータがバージョン 2 になること、拒否する主キーの形のエラーを確かめる。ホスティング側の `verify-plugin.sh` で許可リストの 24 本が通り、Yoast の表がすべてできる。PHPUnit の全テストで差が 43 から増えない。公開済みの 0.1.5 がバージョン 2 のデータを拒否する。
- 実装: `rowenc.appendTextKey`（インデックスの文字列のキーの符号化を切り出した）を、`EncodePK` と `AppendPKValue`（型を受け取るようにした）が文字列の主キーに使う。`rowenc.StringPKType` で主キーに使える型を決め、`validateSchema` は整数か 1 列の文字列だけを通す。`Table.pkOfEntry` は、文字列の主キーの表では `rowenc.SkipIndexValue` でインデックスの列を前から読み飛ばす（一意の検査と走査の両方）。前方の長さを付けた主キーは go-mysql-server が長さを捨てて渡すので、構文解析の直後の `checkPrimaryKeyPrefix` で拒否する。`store.FormatVersion` を 2 にし、`checkFormat` は古いバージョンのデータを開いたら番号を書き換える。レプリケーションのバージョンの確認（段階 36）はそのまま効き、バージョンを示さない 0.1.5 以前とはつながらない。
- 結果: `TestStringPKOrder`（4 つの照合順序とランダムな文字列で、キーの順序が照合順序の比較と一致し、違うキーが前方で一致しない。NULL と壊れた UTF-8 はエラー）、`TestSkipIndexValue`、`TestStringPrimaryKey`（Yoast の `CREATE TABLE` そのまま、大小の違う値での検索、大小だけ違う値の重複のエラーと `ON DUPLICATE KEY UPDATE`、空文字列、`IN`、範囲、`BETWEEN`、`LIKE`、`ORDER BY ... DESC LIMIT`、二次インデックスと一意インデックスでの読み出しと重複の検査、結合、大小だけを変える更新、主キーの変更、削除、`AS OF`、`ANALYZE TABLE`、ブランチの差分（`k=abc`、`k=branch`）とマージ、`heimdb_changes`、復元、前方の長さ付きの主キーの拒否）、`TestNonIntegerPrimaryKeyRejected`（拒否する形）、`store.TestFormatVersion`（バージョン 1 のデータがバージョン 2 になる）、レプリケーションの `TestFormatVersion`（バージョンを基準にした書き方に直し、バージョンを示さない相手とつながらないことを確かめる）を足した（前から読む取り出しを外すと「index v of s points to a missing row」、バージョンの書き換えを外すとバージョン 1 のままで落ちる）。Go のテストは 332 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。本物のバイナリで、文字列の主キーの表（Yoast の形と二次インデックス）が同期のレプリカに写って主キーとインデックスで読め、mysqldump で書き出して消して戻すと元に戻った。公開済みの 0.1.5 は、バージョン 2 のデータを「newer heimdb」のエラーで開かなかった。ホスティング側の `verify-plugin.sh` を、このバージョンのイメージで許可リストの 24 本に回して、すべて通った。Yoast は `-debug` のログで、6 つの表がすべてでき（`wp_yoast_expiring_store` を含む）、移行が `20260325155530`（文字列の主キーの表を作る移行）を含めて 27 件記録され、作る前の存在の確認のほかにエラーがないことを確かめた。段階 37 と 38 を合わせて 0.1.6 として公開した（データ形式はバージョン 2）。公開したイメージを取り込んで動かし、サイト用のユーザーで Yoast の `wp_yoast_expiring_store` を作れて（utf8mb3 の警告 3719 が出る）、大小の違う値で読めることを確かめ、ホスティング側の `verify-plugin.sh` を既定の `latest` で Yoast に回して 6 つの表と 27 件の移行を確かめた。ホスティング側の依頼の文書は、解決したので消した（段階 36 のコミットに誤って入っていた）。

## 段階 39: 履歴のあるサイトの形のスキーマのテストと、運用の注意

- 背景: ホスティング側から、段階A の一時 DB を 0.1.6 の HeimDB にして本番と同じ経路で動かせた（2 サイトが自動合格）という報告と、3 サイト目の取り込みが主キーのない 2 つの表（`wp_xsg_sitemap_meta`、古い Yoast の `wp_yoast_seo_meta`）で止まり、どちらも使われていないプラグインの置き忘れだったという報告があった。新しく入れた WordPress での検査では、履歴のある本番のデータにだけある形（古いプラグインの表、utf8mb3、主キーのない表）を見つけられない。あわせて、データディレクトリの所有者（HeimDB は UID 65532 で動く）と、TLS なしの HeimDB に TLS を求めるクライアントがつながらないことを、文書にあると親切という報告があった。
- 方針: 履歴のあるサイトの mysqldump の形のスキーマ（MySQL 8.0 の mysqldump の書き方、utf8mb3 と utf8mb4 の照合順序が混ざった表、MyISAM、前方の長さ付きのインデックス、`0000-00-00` の既定値、古いプラグインの表、主キーのない表、文字列の主キーの表）を `internal/testdata/legacy_dump.sql` に置き、文ごとに受け入れるか拒否するか（とエラーの文）を確かめる。拒否する文は直前の `-- expect error:` の行で示す。InnoDB と同じく NOT NULL の一意インデックスを主キーとみなす提案は、見送って記録だけにする（`SHOW CREATE TABLE` とダンプには元の `UNIQUE KEY` を出す必要があり、主キーとして持つのに主キーとして見せない食い違いを抱える。ホスティング側も今の拒否で困らず、置き忘れに気づけるほうがよいとしている）。`operations.md` と Docker Hub の説明文に、バインドマウントのデータディレクトリの所有者（`chown 65532:65532`）を、`operations.md` の TLS の節に、TLS なしで動かすときはクライアントに TLS を求めさせない（mysql2 の `ssl` など）ことを書く。
- 完了条件: Go のテストで、そのダンプの受け入れる文がすべて通って行数とスキーマ（照合順序、インデックス）が合い、拒否する文が明示的なエラーになって接続が切れない。
- 結果: `internal/testdata/legacy_dump.sql`（MySQL 8.0.46 の mysqldump の形。utf8mb3 の `wp_options`、MyISAM で `meta_key(191)` の `wp_postmeta`、`0000-00-00` の既定値と表示幅付きの整数の `wp_posts`、utf8mb3_unicode_ci の古い Yoast の `wp_yoast_seo_links`、主キーのない `wp_yoast_seo_meta` と `wp_xsg_sitemap_meta`（ホスティングの 3 サイト目の実物の定義）、latin1 の古いプラグインの表、文字列の主キーの `wp_yoast_expiring_store`）と `TestLegacyDump` を足した。受け入れる文がすべて通って行数、大小を無視した検索、照合順序（`utf8mb4_general_ci`、`utf8mb4_unicode_ci`）、前方の長さ（191）、AUTO_INCREMENT が合い、拒否する 7 文（主キーのない 2 表、latin1 の表、作られなかった表への `LOCK TABLES` と `INSERT`）が明示的なエラーになり、接続は切れなかった。日時のゼロの値を `CAST` で読むと `0000-01-01` になるのは、段階 21 で記録した go-mysql-server の差（列をそのまま読めば同じ）。Go のテストは 333 件（-race でも成功）。`operations.md` の Docker と TLS の節、Docker Hub の説明文（英語と日本語）に注意を足した（TLS を必須にした mysql クライアントのエラーの文は、実際に確かめた）。
