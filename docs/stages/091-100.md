# 段階 91〜100

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 91: MySQL との互換を PHP（wpdb）から確かめるテスト集

- 背景: これまでの MySQL との比べは、Go のゴールデン（Go のドライバを通すので、`SET NAMES` の有無や double の字の形、mysqli が返す字が見えない。段階 88、90）と、PHPUnit の全体（30 分。テストが落ちない違いを見ない）だった。ホスティング側は、MySQL 側のクライアントが latin1 で接続していたのに気づかず、照合順序の違いと取り違えた（段階 90）。ユーザーの案で、WordPress と同じ接続で MySQL との違いを見るテスト集を作る。回帰テストに使い、ほかの人が WordPress 互換の DB を作るときにも使えるようにする。
- 方針: wordpress-develop のテストの仕組み（`WP_UnitTestCase`）の上に、期待値を書かず、観察した値（mysqli が返す字、エラーの文と番号と SQLSTATE、`rows_affected`、`insert_id`、`SHOW WARNINGS`）を JSON に記録するテストを置く（`compat/`）。同じテストを本物の MySQL と HeimDB に流し、`cmd/compatdiff` で並べる。最初に接続の文字セットと照合順序と `sql_mode` を確かめ、WordPress と違えば止める。中身は、これまで見つかった違い（文字列から数、double の字、DECIMAL、文字列の列と数の比べ、日本語の照合順序、複数の表の DELETE、警告とエラー、書いた行の数と ID、WP_Query の並び、主キーのない表、サイトヘルス）。`compat/` は GPL-2.0-or-later（WordPress のテストの仕組みの上に作るため）で、Go のモジュールにもイメージにも入らない。HeimDB は変えない。
- 計画のレビュー（Fable）で変えたこと: WordPress のテストはテストごとにトランザクションで包み、`CREATE TABLE` を一時テーブルに書き換えるので、表は `set_up_before_class` で作る。wpdb は `sql_mode` を決めず、サーバの値から外すだけなので、確かめは「wpdb が外すものが残っていない」にし、値そのものは記録する（MySQL と HeimDB の既定の違いが出る）。HeimDB は `CREATE DATABASE` をしないので、`-db heimdb_compat` で起動し、テストの設定（`compat/wp-tests-config.php`）でデータベースの名前を環境変数から決める。コンテナに wordpress-develop と `compat/` の両方をマウントする（`scripts/compat/run.sh`）。`wp_terms` に一意インデックスはないので、「あ」のある所に「ア」のタグを作る形（WordPress は `term_exists` で拒否する）と、一意インデックスの表の 1062 を分けて記録する。ID は差で記録し、ベースラインは 2 回流して同じになることを確かめる。
- 完了条件: 本物の MySQL 8.0 と HeimDB 0.2.31 に流して、違いが、理由を書いた知っている違いだけになる。古い HeimDB（0.2.26 のイメージ）に流すと、段階 85〜90 で直した違い（double の字、DECIMAL、文字列の列と数の比べ、DELETE の行の数、重なりのエラーの字など）が出る。接続の文字セットを変える（latin1）と、最初の確かめで止まる。本物の MySQL と HeimDB のどちらも、2 回流して記録が同じ。1 回が数秒で終わる。Go のテストが通る（HeimDB は変えないので、PHPUnit は段階 90 の結果のまま）。
- 実装後のレビュー（Fable）で直したこと: insert_id を、表の最大ではなく同じテストの最初の行の ID との差で記録する（前のテストが使った番号が飛ぶので、流す順で変わっていた）。`found_posts` をテストの記事だけで数える（WordPress が入れる記事が、ほかのクラスの後片付けで消えるかどうかが順で変わる）。期限切れの transient を消す前に、もとからあるものを消す。文字列の式の `GROUP BY` と、式の照合順序も記録する（知っている違いの理由に書いたことを測る）。同じ名前の列で値が欠けたら止める。`run.sh` は、出力のファイルをホストのユーザーのものにし、`mysql` のコマンドがなければ知らせる。
- 結果: テストは 5 つのクラスの 20 で、77 の記録。本物の MySQL 8.0.46 と HeimDB 0.2.31 のどちらも、2 回流しても逆の順で流しても記録が同じで、1 回は 4〜5 秒。違いは 13 で、すべて `compat/known-differences.txt` に理由を書いた（下の記録だけ）。古い 0.2.26 のイメージでは 40 の違いが出て、段階 85〜90 で直したもの（double の字、`DECIMAL`、文字列の列と数の比べ、複数の表の DELETE の行の数、重なりのエラーの字、INSERT IGNORE の警告、strict でない数の書き込み）がすべて含まれた。本物の MySQL に latin1 でつなぐと、最初の確かめで止まった（終了コード 2。HeimDB は latin1 の表を作らないので、WordPress の入れ直しで止まる）。Go のテストは 472 件（-race でも成功。`cmd/compatdiff` のテスト 2 件を足した）。HeimDB は変えていないので、PHPUnit は段階 90 の結果（26,475 件で差は 35 件）のまま。
- 記録だけ（このテスト集で見つけた、HeimDB と MySQL の違い。どれも以前から）: (a) strict でない書き込みで、列より長い文字列と範囲の外の整数を、MySQL は切って（端の値にして）警告 1265、1264 で入れるが、HeimDB はエラー 1105 で入れない。WordPress は strict を外して接続するので、プラグインの書き込みが MySQL では通り、HeimDB では失敗しうる。(b) 失敗した文の後の `SHOW WARNINGS` に、MySQL はそのエラーを出す。HeimDB は出さず、前の文の警告を残すことがある。(c) 文字列の式の `DISTINCT` と `GROUP BY` で、照合順序で等しい値をまとめない。(d) unicode_520_ci の PAD SPACE と `'ß' = 'ss'`。(e) サーバの既定の `sql_mode`（wpdb が外した後、MySQL は `NO_ZERO_IN_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`、HeimDB は `NO_ENGINE_SUBSTITUTION`）。(f) `VALUES()` の非推奨の警告 1287、日付の 0 の警告の文。

## 段階 92: strict でない書き込みで、列に収まらない値を MySQL と同じく直して入れる

- 背景: 段階 91 のテスト集で見つけた違い (a)。WordPress は strict を外して接続する。そのとき MySQL は、列より長い文字列を切って警告 1265 で、範囲の外の数を型の端の値にして警告 1264 で入れるが、HeimDB はエラー 1105 で入れなかった（段階 21 で「全テストで見つかっていない」として対象外にしたもの）。プラグインの書き込みが MySQL では通り、HeimDB では失敗しうる。`INSERT IGNORE` と `UPDATE IGNORE` は、STRICT でも MySQL が同じように直すが、HeimDB（go-mysql-server）は、UNSIGNED の -1 を 4294967295、DECIMAL を 0.00 にし、文字列をバイトで切り（文字の途中で切りうる）、警告を Note 1105 の別の字にしていた。
- 方針: 段階 21 と 85 の `internal/backend/nonstrict.go` の `fixValue` に、文字列の切り詰め（`fixString`）と範囲の外の数（`fixNumber` に足す）を加える。go-mysql-server が値を確かめる前に直すので、エンジンは変えない。`INSERT IGNORE` と `UPDATE IGNORE` は、非 STRICT の複数行の INSERT と同じ扱いにする。
- 計画のレビュー（Fable）で変えたこと: DECIMAL の範囲の外は go-mysql-server の Convert が値を返さず、UNSIGNED の負の数は回り込むので、端の値は自分で決める。`'99999999999abc'` のように、後ろが数でなく範囲の外の値は 1264 だけにする（DECIMAL だけ Note 1265 の後に 1264）。長さの数え方は go-mysql-server の `ConvertToBytes` と同じ分け方にする（TEXT はバイト、1 文字が 1 バイトの文字セットはバイト、それ以外は文字）。文字列でない値は go-mysql-server と同じ字にしてから切る。IGNORE は長さと範囲だけでなく全部を通す（go-mysql-server の `convertDataAndWarn` は `[]byte` の値で panic しうる）。ON DUPLICATE KEY UPDATE の警告の行の番号を MySQL で確かめる。
- 完了条件: 本物の MySQL で作ったゴールデン（`stage92_golden.txt`）と、値、警告の Level、番号、文、行の番号が同じになる。互換のテスト集で、思わぬ違いが 0 になる。直しを 1 つずつ外すと、対応するテストが落ちる。Go のテスト（-race も）が通り、PHPUnit の全テストで差が 35 件のまま。データ形式は変えない。
- MySQL 8.0.46 で確かめた振る舞い: 長すぎる文字列は、`CHAR` と `VARCHAR` は文字の数で、`TEXT` 系は文字の境目でバイトの上限まで、バイナリはバイトで切り、警告 1265 `Data truncated for column 'x' at row N`。切ったのが末尾の空白類（空白、タブ、改行など）だけなら Note（バイナリは Warning、`CHAR` は警告なしで、末尾の空白を除いた値）。範囲の外の整数、`DECIMAL`、`FLOAT`、`DOUBLE` は、入れようとした値の符号で型の端の値と警告 1264 `Out of range value for column 'x' at row N`（整数は丸めてから、DECIMAL は小数の桁に丸めてから比べる。UNSIGNED には、丸めると 0 になる -0.4 も範囲の外）。DECIMAL の小数の桁より細かい値は、丸めて Note 1265。警告は行ごとに、行の中は INSERT に書いた列の順で出る。ON DUPLICATE KEY UPDATE の警告の行の番号は、INSERT の何行目か。`INSERT IGNORE` と `UPDATE IGNORE` は、STRICT でも、非 STRICT の複数行の INSERT と同じ値と警告（単一行の NULL も警告 1048 と型の既定値、省いた列は 1364）。
- 実装後のレビュー（Fable）で直したこと: go-mysql-server の Convert は、UNSIGNED の整数の列への float の 0 や 2^31 以上を範囲の外とし（3e9 がエラーになった）、DECIMAL の値は上限を超えても範囲の中とする（`5000000000.0` が警告なしに端の値になった）ので、この 2 つは自分で端と比べる。指数が 10000 を超える文字列（`'1e99999'`）を shopspring/decimal が読めず、DOUBLE に +Inf が入ったので、double として読んで端の外とする。`CHAR` の切り詰めを MySQL に合わせ、DECIMAL の丸めの確かめを、小数の桁を字で数えてから行う（WooCommerce の `DECIMAL(19,4)` の列への書き込みが、値ごとに丸めて比べないように）。ゴールデンに、`add_option` と同じ形の `ON DUPLICATE KEY UPDATE v = VALUES(v)` と、単一行の `INSERT IGNORE` の NULL と省いた列を足した。
- 結果: `fixString` と、範囲の外を扱う `fixNumber`（`numberBounds`、`numberValue`、`boundValue`）を足し、IGNORE の文を非 STRICT と同じに包み、ON DUPLICATE KEY UPDATE の右辺に INSERT の行の番号を渡し（`rowCounter`）、値を直す列の順を INSERT に書いた列の順にした（`columnOrder`）。ゴールデンは本物の MySQL と同じ（`VALUES()` の非推奨の警告 1287 の行だけ除いて比べる。段階 91 の記録の (f)）。段階 21 のテストの、行の中の警告の順の期待（表の列の順）が誤っていたので、MySQL で確かめた順に直した。互換のテスト集に、日本語の切り詰め、末尾の空白、`CHAR`、UNSIGNED の負の数、DECIMAL の端と丸め、`UPDATE`、`INSERT IGNORE`、`wpdb::insert`（列の長さを自分で確かめ、長すぎる値は送らずに失敗する）の記録を足した（82 の記録）。思わぬ違いは 0 で、知っている違いは 11（直った 3 つを消し、下の (a) を足した）。MySQL も HeimDB も、2 回流して記録が同じ。直しを 1 つずつ外すと（16 とおり）、どれもテストが落ちる。Go のテストは 475 件で、-race でも通り、エンジンのテストも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 90 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。
- 記録だけ: (a) `UPDATE` の警告の行の番号は、MySQL は読んだ行の番号（索引で絞らなければ表の何行目か）、HeimDB は書き換えた行の何番目か（段階 21 から。`compat/known-differences.txt`）。(b) STRICT のエラーは 1105 のまま（MySQL は 1406（22001）`Data too long for column ...` と 1264（22003））。末尾の空白だけが余る値も、STRICT では HeimDB はエラー（MySQL は Note で入れる）。(c) `ENUM` と `SET` の正しくない値（MySQL は `''` と 1265）。(d) `VARCHAR(2)` への 1.5e10（MySQL は `'2e'`。数の字の形が違う）。(e) 整数の列への `[]byte`（`X'FFFFFFFFFF'`）は直さない。WordPress のコアは、どれも使わない。

## 段階 93: 失敗した文の後の `SHOW WARNINGS`、照合順序で等しい値の扱い、`sql_mode` の既定

- 背景: 段階 91 のテスト集で見つけた違いのうち、小さなもの 3 つ。(1) 失敗した文の後の `SHOW WARNINGS` に、MySQL はエラーを `Error` の行として出すが、HeimDB は出さず、構文の誤りなど計画の前に失敗すると前の文の警告を出した。(2) 文字列の式（`LEFT`、`SUBSTRING_INDEX`）の `DISTINCT` と `GROUP BY` が、照合順序で等しい値（`utf8mb4_unicode_520_ci` の `a`、`A`、`ａ`）を一つにしない。調べると、列そのものの `DISTINCT`、`COUNT(DISTINCT)`、`GROUP_CONCAT(DISTINCT)`、`UNION`、文字列の列のハッシュ結合（`JOIN ... ON a.s = b.s` が `b` と `B` を結ばない）も同じだった。値をまとめるハッシュが字そのものを見ていたため（列の `GROUP BY` だけは照合順序を見ていた）。式は、結果の型の照合順序が既定（`utf8mb4_0900_bin`）で、式の `ORDER BY` も `A, B, a, b` の順だった。(3) サーバの既定の `sql_mode` が MySQL と違い、並びもアルファベット順だった
- 方針: (1) 文の終わりにエラーの行を足し、文の警告を消す前に失敗したら前の文の警告を消す（`server/handler.go`）。(2) 値の等しさでまとめるハッシュを、文字列は照合順序の重みで取る（`sql.HashOfTypes`）。文字列の関数の結果の型に、引数の照合順序を付ける。PAD SPACE（`'b '` = `'b'`）はデータ形式に関わるので扱わない。(3) 既定を MySQL 8.0 と同じにし、MySQL と同じ順に並べる。どれもエンジンの変更（`docs/engine.md` の段階 93）で、データ形式は変えない
- 計画のレビュー（Fable）で変えたこと: 掃除とエラーの行は `doQuery` の 1 か所にまとめる（構文解析は handler で、engine に入る前に失敗する）。エラーの行は警告の上限（1024）を超えても残す。ハッシュの照合順序は、並べ替えや `OrderedDistinct` が使う `Type()` の照合順序に揃える（`GetCoercibility` を使わない）。行そのものを見分けるハッシュ（`plan.Concat`、FULL OUTER JOIN、UPDATE、DELETE）は変えない。`COUNT(DISTINCT)` の値の区切りを `,` から NUL にする（`('a,b', 'c')` と `('a', 'b,c')` が同じになっていた）。`LEFT` などは、引数が文字列のときだけ引数の型を返す。`SqlMode` の字（`SHOW CREATE TRIGGER` などに出る）もアルファベット順に並べ直さない
- 完了条件: 本物の MySQL で作ったゴールデン（`stage93_golden.txt`）と同じになる。互換のテスト集で、思わぬ違いが 0 になり、知っている違いが 11 から 4 に減る。直しを 1 つずつ外すと、対応するテストが落ちる。Go のテスト（-race も）が通り、PHPUnit の全テストで差が 35 件のまま
- MySQL 8.0.46 で確かめた振る舞い: 文が失敗すると、警告を消してからエラーを `Error` の行として足す。失敗する前に出た警告は残る（複数行の INSERT で `Warning 1265` の後に `Error 1062`）。構文の誤りと列名の誤りも同じ。`SHOW WARNINGS` は消さない。照合順序で等しい値は、`DISTINCT`、`COUNT(DISTINCT)`、`GROUP_CONCAT(DISTINCT)`、`UNION`、`INTERSECT`、`EXCEPT`、再帰の CTE の `UNION`、結合、`IN (SELECT ...)`、`PARTITION BY` で一つになる（残るのは最初に読んだ値）。文字列の関数（`LEFT`、`RIGHT`、`SUBSTRING`、`SUBSTRING_INDEX`、`CONCAT`、`CONCAT_WS`、`REPLACE`、`LPAD`、`RPAD`、`REPEAT`、`REVERSE`、`TRIM`、`LOWER`、`IF`、`IFNULL`、`COALESCE`）の結果は引数の照合順序で、バイナリの引数があればバイナリ。`LEFT(123, 2)` は `'12'`。`LPAD` と `RPAD` は文字の数で数える。既定の `sql_mode` は `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` で、値は決まった順（`REAL_AS_FLOAT`、`PIPES_AS_CONCAT`、`ANSI_QUOTES`、`IGNORE_SPACE`、`ONLY_FULL_GROUP_BY`、…）に並ぶ
- 実装後のレビュー（Fable）で直したこと: ハッシュ結合の複数の列のキー（`ON a.w = b.w AND a.n = b.n`）も照合順序の重みでハッシュする（1 列のキーだけ直していた）。文字列の型の式に文字列でない値が来るとき（`IF(id = 1, w, n)` は枝の値を変換しない）、型の字にしてから重みを取る（`'1'` と `1` が別の値になり、段階 92 より悪くなっていた）。`LPAD` と `RPAD` の負の長さは NULL（MySQL と同じ）。ゴールデンにこの 3 つを足した
- 結果: 失敗した文の後の `SHOW WARNINGS`、照合順序で等しい値（列と式の `DISTINCT`、`COUNT(DISTINCT)`、`GROUP_CONCAT(DISTINCT)`、`GROUP BY`、`ORDER BY`、集合演算、再帰の CTE、結合、`IN (SELECT ...)`、`PARTITION BY`）、文字列の関数の照合順序、`sql_mode` の既定と並びが、本物の MySQL 8.0.46 のゴールデンと同じになった。作る途中で、`LEFT(123, 2)` がエラーになり、`LPAD` と `RPAD` が日本語で失敗することもわかったので直した。段階 15 から記録だけにしていた、構文解析の警告が 2 つ以上だと MySQL と逆の順になる違いも、警告を残す処理を直して消えた（`TestReview15PlanWarningsOrder` を、MySQL の順を確かめる形にした）。互換のテスト集は、思わぬ違いが 0 で、知っている違いは 11 から 4 に減った。`distinct` の記録は、等しい値のうちどれが残るかが読む順で変わる（MySQL は `v` の一意インデックスを読む）ので、数を記録する形にし、ベースラインを取り直した（MySQL も HeimDB も 2 回流して同じ）。直しを 1 つずつ外すと（23 とおり）、どれもテストが落ちる。Go のテストは 478 件で、-race でも通り、エンジンのテストも通った（既定の `sql_mode` の字と並び、数の引数の `LEFT`、負の長さの `LPAD` の期待を直した）。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 92 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0
- 記録だけ: (a) `DISTINCT` と `GROUP BY` で等しい値のうちどれが残るかは、読む順で決まり、MySQL と違うことがある（MySQL はインデックスを読むことがある）。(b) `COLLATION()` が、文字列とバイナリを混ぜた式（`CONCAT(w, b)`）で HeimDB は文字列の照合順序、数の引数の `LEFT(id, 1)` で `binary` を返す（MySQL は `binary` と接続の照合順序）。値と並びは同じ。(c) `@@warning_count`、`@@error_count`、`SHOW ERRORS`、`SHOW COUNT(*) WARNINGS` はエラー。バイナリのプロトコルの PREPARE（`COM_STMT_PREPARE`）の失敗は Error の行にならない。WordPress はどれも使わない。(d) 既定に入る `NO_ZERO_DATE`、`NO_ZERO_IN_DATE`、`ERROR_FOR_DIVISION_BY_ZERO` は見える値だけで、効き目はない（前も同じ。WordPress は `NO_ZERO_DATE` を外す）。`TRADITIONAL` と `ANSI` は、MySQL と違って中身の値に開かない。(e) `CONCAT` などの `Type()` は、呼ぶたびに型を作る（共有の状態はない）

### エンジンの変更

- 失敗した文のエラーを、`SHOW WARNINGS` に `Error` の行として出す（`server/handler.go` の `doQuery`。接続先に返すのと同じ番号と文）。文の警告を消す前に失敗した（構文解析や計画のエラー）ときは、前の文の警告を消してから足す（`sql/base_session.go` の `BeginStatementWarnings`、`WarningsCleared`）。エラーの行は、覚える警告の上限（1024）を超えても覚える
  - 理由: 互換。MySQL は失敗した文の後の `SHOW WARNINGS` にエラーを出す。前は出さず、構文の誤りの後は前の文の警告を出していた

  - 理由: 正しさ。前は警告を写して消してから足し直していたが、並びの取り違えで、前の文の警告があるときに、新しい警告ではなく古い警告を残していた

- 文字列の関数の結果の型に、引数の照合順序を付ける（`function/collated_type.go`）。`LEFT`、`RIGHT`、`SUBSTRING`、`SUBSTRING_INDEX` は文字列の引数の型（数の引数は `LONGTEXT`）、`CONCAT`、`CONCAT_WS`、`REPLACE`、`LPAD`、`RPAD`、`REPEAT`、`IF`、`COALESCE` は引数の照合順序の `LONGTEXT`（`IF` は `TEXT`）。バイナリの引数があれば今までどおり
  - 理由: 互換。MySQL の結果は引数の照合順序になる。前は照合順序が既定（`utf8mb4_0900_bin`）で、式の `ORDER BY`、`GROUP BY`、`DISTINCT`、`PARTITION BY` が `a` と `A` を別にしていた（`COLLATION()` の答えだけは正しかった）

  - 理由: 互換。`LEFT(123, 2)` は MySQL では `'12'`。前はエラー 1105

  - 理由: 互換。wpdb はサーバの `sql_mode` から外すだけなので、MySQL と同じ `NO_ZERO_IN_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` になる。HeimDB は `NO_ZERO_IN_DATE`、`NO_ZERO_DATE`、`ERROR_FOR_DIVISION_BY_ZERO` を見ない（前の既定にもなく、見える値だけが変わる）

## 段階 94: 親の変更をブランチに取り込む（`heimdb_branch_sync`）

- 背景: ブランチ A と B を本番にマージした後、検証に時間のかかるブランチ C だけが古い本番のまま残る。C に本番の最新を取り込んでから確かめたい（ヘッドレスの API で使う。プラグインは全サイト固定、テーマはない）。これまでは、ブランチを作り直す（C の変更は消える）しかなかった。効く軸は WordPress に特化した運用。
- 方針: 三方向の比べ方を逆向きに使い、親だけが変えた列を 1 つのコミットでブランチに書く。ブランチの検証中の変更（まだマージしていない変更）は残す。取り込みの記録 `m/sync/<ブランチID>/<反転時刻>`（キーは取り込みのコミット時刻 T、値は読んだ親の時刻 S）を足し、データ形式のバージョンを 6 にする（古い HeimDB は記録を知らず、マージの基準を読み違えるので開かせない）。両側に共通の基準の中身（git の共通の祖先にあたる）を、直近の出来事で決める: 取り込みなら両方向とも親@S、マージなら取り込みの向きはそのマージが読んだブランチの状態 C@s、どちらもなければ分岐の時点。比べる行の候補は、マージなら C が前のマージの s より後に書いた行（取り込みの T からではない）、取り込みなら親が前の取り込みの S（なければ分岐）より後に書いた行。親はロックせずスナップショットで読み、ブランチのロックを取る。同じブランチのマージ、取り込み、復元はブランチごとの鍵で同時に流さない。
- 計画のレビュー（Fable）で変えたこと: 最初の計画は、マージの基準を（親 S、ブランチ T）に進め、競合をブランチの値で残すときは 2 回コミットするものだった。基準を T に進めると、取り込みの前に C で変えてまだマージしていない行が後のマージで C の変更に数えられず、本番に入らない（致命的）。窓をマージの基準から始めると、マージを挟んだ本番の変更（コメント）が取り込まれない。GC と C の復元の組み合わせで前の基準に戻れない。マージと取り込みを同時に流すと記録が捨てられる。そこで、記録をマージの基準と分け、共通の基準の中身の考え方にした（値にコミット時刻を入れる仕組み、記録の見分け、2 回のコミット、向きによらない解決のハッシュは要らなくなった）。2 回目のレビューで、マージの後の取り込みの ID の衝突（前のマージで飛ばした C の行と同じ ID の行を本番が足した）、取り込みの後のマージでぶら下がる行の revived、GC で残す時点（直近でない記録も）、基準の定義と候補の列挙を分けることを足した。
- 完了条件: 競合のない書き込みを本番、A、C に入れ、マージ、GC を挟みながら片方の世界でだけ取り込むプロパティテストで、最後に C をマージした本番が両方の世界で同じ。取り込みの後の C は、C だけが変えた列は取り込まない世界と同じ、本番だけが変えた列は本番と同じ。競合、ID の衝突、自然なキーの重複、新しい表、定義の違い、戻す文、本番を戻した後のマージ、`db_version`、`dry_run`、同時実行の単体テスト。本物の WordPress で A、B、C の流れ。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集に思わぬ違いがない
- 計画からの割り切り: 両側で定義の違う表（列、インデックス、主キー）があれば、親の定義をブランチに当てずに 51010（`schema_differs`）で拒否する（ヘッドレスの API はプラグインが固定で、両側で同じ dbDelta が流れる。親で作られた表は作って行を写す）。競合は `heimdb_branch_resolve` の行ごとの記録を使わず、`'branch'` か `'parent'` で全体をまとめて決める（行ごとに決めたいときは、ブランチでその行を親と同じ値に直してから取り込む）。
- 実装後のレビュー（Fable）で直したこと: 両側が同じ ID で別の行を足した競合は `'branch'` で残せない（残すと、次のマージで本番の行を黙って上書きする。マージの `Forbid` と同じく `'parent'` だけ）。競合でブランチの側を採って入れなかった親の記事などにぶら下がる行（メタ、コメント、タームの関連）も写さない。マージから外した表は `excluded` の行に出す。

## 段階 95: 範囲に入らない条件で捨てる行の見積もり（meta_query の two_filters）

- 背景: 段階 83、84 の後に残っていた差を 0.2.33 で測り直した（手元、記事 2 万件、メタ 32 万行。MySQL 8.0.46 は Docker）。ヘッドレスの API が実際に流す組み立て直した形は、どの文も MySQL と同じくらいだった。WP_Query が NUMERIC の比べで作る形（`CAST(mt2.meta_value AS SIGNED) = '1'`。WordPress 本体と、ヘッドレスの API の比べるための経路）の two_filters だけが、API 用の索引で 45 ms と MySQL の 15 ms だった。MySQL は `category = 'cat3'` の点（2,000 行）から読み、featured と event_date を `(post_id, meta_key)` で記事ごとに 1 行ずつ引く。HeimDB は featured の範囲（2 万行）を全部読んで CAST で 1 割に絞っていた。go-mysql-server は、範囲に入らない条件の Filter のグループを、コストを数える前に決めてしまう（memo の `MemoizeStaticIndexAccess`）。そのうえ JOIN は子の出力の行数しか見ないので、CAST で 1 割に絞る読み出しが、範囲の点で同じ行数に絞る読み出しと同じに見えていた。効く軸は性能。
- 方針: JOIN が読み切る子（lookup JOIN の左、ハッシュ JOIN とマージ JOIN の両方）が、範囲を読んで Filter で捨てる行を JOIN のコストに足す。主キーで引く lookup JOIN の、早めに返す経路にも足す。捨てる行は、出力の行数と、範囲に入らない条件の割合から数える（出力 × (1 / 割合 − 1) × 0.4）。範囲に入らない条件の割合は、`filterSelectivity` と同じ規則で決める。点で決まる列、標本で数える次の列の等号、その列の上か下を決める条件（後で `narrowRange` が範囲に入れるもの）は除く。CAST した列の条件と、インデックスのない列の条件は数える。エンジンは変えない。データ形式も変えない。1 行あたりの手間（GCE で測る）は段階 96 に分けた。

- 記録だけ: (a) 標準の索引には `meta_value` の統計がないので、`category = 'cat3'`（20% なら 4,000 行）も `featured = '1'`（2,222 行）も、決め打ちの 0.1 で 2,000 行と見積もる。同点なので、ハッシュ JOIN のどちらを作る側にするかは重みの付け方しだいで決まる。組み立て直した two_filters は、0.2.33 では当たりの側を選んでいて、段階 95 では外れの側を選ぶ（MySQL も同じ割合で見積もる）。値の割合が 10% なら起きない。(b) ハッシュ JOIN の作る側を主キーの一部と範囲で引く形（`pkByKeysAndRange`）は、同じ左から主キーで引く lookup JOIN のすぐ下のコストにする。そのコストには、左で捨てる行を足していない。今のテストと文では計画が変わらないので、そのままにした。(c) memo の Filter のグループは、読む索引を 1 つに決めてからコストを数える。そのため、date_query の `post_date` の範囲は、決めた索引（`type_status_author` など）に `post_date` がなければ、読んだ後で捨てる条件に数える。

## 段階 96: 1 行あたりの手間を減らす（GCE で測ったプロファイルの上位）

- 背景: GCE（n2-standard-4、asia-northeast1-b）で、記事 2 万件、メタ 32 万行のデータを MySQL 8.0.46（Docker）、0.2.33、段階 95 に入れ、記事 API の形の文を 4 vCPU と 1 vCPU で測った。段階 95 で CAST の形の two は 165 ms から 59 ms（API 用の索引）になり、10 本同時に流したときの処理件数は 4 vCPU で MySQL を上回った（API 用の索引で 9.8 件/秒と 9.2 件/秒）。一方で category（33 ms と 17 ms）、range_t（19 ms と 8 ms）、two_filters_t（87 ms と 16 ms）は、MySQL と同じ形の計画（category の点から読み、記事ごとに引く）なのに 2〜5 倍遅い。差は 1 行あたりの手間。段階 95 のプロファイルの上位は、pebble の検索（17〜27%）、長さを指定した索引で範囲の条件を行ごとに式で評価し直す処理（9〜14%。その式を引くたびに作るのに two_filters_t で 5%）、TopN が比べるたびに `CAST(meta_value AS CHAR)` を計算し直す処理（range_t と priority_t の 17〜20% のうち 6 割）、列と定数の文字列の比較で行ごとに両辺を変換して型を作る処理（4〜6%）、GROUP BY がグループごとに 23 列の式を写す処理（3〜6%）。効く軸は性能。
- 方針: データ形式を変えずに、次の 4 つを直す。
    1. 長さを指定した索引の点の値が長さより短ければ、キーに値が丸ごと入っているので、範囲の条件を評価し直さない。列の値が長さ以上の行（切り詰めたキーがたまたま等しい行。末尾の空白など）だけ評価し直す。式は要るときだけ作る。
    2. TopN の並べ替えのキーを、1 行に 1 回だけ計算する（エンジン）。
    3. 比較の両辺がもともと utf8mb4 の文字列なら、文字列への変換を省き、比較の型を行ごとに作らない（エンジン）。
    4. GROUP BY で、ただの列の参照なら、グループごとのバッファを作るときに式を写さない（エンジン）。
- 計画のレビュー（Fable）で変えたこと: (1) 点の値が長さより短ければ、範囲の条件で落ちる行は 1 行もない。キーは文字ごとの重みを並べて 0x00 で終えるので、長さで切ったキー（重みが長さの数だけ並ぶ）は短い点のキーと一致しない。エンジンは PAD SPACE を持たないので（`compat/known-differences.txt`）、末尾の空白も別の値になる。そこで、行ごとに値の長さを見るのはやめ、条件の式をまるごと外す。外せる条件は「範囲が付いている長さ指定の列がすべて短い点で、ほかの列は `exactIntervals` が区間で表せると判断する」。範囲が付いていない後ろの列（API 用の索引の `key_value` で `meta_key = 'priority'` だけの文）も外せる。並べ替えを省ける条件（`shortPrefixPoints`）は今のまま（後ろの列が自由だと、切ったキーの順が値の順と違う）。PAD SPACE を入れるときは、キーと範囲の条件を一緒に変える（データ形式のバージョン）。(2) TopN では、ヒープが LIMIT の数に達したら、新しい行を先に頂点と 1 回比べ、残らないなら入れない（順番の列が最後の鍵なので、入れて出すのと同じ結果）。(3) 文字列の比較では、不正な UTF-8 の値は今の経路に回す（今は変換で NULL になって一致しない。速い経路では比較がエラーになる）。比較の型は照合順序ごとに 1 つ作って使い回す（式に覚えさせると `SET NAMES` で変わる。実装の途中で、使い回さないことにした）。(4) GROUP BY の `transform.Clone` は列の参照を写していなかった。グループごとの手間は `NewFirst` の作成なので、列の参照と定数は `NewFirstBuffer` を直接作る。効きは小さい見込み（実装の途中で、入れないことにした）。(5) 範囲の条件のテストは、結果が変わらないので外しても落ちない。条件を評価した回数を数えて確かめる。
- 完了条件: 直しごとの単体テスト（長さ指定の列の点、大小文字や全角の同じ重み、ちょうど長さの値と先頭が同じ長い値、範囲の付かない後ろの列、covered、逆順。複数の列で並べる同順位の多い TopN、`LIMIT 20, 20`、`FOUND_ROWS()`、並べ替えの式のエラー。照合順序の違う列と定数、`COLLATE` 付きの定数、utf8mb3 の列、不正な UTF-8 との比較）。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。手元で段階 95 と交互に測り、category、range_t、priority_t、two_filters_t が速くなり、ほかが遅くならない。最後に GCE で MySQL と比べ直す（1 vCPU で 10 本同時に流すと段階 95 が 0.2.33 より少なかった件（4.2 件/秒と 5.5 件/秒）も見直す）。
- 実装の途中で変えたこと: (3) の比較の型を `sync.Map` で使い回すと、アロケーションは 1 回から 0 回になるが、1 回の比較が 64 ns から 79 ns に遅くなったので、行ごとに作るまま（変換を省くだけで 8 回から 1 回になる）。(4) は、`NewFirst` を飛ばしても 1 つのバッファで 10 ns が 7 ns になるだけで、プロファイルの割合のほとんどはバッファそのもののアロケーションだった（23 列 × 2,000 グループで 0.2 ms 弱）。結果が変わらずテストで確かめられないので、入れなかった。(1) で、短い点なら行の読み出しで索引の列を復号しない直しも試したが、効いている証拠がないので外した。実装後のレビュー（Fable）で、並べ替えを省けるかと範囲の条件を省けるかの 2 つの判定を `shortPrefixPoints` の 1 つにまとめ、テストに IS NULL の評価回数と、lookup JOIN の計画の確認を足した。
- 結果: `rows.go` の `lookupRows` と `shortPrefixPoints`（引数 `ranged`）、エンジンの `iters/rel_iters.go`（TopN）と `expression/comparison.go`（文字列の比較）。手元（macOS）で GCE と同じデータ（記事 2 万件、メタ 32 万行）を段階 95 と交互に 2 回ずつ測った（中央値、ms）。

    - 標準の索引: category 27.5〜28.4 から 19.6〜20.0、range 201〜202 から 181〜182、priority 78〜79 から 62〜65、two 44〜46 から 36、two0 65 から 56、range_t 25.4〜26.3 から 16.4〜17.3、priority_t 102 から 63〜65、two_filters_t 59〜60 から 51。list20 は同じ（15 前後）。
    - 遅くなった文はない。
  GCE（n2-standard-4）で、MySQL 8.0.46、0.2.33、段階 95、段階 96 を同じデータで測り直した（中央値、2 回の平均、ms）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- TopN で、列の参照でない並べ替えの式（`ORDER BY CAST(meta_value AS CHAR)` など）を 1 行に 1 回だけ計算して行の後ろに足し、ヒープが LIMIT の数に達したら新しい行を頂点と 1 回比べて、残らない行は入れない（`iters/rel_iters.go`）
  - 理由: 性能。比べるたびに式を評価し直していた（ヘッドレスの API の range_t と priority_t の CPU の 1 割強）。順番の列が最後のキーなので、同順位の並びは変わらない。並べ替えの式のエラーは、行が 1 つでも返る（MySQL もエラー）
- 文字列どうしの比較で、両辺の型が文字列（バイナリでない）で値が正しい UTF-8 なら、LONGTEXT への変換（写すだけ）を省く（`expression/comparison.go`）
  - 理由: 性能。列（`utf8mb4_unicode_520_ci`）と定数（接続の照合順序）は型が違うので、行ごとに両辺を写していた（1 回の比較で 8 回のアロケーションが 1 回になる。比較に使う型を `sync.Map` で使い回すと 0 回になるが、引く分だけ遅い）。不正な UTF-8 は今までの経路（変換で NULL になり一致しない）

## 段階 97: `SQL_CALC_FOUND_ROWS` で数えるだけの行を引かない

- 背景: 記事の一覧（`SELECT SQL_CALC_FOUND_ROWS wp_posts.* FROM wp_posts WHERE … post_type = 'news' AND post_status = 'publish' ORDER BY post_date DESC, ID DESC LIMIT 0, 20`。WordPress のトップページとアーカイブが毎回出す文）は、`Limit → Project → IndexedTableAccess(type_status_date)` で、範囲は区間でちょうど表せる。エンジンの `LimitIter` は 20 行を返した後も残りの行を `Next` で数えるので、残りの約 1 万行の本体を引いて、本文まで全列を復号していた（段階 96 の GCE のプロファイルで list20 の時間の 42%。記録の (b)）。数えるのに要るのはインデックスのエントリの数だけ。効く軸は性能。
- 方針: データ形式は変えない。エンジンに `sql.RowCounter`（`CountRest`。まだ返していない行を、行を作らずに数える。数えられないなら何も読み進めずに ok を false）を足し、`SQL_CALC_FOUND_ROWS` の `LimitIter` は LIMIT に達したら子に数えさせる。数えられなければ今までどおり `Next` で数える。中継するのは `TableRowIter` と、列を選ぶだけの `ProjectIter`、HeimDB の `projectIter` と `visibleIter`。数えるのは、範囲の条件で絞らず、ALTER の途中で NULL を埋めていない `pkRowIter`（インデックスの走査）だけ（範囲の条件を持つのは長さを指定した列の長い点で、並べ替えのために集めるので、今は LIMIT の直下に来ない。区間がちょうど表さない範囲は、エンジンが Filter を残す）。エントリの走査は、ブランチの重ね合わせ、削除の印、読む時点（スナップショット、AS OF、トランザクションの中の変更）をもう済ませているので、数は `Next` が返す行と同じ。Filter、TopN、GROUP BY を通る文（category など）は今のまま。
- 計画のレビュー（Fable）で変えたこと: (1) 本番の経路では、サーバーが deferred projection の Project を `LimitIter` の子から外すので、Limit の直下は `TableRowIter` になる。判定は作るときでなく `Next` の中で行い、サーバーを通すテストで確かめる。(2) `spanIter`（トレースのときだけ挟まる）は中継しない。インデックスのない全走査（`scanRowIter`。`ProcessTable` の `TrackedRowIter` が挟まる）も対象にしない。WordPress の一覧はインデックスで読む。(3) 先読みした行（`rows`）は `pks` と同じ並びなので、残りは `pks` の数だけ数える。(4) 数えた後に `Next` が来ても子を読まない（`LimitIter` に印を持たせ、`Next` で数え終えたときも付ける）。(5) 走査は使い回しの置き場所に戻すと閉じた印が付かないので、数えた後の `Next` が読み直さないか（数えた直後の `Next` は読み終えた走査を読んで終わり、その間にほかの検索は走査を取らないので、数える経路では起きない）。(6) `LIMIT 0` では、まだパーティションを開いていないので、数える側で開く。(7) 別名を付けた列（`SELECT SQL_CALC_FOUND_ROWS wp_posts.ID`）も中継する。(8) 数えるときは本体の行があるかを確かめない（インデックスが壊れたときだけの違い）。
- 実装後のレビュー（Fable）で見つけたこと: (5) は数える経路の外で起きていた（段階 83 で走査を使い回し始めてからの不具合。0.2.25 から）。同じインデックスを引く semi join（`EXISTS (SELECT 1 FROM wp_posts q WHERE q.post_type = 'post' AND … AND q.post_date < p.post_date)`）で、外側の走査が尽きて置き場所に戻ると、内側の検索がそれを取って区間を移す。外側の次の `Next` は内側の区間のエントリを自分の行として読み、50 行の表で文が終わらなかった（再現した）。閉じた走査はもう読まず（`intervalScan.done`）、2 回目の `close` で置き場所に重ねて戻さない（取った検索と同じ走査を、次の検索がまた取る）。WordPress のコアはこの形を出さない。ほかに、`CountRest` がエラーを返した後の `Next` も子を読まない、コメントの直し。
- 完了条件: エンジンの単体テスト（数えさせる、数えられなければ `Next`、`LIMIT 0`、総数が LIMIT 未満とちょうど、数えた後の `Next`、`SQL_CALC_FOUND_ROWS` のない LIMIT、列と別名だけの Project と式のある Project）。サーバーを通すテストで、`FOUND_ROWS()` が同じ条件の `COUNT(*)` と同じこと（一覧の形、`LIMIT 20, 20`、先読みの後の `LIMIT 300, 20`、`LIMIT 0`、総数より後ろ、covered、式のある射影、残りの条件、範囲の条件で絞る範囲。main、ブランチ（親で消した行、ブランチで消した行と変えた行）、AS OF、トランザクションの中の変更、同じ文で同じインデックスを 2 回引く形）と、引いた本体の行と復号した行の数が返した行の数と同じこと。同じインデックスを引く semi join と、閉じた走査を 2 回閉じる単体テスト。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。手元で段階 96 と交互に測り、list20 が速くなり、ほかが遅くならない。
- 結果: エンジンの `table_iter.go`（`sql.RowCounter` と `TableRowIter`）、`iters/rel_iters.go`（`LimitIter`）、`rowexec/rel_iters.go`（`ProjectIter`）、HeimDB の `rows.go`（`pkRowIter.CountRest`）、`table.go`（`projectIter`、`visibleIter`）、`scan.go`（`intervalScan.done`）。手元（macOS）で段階 96 と同じデータ（記事 2 万件、メタ 32 万行）を交互に 2 回ずつ測った（中央値、ms）。list20 は、API 用の索引で 15.0〜17.5 から 2.4〜2.7、標準の索引で 14.4〜16.8 から 2.5〜2.8（約 6 倍）。ほかの文は数える経路を通らず、揺れの範囲（1 回だけ遅い回は、もう 1 回で同じ）。標準の索引の priority が 1 回目の計測で 4〜7% 遅く見えたので 3 回ずつ測り直したが、同じ源から作り直した段階 96 どうしでも 1.5 ms 違い、最後の計測では差がなかった。GCE では、次の段階とまとめて MySQL と比べ直す。

## 段階 99: lookup JOIN が引くたびに行の読み手を開かない

- 背景: 段階 96 の GCE のプロファイル（記録の (c)）で、two_filters_t の CPU の 5.3% が `pkRowIter.openReader` だった。lookup JOIN が右のセカンダリインデックス（`wp_postmeta.post_id` など）を左の行ごとに引くと、そのたびに本体の行を引く読み手（層の数だけの Pebble のイテレータ）を作り、文の終わりまで閉じていなかった。主キーの点で引く経路（`getPoint`）は、段階 27 からトランザクションの `PointReader` を使い回している。効く軸は性能。
- 方針: 書かない文（SELECT とかっこで始まる文）では、`pkRowIter` も同じトランザクションの `PointReader` を使う（閉じない。トランザクションが書くか終わると閉じる）。書く文と AS OF は今までどおり引くたびに開く。データ形式とエンジンは変えない。
- 計画のレビュー（Fable）で変えたこと: 共有する読み手を `pkRowIter` の後始末で閉じると、トランザクションの `PointReader` の置き場所に閉じた読み手が残り、次の lookup が「行がない」エラーになり、同じ文の主キーの点は黙って 0 行を返す。共有するときは後始末を登録しない。閉じた `RowReader` の `Peek` はエラーでなく「ない」と答えるので、`RowReader.Closed` を足し、共有した読み手が閉じていれば明示のエラーにする（接続が切れたときのロールバックは別のゴルーチンから閉じうる）。走査の使い回し（段階 83）の門だった `stmtType` は `WITH` を SELECT に数え、`WITH ... ## 段階 100: ベンチの文を WordPress が実際に流す形に直し、GCE で MySQL と比べ直す

- 背景: 段階 83 からのベンチ（作業用の perfq）の文は、どれも `SELECT SQL_CALC_FOUND_ROWS wp_posts.* … GROUP BY wp_posts.ID … LIMIT 0, 20` の形だった。WordPress 本体の WP_Query は、LIMIT があると文を分け（`split_the_query`）、`SELECT SQL_CALC_FOUND_ROWS wp_posts.ID …` の後に `SELECT FOUND_ROWS()`、`SELECT wp_posts.* FROM wp_posts WHERE ID IN (…)`、`SELECT post_id, meta_key, meta_value FROM wp_postmeta WHERE post_id IN (…) ORDER BY meta_id ASC` を流す。段階 95 で取ったページの文 352 種類では、ID の形が 113、記事の IN が 14、メタの IN が 15 で、`wp_posts.*` に GROUP BY と LIMIT の付いた形は 0。ヘッドレスの API のゴールデン（`metaquery_golden.txt`、`stage95_golden.txt`）も `wp_posts.ID` か `wp_posts.ID, wp_posts.post_title`。段階 99 のプロファイルの行の復号（10 本同時で 9%）は、メタで見つかった何千件もの記事を全列復号して 20 件だけ返す、この形から来ていた（同じ計画で ID だけを返すと category、priority、priority_t が約 3 割速い）。MySQL との差（two_filters_t で 3.4 倍など）が実際の形でどれだけあるかは測っていない。段階 99 の記録の (b) の 2 つは、手元で試して見送る。bloom filter（行のキーの末尾のバージョン 8 バイトを除いて Split、全層に 10 ビット）は、main でもブランチでも速くならなかった（filter は引かれている。記事 2 万件で 72 MB、L0 に 13、L6 に 18 の SSTable、ブロックのキャッシュが温まった状態。大きいデータや冷えたキャッシュでは結果が変わりうる）。`SeekGE` の重さは、行が見つかる検索（最下層のブロックの中の探索）から来ていて、filter で省ける「ない」検索ではない。行の復号は、文字列の写しを 1 回にまとめると 1 行 330 ns が 260 ns になるが、文全体で約 2%。返す 20 行だけを後から引く仕組みは、エンジンの変更が大きく、効くのは WordPress が流さない形だけなので作らない。効く軸は性能（次に直す場所を正しく選ぶ）。
- 方針: HeimDB のコードとデータ形式は変えない。perfq を `scripts/bench/perfq/` に入れる（今は作業用のフォルダにしかなく、消えることがある。go-sql-driver/mysql はリポジトリのモジュールにあるので、別の go.mod は作らない）。文ごとに、WordPress と同じ 4 本の組（ID の文、`FOUND_ROWS()`、記事の IN、メタの IN）を同じ接続で流し、ID の文だけの時間と組全体の時間を測る。IN の ID は 1 本目が返した順のまま、空白なしのカンマでつなぐ（`_prime_post_caches` と `update_meta_cache` は並べ替えない。ページの文で小さい順が多いのはデータの偶然で、順の違う組もある）。4 本の時間はそれぞれ記録する（MySQL との差が 20 行の復号か、320 行のメタの IN かを分ける）。ID の形は、今の 9 つの文（list20 を含む）の `wp_posts.*` を `wp_posts.ID` に替えたもの。前の段階と続けて比べるため、今の `wp_posts.*` の形も残す。10 本同時も組で流し、組の数を毎秒で数える（今の形の 10 本同時も 1 回測る）。記事の種類 `news` にタクソノミーはないので、タームを引く文は組に入れない（`update_object_term_cache` はタクソノミーのない種類では文を流さない）。ヘッドレスの API は `fields => 'ids'` で ID の文と `FOUND_ROWS()` だけを流すので、組はページの負荷、ID の文だけの時間はヘッドレスの API の負荷にあたる。GCE（n2-standard-4、作って使い、終わったら消す）で MySQL 8.0.46、0.2.34、段階 99（6ca6be6）を、標準の索引と API 用の索引、4 vCPU と 1 vCPU で 2 回ずつ測り、段階 99 の CPU プロファイルを組の形で取る（10 本同時と文ごと）。計測のスクリプトは、待つジョブの PID を `wait` に渡し、走っているスクリプトの関数を抜き出して読み込まない（段階 99 の失敗）。1 vCPU は今までどおり HeimDB を CPU に固定し、MySQL は `--cpus 1`（割り当て）なので、同じ条件ではない。
- 計画のレビュー（Fable）で変えたこと: IN の ID を小さい順に並べず、返した順にした。list20 にも ID の形を作る。4 本の時間を別々に記録する。ID の集まりも MySQL と比べる。bloom filter を試したデータの大きさを書いた。
- 完了条件: perfq の組が、ページの文と同じ形（記録したページの文と並べて確かめる）。HeimDB と MySQL で、組の `FOUND_ROWS()` と各文の行数が同じ（perfq が比べ、違えば止まる）。ID の集まりと並びも比べて記録する（`priority` と `range` は、同じ値の行の並びが段階 84 から MySQL と違い、LIMIT の境目で入る記事が変わりうる。記事ごとのメタは 16 行で同じなので、行数だけでは見分けられない）。GCE の結果を `docs/bench.md` とこの段階の記録に入れ、次の段階の候補を、組の形のプロファイルの割合とともに決める。HeimDB のコードは変えないので、Go のテストと PHPUnit は流さず、perfq の `go vet` を通す。
- 結果: `scripts/bench/perfq`（`load`、`bench`、`conc`、`check`。名前に `_all` を付けると前の形）。組の 4 本は、ページの文（段階 95 で取ったもの）の記事とメタの IN と同じ文で、ID の文は WP_Query の文の列を `wp_posts.ID` にしたもの（WordPress は `SQL_CALC_FOUND_ROWS` の後の空白が 2 つ）。手元で MySQL 8.0 と比べ、GCE でも 0.2.34 と段階 99 の両方、標準の索引と API 用の索引で `check` を流し、9 つの組と前の形の 9 つの文のすべてで、`FOUND_ROWS()`、各文の行数、ID の並びが MySQL と同じだった。GCE（n2-standard-4）で MySQL 8.0.46、0.2.34、段階 99 を測った結果は `docs/bench.md` の「段階 100」。
    - 4 vCPU、API 用の索引の組の時間（ms、括弧は MySQL）: two_filters_t 49.6（15.3）、range 394（136）、two0 64.4（28.4）、two 38.2（19.4）、category 21.8（11.2）、range_t 11.7（7.0）、list20 9.3（8.3）、priority 129（145）、priority_t 131（144）。記事とメタを IN で引く 2 本は合わせて約 2.4 ms（MySQL 約 1.9 ms）で、差はほとんど ID の文から来る。
    - 10 本同時の毎秒の組の数は、4 vCPU、API 用の索引で段階 99 が 21.2、MySQL が 38.5。前の形では段階 99 の 14.2 件/秒が MySQL の 11.1 件/秒を上回っていたが、MySQL は ID の形で priority、priority_t、list20 が大きく速くなる（全列を持ったまま並べ替えない）ので、実際の形では MySQL の約半分。標準の索引では 14.7 と 13.6、1 vCPU では API 用の索引で 9.9 と 10.1、標準の索引で 7.6 と 3.8。MySQL は標準の索引で、ID の形の two と two_filters_t が前の形より遅い（100 ms 前後から 190 ms 前後。`EXPLAIN` は取っていない）。
    - 段階 99 のプロファイル（API 用の索引、4 vCPU、組の形）: 10 本同時では lookup JOIN の右（`lookupRows`）が 51%、そのうち本体の行の `Peek` が 24%、引くたびのインデックスの走査の作り直し（`newPKRowIter` の `Scan.Reset`。層ごとに `First` から合わせ直す）が 12%。two_filters_t だけでは、走査の作り直しが 21%、引く区間を作る処理（`indexInterval` と `mergeIntervals`、スライスの伸長）が 9%、`Peek` が 18%。行の復号は category で 9%、ほかの組では上位にない。
- 実装後のレビュー（Fable）で直したこと: 引数が足りないときに panic せず使い方を出す。10 本同時は、終わりの時刻の後に終えた組も数えるので、名目の秒数でなく最後の組が終わるまでの時間で割る（GCE の値は直す前の perfq で測ったもので、組が 1 本あたり数百 ms なので 30 秒に対して 1〜2% ほど多めに出ている）。p90 の説明を、並べた値の 9 割の位置（10 回なら最大）と直した。記事の数が 1000 の倍数でなければ止める。メタの serialize の長さが合わない値は、前の段階のデータと同じにするため直さない（コメントに書いた）。
  HeimDB のコードは変えていないので、Go のテストと PHPUnit は流していない（perfq の `go vet` は通る）。
- 記録だけ: (a) 次の候補は、lookup JOIN が左の行ごとにする手間（インデックスの走査の作り直しと、引く区間を作るアロケーション）。two_filters_t と 10 本同時の組で、合わせて 2〜3 割。(b) 本体の行の `Peek`（Pebble の層ごとの検索）は残る。bloom filter は効かなかった（背景）。(c) MySQL が標準の索引で ID の形を遅くする件は、HeimDB の計画を合わせる対象ではない（標準の索引では HeimDB の方が速い）。
