# 段階 21〜30

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 21: 非 STRICT の sql_mode での値の扱い（段階 20 で見つけた 11 件）

- WordPress は接続ごとに STRICT を外した sql_mode にする。そのとき MySQL は、次の値をエラーにせず、値を直して警告にする。HeimDB はエラーにしていた。
  - NOT NULL の列への NULL（`UPDATE` と複数行の `INSERT`）: 暗黙の既定値（`''`、0、ゼロの日時）にして警告 1048。単一行の `INSERT` は MySQL でもエラー 1048。
  - 不正な日時（`'2012-01-01 25:00:00'`、`'2020-12-41 …'`、`'…T00:00:00+0100'`）: ゼロの日時にして警告 1265（`'2012-01-01 0'` は日付の部分を取る）。
  - 既定値のない NOT NULL の列の省略: 暗黙の既定値にして警告 1364。
- MySQL 8.0.46 で確かめた振る舞い: `UPDATE`、複数行の `INSERT`、`INSERT ... SELECT`、`REPLACE` の NOT NULL の列への NULL は型の既定値（`''`、0、ゼロの日時、ENUM は `''`、TIMESTAMP もゼロの日時）と警告 1048 `Column 'x' cannot be null`。単一行の `INSERT ... VALUES` の NULL は MySQL でもエラー 1048。省いた既定値のない NOT NULL の列は、単一行でも型の既定値と警告 1364 `Field 'x' doesn't have a default value`。不正な日時はゼロの日時と警告 1265 `Data truncated for column 'x' at row N`。時刻が途中までの `'2012-01-01 0'` は正しい値（警告なし）。STRICT ではどれもエラー。
- 実装の方針: go-mysql-server の `INSERT IGNORE` 用の経路は重複キーのエラーも無視するので使わない。単一行の `INSERT ... VALUES` と単一のテーブルの `UPDATE` は HeimDB の解析ルールを通らないので、段階 20 の `Analyzer.ExecBuilder` の包みを広げ、STRICT でないセッションのときだけ実行の直前に書き換える。`INSERT` と `REPLACE` は挿入する行の元を包み、go-mysql-server が確かめる前に行の値を直す（省いた列は `DeferredDefaults` の印で見分ける。明示した NULL は行が 2 つ以上か SELECT のときだけ直す。AUTO_INCREMENT の列には触れない）。`UPDATE` は `SET` の右辺の式を包む（go-mysql-server は `SET` の評価の中で型を変換してエラーにするので、その前に直す）。日時の文字列は、go-mysql-server で変換できなければ `YYYY-MM-DD` と空白か `T` と途中までの時刻（`H`、`H:M`、`H:M:S`、小数秒）の形だけを範囲を確かめて受け付け、それでも読めなければゼロの日時と警告 1265。`INSERT IGNORE` と `UPDATE IGNORE` は go-mysql-server に任せる。
- 対象外（記録だけ）: `WHERE ... IN (SELECT ...)` や `JOIN` の形の `UPDATE`（段階 20 と同じく対象のテーブルの経路をたどれない）。長すぎる文字列の切り詰めと範囲外の数値（全テストで見つかっていない。段階 92 で対応）。STRICT のときの不正な日時のエラー番号（MySQL は 1292、HeimDB は 1105）。
- 完了条件: 上の各場面で、MySQL で確かめた値と警告（番号と文面）をテストで確かめる。STRICT ではエラーのまま。PHPUnit の全テストで、段階 20 で残した 11 件が通り、差は記録だけの 1 件と既知の 42 件だけで増えない。
- 結果（実装済み、`backend/nonstrict.go`、`backend/exec.go`）:
  - 段階 20 の `UPDATE` の書き換えとあわせて、実行の直前の書き換えを `execBuilder` にまとめた。STRICT の判定（`strictMode`）は段階 15 の ALTER と共通にした。
  - 上の各場面の値と警告が MySQL と同じになった（`nonstrict_test.go`）。単一行の `INSERT ... VALUES` の NULL と STRICT はエラーのまま。重複キーは非 STRICT でもエラー 1062（`INSERT IGNORE` の扱いにしていない）。
  - PHPUnit の全テスト: 本物で成功し HeimDB で失敗するものは 43（既知の 42 と、段階 20 で記録だけにした `tags_exclude` の 1）。段階 20 で残した 11 件はすべて通る。接続の切断と panic は 0。
  - 記録だけ: `CONCAT` などの文字列の関数は、ゼロの日時を `0000-01-01 00:00:00`、DATE を時刻つき、ENUM を番号で返す（go-mysql-server の以前からの差。列をそのまま読めば MySQL と同じ）。エラー 1048 の文面は go-mysql-server のもの（`column name 's' is non-nullable but attempted to set a value of null`）。
  - レビューで直したもの:
    - `INSERT ... ON DUPLICATE KEY UPDATE col = NULL` が、sql_mode に関係なく（STRICT でも）NOT NULL の列に NULL を書き込んでいた（go-mysql-server は ON DUPLICATE KEY UPDATE の結果の行の NULL を確かめない。段階 21 より前からの問題）。右辺を STRICT でも包み、複数行の非 STRICT では型の既定値と警告 1048（文で 1 回）、単一行と STRICT ではエラー 1048 にする。右辺の不正な日時も非 STRICT では直す。
    - 複数行の `INSERT`、`INSERT ... SELECT`、`REPLACE` の警告 1048 と 1364 を行ごとに出していた。MySQL と同じく列ごとに文で 1 回にした（1265 と `UPDATE` の 1048 は行ごとで MySQL と同じ）。段階 21 のテストの期待値（行ごと）が誤っていた。
    - 型の範囲の外の TIMESTAMP（`'1900-01-01 00:00:00'`）が非 STRICT でもエラーだった。ゼロの日時と警告 1264 `Out of range value for column 'x' at row N` にする。
  - 記録だけ（レビューで見つけた。WordPress は使わない）: 正しい日時の後ろに余計な文字がある `'2012-01-01 00:00:00x'` は、MySQL は読めた部分と警告 1265、HeimDB はゼロの日時と警告 1265。先頭の空白も MySQL は受け付ける。省いた既定値のない ENUM NOT NULL の列は、MySQL は先頭の値（警告なし、STRICT でも通る）、HeimDB は `''` と警告 1364。`VALUES (1, DEFAULT)` で既定値のない NOT NULL の列を指すと、MySQL は警告 1364、HeimDB はエラー 1048。同じ行の中の警告の順は、MySQL は `INSERT` の列の並び、HeimDB はテーブルの列の順。`'2012-00-01'` は MySQL は警告 1264、HeimDB は 1265（値は同じゼロの日時）。`NO_ZERO_DATE` と `ALLOW_INVALID_DATES` の扱いは未対応。

## 段階 22: JOIN と、WordPress のクエリに合わせた読み出しの最適化

- 背景: ベンチマーク（`docs/bench.md`）で、ページの表示の DB の時間が MySQL の 13 から 52 倍、記事の作成と削除が 1 回 324 秒と 166 秒だった。主な原因は、go-mysql-server が統計のない `IndexScan` を 1 行と見積もり、等号の JOIN を入れ子のループ（内側を外側の行ごとに読み直す）にすること。次に、`ORDER BY ... LIMIT` でも範囲のすべての行を読むことと、数えるだけの文で本体の行を読むこと。
- 方針（1 つ入れるごとにベンチマークで効果を測り、効かないものや複雑になるものはそこで止めて記録だけにする）:
  - A. HeimDB のコスト計算（`Analyzer.Coster`。go-mysql-server の既定を包む）で、lookup、ハッシュ、マージでない入れ子のループの JOIN に割り増しを掛ける。
  - B. 表の行数をコスト計算に渡し、lookup の向き（どちらの表から引くか）を表の大きさで決める。WordPress の表は役割で大きさがほぼ決まる（`wp_terms`、`wp_term_taxonomy`、`wp_options`、`wp_users` は小さく、`wp_posts`、`wp_postmeta`、`wp_comments`、`wp_term_relationships` は大きい）。ヒストグラムなどの統計の仕組みは作らない。
  - C. 並べ替えの要らないインデックスの読み出し（範囲が 1 つで、インデックスの順が結果の順）では、`LIMIT` の行数で読むのをやめる（記事の一覧、前後の記事、最近のコメント）。
  - D. 条件の列がすべてインデックスにある `COUNT(*)` は、本体の行を読まずにインデックスだけで数える（承認済みのコメントの数など）。どこまで済むかは実装の初めに確かめる。
- 完了条件: 各項目で、実行計画か読んだ行数をテストで確かめ、結果が本物の MySQL と同じことを確かめる。PHPUnit の全テストで、差（43 件）が増えない。ベンチマークを流し直して `docs/bench.md` に前後の表を残す（目安: 記事の作成と削除が 1 秒未満、ページの表示の DB の時間が今の数分の 1 以下）。
- 対象外（次の候補）: `REGEXP` の遅さ、検索の全件の `LIKE`、コメントの追加の遅さ。
- 実装:
  - A: `coster`（coster.go）が、条件のある `InnerJoin`、`LeftOuterJoin`、`SemiJoin`、`AntiJoin` のコストに 1 万倍の割り増しを掛ける。条件のない JOIN とほかに方法のない JOIN はそのまま。
  - B: `Table` に `sql.StatisticsTable` を実装した（rowcount.go）。行数は数えて覚え、数えた後の挿入と削除が行数の 4 分の 1 と 64 の和を超えたら数え直す（書き込み 1 回あたりの手間は一定。時刻では数え直さないので、同じ文の並びなら同じ計画になる）。マージと復元の後は忘れる。TRUNCATE はテーブルの ID が変わるので数え直す。正確でない（`exact` が false）ので、go-mysql-server は `COUNT(*)` の置き換えには使わない。go-mysql-server は `information_schema.TABLES` に権限を見ずにこの行数を出すので、段階 20 の `tableRows` で、読めないテーブルは 0 にする。
  - C: セカンダリインデックスの検索は、エントリ（主キー）を先に読み、行は返すときに引く（`pkRowIter`）。複数の範囲を逆順に読むときは範囲を後ろから読み、並べ替えをやめた（プレフィックス長のある列を含むインデックスだけ並べ替える）。行を引くのは store の `RowReader`（層ごとに Pebble のイテレータを 1 つ作り、`SeekGE` で位置を移す。以前は 1 行ごとに層の数だけイテレータを作っていて、これが読み出しの時間の大半だった）。段階 7 の `orderByIndexWithFixedPrefix` は、最初のソート列の範囲を条件から決める（前後の記事の `post_date < X OR (post_date = X AND ID < N)` なら `post_date <= X`）。値の丸めで行を落とさないよう、日時の列と、整数の列と整数の定数の比較だけを見る。
  - D: 上位の `COUNT(*)` は、条件にインデックスにない列（`comment_type`）を含むか、文字列の列の値を返す（インデックスのキーは照合順序の重みで、値に戻せない）ので、当てはまらなかった。作らずに記録だけにした。
  - Pebble のブロックキャッシュの既定を 8 MB から 128 MB（MySQL の `innodb_buffer_pool_size` の既定）にし、`-cache-size` で変えられるようにした。記事 5,000 件のデータでも、行を読むたびにファイルを読み直していた（term 数の JOIN で 1 割ほど速くなった）。
- 結果（`docs/bench.md` の「段階 22 の後」）:
  - ページの表示の DB の時間: トップページ 233 → 27 ms、REST API 1,853 → 75 ms、ダッシュボード 735 → 152 ms など、4 分の 1 から 25 分の 1（MySQL の 2.2 から 7.7 倍）。10 並列の件数/秒はトップページ 11.7 → 71.6（MySQL 86.2）。ページの中身は MySQL と同じ。
  - 記事の作成 324 秒 → 280 ms、削除 166 秒 → 225 ms、コメントの追加 170 → 41 ms。
  - ページの表示で出たクエリ（212 種類の SELECT）を本物の MySQL と HeimDB に流して結果を比べた。違ったのは、ベンチマークの書き込みで変わったデータと、記事の term の読み出し（`ORDER BY t.name`）の同順位の行の並びだけ。並びは段階 21 の HeimDB と同じ（以前からの差）。
  - テスト: WordPress の JOIN の形（term 数、記事の term、term の読み込み、カテゴリのアーカイブ、タグの除外、メタの条件）の結果を本物の MySQL のゴールデン（`internal/testdata/joins_golden.txt`）と比べ、計画に入れ子のループがないことを確かめる。行数の見積もりの数え直し、`LIMIT` で行を読むのをやめること（読んだ行の数）、`RowReader` がブランチの重ね合わせ、削除の印、未コミットの変更、スナップショット、AS OF で `ScanRows` と同じ行を返すことも確かめる。Go のテストは 273 件（-race でも成功）。
  - PHPUnit の全テスト: 本物で成功し HeimDB で失敗するものは 43（既知の 42 と、段階 20 で記録だけにした `tags_exclude` の 1）で、段階 21 と同じ。接続の切断と panic は 0。
  - 記録だけ（段階 22 より前からの差。WordPress への影響は見つかっていない）: 主キーを明示した複数行の `INSERT` の insert_id（MySQL は最後の値、HeimDB は先頭の値）。`post_author IN (1, 3) ORDER BY post_author DESC` のような等号の範囲が複数ある逆順の読み出しは、MySQL は範囲の中を主キーの昇順、HeimDB は降順で返す。`GROUP BY` のない集約の文（`SELECT COUNT(*) FROM t` など）の `EXPLAIN PLAN` が go-mysql-server のエラー（`result max1Row iterator returned more than one row`）になる。
  - レビューで直したもの:
    - 文字列の列の JOIN（`ON t.name = pm.meta_value`）で、大文字と小文字だけが違う行がつながらなかった。A と B でハッシュ JOIN が選ばれるようになったが、go-mysql-server のハッシュ JOIN は照合順序を見ずに値をそのまま比べる。キーに整数でない列があるハッシュ JOIN にも同じ割り増しを掛け、lookup（照合順序の重みで引く）か入れ子のループにする（WordPress の JOIN のキーは整数の ID）。
    - 小数秒つきの日時と `DATETIME(0)` の列の比較（`post_date < '2024-01-03 10:00:00.4' ORDER BY post_date DESC`）で、境目の行を落としていた。C の最初のソート列の範囲で、定数が列の精度に四捨五入されていた（条件は最大の精度で比べる）。列の型に直して値が変わるときは範囲の端にしない。
    - 行数の見積もりを、テーブルの削除、TRUNCATE と ALTER の書き直し（古い ID）、ブランチの削除、一時テーブルのブランチの片付けでも忘れる（テーブル ID は使い回さないので見積もりは狂わないが、覚える数がテーブルを作った数だけ増えていた）。
    - 上の 2 つの文をゴールデンに足した（直す前は MySQL と違う結果になることを確かめた）。Go のテストは 274 件（-race でも成功）。PHPUnit の全テストの差は 43 のまま（panic は 0）。
  - 記録だけ（レビューで見つけた）: `SHOW TABLE STATUS` の `Rows` は見積もり（最大で行数の 4 分の 1 と 64 だけ古い。MySQL も概算）。`information_schema.TABLES` は数えた値。`AS OF` のテーブルの見積もりも最新の行数。
  - 次の候補: 記事の作成の残りの大半は term 数の JOIN（1 回 30 ms 台。MySQL はカバリングインデックスで約 2 ms）で、必要な列だけを返す `sql.ProjectedTable` が要る。承認済みのコメントの数と、最近のコメントの `ORDER BY comment_date_gmt DESC LIMIT`（MySQL は日付のインデックスを逆順に読む）。

## 段階 23: 統計によるインデックスと JOIN の選択

- 背景: 段階 22 の後のベンチマークで、記事の作成（277 ms、MySQL 28 ms）の約 9 割が term 数の JOIN、コメントの追加（42 ms、MySQL 3 ms）の大半が記事ごとの承認済みコメントの数、ダッシュボードの DB の時間（154 ms、MySQL 20 ms）の大半が最近のコメントとコメントの数だった。どれも go-mysql-server が読む行の多い方法を選んでいる。統計がないとインデックスはどれも同じ行数（表の行数から一様に決めた値）に見積もられ、同じならインデックスの名前の順で選ばれる（`comment_post_ID` ではなく `comment_approved_date_gmt` で 2 万行を読む。記事が 75 件のタグの term 数でも記事 5,000 行から引く）。
- 方針:
  - A. インデックスごとの統計（ヒストグラム）を作り、go-mysql-server に渡す（`Analyzer.Catalog` の `StatsProvider`）。表を 1 回読んで、インデックスの列の値の並びからバケットを作る。行数の見積もり（段階 22 の `rowCountCache`）と同じく、数えた後の挿入と削除が行数の 4 分の 1 と 64 の和を超えたら作り直し、マージ、復元、テーブルの削除、ブランチの削除で忘れる。初めに、統計を渡すとインデックスと JOIN の選び方が変わることを確かめる（変わらなければ B と C だけにするか、相談する）。
  - B. HeimDB のコスト計算で、カバーしないセカンダリインデックスの読み出し（行ごとに主キーで本体を引く）を、表の頭からの読み出しより 1 行あたり重くする。ほとんどの行が当てはまる条件（承認済みのコメントの数）では表を頭から読む。
  - C. `ORDER BY 列 LIMIT n` で、その列から始まるインデックスがあり、統計で条件に当てはまる行の割合が大きいと分かるときは、そのインデックスの順に読んで `LIMIT` で止める（最近のコメント）。
- 完了条件: 各項目で実行計画をテストで確かめ、結果が本物の MySQL と同じことを確かめる。PHPUnit の全テストで、差（43 件）が増えない。ベンチマークを流し直して `docs/bench.md` に前後を残す（目安: 記事の作成が 100 ms 未満、コメントの追加が 15 ms 前後、ダッシュボードの DB の時間が半分以下）。
- 対象外（記録だけ）: 記事 5,000 件のカテゴリの term 数（インデックスだけで数えるには `sql.ProjectedTable` が要る）。`REGEXP` と検索の全件の `LIKE`。
- 実装:
  - A: `statsProvider`（statistics.go）が `GetTableStats` で HeimDB の表のインデックスごとの統計を返す。表を頭から読み（2 万行を超える表は等間隔に間引く）、インデックスの先頭の列の値の符号化（文字列は照合順序の重み）で並べて、行数のほぼ等しい 100 個のバケットにする（段階 98 から、同じ値の並びの手前で閉じるので最大で約 200 個）。行数の見積もりと同じ `rowCountCache` に置き、同じ条件で作り直す。go-mysql-server の見積もりの癖に合わせて次の 3 つを足した。
    - バケットの前に、そのバケットの最小の値を上端にした空のバケットを置く。go-mysql-server は等号の値より上端が大きい最初のバケットの行数を見積もりにするので、値の種類が少ない列（`meta_key`）では、表にない値（メニューの項目のメタのキー）でも何千行と見積もっていた。
    - 最後に、先頭の列の型の最大値（整数と日時）を上端にした空のバケットを置く。表のどの値より大きい値（作ったばかりのタグの term の ID）では、バケットが 1 つもない見積もりになり、表の半分の行数と見積もっていた。
    - ヒストグラムは先頭の列だけで作る。go-mysql-server の `stats.Union`（OR の条件の見積もり）は、上端が複数の列のバケットで範囲の外を読んで panic した（PHPUnit の `Tests_General_wpGetDocumentTitle::test_search_title` で接続が切れた）。
  - コスト計算（coster.go）: 一意なインデックス（主キーを含む）のすべての列で引く lookup JOIN は、左の行数で見積もる（go-mysql-server は JOIN の出力の見積もりを使い、それが条件を見ない表全体の統計から作られることがあった）。マージ JOIN は、両方の表を全部読むコストを下限にする（子が Filter だと、絞った行数で見積もっていた）。この 2 つで、wp_posts と wp_postmeta の JOIN がマージ JOIN から lookup JOIN になった。
  - B: 統計を渡しても、go-mysql-server は単一の表の文でインデックスと表の頭からの読み出しを比べない（条件に合うインデックスがあれば必ず使う）。代わりに読み出しを速くした。区間が範囲をちょうど表すとき（`exactIntervals`。等号の列、範囲のある列 1 つ、残りはすべての値で、端の値が列の型にそのまま入る）は、読んだ行を範囲の条件で絞り直さない（go-mysql-server の Filter が同じ条件をもう一度見るので二重だった。読み出しの CPU の約半分）。256 行より多く引くときは、4,096 行ずつ主キーの順に並べて引く（`prefetch`。約 2 割）。
  - C: 段階 7 の `orderByIndexWithFixedPrefix` を、LIMIT のある Sort（TopN と、Limit の下の Project と Sort）で、先頭の列がソート列のインデックスにも広げた（`sortIndexForLimit`）。go-mysql-server が選んだインデックスの範囲がどれも先頭の列の等号なら、統計で条件に当てはまる割合 f を見積もり、ソート列のインデックスで読む行（LIMIT / f）が今の行（f × 行数）より少ないときだけ置き換える。同順位の行は主キーの降順で、MySQL のインデックスの逆順の読み出しと同じ。

## 段階 24: コミットの記録と非同期のレプリカ

- これまでは 1 つのプロセスでしか動かせず（Pebble がデータのディレクトリを 1 つのプロセスに固定する。書き込みロック、AUTO_INCREMENT、GC もプロセスのメモリの中）、マシンが壊れると段階 16 のバックアップの時点まで戻るしかなかった。目的は障害に備えて止まらないようにすること。切り替えは手動で、数分の停止は許容する（自動の切り替えはしない）。
- 方針: 書き込みはすべて Store のコミット（`Store.Update`）を 1 か所で通るので、コミットごとの変更（そのバッチの中身）を、同じバッチで `l/<コミット時刻>` に記録として残し、レプリカの HeimDB に順に送る。レプリカは同じ順に適用するので、ブランチと `AS OF` もそのまま持つ。ユーザーと権限（`m/users`）もコミットを通して書く。レプリカは読み取り専用（書き込みはエラー）。新しいレプリカは、段階 16 のバックアップから始めて記録で追いつく（バックアップの時刻がそのまま始まりの位置。レプリカの位置は自分の `m/clock`）。
- GC はレプリカも自分で動かし、複製しない（InnoDB の purge と同じ。本番の GC がレプリカで読み取り中のスナップショットのバージョンを消さないように）。
- 記録は時間で消す（`-replication-log-retention`、既定 24 時間。0 なら記録しない。MySQL の `binlog_expire_logs_seconds` と同じ考え方）。計画の初めは「すべてのレプリカが受け取ったものから消す」だったが、バックアップからこれから作るレプリカは本番に登録されていないので、その間に消えうる。最新の記録は消さない（書き込みのない間に、追いついたレプリカの位置が消えないように）。求められた位置の記録がなければ、作り直し（バックアップから）を求めるエラーにする。
- 送り方: 本番は `-replication-addr` で HTTP を待ち受け、合言葉（`-replication-token`、環境変数 `HEIMDB_REPLICATION_TOKEN`）で認証する。レプリカ（`-replicate-from`）は `GET /v1/log?after=<適用した時刻>` で次の記録をまとめて受け取る（なければ数秒待つ）。次の要求の位置が受け取ったことの知らせになる。本番は `after` の時刻の記録が自分にあることを確かめる（消えた記録、違う本番）。暗号化はしない（閉じたネットワークか SSH のトンネルで使う）。
- 昇格は、本番を止めてレプリカが追いついたことを確かめ、`-replicate-from` なしで起動し直す。レプリカも記録を持つので、昇格した後はそのまま次のレプリカの元になる。
- 完了条件: 書き込みが続いている最中にレプリカを足しても、追いついた後は本番と同じ内容になる（ブランチ、`AS OF`、ユーザーと権限を含む）。レプリカを止めて再開すると、途中から追いつく。本番を止めてレプリカを昇格させる手順で、WordPress がレプリカで動く。どこまで追いついているかを `heimdb_status` で見られる。
- 実装: `internal/store/replication.go`（記録の読み出し、適用、時間での削除、コミットを待つ `WaitCommit`）、`internal/replication`（HTTP の本番とレプリカ）。`Store.Update` は、`m/clock` まで書いたバッチの中身を写して `l/<時刻>` に入れ、同じバッチでコミットする。`SetUsers` もコミットを通す。レプリカ（`store.Options.Replica`）は、`Update` をすべて `HeimDB: this server is a read-only replica` にし、起動時の一時テーブルの片付けをせず、空のデータや存在しないディレクトリでは起動しない。記録はそれぞれ 1 つのバッチで適用し、受け取ったまとまりの最後だけ同期書き込みにする。記録の中の `m/clock` が記録の時刻と違えば止める。適用の後に、ブランチの一覧を読み直し、AUTO_INCREMENT のカウンタを捨て、ユーザーと権限が変わっていれば go-mysql-server の `OverwriteUsersAndGrantData` で置き換え、書いた行の数を行数の見積もりに足す。本番は、要求の `after` を受け取ったときにレプリカの位置として覚える（新しい記録を待つ前）。バックアップのときに最後のコミットの記録がなければ（記録を残す前のデータで起動して、まだ書いていない）、何も変えないコミットをして記録を作る。
- 結果:
  - テスト: Store（記録を適用すると、そのマシンだけのキーを除いてすべてのキーが本番と同じ。止めて開き直すと続きから。読み取り専用、同じ記録を 2 度適用しない、記録にない位置、時間での削除で最新を残す、記録のない古いデータのバックアップ）、送受信（待ち受けの途中の記録をすぐ受け取る、合言葉の誤りと記録にない位置で止まる）、HeimDB のプロセスでの結合（行の挿入・更新・削除、ブランチの作成と削除、`CREATE USER` と `GRANT`、列の追加と削除を続けている最中にバックアップからレプリカを足し、途中で止めて再開。追いついた後、すべてのブランチのすべてのテーブル、`AS OF` の過去の時点、`mysql.user` が本番と同じで、本番で作ったユーザーでレプリカに接続できる。書き込みと `heimdb_branch_create` はエラー。本番を止めてレプリカを昇格させると書ける）。ユーザーの読み直しを外すと落ちることを確かめた。Go のテストは 283 件（-race でも成功）。
  - WordPress（記事 5,000 件のベンチマークのデータの写し）: 本番の書き込みの最中にバックアップからレプリカを起動し、wp-cli で記事、コメント、オプション、ユーザーを作ると、本番とレプリカの mysqldump が 1 バイトも違わなかった（`replication_behind` は 0s）。本番とレプリカを止めてレプリカを昇格させると、トップページに反映した記事と説明が出て、レプリカの間に作ったユーザーで管理画面にログインでき、記事を作れた。
  - PHPUnit の全テストの差は 43 のまま（同じテスト。panic は 0）。書き込みのベンチマークは、記録あり（既定）と記録なし（`-replication-log-retention 0`）で揺れの範囲で同じ（記事の作成 139〜149 ms と 149 ms、コメントの追加 15 ms と 16 ms。`docs/bench.md`）。
  - レビューで直した: GC の境界（`m/gc`）をコミットで書いていたので、レプリカの GC が読み取り専用のエラーで一度も動かず、本番の GC のたびに境界だけのコミットが記録されてレプリカに送られていた（レプリカを開き直すと本番の境界に戻り、自分の GC で消えた時点を `AS OF` で読めてしまう）。境界はコミットを通さず Pebble に直接書く。記録の読み出しは、位置の確かめと読み出しを別々に読んでいたので、間に記録の削除が入ると記録を飛ばして返しえた（同じスナップショットで読む）。記録の削除は閉じた後にも動きえた（GC と同じロックで止める）。適用が途中で失敗すると、それまでに同期せずに書いた分を確定させずに戻っていた（WAL を同期してから戻る）。最新の記録を残すだけでは、長く書き込みがなかった後の 1 回の書き込みで、追いついていたレプリカの位置の記録が消えた。消した最後の記録の時刻を `m/logtrim` に残し、その位置からの続きも返す。
    - テスト: レプリカの GC が動き、本番の GC は記録に入らず、レプリカの境界は記録の適用でも開き直しても本番の境界にならない。消した最後の位置から続けられ、閉じた後の削除はエラー。削除と並行して読んでも記録を飛ばさない（直す前のコードで落ちることを確かめた）。適用が途中で失敗すると、その前までが残り（開き直しても）、続きから追いつく。昇格の後の AUTO_INCREMENT が本番の続き（明示した値の続きも）。Go のテストは 287 件（-race でも成功）。PHPUnit は実行していない（SQL の経路は変えていない）。
  - 記録だけ: レプリカの一時テーブルの書き込み（`CREATE TEMPORARY TABLE`）もエラーになる（レプリカで WordPress を動かすのは昇格させてから）。本番の位置を確かめるのは記録の時刻だけで、同じ時刻の違う記録（別の本番から昇格させたデータ）は見分けない（作り直しの手順で避ける）。一時テーブルの書き込みも記録して送る（本番が片付けると、レプリカでも消える）。大きなコミット（復元、`ALTER TABLE`）は記録の分だけメモリと WAL が 2 倍になる。レプリカで明示的なトランザクションの書き込みは、`COMMIT` のときに初めてエラーになる。レプリカを元にしたレプリカ（連鎖）の `heimdb_status` には、レプリカの側の項目だけが出る。

## 段階 25: 待ち時間つきの同期のレプリカと、手動の切り替えの手順

- 目的: 段階 24 の非同期のレプリカでは、本番が壊れると、レプリカに届く前のコミット（クライアントには OK を返したもの）が失われる。OK を返したコミットが、レプリカにもあるようにする。
- 方針: 本番はコミットをディスクに書いた後、どれか 1 台のレプリカが「適用してディスクに確定させた」と知らせるまで OK を返さない。知らせはレプリカの次の要求の `after`（適用の後すぐに出す）で、送り方は段階 24 のまま。知らせとして数えるのは、本番の記録で確かめられた位置だけで、増える方向にしか動かさない（違う本番から作ったレプリカや、再送された古い要求を数えない）。MySQL の AFTER_SYNC と同じく、待っている間そのコミットはほかの接続から見えない（Pebble にはあるが、スナップショットの時点 `committed` を進めない。記録の送り出しは書いた時点 `written` で始める。`AS OF` の時刻も `committed` までにする）。待つ間は書き込みのロック（とトランザクションのブランチのロック）を持ったままにし、知らせを待つコミットは常に 1 つにする（まだ見えないコミットの上に、ほかの書き込みが積まれない）。WordPress は main だけに書くので、ロックを放しても速くならない。
- 待ち時間（`-replication-sync-timeout`、既定 10 秒。MySQL の `rpl_semi_sync_source_timeout` と同じ）を過ぎても知らせがなければ、OK を返して非同期に切り替え、ログに出す。レプリカが本番の書いた最後のコミットまで追いついたら（知らせの位置 ≥ `written`）同期に戻り、ログに出す。起動したときは非同期から始め、レプリカが追いついたら同期にする（レプリカのない本番が待たないように）。0 なら常に非同期（段階 24 と同じ）。書き込みが続いていると、レプリカは 1 回分遅れたままで同期に戻れないことがある（MySQL と同じ規則）。
- 止めるとき: 実行中の文を終わらせ（同期なら知らせを待つ）、AUTO_INCREMENT のカウンタを保存し、最後のコミットの知らせを待ってから（知らせが待ち時間のあいだ進まなければやめる。進んでいる間は、適用に時間のかかるレプリカを待ち続ける。最近来ていない、またはエラーになったレプリカは待たない）、「最後のコミットの時刻と、知らせたレプリカ（または知らせがない）」をログに 1 行出し、送り出しを閉じる。その後はコミットしない。
- 状態: 本番の `heimdb_status` に、同期の状態（`sync`、`async`、`off`）、切り替えた時刻と非同期に切り替えた回数、知らせを待った時間の平均、知らせを待っているコミット。本番は応答のヘッダに同期の状態と書いた最後のコミットを入れ、レプリカの `heimdb_status` にも出す（本番のマシンが壊れても、レプリカだけで判断できるように）。
- 切り替えの手順（README）: 本番を止め、ログの最後の行で、最後のコミットがレプリカに届いたかを確かめて昇格させる。本番のマシンが壊れたときは、レプリカの状態で、本番が同期で、本番が止まった時刻が最後の連絡の時刻 + 待ち時間より（時計のずれの分）前なら、OK を返したコミットはすべてレプリカにある。最後の連絡の時刻は、本番がそれより後に待ち始めたコミットしか知らせを待っていないと言える時刻にする: 最後の応答が空ならその要求を送った時刻、記録を受け取ったならその前の要求を送った時刻（受け取った記録は、前の要求の読み出しより後に書かれた）。受け取って適用し終えた時刻や、最後の要求を送った時刻では、適用やつなぎ直しに時間がかかったときに、本番が非同期に切り替わった後になる。本番の状態は、記録を受け取りきった応答のものだけを使う。レプリカが複数台なら、いちばん進んだレプリカで判断し、それを昇格させる。古い本番は、知らせを待っていたコミット（OK は返していない）を持ちうるので、レプリカとしてつながず、バックアップから作り直す。落ちた本番を本番のまま起動し直すと、知らせを待っていたコミットが見えるようになる（MySQL と同じ。記録はレプリカに送られるので食い違わない）。
- 完了条件: 同期の間は、本番を強制終了してもレプリカにすべての OK を返したコミットがある（テスト。強制終了の直前に同期だったことを確かめる）。レプリカを止めても本番の書き込みは待ち時間の後に続き、レプリカが戻ると同期に戻る。手順書どおりに、本物の WordPress を本番からレプリカに切り替えられる。
- 記録だけ: バージョンのないデータ（ブランチの作成、ユーザー、AUTO_INCREMENT のカウンタ、マージの記録）は、知らせを待つ間にもほかの接続から見えることがある。ロックを持たずに最新のテーブル定義を読む運用の操作（差分、マージ、一時テーブルの名前）も同じ。レプリカは本番より先にコミットを見せることがある。1 つの文で何度もコミットする操作（複数の操作の `ALTER TABLE`、ブランチの削除、マージ）と、ほかの接続が AUTO_INCREMENT を進めた後の読み取りだけの `COMMIT`（カウンタの保存）は、そのたびに知らせを待つ。大きなコミット（`ALTER TABLE` の書き直し、復元）は、レプリカの適用が待ち時間を超えて、非同期に切り替わることがある。適用がいつも待ち時間より遅いレプリカでは、同期に戻るたびに書き込みが待ち時間だけ止まる（MySQL と同じ）。復元のプレビュー（`heimdb_restore_preview`）は、知らせを待っているコミットのバージョンも数えることがある。レプリカが送り出しもする（連鎖する）ときは同期にしない（自分ではコミットしない）。
- 実装: `Store.Update` は、Pebble に書いた後に `written` を進めて記録を送り出し、`SetCommitWait` で渡された関数（`replication.Primary.WaitAck`）で知らせを待ってから `committed` を進める。本番は、記録で確かめた要求の `after` の最大を知らせの位置にする。`AS OF` の時刻は `committed` までにする（`Database.asOfTS`）。止めるときは、実行中の文、AUTO_INCREMENT の保存（`Store.FlushAutoIncrements`）、最後の知らせの確認とログ（`Primary.Finish`）、送り出しを閉じる、の順。本番の `heimdb_status` に `replication_sync`、`replication_sync_since`、`replication_sync_timeout`、`replication_sync_async_switches`、`replication_sync_ack_wait_avg`、`pending_commit`、レプリカに `replication_primary_sync`、`replication_primary_last_commit`。応答のヘッダ `X-HeimDB-Sync`。
- 結果:
  - テスト: Store とバックエンド（知らせを待つコミットは、ふつうの読み取りでも今と未来の時刻の `AS OF` でも見えず、`heimdb_status` に出る。`AS OF` の制限を外すと落ちる）、送受信（同期ならコミットが返ったときレプリカが適用している。レプリカが止まると待ち時間の後に非同期、戻ると同期。本番の記録にない位置は知らせにならない。確かめる前に数えると落ちる）、HeimDB のプロセス（同期の間に 4 本の書き込みを続け、レプリカを一時停止して本番を強制終了しても、OK を受け取ったコミットはすべてレプリカにある。待たないようにすると 455 件のうち 224 件が欠けて落ちる。レプリカを止めて書き、戻して同期に戻り、止めるときのログに知らせたレプリカが出る）。段階 24 の結合テストに、昇格の後の AUTO_INCREMENT を足した。Go のテストは 292 件（-race でも成功）。
  - WordPress（記事 5,000 件のベンチマークのデータの写し）: 同期の本番に wp-cli で記事、ユーザー、オプションを書いた直後に本番を強制終了した。レプリカの `replication_primary_sync` は `sync`、最後に受け取った時刻は 1 秒前で、手順書の条件を満たした。レプリカを昇格させると、トップページに記事と説明が出て、作ったユーザーで管理画面にログインでき、記事を作れた。
  - PHPUnit の全テストを同期のレプリカをつないで流し、差は 43 のまま（同じテスト。panic は 0。非同期への切り替えは 0 回、知らせの待ちは平均 4.8 ms）。ベンチマーク（同じマシンのレプリカ）: 知らせの待ちは 1 回のコミットで約 5 ms。コメントの追加は 13.5 ms から 24 ms、記事の作成は 163 ms から 204 ms、ページの表示は変わらない（`docs/bench.md`）。
  - レビューで直した: レプリカの最後の連絡の時刻を、受け取って適用し終えた時刻にしていたので、適用に時間がかかると本番はその時刻 + 待ち時間より前に非同期に切り替わり、README の「本番のマシンが壊れたとき」の判断が成り立たなかった。上の定義の時刻にした（最後の要求を送った時刻でも、つなぎ直したときに成り立たない）。止めるときの待ちは、知らせが進んでいる間は延ばす（README の「レプリカが追いつくまで待つ」は、待つ手段がなかった。追いつかなければ起動し直して追いつかせる手順にした）。同期しない構成で止めるときのログを警告にしない。エラーになったレプリカは待たない。連鎖するレプリカは同期にしない。README に、複数台のときと、`last commit` の行がないときと、適用がいつも遅いレプリカのことを書いた。
    - テスト: 連絡の時刻は、待ち受けで受け取って適用に時間がかかるときも、つなぎ直して受け取るときも、本番が待ち始めた時刻より前（適用し終えた時刻と、最後の要求を送った時刻のどちらでも落ちる）。止めるときは知らせが進む間は待ち（延ばさないと落ちる）、来ていない・エラー・古いレプリカは待たない（エラーを数えると落ちる）。低い位置の知らせが先に来ても同期のまま返る。連鎖するレプリカは同期にしない。レプリカ 2 台で、遅れた方も本番を同期と見る。強制終了のテストは、一時停止したレプリカを必ず再開し、OK を受け取っていない行が書き込み手の数以下であることも確かめる。Go のテストは 301 件（-race でも成功）。PHPUnit は実行していない（WordPress の文の経路は変えていない）。
- 先の候補（今は作らない）: レプリカのディスクの確定を待たずに知らせる設定（MySQL の `sync_relay_log` の既定と同じ強さ）。レプリカを 2 台にしてどちらか 1 台の知らせで返す（今も 1 台の知らせで返すが、切り替えの手順は 1 台を前提にする）。3 台で Raft を使う自動の切り替え（CockroachDB の 1 つのレンジと同じ形）。

## 段階 26: 通信の暗号化（TLS）

- 目的: WordPress から HeimDB への接続も、本番からレプリカへの記録の送り出しも暗号化していないので、DB を別のマシンや拠点に置くには SSH のトンネルが要る。TLS で暗号化して、トンネルなしで置けるようにする。
- 方針: `-tls-cert`、`-tls-key`（PEM）を指定すると、MySQL の接続で TLS を受け付け（クライアントが望んだとき。go-mysql-server の `server.Config.TLSConfig`）、同じ証明書でレプリカへの送り出し（`-replication-addr`）を HTTPS だけにする。`-require-tls` で TLS でない MySQL の接続を拒否する（`-tls-cert` がなければ起動でエラー）。TLS 1.2 以上。証明書の差し替えは起動し直して行う（WordPress は要求ごとにつなぎ直すので数秒で済む。自前の CA なら期限を長くできる）。
- 必須の確かめは HeimDB で行う: vitess の `RequireSecureTransport` は、TLS でない接続にエラーを送った後 `return` せずに認証を続ける（`go/mysql/server.go` の 483〜485 行。しかもエラーは `*SQLError` でないので 1105 になる）ので使わない。`ProtocolListenerFactory` で gms の既定の処理（`MySQLProtocolListenerFactory`）を写し、認証の部品（`AuthServer`）を包む。各方式の `HandleAuthPluginData`（パスワードを確かめる唯一の入り口。`server.go:549`）の前に、TLS でない接続を MySQL と同じエラー 3159（`ER_SECURE_TRANSPORT_REQUIRED`）で拒否する。エラーは `*mysql.SQLError` のまま返す（包むと番号が伝わらない）。`-no-auth` も同じ入り口を通る。認証し直す経路（`COM_CHANGE_USER`）は vitess にない。
- WordPress の側は暗号化するが、HeimDB の証明書を確かめない: WordPress 本体は `MYSQL_CLIENT_FLAGS`（`MYSQLI_CLIENT_SSL`）しか渡せず、CA を渡す手段がない。mysqlnd は CA などを渡さないと証明書を確かめない（自己署名でもつながる）。盗聴は防げるが、なりすましの中継は防げないので、WordPress と HeimDB はプライベートなネットワークか VPN の中に置く（README）。`wpdb` の接続を差し替える `db.php` は作らない。証明書を確かめるのは、mysql のクライアント、レプリカ、Go のテスト。
- レプリカ: `-replicate-from https://host:port` で HTTPS。本番の証明書は `-replication-ca`（PEM）か OS が信頼する証明書で確かめる。`-replication-ca` があれば、方式のない `host:port` も https にする。`http://` と `-replication-ca` の組は起動でエラー。確かめられないときは、エラーを状態とログに出して間をおいてやり直す（止めない）。合言葉は TLS の中で送られる。
- 状態: `heimdb_status` に `tls`（`off`、`on`、`required`）、証明書の期限 `tls_cert_not_after`、この接続が TLS か `connection_tls`。起動のログに証明書の名前（SAN）と期限を出す。
- 完了条件:
  - Go のテスト（CA と証明書をテストの中で作る）: TLS を受け付けて必須にしないとき、暗号化しない接続も使え、TLS の接続で証明書とホスト名を確かめられる。`-require-tls` で、暗号化しない接続は正しいパスワードでも誤ったパスワードでも 3159（パスワードを確かめる前に拒否する）、`-no-auth` でも 3159。起動のエラー（`-require-tls` だけ、証明書か鍵だけ、読めないファイル、組にならない証明書と鍵）。HTTPS でレプリカが追いつき、違う CA では止まらずにエラーを出し、正しい CA で起動し直すと続きから追いつく。`http://` と CA の組は起動のエラー。
  - mysql 8.0 のクライアント（3307 の MySQL のコンテナ）: CA を写して `--ssl-mode=VERIFY_CA` と `VERIFY_IDENTITY`（SAN に `host.docker.internal`）、既定の認証（方式の切り替えを含む）で接続でき、mysqldump も通る。
  - WordPress: `MYSQL_CLIENT_FLAGS` を指定して `-require-tls` の HeimDB でトップページ、管理画面、記事の作成が動き（暗号化していることは `-require-tls` で保証する。証明書は確かめない）、指定しなければ拒否される。
  - PHPUnit の全テストを `-require-tls` で流し、ベースラインとの差が 43 のまま。
  - ベンチマーク: TLS あり（`-require-tls`）となしで、ページの表示と記事の作成を比べる（`docs/bench.md`）。README の証明書の例は ECDSA P-256（RSA より握手が速い）。
- 実装: `internal/backend/tls.go`（証明書の読み込み `LoadTLS`、受け付けを作る `ListenerFactory` と、TLS を確かめる認証の包み）。`cmd/heimdb` で MySQL の `server.Config.TLSConfig` と、送り出しの `http.Server.ServeTLS` に別々の `tls.Config`（同じ証明書）を渡す。レプリカは `replication.Source` で方式を決め（ストアを開く前に確かめる）、CA を入れた `http.Transport` で受け取る。`heimdb_status` の `connection_tls` は、接続の能力の `CLIENT_SSL`（vitess が TLS に切り替えたときに立てる）で見る。
- 結果:
  - テスト: HeimDB のプロセスで、TLS を受け付けて必須にしないとき（暗号化しない接続も使える、テストの CA で証明書とホスト名を確かめられる、違う CA と違う名前はクライアントが拒否する、起動のログに証明書の名前）、`-require-tls`（暗号化しない接続は正しいパスワードでも誤ったパスワードでも 3159、`-no-auth` でも 3159、TLS なら誤ったパスワードは 1045）、起動のエラー 8 通り、HTTPS のレプリカ（方式のない `host:port` で HTTPS の本番につなぐと「HTTP request to an HTTPS server」、違う CA で「certificate」のエラーを出して動き続け、正しい CA で起動し直すと追いつく）。認証の包みをやめて vitess の `RequireSecureTransport` にすると、3159 ではなく 1105 になって落ちる。Go のテストは 307 件（-race でも成功）。
  - mysql 8.0 のクライアント（3307 の MySQL のコンテナから `host.docker.internal`）: `VERIFY_IDENTITY` と `VERIFY_CA` で接続でき、既定（`PREFERRED`）でも TLS（`TLS_AES_128_GCM_SHA256`）になり、既定の認証で入れた。mysqldump も通った。`DISABLED` は 3159、MySQL の CA では証明書の確認で失敗した。
  - WordPress（ベンチマークのデータ）: `-require-tls` の HeimDB で、`MYSQL_CLIENT_FLAGS` がなければ「データベース接続確立エラー」、あればトップページ、管理画面（ログインしてから）、wp-cli での記事の作成と削除が動いた。
  - PHPUnit の全テストを `-require-tls` と `MYSQL_CLIENT_FLAGS` で流し、差は 43 のまま（同じテスト。panic は 0）。
  - ベンチマーク: 1 回の接続が 0.98 ms から 2.45 ms になるが、ページの表示と書き込みは揺れの範囲で同じ（`docs/bench.md`）。
  - レビューで直した: 期限切れか、まだ有効でない証明書でも黙って起動していた（WordPress は確かめないので気づけない）。起動は止めずに警告を出す。本番の指定のユーザー名、パス、クエリ、フラグメントを黙って捨てていたので、起動のエラーにする。TLS のときだけレプリカへの送り出しが HTTP/2 になっていたので、TLS なしと同じ HTTP/1.1 にした。テストで起動した HeimDB を、テストが途中で落ちても必ず止める。`tls_cert_not_after` の書式をほかの時刻と揃えた。
    - テスト: 期限切れ、まだ有効でない、有効な証明書の起動とログ、本番の指定の読み取り（13 通り）、送り出しが HTTP/2 を選ばない（どれも直す前のコードで落ちることを確かめた）。Go のテストは 309 件（-race でも成功）。
- 記録だけ: レプリカに `-tls-cert` を付けたまま `http://` の本番から受け取っても警告しない（MySQL の側の設定として正当）。`caching_sha2_password` は TLS なら技術的には動くが、対応しないまま（段階 14 では TLS の段階で使えるようにするとしていたが、WordPress は使わず、go-mysql-server の実装はキャッシュがなく毎回パスワードを送る完全な認証になる）。`CREATE USER ... REQUIRE SSL` は効かない（全体の `-require-tls` だけ）。クライアントの証明書での認証、`Ssl_cipher` などの状態変数は作らない。TLS の握手の途中で止まったクライアントは接続を持ち続ける（暗号化しない握手と同じ。読み取りの待ち時間を設定していない）。クライアントが最初から `mysql_clear_password` を選ぶと、暗号化しない接続でもパスワードがそのまま送られる（クライアントの選択。`-require-tls` なら拒否する）。

## 段階 27: インデックスだけで読む

- 背景: 段階 23 の後に残った最も大きい差は、記事の作成のたびに 3 回走るカテゴリの term 数（記事 5,000 件で 1 回 28 ms、MySQL 6 ms）。HeimDB は `wp_term_relationships` のインデックスで 5,001 行を取り、1 行ごとに `wp_posts` を主キーで引いて、本文を含む行全体を復号していた。MySQL は `type_status_author` のインデックスだけで記事の ID を取り（Covering index lookup）、`wp_term_relationships` の主キーを引く。HeimDB のインデックスのキーは文字列を照合順序の重みで持つので、`post_status` の値を返せない。

  - C. コスト計算で、インデックスだけで読める読み出しを軽く見積もり、term 数の JOIN を MySQL と同じ順（`wp_posts` が先）にする。
- 完了条件: term 数の JOIN の結果を本物の MySQL のゴールデンと比べる。インデックスだけで読むときのテスト（照合順序で等しい違う値、NULL、プレフィックス長のあるインデックス、AS OF、ブランチとマージ、自分の未コミットの変更、ALTER の後、インデックスの作成の後、照合順序で等しい値への更新）。符号化の単体テスト。PHPUnit の全テストで差が 43 から増えない。ベンチマークの前後を `docs/bench.md` に残す（目安: カテゴリの term 数が 10 ms 前後、記事の作成が 100 ms に近づく）。
- 実装:

- 結果:

## 段階 28: 小さな速さの改善

- 背景: 段階 27 の後も、承認済みコメントの数（17〜18 ms、MySQL 約 10 ms）、カテゴリの term 数（約 16 ms、MySQL 約 6 ms）、投稿一覧（約 85 ms、MySQL 55 ms）が遅い。段階 27 のレビュー（Fable）で、行ごとのメモリ確保、文字列の定数との比較の型の変換、JOIN の方法、インデックスの選び方が原因と分かった。
- 方針（1 つ入れるごとに効果を測り、効かないものや MySQL と並び順が変わるものはやめて記録だけにする）:
  - A. 段階 27 のレビューの指摘: `Txn.RefreshSnapshot` で `RowReader` を捨てる。キーを持つインデックスの一覧をテーブルを作るときに 1 回だけ作る。テストの抜け（明示的なトランザクションの中の未コミットの更新をインデックスだけで読む、ROLLBACK TO SAVEPOINT の後の主キーの 1 行の読み出し）。
  - B. 行ごとのメモリ確保を減らす（主キーで 1 行を引くときに行の値をコピーしない、範囲の条件にも並べ替えにも使わない列を復号しない、主キーの符号化に行を作らない、インデックスのエントリのコピーを 1 回にする）。
  - C. 文字列の列と文字列の定数の比較で、定数を列の型にする（MySQL も列の照合順序で比べる）。値が 1 つの `IN` と `NOT IN` を `=` と `<>` にする。
  - D. go-mysql-server が選んだインデックスで本体の行を引くとき、先頭の等号の列が同じで、文が使う列をすべて持つインデックスがあれば替える（投稿一覧の `type_status_author` を `type_status_date` に）。本物の MySQL の `EXPLAIN` で同じインデックスを選ぶことを確かめる。
  - E. 片側をインデックスだけで読めるハッシュ JOIN のコストを軽く見積もる（カテゴリの term 数）。
- 完了条件: Go のテストが通る（-race でも）。PHPUnit の全テストで差が 43 から増えない。C、D、E の文を本物の MySQL のゴールデンと比べる。ベンチマークの前後を `docs/bench.md` に残す（目安: 承認済みコメントの数 13 ms 以下、term 数 11 ms 以下、投稿一覧 75 ms 以下）。
- 作らないもの: コミットの fsync を間隔でまとめる設定（障害で失う範囲が変わる。本番の Linux で差を測ってから決める）。インデックスの範囲を必要な分だけ読む（次の段階の候補）。
- 実装:
  - A: 上のとおり。`Table.keyIndexes` は `newTable` で作った一覧を返す（ALTER は `newTable` で作り直したテーブルに置き換わる）。
  - B: `RowReader.Peek`（値を写さずに返す。復号で写すので、主キーで 1 行を引く近道と `pkRowIter` が使う）。`pkRowIter` の先読みは、値ではなく復号した行を持つ。区間がちょうど条件と同じで（範囲の条件がない）プレフィックス長もなければ、文が使う列と主キーだけを復号する（`projection.want` を使い回す）。主キーの符号化は `rowenc.AppendPKValue` で行を作らずに行う。層を重ねる走査（`scanLayered`）はエントリと値を 1 回の確保で写し、`ScanIndex` の 2 回目の写しをやめた。
  - C: 解析の後のルール `columnTypedLiterals`。WHERE（Filter）の中の、文字列だけの型の列と同じ文字セットの文字列の定数の比較（=、<>、<、<=、>、>=、<=>）で、定数の型を列の型にする。値が 1 つの IN は = にする（NOT IN は NOT (=)）。go-mysql-server は文字列の定数の照合順序の強さをいつも 4（列より弱い）とするので、`_utf8mb4'x' COLLATE ...` のように定数にまとめられた照合順序も、もともと使っていなかった（比べ方は変わらない）。
  - D: 解析の後のルール `coveringIndexForSort`（`narrowIndexRanges` の前）。Sort か TopN の下（Project と Filter を挟む）の、インデックスの範囲が「先頭の等号の列、残りはすべての値」の読み出しで、そのインデックスでは本体の行を引くとき、先頭の列が同じで文が使う列をすべてエントリに持つインデックス（プレフィックス長なし）に替える。上に Sort があるので、結果の並びは同順位の行だけが変わる。
  - E: `coster` で、ハッシュ JOIN の作る側（右）が、文が使う列をすべてエントリに持つセカンダリインデックスの読み出しで、作る側の主キーのすべての列で引くとき、作る側の 1 行を 3 から 1.5 に見積もる（`coveredPKHash`）。主キーで引くので、左の 1 行に当たる行は高々 1 行で、行の並びは同じ左から主キーで引く lookup JOIN と同じになる（主キーでない列で引く場合も軽く見積もると、ORDER BY のない JOIN で、term_relationships を作る側にして wp_posts の順に返し、MySQL と並びが違った）。作る側の見積もりが 100 行未満なら変えない（統計の見積もりが外れると作る側をすべて読む。少なければ差もない）。
- 結果:
  - ベンチマーク（`docs/bench.md` の「段階 28 の後」。交互に 2 回ずつ）: カテゴリの term 数 14.3 / 14.7 → 9.3 / 10.2 ms（MySQL 5.9〜7.0 ms）、承認済みコメントの数 17.6 / 18.5 → 11.4 / 12.5 ms（MySQL 9.9〜11.3 ms）、投稿一覧の文 9.3 / 9.6 → 4.9 / 5.9 ms（MySQL 4.1〜4.9 ms）。ダッシュボード 87 / 85 → 68 / 66 ms、投稿一覧 86 / 88 → 70 / 67 ms。目安はどれも満たした。記事の作成と削除はほとんど変わらない（コミットの fsync が大半）。
  - プロセスの中のベンチマーク（記事 5,000 件、コメント 2 万件）では、B で term 数 10.1 → 8.6 ms、承認済みコメントの数 15.0 → 14.0 ms、投稿一覧の文 7.9 → 6.6 ms。C で承認済みコメントの数 14.0 → 9.2 ms。D で投稿一覧の文 6.6 → 3.0 ms。E で term 数 8.6 → 5.4 ms。
  - テスト: 段階 28 の文を本物の MySQL のゴールデン（`internal/testdata/speed_golden.txt`）と比べる（照合順序で等しい違う値との比較と、定数が左、<=>、値が 1 つの IN と NOT IN と NULL の列、COLLATE の付いた定数、数値の定数と列、UPDATE と DELETE の条件、同じ日時の記事を含む投稿一覧、ハッシュ JOIN になる量の term 数と ORDER BY のない JOIN の並び）。投稿一覧が `type_status_date` を読んで本体の行を引かないこと、カテゴリの term 数がハッシュ JOIN、タグの term 数が lookup JOIN のままであること（`TestSpeedPlans`）。段階 27 のゴールデンに、明示的なトランザクションの中の未コミットの更新をインデックスだけで読む文と、ROLLBACK TO SAVEPOINT の後に主キーで 1 行を引く文を足した。`RefreshSnapshot` で `RowReader` を作り直すこと。直す前のコード（`RefreshSnapshot` で捨てない、C と D と E のルールがない、E で主キーでない列で引く場合も軽く見積もる）で落ちることを確かめた。C は、直す前は `meta_key <=> '_THUMB'` が MySQL と違った（照合順序を使わずに比べていた）のも直った。D は、直す前は同じ日時の記事の並びが MySQL と違った（type_status_author の順）のも直った。Go のテストは 318 件（-race でも成功）。
  - PHPUnit の全テスト: 本物で成功し HeimDB で失敗するものは 43 で、段階 27 と同じテスト。接続の切断と panic は 0。
- 記録だけ: B の、範囲の条件にも並べ替えにも使わない列を復号しないことは、go-mysql-server が条件の Filter をいつも残す（条件の列はいつも文が使う列に入る）ので、復号を絞りすぎてもテストで落ちない（段階 27 と同じ）。E の 100 行の下限も、テストのデータでは見積もりが 0 行で効かないので、外しても落ちない。`_binary'Post'` との比較は、MySQL は照合順序で比べて大文字と小文字の違う行も返すが、HeimDB は返さない（段階 28 より前から。WordPress は使わない）。投稿一覧で LIMIT が小さい（LIMIT 0, 3 など）と、同じ日時の記事の並びが MySQL と違う（MySQL は優先度付きキューで並べ替える。段階 28 より前から）。term 数の形の文で ORDER BY がないと、MySQL は wp_posts から読むので行の並びが違う（段階 27 から）。

## 段階 29: 統計の間引き方

- 背景: GCE（Linux）で測ると、fsync は記事の作成の主な時間ではなかった（`docs/bench.md` の「Linux（GCE）での書き込み」）。記事の作成の MySQL との差（約 40 ms）の半分は、`add_metadata` の重複の確認 `SELECT COUNT(*) FROM wp_postmeta WHERE meta_key = '_encloseme' AND post_id = N`（2 回で 23 ms、MySQL 0.7 ms）。統計を作るときに 2 万行を超える表は等間隔（`i % step == 0`）に間引くので、記事ごとに続けて挿入されるメタの組（`_pingme` と `_encloseme`。実際のサイトでも `_edit_lock` と `_edit_last`、`_wp_attached_file` と `_wp_attachment_metadata` など）の片方だけが残る。残らなかったキーは 0 行と見積もられ、go-mysql-server が `meta_key` のインデックスで同じキーの数千行を読む。
- 方針: 間引く行を、符号化した主キーのハッシュ（FNV-1a を splitmix64 の最後の段で混ぜる）で決める（`hash % step == 0`）。行の並びの周期と重ならない。同じデータなら同じ統計になる（ハッシュは固定）ことは変えない。行を挿入しても、ほかの行が残るかどうかは変わらない。バケットの作り方、読む行の上限、コストの計算は変えない。
- 完了条件: Go のテストが通る（-race でも）。記事ごとに組で挿入した 2 万行を超えるメタで、どのキーでも `meta_key = X AND post_id = N` が `post_id` のインデックスを使う（等間隔の間引きに戻すと落ちる）。PHPUnit の全テストで差が 43 から増えない。手元と GCE の `writes.php` の前後を `docs/bench.md` に残す（目安: 記事の作成が 20 ms 前後速くなる）。
- 作らないもの: go-mysql-server は等号の見積もりに値を含むバケット全体の行数を使う（`post_id = N` は約 5 行でも約 250 行）ので、250 行より少ないメタのキーでは今後も `meta_key` を選ぶ（MySQL はインデックスを引いて数えて `post_id` を選ぶ）。読む行は 250 行以下なので直さない。カテゴリの term 数の残りの差（記事の作成 1 回で 39 ms、MySQL 23 ms）は別の候補。
- 実装: `buildStats` の間引きを `sampled`（statistics.go）に替えた。FNV-1a だけでは、下位のビットが各バイトの下位のビットだけで決まり（掛ける素数が奇数）、連番の主キーでは 256 行の中で偶数行と奇数行のどちらかだけが残る（全体の割合は合うので、組のどちらのキーも統計に入り、メタのテストでは落ちない）。splitmix64 の最後の段で混ぜてから割る。
- 結果:
  - ベンチマーク（`docs/bench.md` の「段階 29 の後」。交互に 2 回ずつ）: 記事の作成が GCE で 116 / 120 → 99 / 100 ms、手元で 150 / 143 → 113 / 106 ms（ほかのアプリが CPU を使い切っていた。止めて測り直すと 144 / 139 → 124 / 131 ms で、マシン全体が段階 28 の後の約 2 倍遅かった）。メタの重複の確認は記事 1 件あたり 25 ms から 3 ms 未満。ほかの書き込みは揺れの範囲で同じ。
  - テスト: 記事ごとに組で挿入した 25,002 行のメタで、どのキーでもメタのキーと記事の ID で引く文が `post_id` のインデックスを使うこと（`TestStatisticsSamplePairedMeta`。等間隔の間引きに戻すと落ちる）。連番の主キーで、組のどの位置の行も step 行に 1 行ほど残り、隣り合う 2 行が両方残る割合が step² 組に 1 組に近いこと（`TestSampledNotPeriodic`。splitmix64 の段を外すと落ちる）。Go のテストは 320 件（-race でも成功）。
  - PHPUnit の全テスト: 本物で成功し HeimDB で失敗するものは 43 で、段階 28 と同じテスト。接続の切断と panic は 0。
- 記録だけ: `EXPLAIN PLAN` は `SELECT COUNT(*)` の文で `result max1Row iterator returned more than one row` のエラーになる（go-mysql-server。テストは `SELECT meta_id` で確かめた）。`internal/replication` の `TestReplicaReceivesWhileWaiting` は、ときどき「the replica does not see the branch」で落ちる（段階 29 の前の HEAD でも 15 回に 3 回。最後のコミットの位置が追いついた後で、ブランチの一覧がまだ読み直されていないと見られる）。

## 段階 30: レプリカの位置を、メモリの内容を作り直してから進める

- 背景: `TestReplicaReceivesWhileWaiting` がときどき落ちる（段階 29 の記録）。レプリカの `ApplyRecords` は、記録を 1 つ適用するたびに位置（`LastCommitted`）を進め、ブランチの一覧の読み直し（`refreshAfterApply`）と適用の通知（`onApply`。ユーザーと権限の読み直し、行数の見積もり）はその後に行う。その間にレプリカで読むと、位置は本番に追いついているのに、本番で作ったばかりのブランチのデータベースがない、作ったばかりのユーザーでログインできない、ということが起きる（とても短い間だけ）。同期のレプリカの知らせは、読み直しの後の次の要求で届くので、同期の保証には関わらない。
- 方針: ループの中では Pebble への書き込みと `lastTS`、`written`（記録の配信の待ちが使う）だけを進め、`refreshAfterApply` と `onApply` の通知の後で位置（`committed`）を進めて `notifyCommit` する。位置が X に達したら、X までのブランチ、ユーザー、行数の見積もりはメモリに反映済み。途中で失敗しても、適用してディスクに確定した分まで位置を進める（今と同じ）。`Applied.Through` は適用した最後の時刻にする。本番の `Update` と `CreateBranch` は変えない（ブランチを作ったセッションには戻った時点で見える）。
- 完了条件: `onApply` の通知の中で止めている間は位置が前のままで、通知の後に位置が進みブランチが見える単体テスト（今のコードでは毎回落ちる）。`TestReplicaReceivesWhileWaiting` が 50 回続けて落ちない。Go のテストが通る（-race でも）。レプリカの適用の順序だけの変更なので、PHPUnit とベンチマークは流さない。
- 結果: `TestReplicaPositionAfterRefresh`（store）で、`onApply` の通知の中ではブランチが読み込み済みで、位置は前のまま、通知の後に位置が本番に追いつくことを確かめた（直す前のコードでは、通知の中で位置がもう進んでいて落ちた）。`TestReplicaReceivesWhileWaiting` は 50 回続けて成功（直す前は 15 回に 3 回落ちた）、-race でも 20 回続けて成功。Go のテストは 321 件（-race でも成功）。
- 段階 29 と 30 のレビュー（Fable）で直したこと: レプリカでも、記録の適用の後にメモリの内容を作り直す間は `Written` が `LastCommitted` より先にあり、`heimdb_status` に本番の同期の知らせ待ちの `pending_commit` が出ていた。レプリカでは出さない。`ApplyRecords` は位置を書き込みのロックの外で進めるので、同時に呼ばないことをコメントに書いた。`TestReplicaPositionAfterRefresh` で、通知の中で `Written` はもう進んでいることも確かめる。段階 29 の結果に、手元の測り直しの値を足した。
