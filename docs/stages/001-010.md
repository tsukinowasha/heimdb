# 段階 0〜10

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 0: インターフェースの把握

- 使用する go-mysql-server のバージョンを固定し、`memory` パッケージを読んで実装すべきインターフェース（トランザクションとセッションのものを含む）を `docs/gms-interfaces.md` にまとめる（段階 67 で消した。フォークの後は `internal/sqlengine` のコードを正とする）。
- 完了条件: 各インターフェースのメソッドと、`memory` での実装箇所が一覧になっている。

## 段階 1: 符号化とスキーマの永続化

- 順序を保つキー符号化を実装し、単体テストで「元の値の順序 = バイト列の順序」を検証する（プロパティテスト推奨）。
- テーブル定義をバージョン付きで保存し、起動時に読み直す。`CREATE TABLE` にインデックスがあると go-mysql-server が `IndexAlterableTable` と `IndexAddressable` を要求するため、インデックス定義の保存と `GetIndexes` も実装する（検索には使わせない）。
- 完了条件: WordPress コアの `CREATE TABLE` がすべて通り、サーバを再起動しても `SHOW TABLES`、`SHOW CREATE TABLE`、`SHOW INDEX FROM` の結果が変わらない（テーブルの削除と名前変更の後も含む）。

## 段階 2: バージョン付きの行の読み書きと最小限のトランザクション

- ブランチは `main` のみ。キーにはバージョンと時刻を含める。INSERT、UPDATE、DELETE、全件走査、主キー検索、AUTO\_INCREMENT を実装する。
- セッションごとに Pebble の `IndexedBatch` を持たせ、`COMMIT` で確定、`ROLLBACK` で破棄する。自分の未コミットの変更は自分だけが読める。テストスイートは全テストを `START TRANSACTION` と `ROLLBACK` で囲むため、これがないとテスト間でデータが漏れる。
- 完了条件: WordPress のインストーラが通り、option グループがベースラインと一致する。再起動後も管理画面にログインできる。

## 段階 3: タイムトラベル

- `SELECT ... AS OF <時刻>` を受け付け、指定時刻以前の最新バージョンを読む。古いバージョンを消す保持期間の方針も決める。
- 完了条件: 最初のデモが動く。

## 段階 4: セカンダリインデックス

- インデックスの書き込み、検索、範囲走査、逆方向走査を実装し、go-mysql-server にインデックスの存在を伝える。`SHOW INDEX FROM` も正しく返す。
- 完了条件: `test_query_sticky_posts_change` が単独で通り、meta グループがベースラインと一致する。

## 段階 5: トランザクションの分離

- 読み取りをトランザクション開始時刻のスナップショットに固定し、同じ行への同時書き込みを検出する。分離レベルは InnoDB の既定（REPEATABLE READ）に近づける。
- 実装した方針（WordPress での利用を前提にした割り切り）:
  - 書き込むトランザクションはブランチ全体で一度に 1 つ。ブランチの書き込みロックを COMMIT か ROLLBACK まで持つ。ロックが 1 つなのでデッドロックは起きない。待ち時間の上限（既定 50 秒、`-lock-wait-timeout`）を超えたらエラー 1205。
  - 読み取りは、最初に読んだ時点のコミット時刻以前のバージョンと自分の変更を見る（スナップショット）。
  - 書き換える文（INSERT、UPDATE、DELETE、REPLACE）は、行を読む前にロックを取る。スナップショットがロックの後に決まるので、自動コミットの文は競合しない。主キーと一意制約の検査は、ロックを持った状態で最新の確定済みデータに対して行う。
  - トランザクションの中で読んだ後に、他のトランザクションが変更した行を書こうとしたら、エラー 1213（やり直し）。InnoDB は最新の値で更新を続けるが、go-mysql-server の構造上再現できない。
- 完了条件: query グループがベースラインと一致する。

## 段階 5.5: 列の変更、TRUNCATE、一時テーブル

- 列の追加・削除・型の変更（go-mysql-server の `RewritableTable`）は、新しい形の行を**新しいテーブル ID** に書き直し、テーブル定義の新しいバージョンをその ID に向ける。行、インデックス、テーブル定義、AUTO_INCREMENT の引き継ぎを 1 回の DDL でコミットする。古い ID のデータは残るので、`AS OF` で変更前の定義と行がそのまま読める。列名、DEFAULT、コメントだけの変更は、テーブル定義だけを更新する。
- `TRUNCATE` 文は、新しいテーブル ID を割り当てる DDL（AUTO_INCREMENT は 1 に戻る）。go-mysql-server は AUTO_INCREMENT 列のないテーブルへの条件のない `DELETE` も `Truncate` に変換するので、`DELETE` から来たときはトランザクションの中で全行を削除する。
- 一時テーブルは、セッション専用の隠しブランチに普通のテーブルとして作り、切断時に捨てる。
- 完了条件: 古い WordPress から最新バージョンへの `wp core update-db` が通り、`SHOW CREATE TABLE` が新規インストールと一致する。ALTER と TRUNCATE のゴールデンテスト（本物の MySQL と比較）が通る。

## 段階 6: ブランチ

- ブランチの作成、一覧、削除。接続時のデータベース名 `wordpress@<ブランチ名>` でブランチを選ぶ（段階 14 で区切りを `/` から `@` に変えた）。読み取りは自分のキー空間と親の分岐時点を重ね合わせる。
- 実装の方針:
  - ブランチの情報（名前、親、分岐時刻）は `m/branch/<ID>`。分岐時刻は作成時の最後のコミット時刻で、過去の時刻も指定できる。
  - 読み取りは「自分のキー（未コミットの変更を含む）」「親の分岐時刻以前のバージョン」「その親の、さらにその分岐時刻以前のバージョン」…の層を重ね、同じエントリ（行、インデックスのエントリ、テーブル定義）は上の層が勝つ。削除の印も勝つ。スナップショットと `AS OF` は各層に効く（時計はすべてのブランチで共通）。
  - 書き込みは自分のキー空間だけ。書き込みロックはブランチごと。1 つのトランザクションが書けるのは 1 つのブランチだけ（一時テーブルの隠しブランチは別）。
  - 操作は SQL の外部プロシージャ: `CALL heimdb_branch_create(名前[, 親[, 時刻]])`、`CALL heimdb_branch_list()`、`CALL heimdb_branch_delete(名前)`（子があれば拒否）。
  - AUTO_INCREMENT の番号帯: ブランチ ID n（main は 1）の 64 ビットの列は (n - 1) × 10^10 から採番する。main は今のままの番号。32 ビット以下の列は番号帯を分けない（マージで衝突を検出する）。段階 61 で 32 ビットの列にも帯を設けた（main は 10^9 未満、ブランチは 10^9 から上の 10^7 の幅の枠を 100 個使い回す）。
  - 一時テーブルの隠しブランチの ID は 2^62 以上から払い出し、ユーザーのブランチ ID と分ける。
  - テーブルの書き直しと TRUNCATE はブランチの中で新しいテーブル ID になるので、差分とマージ（段階 7）はテーブル ID ではなくテーブル名と主キーで対応づける。
  - ステージングの URL は、WordPress の `wp-config.php` の `WP_HOME` と `WP_SITEURL` で切り替える（DB 側の上書きは作らない）。
- 完了条件: 本番とステージングの 2 つの WordPress が同じ DB の別ブランチで動き、互いの変更が見えない。

## 段階 7: 差分とマージ

- ブランチの差分の表示、競合の検出、マージ。「WordPress 特有の課題」のマージ方針を実装する。
- 完了条件: ステージングで変えた固定ページを本番にマージでき、その間に本番へ入ったコメントが残る。
- 7a（差分、読み取りのみ）と 7b（適用）に分ける。7a の差分を実際の WordPress のデータで確かめてから 7b に進む。
- 実装の方針:
  - 行は「テーブル名 + 同一性の列」で対応づける。同一性の列はふつう主キーで、`wp_options` だけは `option_name`（両側で `add_option` した同名のオプションは option_id が違うため）。
  - 比較は片側ずつ、値で行う。ブランチの変更は「基準のブランチ（AS OF 基準のブランチ時刻）と今のブランチ」の差、親の変更は「基準の親（AS OF 基準の親時刻）と今の親」の差。基準は、最初は両側とも分岐時刻、マージの後はそのマージで親に書いた時刻（親）と、マージが読んだブランチのスナップショットの時刻（ブランチ）。マージで本番を優先した行などは両側の値が一致しないので、共通の基準値を 1 つにしない。
  - 列単位の三方向比較。ブランチだけが変えた列は反映し、親だけが変えた列は残し、両側が同じ列を違う値に変えたら競合。行の追加と削除も同じ考え方で、両側が同じ同一性の行を違う値で追加したら競合。
  - 候補の行は、ブランチの自分のキー空間で基準より後に書かれたエントリから列挙し、親は該当する行だけを読む（親の全件は読まない）。ブランチでテーブルが書き直された（テーブル ID が変わった）ときは、そのテーブルの全行を比べる。
  - マージの基準の時点は、バージョン付きのキー `m/merge/<ブランチID>/<反転時刻>` に、行の反映と同じコミットで書く（キーの時刻が親の基準時刻、値がブランチの基準時刻）。
  - 段階 94 で、親の変更をブランチに取り込む記録 `m/sync/<ブランチID>/<反転時刻>`（キーの時刻が取り込みのコミット時刻、値が読んだ親の時刻 S）を足した。直近の出来事（マージの記録のキーの時刻と取り込みの時刻の新しい方）が取り込みなら、マージと差分は両側の基準を親@S にする（候補は今までどおり、マージの基準のブランチの時刻から）。
  - `db_version` が両側で違えば、差分はエラーを返し、マージは拒否する（片側だけ DB の更新処理を済ませた状態で、形式の違う行を混ぜない）。
  - 列が違うテーブル（ALTER の差）は、テーブル単位で報告し、そのテーブルを除いて続行できる。列は定義のバージョンではなく内容で比べる（dbDelta が毎回 ALTER を出すため）。
  - 7a の結果（実装済み）: `CALL heimdb_branch_diff('staging')` がテーブルごとの要約、`CALL heimdb_branch_diff('staging', 'wp_posts' | '*')` が行ごとの判定（insert、update、delete、skip、conflict、warning）を返す。実際の WordPress（本番とステージング、wp-cli と管理画面の操作）で確かめて、次を方針に加えた。
    - `post_modified` と `post_modified_gmt` は、別の列を変えただけでも両側で変わるので、競合にせず新しい方の値を採る。
    - 両側で同じ自然なキーの行を追加したら、記事（`post_type` と `post_name`）とターム（`slug`）は競合、記事のメタ（記事 ID とキー）は警告。ブロックテーマでエディタを開くと、両側で別々に `wp_global_styles` の記事と `wp_theme` のタームができるため（7b で親の側を採る解決を用意する）。
    - テーブルの削除はマージしない（要約に `dropped on branch` と出す）。
  - 7b では、マージの手続きは最初に親の書き込みロックを取ってから読む。ブランチで新しく作ったテーブルは先に親に作り（別のコミット）、行の反映は 1 つのトランザクションで行う。マージの後に、件数の列を親の側で数え直し、`rewrite_rules` を空にして作り直させる。
  - 7b の競合の解決: `CALL heimdb_branch_resolve(ブランチ, テーブル|'*', id|'*', 'branch'|'parent'|'none')` で記録し、`CALL heimdb_branch_merge(ブランチ)` は解決していない競合が残れば何も書かずに拒否する。
    - 記録は `m/resolve/<ブランチID>/<テーブル名>/<id>`（バージョンなし）。値は解決の種類と、行を指定したときは記録した時点の両側の行の値のハッシュ。ハッシュが合わなくなった解決は `stale` として競合に戻す。ワイルドカード（`*`）はハッシュを持たない。マージの成功とブランチの削除で消す。
    - `branch`: 競合した列もブランチの値にする。同名のオプションと同じ自然なキーの記事・タームは、親の既存の行に主キー、`guid`、件数の列以外をコピーする（ブランチ側の行のメタと関連は反映しない）。削除と変更の競合は、ブランチの側（削除、または作り直し）に従う。主キーが同じ別の行（AUTO_INCREMENT の衝突）、著者がいない記事、列の定義が違うテーブルでは拒否する。
    - `parent`: その行（列の競合なら競合した列）は親のままにする。列の定義が違うテーブルは、そのテーブルを除いてマージする。
    - 親に作らない記事・タームにぶら下がる行（記事のメタ、`term_relationships`、`term_taxonomy`、`termmeta`）は反映しない。
  - 段階 7 のレビューで直したこと:
    - 基準のバージョンにない列（両側で同じ `ALTER TABLE ... ADD COLUMN` をした後）は、その列の既定値とみなして比べる。dbDelta で両側の列が増えても偽の競合にならず、ブランチがその列を変えた行は反映する。
    - 行を指定した解決のハッシュは、競合した列（なければ比べた列。件数の列と更新日時は除く）の両側の値と変化の種類から求める。本番でコメントが付いて `comment_count` が変わっても、解決は無効にならない。
    - 前のマージで反映しなかったブランチの行（方針で飛ばした自動下書き、親の側で解決した行）は、親に分岐の時点にも基準にも今にもなければ、追加として比べる。今回親に作るなら、ぶら下がる行も変わっていなくても候補にする。重複の確認は、分岐の後に親で追加された行（ブランチにも同じ主キーがあるものを除く）と比べる。
    - 親に行がないまま作らない記事・タームは、追加の判定でなくても、ぶら下がる行を反映しない。
    - 競合の行でも、競合しない列に `post_author` があれば、著者が親にいるかを確かめる。
    - テーブルの接頭辞は、親の `option_name` 列を持つ `<接頭辞>options` と `<接頭辞>posts` から見つける（最も短いもの）。マルチサイトは対象外。
    - 行の反映が失敗しても、先に作ったテーブルは親に残る（エラーに書く。再実行でマージできる）。→ 段階 12 のレビューで、新しいテーブルの定義も行と同じトランザクションに書くようにした（マージは 1 つのコミット）。
    - タームの件数は、`link_category` なら関連の行の数、それ以外は公開済みの記事（親が公開済みの添付ファイルを含む）の数で数え直す（WordPress の登録済みの関数の近似。正確には `wp term recount`）。
  - 7b の結果（実装済み）: 実際の WordPress で、ステージングの固定ページの更新（本番と競合した本文はブランチの側で解決）、新しい固定ページ、メニュー、プラグインの有効化、キャッチフレーズを本番にマージし、その間に本番に付いたコメントとコメント数が残った。グローバルスタイルの記事とタームの重複は親の側で解決し、ぶら下がる関連は反映されなかった。タームの件数は `wp term recount` の結果と一致した。2 回目のマージ（新しい基準からの比較）と、`wp search-replace` によるステージングの URL の置き換えも確かめた。

## 段階 8: 過去の時点への復元

- ブランチの状態を過去の時刻の状態に戻す。「プラグイン更新で壊れたら更新直前に戻せる」の「戻す」操作。
- 完了条件: 本物の WordPress で、時点 T の後にプラグインの有効化、テーマの変更、記事の追加と削除をし、その間に本番にコメントが付いた状態から T に復元すると、サイトが T の状態で動き、コメントが残る。復元は元に戻せる。
- 実装の方針:
  - `CALL heimdb_restore_preview(ブランチ, 時刻[, テーブル,...])` でテーブルごとの件数（追加、変更、削除）を表示し、`CALL heimdb_restore(ブランチ, 時刻[, テーブル,... | '*'])` で戻す。時刻はセッションの `time_zone` で解釈する（`AS OF` と同じ）。
  - テーブルを省略したときは、コメント（`comments`、`commentmeta`）とユーザー（`users`、`usermeta`）を戻さない（その間に入ったコメントや登録を消さない）。`'*'` ならすべて戻す。消える記事にコメントが残るときは警告する。
  - 復元は、過去のバージョンを新しいバージョンとして書く 1 つのコミット。履歴は消えず、復元の直前の時刻に復元し直せば元に戻る（その時刻を結果に出す）。
  - ブランチの書き込みロックを取り、1 つのトランザクションで書く。戻す行は、その時刻より後に書かれたキー（自分のキー空間）から求める。行はエディタを通して書き（インデックスと一意制約）、削除、変更、追加の順にする。
  - その時刻の後に作られたテーブルは削除し、消されたテーブルと書き直されたテーブル（列の変更、TRUNCATE）は、その時刻の定義（古いテーブル ID）に戻して行も戻す。テーブル定義も同じトランザクションに書く。
  - AUTO_INCREMENT のカウンタは戻さない（ID を再利用しない）。テーブル ID を戻すときは、今のテーブルのカウンタまで進める。
  - 定義を戻すテーブルは、T の定義のインデックスを今の行から作り直してから行を戻す（T の後に消したインデックスのエントリは、その後の行の変更を反映していないため）。
  - 記事とコメントの片方だけを戻すときは、コメント数を承認済みのコメントで数え直す（記事だけなら戻した記事、コメントだけならすべての記事）。
  - 段階 8 のレビューで直したこと: 行は「消す（削除と変更の対象）→ T の値を入れる（変更と追加）」の 2 段で書く（一意な値の入れ替えで途中の一意制約に当たらないように）。T の後に名前を変えたテーブルは、両方の名前を指定しないとエラーにする（片方だけ戻すと 2 つの名前が同じテーブルを指すため）。取り消しの時刻は UTC のオフセット付きで出し、`AS OF` と復元はオフセット付きの時刻も受け付ける（夏時間の切り替わりや別の time_zone でもずれない）。何も変わらない復元は何も書かず、取り消しの行も出さない。今より先の時刻はエラー。
  - 結果（実装済み）: 本物の WordPress で、T の後にプラグインの有効化、テーマの変更、設定の変更、記事の追加と固定ページの削除をし、コメントが付いた状態から T に復元した。サイトは T の状態（テーマ、プラグイン、固定ページ、設定）で動き、コメントとコメント数は残り、ログインできた。結果に出る呼び出しで復元を取り消すと、復元の直前の状態に戻った。

## 段階 9: 古いバージョンの削除（GC）

- 「タイムトラベルの時刻と保持期間」の方針で、保持期間を過ぎたバージョンを消す。分岐の時点とマージの基準の時点で見えるバージョンは残す。保持期間の境界より前の `AS OF` と復元はエラーにする。
- 完了条件: 保持期間を短くして GC を繰り返し動かしながら、WordPress の PHPUnit（option、meta、query）がベースラインと一致する。境界以降の `AS OF`、ブランチ、マージ、復元の結果が GC の前と同じ（プロパティテスト）。
- 実装の方針:
  - 境界 B は「今 − 保持期間」。開いているトランザクションのスナップショットがそれより古ければ、B をそこまで下げる。
  - バージョン付きのエントリ（行、インデックスのエントリ、テーブル定義）のバージョンのうち、B より新しいバージョン、B の時点で見えるバージョン、残すべき時点で見えるバージョンを残し、ほかを消す。残すべき時点は、子孫のブランチの層の上限（分岐時刻）と、マージの基準（親の時刻、ブランチの時刻）。
  - 親のないブランチ（main、一時テーブルの隠しブランチ）では、残った最古のバージョンが B 以前の削除の印なら、それも消す。子ブランチの削除の印は親の行を隠すので残す。
  - 残ったテーブル定義のどれからも参照されないテーブル ID のキー空間と、インデックス ID のエントリを、範囲で消す。GC の途中で払い出された ID（GC の開始時の採番器の値、定義の次のインデックス ID 以上）は対象にしない。最新でないマージの基準の記録も消す。
  - 消し始める前に新しい境界を `m/gc` に書く。境界より前の `AS OF`、復元、過去の時点からのブランチ作成はエラーにする。書き込みロックは取らない（誰にも見えないバージョンだけを消す）。
  - 起動時のフラグで間隔ごとにバックグラウンドで動かし、`CALL heimdb_gc()` で今すぐ動かせる（境界と消したバージョンの数を返す）。
  - 段階 9 のレビューで直したこと:
    - 復元、過去の時点からのブランチ作成、`AS OF` の読み取りは、読む時刻を GC に登録（Pin）する。GC は開いているトランザクションと同じく、境界をその時刻より先に進めない。確かめることと登録することは不可分で、`AS OF` の登録は文の終わりに解く。これで、復元が古いテーブル ID を書く途中で GC がそのキー空間を消すことも、作成中のブランチの分岐時刻のバージョンを消すことも、実行中の `AS OF` が読むバージョンを消すこともない。
    - 復元で定義を戻すとき、次のインデックス ID は戻さない（キー空間に残る、T の後に作ったインデックスの ID を再利用しないため。残ったエントリは GC が消す）。
    - 閉じるときは動いている GC が終わるのを待ち、その後の GC はエラーにする。開いたままのトランザクションが境界を間隔より長く止めていたら警告を出す。終わったトランザクションのスナップショットは登録しない。
  - 残すべき時点は、そのブランチを読むときに使う祖先の層にも、層の上限で切った時刻として伝える（過去の時点から分岐したブランチでは、分岐時刻が親の分岐時刻より前になりうるため）。
  - 結果（実装済み）: 保持期間 30 秒、間隔 10 秒で GC を動かしながら PHPUnit の option、meta、query を流し、ベースラインとの差は 0 件（GC は 8 回、1 回で最大約 4,300 バージョンと 10 テーブルを消し、14〜33 ミリ秒）。ランダムな書き込み、ブランチ、マージの基準の後で、境界以降と残すべき時点の読み取りが GC の前と同じことをプロパティテスト（40 通り）で確かめた。

## 段階 10: FULLTEXT インデックス

- 10a: FULLTEXT インデックスの定義を扱う。WordPress のコアは FULLTEXT を定義も検索もしないが、プラグインは dbDelta で `FULLTEXT KEY` を作る（dbDelta のテストも準備で作る）。
- 完了条件: PHPUnit の wpdb グループで dbDelta のテストがベースラインと一致する。FULLTEXT の DDL と `SHOW INDEX`、`SHOW CREATE TABLE` の出力が本物の MySQL と一致する（ゴールデンテスト）。
- 実装の方針:
  - go-mysql-server の FULLTEXT は、主キーが文字列の補助テーブル（単語の位置、件数など）で実装されていて、整数の主キーだけに対応する HeimDB では使えない。そこで FULLTEXT は HeimDB が自分で持つ。
  - テーブル定義のインデックスに「FULLTEXT」の印を持たせ、検索のエントリは作らない。go-mysql-server は FULLTEXT の作成と削除を補助テーブルの経路に回すので、解析の段階で `CREATE TABLE`、`ALTER TABLE ... ADD/DROP`、`CREATE/DROP INDEX` を差し替えて、定義の操作として実行する。
  - `SHOW INDEX`、`SHOW CREATE TABLE`、`information_schema.STATISTICS` では FULLTEXT として見せる。一時テーブルの FULLTEXT は MySQL（InnoDB）と同じくエラー 1214 にする。
  - `MATCH ... AGAINST` は明示的なエラーにする（go-mysql-server が計画を作る段階で「FULLTEXT インデックスがない」というエラーを返す。真偽モードは「未対応」のエラー）。
  - 10a の実装の詳細: go-mysql-server には `Index.IsFullText` で false を返す（true だと DROP TABLE や列の削除で `fulltext.Database` への型アサーションが走って panic する）。作成は、解析の最後に FULLTEXT の制約をふつうのインデックスに変え、コメントの先頭の印で `Table.CreateIndex` に伝える。`SHOW INDEX` と `information_schema` は `IndexType` の "FULLTEXT" を使い、`SHOW CREATE TABLE` は HeimDB のノードで `FULLTEXT KEY` に直す。検索には使わせない（`CanSupport` が false）。一時テーブルはエラー 1796、文字列でない列はエラー 1283（MySQL と同じ）。
  - 段階 10a のレビューで直したこと:
    - FULLTEXT インデックスも `CanSupport` を true にする（go-mysql-server の結合の計画は `CanSupport` を見ずにインデックスを使い、false だと結合や `IN (サブクエリ)` がエラーになった）。検索はキーを持たないインデックスと同じく全件の走査になる。
    - `ALTER TABLE ... MODIFY/CHANGE` は、解析の前に、`GetIndexes` から FULLTEXT を隠したテーブルの写しに差し替える（go-mysql-server の検証は、TEXT にする列を含む FULLTEXT でないインデックスにプレフィックス長を求めるため）。
    - `CREATE TABLE ... LIKE` は、コピー元が HeimDB のテーブルなら、保存している定義からインデックスを作り直す（go-mysql-server はプレフィックス長を落とし、FULLTEXT をふつうのインデックスにしていた）。go-mysql-server の CreateTable はコピー元を持たないので、文を構文解析し直して探す。
    - FULLTEXT の誤り（一時テーブル、文字列でない列）は、テーブルを作る前、同じ ALTER で足す列を含めて確かめる（失敗してもテーブルや列が残らない）。
    - LIKE のルールは、派生テーブル、WITH、UNION とサブクエリの中にも入り、列を参照しない式のパターン（`CONCAT(...)`）にも ESCAPE を付ける。
    - 照合順序を指定せずに作ったテーブルの文字列の列は、読み直すと照合順序が「なし」の型になり、LIKE が常に偽になっていた（go-mysql-server は既定の照合順序を型の文字列に書かない）。既定の照合順序に戻す。
    - 記録だけ: 末尾が単独の `\` のパターンはエラーになる（MySQL は `\` そのものに一致）。構文解析は未知のエスケープ（`'\_'` など、wpdb::prepare を通らない 1 つの `\`）の `\` を落とす（MySQL は残す）。非 STRICT の sql_mode で NULL のある列を `NOT NULL` に変える ALTER は、MySQL は '' に変えて通すが HeimDB はエラー 1048（段階 15 で対応した）。ESCAPE を付けた `LIKE 'prefix%'` はインデックスの範囲検索にならない（結果は正しい）。
  - 10a の途中で見つけて直したこと: go-mysql-server の `simplifyFilters` は、ワイルドカードのない `LIKE` を等号に、末尾だけが `%` の `LIKE` を範囲に置き換えるが、`\_` や `\%` のエスケープを外さずに比べる。WordPress の `$wpdb->esc_like` を使ったパターン（`option_name LIKE '\_transient\_%'`、`SHOW TABLES LIKE 'wp\_foo'` など）が何にも一致しなかった。エスケープを含む定数のパターンの `LIKE` に、解析の最初で既定と同じ `ESCAPE '\'` を明示して置き換えを避ける（`simplifyFilters` は ESCAPE のある LIKE を置き換えない）。本物の MySQL とのゴールデンテスト（`like_golden.txt`）で確かめた。
- 全文検索（`MATCH ... AGAINST` の実行）は、この DB では対応しない（2026-10-04 に決めた。10b は行わない）。FULLTEXT インデックスは、dbDelta とプラグインのテーブル定義のために定義だけを扱う。
