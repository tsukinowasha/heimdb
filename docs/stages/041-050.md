# 段階 41〜50

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 41: 止めるときに、開いたままのトランザクションを片付ける

- 背景: GitHub Actions で `TestGracefulShutdown` がときどき `panic: element has outstanding references`（Pebble の `DB.Close`）で落ちた。段階 27 から、トランザクションは主キーで 1 行を引く読み手（`Txn.PointReader`、Pebble のイテレータ）を終わるまで持ち続ける。止めるときの手順（段階 18）は実行中の文を待つが、文と文の間で開いたままのトランザクションは待たない（次の文は 1053 で拒否する）ので、読み手を持ったままのトランザクションが残った状態でストアを閉じると panic する。ストアだけのテスト（トランザクションで 1 行を引いてから閉じる）で必ず再現した。本番でも、明示的なトランザクションの途中で止めると、まれに panic で終わりうる（コミット済みのデータは失われない）。
- 方針: ストアが開いているトランザクションを覚え（始めたときに覚え、終わったときに忘れる。スナップショットの登録は最初に読んだときからなので別に持つ）、`Store.Close` は Pebble を閉じる前に残っているトランザクションをすべてロールバックする（読み手、書き込みのバッチ、ブランチの書き込みロックを手放す。MySQL を止めたときと同じく、コミットしていない変更は残らない）。その後にそのトランザクションを使うと「終わったトランザクション」のエラーになる。止めた後は、新しい文も切断の後片付けも止めるときの手順（gate）が拒否するので、ストアには触らない。
- 完了条件: ストアの単体テストで、1 行を引いた読み手を持つトランザクション、書き込みとロックを持つトランザクション、複数のトランザクションがあっても閉じて panic せず、閉じた後のロールバックとコミットはエラーになるだけ。`TestGracefulShutdown` の開いたままのトランザクションに主キーでの 1 行の検索をさせ、毎回再現する形にする。直しを外すと両方が落ちる。CI が通る。0.2.1 として公開する。
- 実装: `Store` に開いているトランザクションの一覧（`openTxns`）を持ち、`Begin` で覚えて `Txn.close` で忘れる。`Store.Close` は GC を止めた後、AUTO_INCREMENT を保存して Pebble を閉じる前に、一覧のトランザクションをすべて `Rollback` する。トランザクションを終わらせる処理は `closeOnce`（`closeMu` で 1 回にする）。テストのサーバは止めるときの手順を通さずにストアを閉じるので、接続が切れたときのロールバックと `Store.Close` のロールバックが同時に来て、`-race` で競合が出た（`TestReview8RestoreAcrossOpenTransaction`、全体を流したときだけ）。本番の止め方では手順が後片付けを拒否するので起きないが、ロールバックだけは同時に呼ばれても安全にした。
- 結果: `TestCloseRollsBackOpenTransactions`（1 行を引いた読み手を持つ読み取りのトランザクション 2 つ、書き込みとロックと読み手を持つトランザクション、終わったトランザクションがある状態で閉じても panic せず、閉じた後のコミットは `ErrTxnDone`、ロールバックは何もせず、コミットしていない行は開き直しても残らない）を足し、`TestGracefulShutdown` の開いたままのトランザクションに主キーでの 1 行の検索をさせた。直しを外すと、どちらも `element has outstanding references` で落ちる（プロセスのテストは最初の周回で必ず落ちる）。`TestGracefulShutdown` を -race で 4 回、`TestReview8RestoreAcrossOpenTransaction` を -race で 40 回繰り返して落ちない。Go のテストは 334 件（-race でも成功）。
- CI で見つけて直したこと（テストの道具）: 直した後の CI で、`TestCrashRecovery` の後片付けが 10 分の時間切れまで止まった。テストがプロセスの終了の知らせ（`done`）を受け取った直後、送る側が `exited` を閉じる前に後片付けが走ると、後片付けの `stopProc` が、もう送られない `done` を待ち続けていた（15 秒後に kill した後も待つ）。前からあった取り合いで、遅い CI のマシンで当たった。`stopProc` は `exited` だけを待つ形にした。
- バージョンを 0.2.1 にした（データ形式は 0.2.0 と同じ）。

## 段階 42: 安全性の回避をエンジンで直す（A1〜A4）と、`go vet` の修正

- 背景: 2026-10-13 から、優先の軸を WordPress 特化、性能、安全性、堅牢性にした。エンジンを取り込んだので（段階 40）、HeimDB の外側（構文解析の後の文の木の検査、解析のルール、表の包み直し）で防いでいた穴を、エンジンの根本で塞ぐ。
- 方針: A1: `LOAD_FILE()`、`SELECT ... INTO OUTFILE / DUMPFILE`、`LOAD DATA` をエンジンから外し、文を組み立てる段階（planbuilder）で今と同じエラー（`HeimDB: reading or writing server files is not supported`）にする（関数の登録、ファイルへの書き出し、`LOAD DATA` の実行を外す）。HeimDB の `checkServerFiles` を消す。`secure_file_priv` は二重の守りとして残す。上流のテストのうち外した機能のもの（`TestLoadData`、`TestSelectIntoFile` など）は除き、`docs/engine.md` に書く。バイナリプロトコルでの `LOAD DATA` のプリペアの panic は vitess の中なので残る。A2: HeimDB の `setGlobalPrivilege` をエンジンの既定の解析のルールにする（順番とエラーは今のまま）。A3: エンジンの `information_schema.processlist` を PROCESS 権限で絞り、認証が済んだ時点で接続の一覧にユーザーを記録する（上流の main と同じ形）。HeimDB の `processListPrivilege` と接続ごとのユーザーの対応表を消す。A4: エンジンの `server/handler.go` の `doQuery` で構文解析のエラーを見る。`go vet` の書式の文字列の 64 か所を直し、エンジンのテストを `-vet=off` なしで流す。変えたファイルの頭に変更の印を付け、`docs/engine.md` の変更の一覧に書く。
- 完了条件: HeimDB の Go のテストが回避を消した状態で -race でもすべて通る（`TestServerFilesRejected`、`TestSecureFilePriv`、`TestGlobalOperationsNeedPrivileges`、`TestReview14PrivilegeGaps` は変えずに通る）。エンジンのテストが `-vet=off` なしで通る（外した機能のテストを除く）。エンジンの直しを外すと HeimDB のテストが落ちる。PHPUnit の全テストで差が 43 から増えない。CI が通る。0.2.2 として公開する。
- 結果: HeimDB の `checkServerFiles`（文の木をたどる確認）、`setGlobalPrivilege` と `processListPrivilege` のルール（`globals.go`）、接続ごとのユーザーの対応表を消し、`checkStatement` はエラーのときも文を返す普通の形にした。`TestServerFilesRejected`、`TestSecureFilePriv`、`TestGlobalOperationsNeedPrivileges`、`TestReview14PrivilegeGaps` は変えずに通った（`TestServerFilesRejected` の複数の文の接続に、前方の長さ付きの主キーを足し、表が作られないことも確かめる）。エンジンの直しを 1 つずつ外すと、`SET GLOBAL` のルール、processlist の絞り込み、ユーザーの記録、構文解析のエラーの確認、`LOAD_FILE` の確認、`LOAD DATA`（planbuilder と rowexec の両方）のどれでも HeimDB のテストが落ちた（`LOAD DATA` は 2 か所で止めているので、片方だけなら落ちない）。`go vet` の書式の文字列は、printf の解析器の自動の直し（`"%s"` を足す）で 64 か所を直し、`sql.CastSQLError` の `%` の置き換えを外した。上流のテストは `-vet=off` なしで 53,208 件が通り、414 件が飛ばされた（外した機能の 4 つのテストを `TestServerFilesRemoved` に置き換え、`TestScripts` の `INTO DUMPFILE` の期待するエラーを直した）。HeimDB の Go のテストは 334 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。CI と README の `-vet=off` を外した。
- バージョンを 0.2.2 にした（振る舞いとデータ形式は 0.2.1 と同じ）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- サーバのファイルを読み書きする SQL を外した: `LOAD_FILE()` の関数（`function/load_file.go`）、ファイルへの `INTO`（OUTFILE、DUMPFILE）の書き出しと、`LOAD DATA` の実行（`loadDataIter`）を消し、planbuilder（`buildLoad`、`buildInto`、関数の組み立て）と rowexec の両方で `sql.ErrServerFiles`（`sql/server_files.go`）にする
  - 理由: 安全性。HeimDB が構文解析の後に文の木をすべてたどって防いでいた（段階 31）。どの道（列の既定値、`EXPLAIN`、`PREPARE`）も planbuilder を通るので 1 か所で止まる
- `SET GLOBAL`、`SET PERSIST`、`SET PERSIST_ONLY` の権限を確かめる解析のルール（`analyzer/global_privileges.go`）を、解析器の既定の最初の段に入れた
  - 理由: 安全性。HeimDB の解析のルールだった（段階 35）
- `information_schema.processlist` を PROCESS 権限で絞り（自分のユーザーの接続だけ）、文を始めるときに接続のユーザーを記録する（`processlist.go`）
  - 理由: 安全性。HeimDB が表を包み直していた（段階 35）。データベースを選ばずにつないだ接続が `unauthenticated user` のままだった
- 複数の文の接続で、構文解析のエラーを見て、その文と残りの文を実行しない（`server/handler.go` の `doQuery`）
  - 理由: 安全性。もとはエラーを見ずに返った文を実行していた。HeimDB は構文解析器がエラーのときに文を返さないことで防いでいた（段階 31）
- `go vet` の書式の文字列の確認に合わせた（64 か所。書式でない文字列を `"%s"` で渡す）。`sql.CastSQLError` の `%` の `%%` への置き換えは、書式として渡さなくなったので外した
  - 理由: 堅牢性。HeimDB（Go 1.25）では `go test` の自動の確認でテストのビルドが止まっていた。文に `%` が入ると表示が崩れていた

## 段階 44: マージの周り（戻すための文、`db_version` の状態、空打ち、差分の要約の重さ）

- 背景: HeimDB を使う WordPress のホスティングが、検証環境のブランチを本番にマージする手順（段階B）を組むにあたっての要望。(1) マージの直後に切り戻すとき、`heimdb_restore` に渡す時刻を推測することになる。(2) `db_version` の食い違いが差分のエラーになり、管理画面がエラーの文を解釈することになる。(3) 本番のトラフィックを切り替える前に、マージを実際の経路で確かめたい。(4) ロックを取らずに「このマージは重いか」を判断したい（列を変えた表は、マージで親を書き直すか、差分で全行を比べる）。また、`docs/procedures.md` の `parent` の解決の説明（「列の定義が違うテーブルを除く」）が、主キーの違いだけを指すことを書いていない。
- 方針: (1) `heimdb_branch_merge` の結果の最後に `*` / `undo` の行を足し、detail にそのまま実行できる `CALL heimdb_restore('<親>', '<時刻>', '<表>')` を入れる。時刻は差分を読んだ時点（親のロックを取った後なので、マージの直前の親の状態そのもの）を UTC のオフセット付きのマイクロ秒で出す。表はマージが書いた表だけ（行、列、インデックス、数え直し）。(2) `heimdb_branch_diff` は `db_version` が違ってもエラーにせず、最初に `*` / `db_version differs` の行（detail に両側の値）を返し、続けて表ごとの行を返す。マージはこれまでどおりエラー。(3) `heimdb_branch_merge('<ブランチ>', 'dry_run')` は同じ経路を最後まで通ってコミットせずに捨て（解決の記録とマージの起点も残す）、`*` / `dry run` の行を足す。親のロックを取る時間は本番のマージと同じ。(4) 表ごとの detail に、マージで親を書き直すなら `rewrite N rows`（N は親の行数）、差分でどちらかの側のテーブル ID が分岐の時点と違い全行を比べるなら `full compare N rows`（N は比べた主キーの数）を足す。マージの結果にも同じものを出す。(5) `procedures.md` を直す。
- 完了条件: 戻すための文を実行すると親がマージの前と同じになる。`db_version` の行が出て、マージはエラーのまま。空打ちで親、解決の記録、マージの起点が変わらない。列を書き直す表と全行を比べる表の detail に行数が出る。Go のテストが -race でも通る。CI が通る。PHPUnit の全テストで差が 43 から増えない。データ形式は変えない。
- 結果: (1) マージの結果の最後に `* | undo` の行を返す。時刻は差分を読んだ時点（`differ.snap`）、テーブルはマージが書いたもの（行を書いた、列を書き直した、インデックスを変えた、作った、件数を数え直して値が変わった、`rewrite_rules` を空にした）。`TestMergeUndo`（行、列の追加、新しいテーブル、件数の数え直しを含むマージを、返された文で戻すと、親のすべてのテーブルの定義と行がマージの前と一致する）。数え直しで書いたテーブルを記録しない、または時刻をコミットの後にすると落ちる。(2) `heimdb_branch_diff` の要約は、`db_version` が違えば最初に `* | db_version differs` の行を返す（マージと空打ちはエラーのまま）。(3) `heimdb_branch_merge(名前, 'dry_run')`。`TestMergeDryRun`（親、行ごとの差分（解決の記録とマージの起点）が変わらず、結果のテーブルの行は実際のマージと同じ。知らないモードはエラー）。(4) `detail` に `rewrite N rows` と `full compare N rows` を出し、全行を比べるがマージで変えるものがないテーブルは `unchanged` の行で出す（`TestMergeWeight`）。調べてわかったこと: 全行を比べるのは、ブランチの側でテーブルを書き直したとき（列の変更、`TRUNCATE`）と、親の側では記事、ターム、記事のメタで分岐の後にテーブルを書き直したとき（親で足された同じ自然なキーの行を、分岐の時点から探すため。ブランチを作り直すまで毎回）。親だけで列を変えたプラグインのテーブルは、ブランチで変えた行だけを見るので重くならない。(5) `procedures.md` の `parent` と `schema differs` の説明を、主キーの列の違いのことだと直し、親だけの列の変更は既定値で埋まることを書いた。Go のテストは 338 件（-race でも成功）。エンジンは変えていない。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。

## 段階 45: 検証環境の歯止め（ブランチの大きさの上限、ブランチの文の実行時間の上限、`MAX_USER_CONNECTIONS`）

- 背景: ホスティングでは、検証環境のブランチが本番と同じ HeimDB に乗る。検証環境の WordPress（信頼しないテーマやプラグインの PHP が動く）が、ディスク、長い文、接続を食い尽くして本番を巻き込まないようにしたい。要望の本命はディスク。
- 方針: (1) `CALL heimdb_branch_limit('<ブランチ>', '<大きさ>', '<時間>')` でブランチに上限を付ける（`K`/`M`/`G`、`ms`/`s`/`m`。`0` は上限なし）。`main` には付けられない。上限はブランチの情報（`m/branch` の JSON）に足すフィールドに入れる（前のバージョンは無視する。データ形式のバージョンは上げない）。レプリカにも届く。子のブランチは引き継がない。`heimdb_branch_list` の最後に `max_size_bytes` と `max_execution_ms` を足す。(2) 大きさの上限: 書き込みの始まり（エディタが文の中で最初に行を書く前、DDL の前）に、`size_bytes` と同じ見積もり（ブランチごとに 1 秒ほど覚える）が上限を超えていれば、エラー 1114（`The table '<表>' is full`）で拒否し、ログに警告を出す。読み取りは通す。メモリ上の分と、始まった 1 つの文が書く分は超えうる（実行時間の上限で抑える）。(3) 実行時間の上限: 接続中のデータベースが上限を付けたブランチなら、すべての文に効く。過ぎたら `KILL QUERY` と同じ仕組みで止め、エラー 3024 を返す（MySQL の `max_execution_time` と同じ）。止めた文の書き込みは捨てる。HeimDB の行とインデックスを読む処理と、`ALTER` の書き直しは、一定の行ごとに取り消しを確かめる。接続ごとの設定にしないのは、信頼しない PHP が外せるため。(4) `CREATE USER` / `ALTER USER ... WITH MAX_USER_CONNECTIONS n` をエンジンで効かせる（ユーザーの情報と保存の形式（flatbuffers の末尾のフィールド）に足し、`mysql.user` に出す）。認証の直後にアカウントごとに数え、超えればエラー 1203。全体の `@@max_user_connections` は入れない。
- 完了条件: 大きさの上限を超えたブランチで、書き込みと DDL がエラー 1114 になり、読み取りは通り、上限を外せば書ける。`main` には付けられない。上限がレプリカに届く。実行時間の上限で、重い `SELECT`、`SLEEP`、大量の `UPDATE`、`ALTER` の書き直しがエラー 3024 で止まり、書き込みが残らない。上限のないブランチは変わらない。`MAX_USER_CONNECTIONS` を超えた接続がエラー 1203 になり、切れば再びつなげ、再起動の後も効く。Go のテストが -race でも通る。CI が通る。PHPUnit の全テストで差が 43 から増えない。データ形式のバージョンは変えない。
- 結果: (1) `heimdb_branch_limit`（`internal/backend/limit.go`、`store/limit.go`）。上限は `BranchInfo` の `max_bytes`、`max_execution_ms`（JSON の省略できるフィールド）。`heimdb_branch_list` に `max_size_bytes`、`max_execution_ms` を足した。(2) 大きさは、エディタが文の中で最初に書く前（マージと復元のエディタを除く）、列を変える `ALTER` の前、`Database.ddl`（テーブルの作成、削除、名前の変更、インデックス、`TRUNCATE`）の前に確かめる。(3) 時計は `ValidateSession`（普通の文と準備した文の両方）で動かし、`CommandEnd` で止める（文ごとの番号で、終わった文の時計が次の文を止めない）。過ぎたら `ProcessList.Kill`（`KILL QUERY` と同じ）。止めた文のエラーは、エンジンに足した `server.QueryErrorTranslator` でエラー 3024 にする。そのとき、コマンドの始まりの位置までトランザクションの書き込みを取り消す（文が書き終えた後に止まると、go-mysql-server は文の取り消しを呼ばないので、明示的なトランザクションに書き込みが残っていた。取り消しの確認を外したテストで見つけた）。取り消しは、HeimDB の行とインデックスを読む処理、主キーで行を引く処理、エディタの書き込み、`ALTER` の書き直し（行を集めるところと書くところ）で 1024 回ごとに確かめる。`SELECT`、`UPDATE`、`DELETE` はエンジンの側でも確かめているが、`ALTER` の書き直しは HeimDB で確かめないと止まらない（外すと `TestBranchTimeLimit` が落ちる）。(4) `MAX_USER_CONNECTIONS` はエンジンの変更（`docs/engine.md`）。認証の方式を包んで、認証が通った直後にアカウントごとに数える。調べていて、`IDENTIFIED` のない `ALTER USER` がパスワードを空にしていたことがわかったので直した（`WITH MAX_USER_CONNECTIONS` だけを変えると、パスワードなしでつなげるようになっていた）。テスト: `TestBranchLimits`（ストア。開き直し、レプリカ、`main`、見積もり）、`TestBranchSizeLimit`、`TestBranchTimeLimit`（明示的なトランザクションの中で止めた文だけを取り消す、重い `SELECT`、`SLEEP`、大量の `UPDATE` と `DELETE`、`ALTER` の書き直し、`main` は止めない、止めた後の同じ接続）、`TestMaxUserConnections`（3 つ目の接続がエラー 1203、他のアカウントは数えない、切れば再びつなげる、`ALTER USER` で外す、パスワードは変わらない、再起動の後も効く）。Go のテストは 297 件（前の段階の終わりは同じ数え方で 293 件。-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。データ形式のバージョンは変えていない。
- レビュー（Fable）の指摘を直す（計画）: (1) 実行時間の上限は、接続中のデータベースのブランチだけで決めていたので、データベースを指定せずにつなぐか `USE information_schema` にして、完全な名前（`` `wordpress@staging`.wp_posts ``）で書けば外せた。認証が有効なら、ユーザーが権限を持つデータベースのブランチの上限の最小（0 は除く）を使う。全体の権限（`*.*`）を持つユーザー（管理者）には上限をかけない（`heimdb_*` の手続きも止まらない）。認証のないとき（`-no-auth`）は、これまでどおり接続中のデータベースのブランチで決め、`CALL heimdb_` で始まる文には時計を動かさない。(2) 一時テーブルは上限のない隠しブランチに書くので、大きさの上限を外せた。上限の付いたブランチを使う接続（(1) と同じ決め方）では、一時テーブルの作成を拒否する（WordPress は使わない）。(3) 段階 45 で直した `ALTER USER` が、`IDENTIFIED BY ''`（空のパスワードにする）も「指定なし」として扱っていた（vitess の構文木では区別できない）。HeimDB の構文解析の包み（`parser.go`）で、文の字句に `IDENTIFIED` がなければ構文木の認証を nil にし、エンジンは nil だけを「指定なし」とする。(4) パスワードのないアカウントが `caching_sha2_password` でつなぐと、認証が接続元のアドレスをホストとして返し、アカウントが見つからずに数えなかった。ホストのパターンで照合して引く。(5) コミットしていないトランザクションの書き込みはメモリに持つので、大きさの上限の付いたブランチでも、短い文を重ねてメモリを使い切れた。上限の付いたブランチに書くトランザクションの大きさ（書き込みのバッチの大きさ）を、大きさの上限と 256MB の小さい方までにし、超えたらエラー 1197 でその文を取り消す。(6) 上限で拒否した警告のログは、ブランチごとに 1 分に 1 回にする。(7) `DROP TABLE` と `TRUNCATE` は、満杯のブランチでも通す。(8) 文の終わり際に止まると、書き込みが残ったままエラー 3024 になることがある（MySQL の `max_execution_time` と同じ）と文書に書く。(9) 上限の内に終わるはずのテストの上限を 1 秒にする。データ形式のバージョンは変えない。
- レビューの直しの結果: 計画のとおり直した。実行時間の上限は `Session.sessionLimits`（`limit.go`）で、エンジンのユーザーと権限（`Provider.users`。`NewEngine` が入れる）から決める。テストのサーバは認証を有効にした root（全体の権限）でつなぐので、上限のテストは、ブランチだけの権限のユーザー `stg` でつなぐ形に書き直した（`limitServer`）。トランザクションの大きさは `Txn.Size`（バッチのバイト数）をエディタが書く前に確かめる。表を消す DDL は `Database.dropDDL`。テストを足した: `TestBranchLimitsByPrivilege`（データベースを指定しない接続、`USE information_schema`、完全な名前の `SELECT` がエラー 3024、一時テーブルがエラー 1235、root は作れる）、`TestBranchTxnSizeLimit`（64K の上限のトランザクションがエラー 1197 になり、それまでの書き込みはコミットできる）、`TestMarkUnspecifiedAuth`（名前やコメントの `IDENTIFIED` は数えない）、エンジンの `TestLimitedAuthMethodHost`（接続元のアドレスを返す認証でも数える）。`TestMaxUserConnections` に `IDENTIFIED BY ''` で空のパスワードになること、`TestBranchSizeLimit` に満杯での `TRUNCATE` と `DROP TABLE`、`TestBranchTimeLimit` に root は止めないことを足した。直しを 1 つずつ外すと（字句の確かめ、権限からの上限、一時テーブルの拒否、トランザクションの大きさ、`TRUNCATE` の確かめ、ホストのパターンの照合）、それぞれ対応するテストが落ちる。Go のテストは 300 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト（1 回目は `Tests_Post_GetPages::test_get_pages_cache` が時刻の比較で 1 件多く落ちた。単独で 3 回流してすべて通った）。接続の切断と panic は 0。
- バージョンを 0.2.5 にした（データ形式は 0.2.4 と同じ）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- `server.QueryErrorTranslator`: 文のエラーを、セッションが置き換えられるようにした（`server/handler.go` の `doQuery`。`CommandEnd` より先に呼ぶ）
  - 理由: 堅牢性。ブランチの実行時間の上限で止めた文を、取り消しのエラーではなく MySQL と同じエラー 3024 にし、その文の書き込みを取り消す（`internal/backend/limit.go`）

  - 理由: 安全性。もとは空のパスワードにしていた（`WITH MAX_USER_CONNECTIONS` だけを変えると、パスワードなしでつなげるようになる）。最初は空の認証を「指定なし」としたが、`IDENTIFIED BY ''` が効かなくなった（レビューで見つけた）

  - 理由: 安全性。パスワードのないアカウントが `caching_sha2_password` でつなぐと、認証が接続元のアドレスをホストとして返し、アカウントが見つからずに数えなかった（レビューで見つけた）

## 段階 46: エンジンの panic を直す

- 背景: go-mysql-server には、接続を切る panic が残っており、HeimDB はエンジンの外側で避けている。(1) 対応していない文字セットへの `CONVERT ... USING` で、変換器が nil のまま使われる（`parser.go` の `checkConvertUsing` で避けている）。(2) ユーザーの保存先がないと、`CREATE USER` や `GRANT` で nil を参照する（`auth.go` の `noAuthPersister` で避けている）。(3) 外部の手続きの登録簿は、引数のない登録しかない手続きを引数付きで呼ぶと、ゼロ値（`Function` が nil）を返す（例: `CALL heimdb_gc(1)`。`provider.go` の `ExternalStoredProcedure` で避けている）。(4) 統計の `stats.Union` と `Intersect`（OR と AND の見積もり）は、複数の列のバケットで先頭の列が違うと次の列に進み、範囲の外を読む（`statistics.go` がヒストグラムを先頭の列だけで作って避けている。上流の #3116 で直っている）。(5) FULLTEXT の表の `DROP TABLE` と列の削除などで、データベースを確かめずに `fulltext.Database` に型アサーションする（`fulltext.go` が `IsFullText` に false を返して避けている）。panic は vitess が回復するが、その接続は切れる。知らない panic も同じく接続を切る。
- 方針: (1) planbuilder で、変換器のない文字セットへの `CONVERT ... - 結果: (1) `Table.strPK` を `newTable` で求める。(2) `sql/collations.go` の `asciiSorter` で、起動時にすべての照合順序の重みの関数を、ASCII の文字は前もって作った表で引く関数に包んだ（`TestASCIISorterMatchesBase`。すべての照合順序で、ASCII の全文字といくつかの ASCII 以外の文字の重みが元の関数と同じ）。(3) `EXPLAIN PLAN` の `max1Row` のエラーは、計画を作る規則が中の文に「最大 1 行」の印をつけるため。`analyzeNode` で、`DescribeQuery` なら印を外す。調べていて、`EXPLAIN`（PLAN なし）の仮の行が `rows`（符号なし整数）と `filtered` にも文字列の `"NULL"` を入れ、Go のドライバがエラーになることもわかったので、NULL にした（上流のテスト `explain select 1` の期待も直した）。`TestExplainOfSingleRowQuery`。直しを外すと（`strPK`、表の値、印を外す、NULL）、それぞれ対応するテストが落ちる。Go のテストは 303 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。GCE（`docs/bench.md` の「段階 48 の後」）: 検索の DB の時間が 26% 減り、記事の作成と削除、ダッシュボード、投稿一覧が 1 割ほど減った。同時アクセスは 5% 増えた。REST API だけ 3% 遅く、次の性能の段階で確かめる。GCE のインスタンスは消した。データ形式は変えていない。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- 照合順序の重みの関数を、ASCII の文字（0〜127）は前もって作った表で引く関数に包む（`sql/collations.go` の `asciiSorter`。起動時にすべての照合順序で包み、`CollationID.Sorter()` が返す）。ASCII 以外は元の関数を呼ぶ
  - 理由: 性能。`sql/encodings` の重みの関数（`utf8mb4_unicode_520_ci` など）は 1 文字ごとに map を引き、検索の `LIKE` の時間の 89%、同時アクセスの CPU の約 1 割（文字列の比較）を占めていた（docs/bench.md の段階 47）。表は元の関数から作るので重みは同じで、インデックスのキー（データ形式）も変わらない（`TestASCIISorterMatchesBase` がすべての照合順序で確かめる。段階 54 で `tableSorter` と `TestTableSorterMatchesBase` に替えた）。`sql/encodings` は変えない
- `EXPLAIN` と `EXPLAIN PLAN` では、中の文につけた「最大 1 行」の印（`QFlagMax1Row`）を外す（`engine.go` の `analyzeNode`）。`EXPLAIN` の仮の行の値のない列を、文字列の `"NULL"` ではなく NULL にする（`sql/rowexec/show.go`）
  - 理由: 不具合。集計や主キーの等号の文の `EXPLAIN PLAN` が `result max1Row iterator returned more than one row` のエラーになっていた。`EXPLAIN` は `rows`（符号なし整数）と `filtered`（浮動小数点）にも文字列を入れ、数として読むクライアント（Go のドライバ）がエラーになっていた

## 段階 49: 既知の脆弱性の確認を CI に入れる（govulncheck）

- 背景: Docker Scout の導入を考えたが、HeimDB のイメージは distroless と Go の単体のバイナリなので、見るのはほぼ Go のバージョンと依存のモジュールのバージョンで、呼んでいるかを見ないため誤報が多い（文字コードの表のためだけに残す go-mysql-server など）。Go の公式の govulncheck は、実際に呼ぶ関数まで調べる。
- 方針: `.github/workflows/vuln.yml` で、push、プルリクエスト、毎週（月曜）に `govulncheck ./...` を流す。Go は最新の安定バージョン（イメージを作る `golang:1.27` と同じ。標準ライブラリの脆弱性は使う Go のバージョンで決まる）。govulncheck のバージョンは固定する。
- 結果: 手元の Go 1.26.0 では、標準ライブラリの 28 件が呼ばれる経路にあった（テストとベンチマークのバイナリを手元で建てるときだけ。リリースのイメージは Docker の Go で建てる）。Go 1.27.2 では 0 件（`klauspost/compress` の 1 件は呼んでいない）。公開している 0.2.6 のイメージのバイナリ（Go 1.27.2）をバイナリのモードで調べると、Pebble の圧縮で間接に入る `klauspost/compress` v1.17.11 の `s2.NewDict`（GO-2026-5841、v1.18.7 で直った）だけが出た。ソースのモードでは呼んでいないので影響はないが、保存の層に関わるので、上げるかは別に決める（dependabot は間接の依存を上げない）。
- 追記: Pebble は `klauspost/compress` を zstd の圧縮にだけ使い、HeimDB は既定の Snappy を使う（`store.go` で圧縮を指定しない）ので、データの読み書きでは動かない。Docker Scout を試すため、v1.20.3 に上げた（Go のテストと PHPUnit で確かめた）。Docker Scout（`docker scout cves tsukinowa/heimdb:0.2.6`）が出したのもこの 1 件だけで、土台の distroless には 0 件。dependabot の go-minor-and-patch（`golang.org/x` の 4 つ）も、今の main に重ねて Go のテストと PHPUnit で確かめて取り込んだ（#4）。

## 段階 50: 性能の直しの 2 回目（REST API の戻り、term 数、カテゴリの一覧）

- 背景: 段階 48 の後の GCE の計測で、(1) REST API が 3% 遅くなった（重みの関数を包んだ分の呼び出しが、元から速い照合順序で効いている見込み）。(2) 記事の作成と削除の MySQL との差の大半はカテゴリの term 数（`SELECT COUNT(*) FROM wp_term_relationships, wp_posts WHERE ...`。12.4 ms、MySQL 5.6 ms）で、インデックスの範囲で絞った後にも同じ条件の Filter（文字列の照合順序の比較）を行に掛けている。(3) カテゴリの 2 ページ目の記事の一覧（77 ms、MySQL 7.4 ms）は、`post_date` を持たない `type_status_author` を選んで本体の行を読み、記事ごとに `wp_term_relationships` を引いている。
- 方針: (1) 手元で、包む前と後のバージョンを同じ文で交互に測って原因を確かめ、包んで遅くなる照合順序（重みの関数がもとから表の引きより安いもの）は包まないなど、戻りをなくす。(2) インデックスの範囲が条件をそのまま表す（等号と IN だけで、範囲が正確な）とき、同じ条件の Filter を外す（go-mysql-server の、インデックスが扱った条件を外す仕組みを調べ、HeimDB のインデックスがそれを申告していないなら申告する）。(3) Sort や GroupBy の下で、文が使う列をすべて持つインデックス（`type_status_date`）に替える（段階 27 の `coveringIndexForSort` を、JOIN と GroupBy を挟む形にも広げるか、選び方を直す）。どれも結果は変えず、`EXPLAIN PLAN` と結果を本物の MySQL と比べる。データ形式は変えない。
- 完了条件: 3 つの文の計画が変わり、結果が変わらない（ゴールデンか本物の MySQL との比較）。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。GCE（作る前に確認を取る）で、REST API の戻りが消え、記事の作成と削除、カテゴリの 2 ページ目が速くなったことを数字で示す。CI が通る。
- 結果: (1) 手元で重みの関数を包む前と後のバージョンを、静かな状態で交互に 2 回ずつ測ると、包んだ方が遅い文はなかった（term の読み込みの文も同じ）。GCE の段階 50 の計測でも、REST API は 0.2.6 より 2 回とも 8〜11 ms 速く、戻りは見えないので、コードは変えていない。(2) `dropRangeFilters`（`rangefilter.go`）。`narrowIndexRanges` の後、`columnTypedLiterals` の前に置く。AND の項の「列 = 定数」と「列 IN (定数, ...)」を、どの範囲でもその列と前の列が 1 つの値（点）で、点が項の定数のどれかと列の型で等しいときに外す。定数は、文字列の列なら同じ文字セットの文字列（`columnLiteral`）、整数の列なら列の型にそのまま入る整数。プレフィックス長の列は外さない。HeimDB はインデックスで範囲の中の行だけを返す（キーの区間がちょうどならキーで、そうでなければ範囲の条件で絞り直す）ので、外した項はどの行でも真。`TestDropRangeFilters`（大文字と小文字だけ違う値、末尾の空白、数との比較、`COLLATE` の付いた定数、プレフィックス長の列、範囲の条件、JOIN の中。件数は入れた行から表の照合順序で数えたものと比べる）と `TestCoveredByRangesGuards`（点が定数と違う、前の列が点でない）。(3) `swapCoveringIndex` が、GroupBy と、外側の行ごとに引く JOIN とハッシュ JOIN の下も替える（マージ JOIN は両側をキーの順に読むので替えない）。`TestCategoryQueryPlans`（ベンチマークに近い 3,000 件で、カテゴリの記事の一覧が `type_status_date` を読み、term 数に記事の条件の Filter が残らない）。結果は、既存の `TestWordPressJoinsMatchMySQL`（本物の MySQL のゴールデン）が同じ。直しを 1 つずつ外すと、対応するテストが落ちる。Go のテストは 306 件（-race でも成功）。PHPUnit の全テストは 43 で、段階 29 と同じテスト。接続の切断と panic は 0。GCE（`docs/bench.md` の「段階 50 の後」）: 0.2.6 から DB の時間が、検索で 32%、ほかのページで 9〜16%、記事の作成で 19%、削除で 16% 減った。カテゴリの記事の一覧は 9% しか減らず、残りは記事ごとに `wp_term_relationships` を引く読み出し（次の候補）。GCE のインスタンスは消した。データ形式は変えていない。
- バージョンを 0.2.7 にした（データ形式は 0.2.6 と同じ。段階 48 から 50 と依存の更新を含む）。
