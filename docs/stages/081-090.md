# 段階 81〜90

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 81: 遅い文の観測と、文を止める口（ホスティング側の依頼）

- 背景: ホスティング側は遅い文の閾値（`-slow-query`）を変えるたびに起動し直していて、それが訪問者の 500 と、表ごとの最初の文の手間（段階 80）になっていた。起動し直した直後の 4.9 秒と 2.7 秒の切り分けに 1 日かかったが、遅い文のログに読んだ行数、使ったインデックス、止まった時間の内訳があれば即決だった。遅い文のログには訪問者が入れた字（検索語、フォームの値）が入りうるので、付けたままにしにくい。ヘッドレスの API では、`SET SESSION max_execution_time` がエラーにならずに効かず、返らない文が同時数の枠を埋め続けた。`SET GLOBAL` は今も管理者（SUPER）だけが打てる（エンジンが確かめる。エラー 1227）。効く軸は堅牢性と運用。
- 方針: (1) `SET GLOBAL long_query_time`（秒、小数）と `SET GLOBAL slow_query_log` を読む。`-slow-query` は起動時の初期値（`slow_query_log` を ON にし、`long_query_time` をその値にする）。起動し直すと `-slow-query` に戻る（MySQL の `SET GLOBAL` と同じ。`SET PERSIST` は対応しない）。接続ごと（`SESSION`）の `long_query_time` は読まない（サイトの PHP が自分の接続でログをあふれさせない）。今の値を `heimdb_status` に出す。(2) `-slow-query-redact` で、遅い文のログの文の値を `?` に畳む（vitess の `RedactSQLQuery`。解析できない文は先頭の 2 語だけ）。(3) 遅い文のログに、文が読んだ行（本体の行とインデックスのエントリ。`rows_examined`）と使ったインデックス（`wp_postmeta.post_id` の形）を出す。(4) 止まった時間の内訳（書き込みのロックの待ち、同期のレプリカの知らせの待ち、統計を作るのを待った時間）を、遅い文のログと指標に出す。(5) 接続ごとの `max_execution_time`（`SET SESSION` と `SET GLOBAL`、ミリ秒）を、MySQL と同じ文（本物の MySQL で確かめる）に効かせ、過ぎたらエラー 3024。ブランチの上限（`heimdb_branch_limit`）があれば短い方に従う（`SET` で外せない）。管理者にも効く（MySQL と同じ）。やらないこと: `EXPLAIN ANALYZE`（(3) で足りる）、`SET PERSIST`、ヒントの `MAX_EXECUTION_TIME(N)`（WordPress は使わない）。データ形式とエンジンは変えない見込み。
- 完了条件: (1)〜(5) にテストがあり、直しを外すと落ちる。`max_execution_time` の効く文とエラーが本物の MySQL と同じ。遅い文のログの欄と新しい指標が `docs/operations.md` にある。ページが流す 219 種類の文の合計が段階 80 と揺れの範囲で同じ（行を数える手間）。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。
- 結果: (1) `SET GLOBAL long_query_time` と `slow_query_log` で閾値が止めずに変わり（`-slow-query` は `SetSlowQuery` で起動時の値として入れる）、`SET SESSION long_query_time` は読まない。今の値は `heimdb_status` の `slow_query`。(2) `-slow-query-redact` で値を `?`、値の並びを `(?)` に畳む（vitess は文を小文字で書き直し、`AS` と `FROM dual` を省く）。(3) 遅い文のログに `rows_examined`（走査が読んだエントリと本体の行、インデックスから引いた本体の行、主キーで引いた行）と `indexes`（`表.インデックス`）を出す。(4) 待った時間は、トランザクションの `store.Waits`（書き込みのロックと、同期のレプリカの知らせ）と、統計を作るのを待った時間（`rowCountCache.build`）を、待ったときだけ `lock_wait`、`replica_wait`、`stats_wait` としてログに出し、指標 `heimdb_lock_wait_seconds_total`、`heimdb_replica_wait_seconds_total`、`heimdb_stats_wait_seconds_total` に足す。(5) 本物の MySQL 8.0.46 で、`max_execution_time` は `SELECT`、`WITH ... SELECT`、かっこで始まる `UNION`、`SELECT` の中のサブクエリ、`FOR UPDATE` に効き（エラー 3024）、`INSERT ... SELECT`、サブクエリを含む `UPDATE`、`SET @v = (SELECT ...)`、`DO` には効かず、root にも効くことを確かめ、同じにした（文の種類は指標と同じ `stmtType`。`WITH` で始まる書き込みの文も `SELECT` と見なすが、WordPress は出さない）。新しい処理の CPU は、219 種類の文を流した CPU プロファイルで 0.4% 未満（サンプルに現れない）。手元の Mac で 219 種類の文の合計を 0.2.24 と交互に測ると、回ごとに -3%〜+11% と揺れが差より大きかった。Go のテストは 441 件（6 件追加）で、-race でも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 80 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。直しを 1 つずつ外すと、対応するテストが落ちる（グローバル変数を読まない、畳まない、エントリを数えない、統計の待ちを数えない、ロックの待ちを数えない、知らせの待ちを数えない、`max_execution_time` を読まない）。
- 記録だけ: ヘッドレスの API の 3 通目（0.2.24、記事 2 万件）で、meta_query の JOIN の計画の残りが分かった。(1) `ORDER BY post_date DESC LIMIT 20` を、記事のインデックスを逆に読んで満たし、JOIN の途中で止める形（MySQL は 197 件で止まる。HeimDB は 2 万件を読んで並べる）。(2) JOIN の順を、定数の条件で強く絞れる表から始める形（`two_filters`。MySQL は `category = 'cat3'` の 2,028 行から）。(3) 同じ計画での 1 行あたりの速さ（2〜3 倍）。同じマシンで 0.2.24 と MySQL を比べると、`category` 1.2 倍、`two_filters` 2 倍、`priority` 5 倍、`range` 4.3 倍で、`priority` と `range` は記事の側から読み、記事ごとに `post_id` でメタを 16 行ずつ読んでいた（lookup JOIN のコストが、引くたびに読んで捨てる行を数えない。段階 80 ではサブクエリの形だけ直した）。(1) は `SQL_CALC_FOUND_ROWS` で止まれないので段階 83 で見送り、(2) と向きは段階 83 と 84 で直した。

## 段階 82: 書き込みのロックを持ったまま止まった接続を見つけて外す（ホスティングの本番の障害）

- 背景: 2026-10-29 07:25Z、ホスティングの本番の 1 サイト（0.2.23、main）で、ある接続（8613）が書き込みのロックを持ったまま 13 分間 1 文も終えず、ほかの書き込みが 50 秒ごとに 1205 になり続けた。HeimDB を 3 回起動し直し、cron を止めてようやく戻った。ホスティング側の見立ては、トランザクションの中で書き込み（ロックを取る）の後に、0.2.23 で返らない meta_query の読みを流して止まった形（実行中の文がロックを持つ）。サイトのユーザー（`GRANT ALL ON <db>.*`）では `SHOW PROCESSLIST`、`CALL heimdb_status()`、自分の接続の `KILL` が `command denied` で、持ち主が分からず、起動し直すと証拠も消えた（`information_schema.processlist` は段階 42 から自分のユーザーの接続を見せるが、知られていなかった）。HeimDB は何もしない接続を切らず（`wait_timeout` は変数があるだけ）、`heimdb_branch_limit` は main に付けられない。ロックを待つ文は KILL しても 50 秒待ち切るまで返らない（`LockBranch` が context を見ない）。効く軸は堅牢性。
- 方針（ホスティング側の優先の順）: (1) `-idle-lock-timeout`（既定 30 秒。0 で無効）: トランザクションの中で何もしないまま（文を実行していない）書き込みのロックをこれより長く持つ接続を切る（切るとセッションの終わりでロールバックし、ロックが外れる）。既定は `-lock-wait-timeout`（50 秒）より短くし、待っている書き込みは遅れるだけで通るようにする。管理者も外さない（MySQL の `wait_timeout` と同じ）。切った接続 ID、ユーザー、持っていた時間、最後の文（遅い文のログと同じく隠すか畳む）をログに出し、指標で数える。見張りはストアのロックの持ち主の記録とエンジンの ProcessList だけを読む（セッションの欄を別のゴルーチンから読まない）。(2) MySQL と同じく、PROCESS 権限がなくても、`SHOW PROCESSLIST` に自分のユーザー（ユーザー名で比べる）の接続を出し、自分のユーザーの接続は `KILL` / `KILL QUERY` できる（他人の接続は 1095、ない接続は 1094。本物の MySQL で確かめる）。エンジンの変更（planbuilder の `SHOW PROCESSLIST` と `KILL` の権限の確かめ）。`information_schema.processlist` の絞り込みと判定を共有する。手続きと運用の説明に「KILL すると、その接続のトランザクションをロールバックしてロックを外す」と書く。(3) ストアの書き込みのロックに持ち主（接続 ID、または内部の操作の名前: マージ、復元、DDL など）と取った時刻を記録し、指標（DB の権限が要らない）に、ブランチごとのロックを持っている時間と持ち主の接続 ID、ロックを待っている文の数、いちばん長く走っている文の時間、何もしないままロックを持つ接続の数、(1) で切った数を出す。`heimdb_status` にも、持ち主、持っている時間、状態（実行中か、何もしていないか、コミット中か）、最後の文を出す。1205 を返すときに、持ち主をログに出す（ブランチごとに間隔を空けて）。ロックを待つ文は KILL で抜けられるようにする。(4) `heimdb_branch_limit` で main にも実行時間の上限だけを付けられるようにする（大きさの上限は今までどおり付けない）。管理者には効かない。SELECT と書き込みの文に効き、DDL と `CALL` には効かない（プラグインの更新の大きな `ALTER` や手続きを止めない）。時間の上限だけでは一時テーブルを拒否しない（今は付けると拒否していた）。止めた書き込みが明示的なトランザクションの中ならロックは残るが、(1) が外す。(5) HeimDB が読まない MySQL の変数（`wait_timeout`、`interactive_timeout`、`innodb_lock_wait_timeout`、`lock_wait_timeout`、`net_read_timeout`、`net_write_timeout` など）を `SET` したときは、変数ごとに 1 回、ログに警告を出す（プラグインが設定するので、エラーにはしない）。読む変数と読まない変数の一覧を文書に置く。データ形式は変えない。
- 計画のレビュー（Fable）で変えたこと: 既定を 5 分から 30 秒にした（50 秒より長いと 1205 が必ず出る）。管理者を外さない。その場でロールバックせず切る（クライアントがトランザクションの中だと思ったまま次の文を自動コミットで流すのを防ぐ）。1205 のときに持ち主をログに出す、ロックを待つ文を KILL で抜けられるようにする、を足した。main の上限は、一時テーブルを拒否する不具合を直し、DDL と `CALL` を外す。ロックが残るほかの経路（バックアップのコミットの待ち、上限や KILL で止めた明示的なトランザクションの書き込み）を持ち主の表示で見分けられるようにする。非管理者向けの `heimdb_status` は作らない（(2) と `information_schema.processlist` で足りる）。`-wait-timeout`（何もしない接続をすべて切る）は次の候補。
- 完了条件: 障害の再現（A が BEGIN して書き込み、何もしない → B の書き込みが待つ → A が切られ、B が 1205 なしで通る）と、実行中の文がロックを持つ形（main の上限で止まり、(1) で外れる）のテストがある。切断と COMMIT が同時に来ても壊れない（-race）。(2) の見える範囲とエラーの番号が本物の MySQL と同じ。各項目は直しを外すとテストが落ちる。`docs/operations.md` に障害の手順（`information_schema.processlist` / `SHOW PROCESSLIST` → `KILL` → 指標 → 起動し直すのは最後）、新しいフラグと指標、`docs/procedures.md` に `heimdb_status` と `heimdb_branch_limit` の main の扱い、`docs/engine.md` にエンジンの変更、`scripts/metrics/rules.yml` にロックを長く持つ規則がある。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。
- 結果: (1) `-idle-lock-timeout`（既定 30 秒）。見張りは 1 秒（時間の 4 分の 1 と 100 ms の間）ごとに、ストアのロックの持ち主（`store.LockHolders`）とエンジンの接続の一覧（`ProcessList`。`Sleep` からの時間が何もしていない時間）を読み、`SessionManager.KillConnection` で切る。手元で、A が BEGIN して書き込み、何もしないと、3 秒（`-idle-lock-timeout 3s`）で切られて書き込みはロールバックされ、待っていた B は 1205 なしで通った。(2) 本物の MySQL 8.0.46 で、PROCESS も SUPER もないユーザーは `SHOW PROCESSLIST` に自分のユーザーの接続だけが出て、ほかのユーザーの `KILL` / `KILL QUERY` は 1095、ない接続は 1094、自分のユーザーの接続の `KILL QUERY` は通り、自分の接続の `KILL` は 1317 になることを確かめ、同じにした（エンジンの変更。`docs/engine.md` の 82）。(3) ストアの書き込みのロックに持ち主（`LockOwner`。接続 ID と内部の操作の名前: `ddl`、`drop branch`、マージ、復元）と取った時刻、待っている数を記録し、指標（`heimdb_branch_write_lock_holder`、`_held_seconds`、`_idle_seconds`、`_waiters`、`heimdb_longest_statement_seconds`、`heimdb_idle_lock_disconnects_total`）、`heimdb_status`（`write_lock <ブランチ>`）、1205 のときのログ（10 秒に 1 回）に出す。最後の文は遅い文のログと同じく隠すか畳む。ロックを待つ文は、トランザクションの `Cancel`（文の context）で `KILL QUERY` から 1317 で抜ける。(4) main には実行時間の上限だけを付けられ、管理者でない接続の SELECT と書き込みに効き、DDL と `CALL` には効かない。時間の上限だけでは一時テーブルを拒否しない。(5) `wait_timeout`、`interactive_timeout`、`innodb_lock_wait_timeout`、`lock_wait_timeout`、`net_read_timeout`、`net_write_timeout`、接続ごとの `long_query_time` を `SET SESSION` すると、変数ごとに 1 回、警告を出す（`SET GLOBAL` は管理者だけなので見張らない）。段階 14 のレビューのテストの「ブランチのユーザーに `SHOW PROCESSLIST` を拒否する」は、MySQL と同じ「自分のユーザーの接続だけを見せる」に直した。Go のテストは 448 件（7 件追加）で、-race でも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 80 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0 で、見張りが切った接続も、読まない変数の警告も 0（WordPress のテストは、テストごとにトランザクションを使うが、何もしないままロックを 30 秒持つことはない）。見張りが切るのと COMMIT が同時に来ても、2 つの書き込みは揃う（20 回、-race）。直しを 1 つずつ外すと、対応するテストが落ちる（見張りが切らない、1205 で持ち主を出さない、ロックを待つ文が KILL で抜けない、`SHOW PROCESSLIST` を拒否する、自分の接続の `KILL` を拒否する、main に上限を付けられない、時間の上限で一時テーブルを拒否する、読まない変数の警告を出さない）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- PROCESS 権限がなくても `SHOW PROCESSLIST` を拒否せず、自分のユーザー（ユーザー名で比べる）の接続だけを出す（`sql/planbuilder/show.go` の `buildShow`、`sql/plan/processlist.go` の `ShowProcessList.OnlyUser`、`sql/rowexec/show.go` の `buildShowProcessList`）。SUPER がなくても自分のユーザーの接続は `KILL` / `KILL QUERY` でき、ほかのユーザーの接続は 1095（`You are not owner of thread N`）、ない接続は 1094（`Unknown thread id: N`。管理者も）にする（`sql/planbuilder/process.go` の `buildKill`）
  - 理由: MySQL 互換と運用。MySQL は PROCESS も SUPER もないユーザーに、自分のユーザーの接続を見せて止めさせる（本物の MySQL 8.0.46 で確かめた）。ホスティングの本番で、書き込みのロックを持ったまま止まった接続を、サイトのユーザーでは見つけることも切ることもできなかった（段階 82）。`information_schema.processlist` の絞り込み（段階 42）と同じ判定

## 段階 83: meta_query の JOIN の計画と 1 行あたりの速さ（ヘッドレスの API）

- 背景: ヘッドレスの API の検証（0.2.24、記事 2 万件、`wp_postmeta` 32 万行 = 記事あたり 16 行）で、meta で絞る文が MySQL の 3〜6 倍かかり、1 vCPU で違う URL を同時に 10 本流すと毎秒 4.5 件で HeimDB の CPU が詰まった。同じマシンで MySQL と比べると `category` 1.2 倍、`two_filters` 2 倍、`priority` 5 倍、`range` 4.3 倍。`priority` と `range` は記事 2 万件から `post_id` で記事ごとに 16 行を読んで捨てる（MySQL は `meta_key` の範囲から記事を主キーで引く）。go-mysql-server の lookup JOIN のコストは引くたびに読んで捨てる行を数えず、同じグループの主キーで引く形の左の行数を借りるので、2 つの向きの差が約 5% しかなく、統計の標本の揺れで入れ替わる（ホスティングの環境で、起動し直した後に `category` が記事の側から読む形になった）。`two_filters` は、Filter の行数の見積もりが条件の種類や数によらず 0.85 を 1 回掛けるだけなので、`category = 'cat3'`（2,028 行）と `event_date`（2 万行）が同点になり、`event_date` から読んだ。`priority` は `GROUP BY` の後の `meta_value+0` の並べ替えで `Limit` と `Sort` の間に `Project` があり、TopN にならず 2 万行を全部並べ替え、比べるたびに文字列から数を作っていた。効く軸は性能。
- 方針: (1) 同じグループに主キー（一意キー）で引く lookup JOIN がある非一意の lookup JOIN に、引くたびに読む行（表の行数 ÷ 引くインデックスの先頭の列の値の種類の数）をコストに足す（段階 80 のサブクエリの形と同じ式。向きの選択にだけ効き、ハッシュ JOIN には切り替えない）。(2) Filter の行数の見積もりを、条件ごとに MySQL の既定の割合（等号 0.1、不等号 1/3、`BETWEEN` 1/9、そのほかは今の 0.85）を掛ける形にする（エンジンの変更。`memo/rel_props.go`）。(3) `Limit` の下の `Project` を越えて `Sort` を TopN にする（HeimDB の解析ルール。同順位の並びは Sort と同じ）。並べ替えのキーを 1 行 1 回だけ計算できるなら、そうする。(4) インデックスのプレフィックス長（`meta_key(191)`）より短い定数との等号は、インデックスの範囲で厳密なので、引いた後の Filter から外す。(5) lookup のたびの割り当て（範囲の式、イテレータ）を減らす。(6) GCE（1 vCPU を `GOMAXPROCS=1` で、4 vCPU）で CPU プロファイルを取り、残りの上位を見る。データ形式は変えない。
- 計画のレビュー（Fable）で変えたこと: 「引くたびに読む行」を lookup JOIN 全般に足す案は、主キーで引く形と対になるときだけに絞った（`LIMIT` で止まる今の一覧はどれも主キーで引く形なので影響を受けない）。Filter の見積もりの変更を足した（`two_filters` の先頭と、`category` の向きの安定に効く）。JOIN の途中で `LIMIT` で止める形は、WordPress 本体の meta_query が `GROUP BY` と `SQL_CALC_FOUND_ROWS` を付けて止まれないので、記録だけにした。手元のプロファイルで当たりを付けた（TopN、並べ替えのキー、プレフィックスの条件、lookup の割り当て、GC）。`information_schema.column_statistics` を読むと panic する（回復して 1105）のを見つけた。

## 段階 84: REST の文で計画が MySQL と違うもの（ヘッドレスの API）

- 背景: ヘッドレスの API が 0.2.25 と MySQL 8.0.46 で REST の 1 リクエストの文を遅い文のログで 1 本ずつ比べ（記事 2 万件、`wp_postmeta` 32 万行。`wp_postmeta` に索引 `post_key (post_id, meta_key(191))` と `key_value (meta_key(191), meta_value(64))` を足している）、計画の形の違う文が 3 つあった。(1) post__in（`ID IN (39 個)` と種類、状態、日付順）: `type_status_date` を逆に 2 万件読んで IN で絞る（MySQL は主キーを 39 点引いて並べ替える。38〜46 ms と 0.25 ms）。HeimDB の ORDER BY のルール（`orderedChild`）が、go-mysql-server の選んだ主キーの点の読み方を捨てて並べ替えのインデックスに替えていた。(2) range（`meta_value BETWEEN`）: `key_value` の 2 列目の範囲が入らず、`event_date` の 2 万行を読んで Filter で絞り、記事をハッシュ JOIN で 2 万件読む（52〜58 ms と 2.5 ms）。統計が先頭の列だけなので go-mysql-server は 2 列目からの条件を範囲に入れず、後から狭める HeimDB のルール（`narrowIndexRanges` の `exprBounds`）は、不等号を日時の列と整数の列だけで見ていた（文字列の列なら、プレフィックスのない索引でも 2 列目の不等号は範囲に入らなかった）。(3) two_filters: `key_value` で `meta_value` が索引の列になったので、段階 83 の Filter の見積もりが `meta_value = 'cat3'` を範囲で使ったものとして数えず、`category = 'cat3'`（約 2,000 行）を `meta_key` の範囲（2 万行）と同じに見積もった。遅い文のログの時間が 1 ms 刻みで、小さい文の差を測れない、という依頼もあった。効く軸は性能。

- 完了条件: ヘッドレスの API の 3 つの文と境目の値の結果と並びが、標準の索引でも API 用の索引でも、本物の MySQL のゴールデンと同じ。計画のテストで、post__in が主キーで引く（点の数が多ければ並べ替えのインデックス）、range が `meta_value` の範囲から記事を主キーで引く、two_filters が `event_date` から読まず、絞り込みの弱い `featured = '0'` なら `category` から読む（MySQL と同じ）。GCE で、ヘッドレスの API の文の時間と同時 10 本の毎秒の件数を、0.2.26 と MySQL と並べる（標準の索引と API 用の索引、1 vCPU と 4 vCPU）。ページの DB の時間が 0.2.26 から遅くならず、ページの文の計画を 0.2.26 と比べて結果が同じ。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。

## 段階 85: 文字列から数への変換を MySQL に合わせる

- 背景: 段階 84 で MySQL と比べて、数の後ろに文字の続く文字列を数にする変換が違うと分かった。`CAST('12abc' AS SIGNED)` が MySQL の 12 に対して 0、`'12abc' = 12` が偽、`'3.5e1abc' + 0` が 3.5（MySQL は 35）。WordPress の meta_query の `'type' => 'NUMERIC'` は `CAST(meta_value AS SIGNED)` を作るので、`'12abc'`、`'100 yen'` のような値の絞り込みと並べ替えが MySQL と変わる。計画のレビューで、数の列を文字列の定数で比べる `n = '12abc'` がエラー 1366 になること、JOIN で数の列を文字列のキーで引くと 0 で引くこと、非 STRICT（WordPress）の INSERT で `'12abc'` をエラーにすること（MySQL は 12 と警告 1265）も分かった。効く軸は互換性。
- 方針: 上流の go-mysql-server の main から、文字列の先頭の数の部分を切り出す関数を取り込み、数の型の変換は、読み残しのある文字列で「先頭の数の部分の値と誤り」を返す。誤りを見て止める側（STRICT の INSERT と UPDATE）は今のまま、警告で済ませる側（CAST、比べ、IN、算術、索引の範囲、JOIN の引き方）は値を使い、MySQL と同じ警告 1292 を出す。非 STRICT の INSERT と UPDATE は、先頭の数の部分と警告 1265（数で始まらなければ 0 と警告 1366）にする（`nonstrict.go`）。エンジンの変更は `docs/engine.md` の 85。データ形式は変えない。
- 計画のレビュー（Fable）で変えたこと: 新しく書く代わりに上流の関数を取り込んだ。誤りを捨てず、値と一緒に返す形にした（STRICT の INSERT が黙って値を入れないように）。索引の範囲、JOIN の引き方、`keyChanged`（`'12.5x'` は 12.5 なので整数の列のキーにしない）、非 STRICT の INSERT を範囲に入れた。`CAST('1e3' AS SIGNED)` が MySQL では 1 になることを足した。
- 完了条件: 境目の値（空、空白だけ、符号だけ、`'.5'`、`'5.'`、`'1e'`、`'1e3'`、`'1e3x'`、`'-5x'`、前後の空白、改行、`'0x1A'`、`'12abc'`、`'12.7abc'`、`'3.5e1abc'`、範囲の外、全角の数字、`'12,5'`、`'abc'`）の CAST（SIGNED、UNSIGNED、DECIMAL、DOUBLE）、比べ、`BETWEEN`、`IN`、算術の値と警告、数の列を文字列で引く文（主キー、索引、JOIN）、非 STRICT の INSERT と UPDATE の値と警告、meta_query の NUMERIC の文が、本物の MySQL のゴールデンと同じ。直しを外すとテストが落ちる。Go のテストが -race でも通る（エンジンのテストを含む）。PHPUnit の差が 35 から増えない。

## 段階 86: カンマで並べた表の、式との等号を結合の条件にする（ホスティングの本番の cron）

- 背景: ホスティングの本番で、WordPress 本体の日次の cron（`delete_expired_transients`）の `DELETE a, b FROM wp_options a, wp_options b WHERE a.option_name LIKE '\_transient\_%' ... AND b.option_name = CONCAT('_transient_timeout_', SUBSTRING(a.option_name, 12)) AND b.option_value < <時刻>` が、期限切れの残骸の溜まった `wp_options`（34,168 行）で 1,101 秒を超えて完走せず、書き込みのロックを持ち続けて、そのサイトの書き込みが 20 分止まった（1205 が毎分 1〜3 本）。KILL しても cron がやり直した。ホスティング側は遅い文のログの `rows_examined=73710`（272 行の表で 272 × 271）から、`a` の 1 行ごとに `b` を全部読んでいると突き止めた。go-mysql-server は、`FROM a, b WHERE` の等号を結合の条件に移すとき、両辺が列そのものの等号しか移さず、右辺が式のこの条件は CrossJoin の上の Filter に残った（`INNER JOIN ... ON` と書けば `option_name` の索引で引く）。あわせて、WordPress のサイトヘルスの `information_schema.TABLES` の問い合わせが 1.8 秒（`rows_examined=0`）かかるという報告もあった。効く軸は性能と堅牢性。
- 方針: (1) 等号の一方の辺の列がすべて結合の片方の表の、もう一方の辺の列がすべてもう片方の表のものなら、片側が式でも結合の条件に移す（エンジンの変更。`docs/engine.md` の 86）。副問い合わせと、評価するたびに値の変わる式は移さない。移した後の索引の選び方は、`INNER JOIN ... ON` と同じ。(2) `information_schema.TABLES` は、統計を作り直す読み込みが原因かを確かめ、簡単に避けられれば直す。データ形式は変えない。
- 計画のレビュー（Fable）で変えたこと: 等号の辺を表の ID で見る形にし（両方の表が混ざる式、外の問い合わせの列、3 つ目の表の列を自然に除く）、等号だけにした。`information_schema.TABLES` は、統計の作り直しではなく、HeimDB が読むたびにすべてのブランチのすべての表の行数を数えていたのが重さだと分かった（ホスティングの遅い文のログにも `stats_wait` が出ていない）ので、WHERE で名前を決めた表だけを数える。本物の MySQL と比べると、複数の表の DELETE の影響を受けた行の数が違う（結び付いた行の数）と分かった。
- 完了条件: 期限切れの transient を消す文（`_transient_` と `_site_transient_`）と同じ条件の SELECT、期限切れのないとき、期限の行のない値の行、値の行のない期限の行、名前が空の transient、数でない期限、複数の表の UPDATE の結果と影響を受けた行の数が、本物の MySQL のゴールデンと同じ。計画のテストで、`b` を `option_name` の索引で引き、CrossJoin がない。3 万 4 千行の残骸の DELETE が数秒で終わる。サイトヘルスの問い合わせが名前を決めた表だけを数え、数えた行数は正確なまま。エンジンのテストで、式との等号を移し、両方の表が混ざる式、値の変わる式、副問い合わせ、定数だけの辺、不等号、3 つ目の表の列を含む式は移さない。ページの文 237 種類の計画と結果を 0.2.27 と比べる。直しを外すとテストが落ちる。Go のテストが -race でも通る（エンジンのテストを含む）。PHPUnit の差が 35 から増えない。
- 結果: (1) `replace_cross_joins.go` の `expressionEqualityCoversJoin` が、等号の一方の辺の列がすべて結合の片方の子の表、もう一方の辺の列がすべてもう片方の子の表のもの（表の ID で見る）なら、片側が式でも結合の条件に移す。期限切れの transient を消す文は、`b` を `option_name` の索引で引く形になり、手元で 3 万 4 千行（1 万 7 千組）の DELETE が 0.2 秒（前は `a` を 500 行に絞っても 23.7 秒）。(2) 本物の MySQL と比べる中で、複数の表の DELETE に以前からの違いが 3 つ見つかったので直した: 1 つの行が何度も結び付くと 2 つ目からの組を消さなかった（読みながら消し、消した行が後の結び付きに現れなかった）。LEFT JOIN で相手のない行があるとエラー 1105 になった。影響を受けた行の数が結び付いた行の数だった（MySQL は消した行の数）。結び付いた行を先に全部読み、消す表ごとの行だけを、主キーのある表は元の表ごとに 1 度だけ集めてから消す（`docs/engine.md` の 86）。上流のテストの、影響を受けた行の数の期待 7 つを MySQL と同じ値に変えた。(3) `information_schema.TABLES` は、すぐ上の Filter が `TABLE_SCHEMA` と `TABLE_NAME` を定数の等号か IN で決めていれば、その表だけを数える（`tablerows.go` の `tableRowsOnlyNamed`）。手元で、ブランチ 5 つ（34 万行ずつ）のときに、すべての表を数える問い合わせが 0.16〜0.68 秒、サイトヘルスの問い合わせが 0.01 秒。期限切れの transient を消す文、同じ条件の SELECT、複数の表の UPDATE、1 つの行が何度も結び付く DELETE、LEFT JOIN の DELETE、同じ表を別名で 2 度消す DELETE の結果と影響を受けた行の数は、本物の MySQL のゴールデン（`stage86_golden.txt`）と同じ。ページの文 237 種類は、GCE で 0.2.27 と比べて計画も結果もすべて同じ。実装のレビュー（Fable）で、同じ表を別名で 2 度消すときに 1 つの行を 2 度数えることと、結び付いた行を全部の列ごと持つこと（メモリ）が見つかり、消す表ごとの行だけを元の表ごとに 1 度だけ持つ形にした。直しを 1 つずつ外すと、対応するテストが落ちる。Go のテストは 459 件で、-race でも通り、エンジンのテストも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 85 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。
- 記録だけ: (a) 主キーのない表を複数の表の DELETE で消すとき、1 つの行が何度も結び付くとエラー 1105（行が見つからない）になり、同じ値の行が 2 つあると影響を受けた行の数が少なくなる（段階 86 の前から。WordPress の表には主キーがある）。(b) 消す表が 1 つで JOIN のある DELETE は、前のまま読みながら消す: LEFT JOIN の相手のない側を消そうとするとエラー 1105、1 つの行が何度も結び付くと影響を受けた行の数が多くなる（段階 86 の前から。WordPress の `DELETE pm FROM wp_postmeta pm LEFT JOIN wp_posts p ... WHERE p.ID IS NULL` は消す側が 1 対 1 で、相手のない側を消さない）。(c) `information_schema.TABLES` の `TABLE_NAME` を、MySQL（Linux）は大文字と小文字を区別し、末尾の空白を無視して比べるが、HeimDB は大文字と小文字を区別せず、末尾の空白を無視しない（段階 86 の前から）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- `FROM a, b WHERE ...` の WHERE の等号を結合の条件に移すとき（`sql/analyzer/replace_cross_joins.go` の `comparisonSatisfiesJoinCondition`）、両辺が列そのものの等号に加えて、一方の辺の列がすべて結合の片方の子の表、もう一方の辺の列がすべてもう片方の子の表のもの（片側が式でもよい）も移す（`expressionEqualityCoversJoin`。表の ID で見る。副問い合わせと、評価するたびに値の変わる式は移さない。等号だけ）。テストを足した（`replace_cross_joins_heimdb_test.go`）
  - 理由: 性能。WordPress 本体の期限切れの transient を消す `DELETE a, b FROM wp_options a, wp_options b WHERE ... b.option_name = CONCAT('_transient_timeout_', SUBSTRING(a.option_name, 12))` が、全部の組み合わせを作ってから絞り込み、残骸が 3 万 4 千行溜まった本番で 20 分を超え、書き込みのロックを持ち続けた。MySQL は b を option_name の索引で引く
- 複数の表から消す DELETE（`sql/rowexec/delete.go` の `deleteIter`）は、結び付いた行を先に全部読み、消す表ごとの行だけを集めてから消す。LEFT JOIN で相手のない側（NULL で埋めた行）は消さない。主キーのある表の行は、元の表ごとに 1 度だけ集めて消す（同じ表を別名で 2 度消す自己結合も含む）ので、影響を受けた行の数は消した行の数の合計になる。消す表の元の名前と主キーの有無は `sql/rowexec/dml.go` の `buildDeleteFrom` が渡す。上流のテスト `enginetest/queries/delete_queries.go` の、複数の表の DELETE の影響を受けた行の数の期待 7 つを、MySQL と同じ値（結び付いた行の数の 2 倍）に変えた。消す表が 1 つの DELETE は前のまま（読みながら消す）
  - 理由: 互換性。読みながら消すと、消した行が後の結び付きに現れず、1 つの行が何度も結び付く `DELETE a, b` で 2 つ目からの組を消さなかった。LEFT JOIN で相手のない行があると、主キーが NULL の行を消そうとしてエラー 1105 になった。影響を受けた行の数は、結び付いた行の数だった（MySQL は消した行の数。`stage86_golden.txt`）

## 段階 87: 退避を別の権限の環境で開く、退避の暗号化（ホスティング側の依頼）

- 背景: ホスティング側は更新の検証（段階A）で使う複製を、論理ダンプ（書き出し 31〜71 秒、取り込み最大 190 秒、311 万行でメモリを使い切る）から `heimdb_backup` の退避に替えたい。しかし、退避には本番の DB のユーザーとパスワードのハッシュが入るので、検証の環境（別のプロジェクト。本番の root のパスワードを渡さない）では誰も入れない（起動時に `users already exist, so the root password was ignored`）。また、退避は平文で、ホスティング側が目印を入れて確かめると、WAL（`000002.log`）から `grep` で読めた。顧客のサイトの DB（氏名、メールアドレス、問い合わせ）なので、退避を別のプロジェクトへ写すなら暗号化したい。鍵は退避ごとに選べ（本番の退避と検証に渡す写しで分け、検証に本番の鍵を渡さない）、差し替えに起動し直しが要らず（引数を変えて起動し直したときに 500 を出した）、展開はサーバなしで動き、鍵が違えば何も作らずに失敗してほしい（空の store で検証が「差分なし」で通るのを避ける）。効く軸は安全性。
- 方針: (1) 起動時の旗 `-reset-passwords`（root とサイトのユーザーのパスワードを上書きし、ほかのユーザーは残す）と `-reset-users`（すべてのユーザーを消して作り直す）。環境変数でも指定でき、ユーザーのいない store では作るだけ、値が同じなら書き込まない。レプリカと `-no-auth` では拒む。(2) 暗号化は age（filippo.io/age、BSD-3）の X25519 の受取人（公開鍵）で、本番の HeimDB には公開鍵だけを置く。`-backup-key 名前=パス` で名前とパスを決め、ファイルの中身は退避のたびに読み、受取人をログに出し、中身が変わっていれば警告する。`CALL heimdb_backup('<名前>', '<鍵>')` は、store の全体（WAL を含む）を tar.gz にして暗号化した 1 つのファイル `<名前>.tar.gz.age` にする。展開は `heimdb restore-backup`（Docker では ENTRYPOINT の後ろ）。鍵を指定しない退避は今のまま。データ形式は変えない。
- 計画のレビュー（Fable）とホスティング側の意見で変えたこと: 共通鍵（AES-GCM）ではなく公開鍵にした（本番のマシンが乗っ取られても過去の退避が解けない。検証の秘密鍵が検証のプロジェクトから出ない）。旗は値が同じなら書き込まない形にし、サイトのユーザーのパスワードも上書きする（`ALTER USER` が要らない）。ホスティング側の意見で、鍵のファイルを退避のたびに読む、展開のコマンドを足す（標準の `age -d | tar -xz` では失敗したときに途中まで展開したものが残る）、ユーザーを全部消す変種を足す、ユーザーのいない store でも同じに動く、ファイル名を時刻の形のまま `.tar.gz.age` にする、受取人をログに出して差し替えに気づけるようにした。
- 完了条件: 暗号化した退避のファイルに、SSTable にある目印も WAL にだけある目印も平文で入らない（同じ時点の平文の退避には入る）。正しい秘密鍵で展開した store が開け、両方の目印が読める。違う鍵、鍵なし、途中で切れたファイル、空でないディレクトリでは、終了コードが 0 以外で、何も残らない。暗号化する前の写しと書きかけのファイルが残らない（止められたときも。起動時に前のものを消す）。ファイルは 0600。名前の重なり、知らない鍵の名前、不正な名前はエラーで、接続は切れない。受取人がログに出て、ファイルを差し替えると、起動し直さずに次の退避から新しい鍵になり、警告が出る。`-reset-passwords` で新しいパスワードで入れ、ほかのユーザーと権限と WordPress の表は変わらず、2 度目の起動では書き込まない。`-reset-users` で root だけ（サイトのパスワードがなければ）になる。ユーザーのいない store でも動く。レプリカ、`-no-auth`、両方の旗の指定は拒む。鍵を指定しない退避は今のまま。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。
- 結果: (1) `backupkey.go`: `-backup-key` の鍵の名前とパスを登録し、退避のたびに受取人（age の X25519 の公開鍵だけ）を読み、ログに出し、前に読んだときと変わっていれば警告する。`heimdb_backup` の 2 つ目の引数で鍵を指定すると、`.<名前>.ckpt` に写しを作り、tar.gz にして暗号化した `<名前>.tar.gz.age`（0600。`.partial` に書いてから名前を変える）にし、写しは消す。止められたときも残さず、起動時に前の残りを消す。退避は 1 つずつ。(2) `cmd/heimdb/restore.go`: `restore-backup` は、空のデータのディレクトリ（`lost+found` と前の中断の残りは除く）の中の仮のディレクトリに展開し、store のファイル（MANIFEST）を確かめてから移す。普通のファイルとディレクトリだけを、ディレクトリの中にだけ書く。失敗したら何も残さず（作ったディレクトリも消す）、終了コードは 1。(3) `-reset-passwords` と `-reset-users`（`auth.go` の `ResetUsers`）。`-reset-users` はロールの結び付きも消す。`-reset-passwords` で残した、`'%'` でないホストの root とサイトのユーザーは警告に出す。手元の確かめで、平文の退避には SSTable と WAL の目印が入り、暗号化した退避には入らず、展開した store で両方が読めた。実装のレビュー（Fable）で、展開が前の中断の残りや `lost+found` で拒み続けること、失敗したときに作ったディレクトリが残ること、`-reset-users` がロールの結び付きを残すこと、`'%'` でないホストの root が本番のパスワードのまま残ることが見つかり、直した（最後は警告。`root@'localhost'` があると、手元からの接続はそちらに当たる）。直しを 1 つずつ外すと、対応するテストが落ちる（展開の最後に age の最後の塊まで読み切る確かめは、最後の塊が欠けると gzip の終わりも欠けて先にエラーになるので、外しても落ちない。二重の守りとして残す）。依存に age（filippo.io/age v1.2.1、BSD-3）を足した。Go のテストは 463 件で、-race でも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 86 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。
- 記録だけ: 動いている store（データのディレクトリ）の暗号化と、Cloud KMS を HeimDB から呼ぶ形は扱わない。退避の置き場所を 2 つの HeimDB で分け合うと、起動時の掃除がもう一方の書きかけを消しうる（そういう使い方はしない）。

## 段階 88: 0.2.28 の確かめで見つけたものと、MySQL との小さな違い

- 背景: 0.2.28 をイメージで確かめると、文書の例どおり新しい名前付きボリュームを `/backups` にすると、`heimdb_backup` が `permission denied` で失敗した（イメージが `/backups` を HeimDB のユーザーのものとして作っていない。0.2.27 も同じ）。`-reset-users` で書き換えるものがないときのログの文が読みにくかった。段階 84〜86 で記録だけにした MySQL との違いのうち、WordPress に関わる小さなもの: double の書き方（`meta_value+0` や `SUM` の 100 万以上の結果が `2.0250331e+07`）、`CAST(... - 計画のレビュー（Fable）で変えたこと: (4) で、索引のある文字列の列を数で比べる（`meta_key = 12`）と、数を文字列にした 1 つの値を索引で読み、`'12abc'` や `' 12 '` を落とす不具合が見つかった（MySQL は全件を読む）ので、索引の範囲にしない直しを足した。(2) の MySQL の規則（小数点の位置が -14 以上 15 以下か、桁の数がそれより多いときに指数を使わない。FLOAT は 6 桁。CONCAT と CAST(... AS CHAR) は 22 文字と 12 文字まで）と、(3) の警告の名前（別名か書いたとおりの式、項目でなければ `(null)`）を、本物の MySQL で確かめた。実装の中で、`CAST(... AS DECIMAL)` の桁の既定が MySQL では `DECIMAL(10,0)` で、WordPress の meta_query の `'type' => 'DECIMAL'` が値を整数に丸めて比べるのに、HeimDB は丸めないことが分かり、(3) に足した。
- 完了条件: double と float の形（1e15 の前後、小さい値、負の値、-0、FLOAT の列、CONCAT と CAST(... AS CHAR) の上限）、DECIMAL の桁の既定と範囲の外の値と警告、文字列の列（索引のあるものとないもの）と数の等号と `IN`、meta_query の DECIMAL と NUMERIC の文が、本物の MySQL のゴールデンと同じ（結果の行の double の形は、Go のドライバが数として読み直すので、エンジンの型のテストで確かめる）。計画のテストで、文字列の列と数の比べは索引の範囲にしない。新しい名前付きボリュームで、イメージから退避が取れる。直しを外すとテストが落ちる。Go のテストが -race でも通る（エンジンのテストを含む）。PHPUnit の差が 35 から増えない。

AS CHAR)、文字列の型の式の中の値に使う。(3) `CAST(... AS DECIMAL)` を `DECIMAL(10,0)` に、`DECIMAL(M)` を `DECIMAL(M,0)` にし、範囲の外を端の値と警告 1264 にした（名前は別名か書いたとおりの式、項目でなければ `(null)`）。範囲の外の桁の指定はエラー 1426、1427、1425。(4) 文字列の列と数は、等号も `IN` も値の組ごとに数として比べ、索引の範囲にもハッシュにもしない（`fixedColumns` も 1 つの値にしない）。上流のテストの期待を 6 つ、MySQL と同じに変えた（`CONVERT(…, DECIMAL)` と小数の列の比べ 5 つ、ハッシュにしない `IN` 1 つ）。実装のレビュー（Fable）で、数の後ろに文字の続く大きな値の CAST で 1292 が出ないこと、10^35 以上の値の CAST が 0 になること、範囲の外の桁の指定を確かめず 256 で折り返すこと、文字列の型の式の中の DOUBLE の符号が消え前の値の文字が混ざること（`IF(1, -1.5e0, 'a')`。以前から）、`IN` で MySQL が出す警告 1292 を出さないこと、警告が上限なくたまることが見つかり、直した。結果の行の double の形は Go のドライバが数として読み直すので、エンジンの型のテスト（`float_format_test.go`）と mysql のコマンドで確かめた。本物の MySQL のゴールデン（`stage88_golden.txt`）と同じ。直しを 1 つずつ外すと、対応するテストが落ちる。Go のテストが -race でも通り、エンジンのテストも通った。PHPUnit は 26,475 件で、本物で通って HeimDB で落ちるのは段階 87 と同じ 35 件（一覧が同じ）。接続の切断と panic は 0。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- DOUBLE と FLOAT の値を、MySQL（strings/dtoa.cc の `my_gcvt`）と同じ形の文字列にする（`sql/types/float_format.go` の `AppendMySQLDouble`、`AppendMySQLFloat`）。DOUBLE は元に戻せるいちばん短い桁、FLOAT は 6 桁で、小数点の位置が -14 以上で 15 以下（か桁の数がそれより多い）なら指数を使わず、指数の形は `1e15`、`1e-16`（+ と先頭の 0 を付けない）。結果の行（`sql/types/number.go` の `SQLFloat64`、`SQLFloat32`、`SQL2`）は上限なし、CONCAT と CAST(... AS CHAR)（`sql/types/strings.go` の `ConvertToBytes`）と、文字列の型の式の中の値（`StringType.SQL`。`IF(1, -1.5e0, 'a')`）は DOUBLE 22 文字、FLOAT 12 文字まで。JSON の数は変えない。MySQL との残りの違い（WordPress には出ない）: MySQL は DOUBLE の列の値には 22 文字の上限を使わず、計算した値で指数の形が 22 文字を超えると桁を減らす（HeimDB は 17 桁のまま）。FLOAT の値を文字列の列に入れると、MySQL は double の桁で書く
  - 理由: 互換性。Go の `'g'` の形で、`SUM` や `meta_value+0` の 100 万以上の結果が `1.234567e+06`、`2.0250331e+07` になり、小さい値も `1.5e-07` になった（MySQL は `1234567`、`20250331`、`0.00000015`）。FLOAT は Go の float32 の最短の桁で `2.02503e+07`（MySQL は `20250300`）。`StringType.SQL` は負の値の符号を落とし、符号がないと前の値の文字まで混ぜていた
- `CAST(... AS DECIMAL)` の桁の既定を MySQL と同じ `DECIMAL(10,0)` に、`DECIMAL(M)` を `DECIMAL(M,0)` にする（`sql/planbuilder/scalar.go`、`sql/expression/convert.go` の `createConvertedDecimalType`。前は桁を決めない内部の型で、小数を丸めなかった）。範囲の外は、0 ではなく同じ符号の型の端の値（`DECIMAL(5,1)` なら ±9999.9）にし、警告 1264 `Out of range value for column '<名前>' at row 1` を出す（`castToDecimal`、`clampDecimal`。数の後ろに文字の続く文字列なら、先に 1292 も出す）。M が 65 を超える、D が M を超える、D が 30 を超える指定は、MySQL と同じくエラー 1426、1427、1425 にする（`sql/planbuilder/scalar.go`）。名前は SELECT の項目の別名か書いたとおりの式で、項目でなければ `(null)`（`sql/planbuilder/project.go` が `Convert` に名前を付ける）。上流のテスト `enginetest/queries/script_queries.go` の、`CONVERT('…', DECIMAL)` と小数の列の比べの期待 5 つを、MySQL と同じ 0 に変えた
  - 理由: 互換性。WordPress の meta_query の `'type' => 'DECIMAL'` が作る `CAST(meta_value AS DECIMAL)` は、MySQL では整数に丸めて比べる（`10.5` は 11）が、HeimDB は丸めなかった
- 文字列の列と数の比べ（`meta_key = 12`、`meta_value IN (12, 9)`）を、MySQL と同じく値の組ごとに数（double）として比べる。`IN` は、左が文字列で右に数があれば、その組を数として比べ（`sql/expression/in.go`。数にできない文字列は、等号と同じく左の値ごとに 1 度、警告 1292 を出す）、ハッシュにしない（`sql/analyzer/apply_hash_in.go` の `textInNumbers`）。索引の範囲にもしない（`sql/analyzer/costed_index_scan.go` の `newLeaf`）。上流のテスト `sql/analyzer/apply_hash_in_test.go` の「cast on left」の期待を、ハッシュにしない形に変えた
  - 理由: 不具合。索引のある文字列の列を数で比べると、数を文字列にした 1 つの値（'12'）だけを索引で読み、`'12abc'` や `' 12 '` を落とした（索引のない列は段階 85 から正しい）。`IN` は、左の文字列の型に揃えて文字列として比べていた
- 文ごとに覚える警告を 1024 個まで（MySQL の `max_error_count` の既定）にする（`sql/base_session.go` の `Warn`。数は全部を数える）
  - 理由: 堅牢性。`ORDER BY CAST(meta_value AS DECIMAL)` のように並べ替えで何度も評価する式が、行の数の何倍もの警告をためた

## 段階 90: 接続の照合順序と重なりのエラー（ホスティング側の報告）

- 背景: ホスティング側が、HeimDB と MySQL 8.0 で文字列の比べが違うと報告した（リテラル同士の `'a'='A'` が HeimDB で 0、列の比べで「あ」と「ア」が等しい、など）。本物の MySQL で確かめると、列の比べ、UNIQUE、ORDER BY は、照合順序 5 つ（0900_ai_ci、unicode_520_ci、unicode_ci、general_ci、指定なし）すべてで HeimDB と同じだった（ホスティング側が測った MySQL の結果は general_ci の振る舞い）。違ったのは、HeimDB が接続のハンドシェイクでクライアントが伝えた照合順序を読まず、`SET NAMES` までは `collation_connection` が `utf8mb4_0900_bin` のままのこと（`@@collation_server` も同じ。MySQL は伝えられた照合順序、既定は `utf8mb4_0900_ai_ci`）。WordPress は接続のたびに `SET NAMES utf8mb4 COLLATE utf8mb4_unicode_520_ci` を送るので出ないが、mysql コマンドや直接つなぐスクリプトでは出る。あわせて、重なりのエラーが、番号は 1062 で同じだが、文（`duplicate unique key given: [ア]`）と SQLSTATE（`HY000`）が MySQL（`Duplicate entry 'ア' for key 'cu.v'`、`23000`）と違った。
- 方針: (1) 接続を作るとき（`internal/backend/session.go` の `handshakeCollation`）、伝えられた照合順序が utf8mb4 のものならそれを `collation_connection` にする。utf8mb3 と ascii は utf8mb4 の同じ名前のもの（33 の utf8mb3_general_ci は utf8mb4_general_ci。HeimDB の挨拶は vitess の定数の 33 を名乗る）、知らない id と utf8mb4 にできないもの（latin1 など）は `utf8mb4_0900_ai_ci`。文字セットの変数は今までどおり utf8mb4。(2) `collation_server` と `collation_connection` の既定を `utf8mb4_0900_ai_ci` にする（`cmd/heimdb/main.go` の `AssignValues`。エンジンの `Collation_Default` は型の既定に使うので変えない）。(3) 重なりのエラーの文と SQLSTATE、INSERT IGNORE の警告を MySQL と同じにする（`docs/engine.md` の 90）。データ形式は変えない（接続の照合順序は保存したデータに入らない。照合順序を書かずに作る表は、今までどおりデータベースの既定）。
- 計画のレビュー（Fable）で変えたこと: セッションの変数は `InitSessionVariable` ではなく `SetSessionVariable` で入れる（既定と違うグローバルの値が入ったセッションでは、`InitSessionVariable` がエラーになる）。エラーの Go の文と `NewUniqueKeyErr` は変えず、値とキーの名前を足した `NewDuplicateEntryErr` を作り、接続に返す文だけを変える（上流のテストが Go の文を期待し、`ON DUPLICATE KEY UPDATE` と `REPLACE` がエラーの中の `UniqueKeyError` を取り出す）。INSERT IGNORE の警告は Level も `Warning` にする（上流は `Note`）。主キーのない表を並べる一意インデックスの重なりは、その一意インデックスの名前にする。utf8mb3 の id は utf8mb4 の同じ名前のものにする（すべて 0900_ai_ci にすると、utf8mb3_general_ci のクライアントで「ア」と「あ」が等しくなり、MySQL と違う）。
- 完了条件: go-sql-driver で照合順序を伝えたとき（0900_ai_ci、general_ci、unicode_ci、unicode_520_ci、bin、utf8mb3_general_ci）、`@@collation_connection`、`@@collation_server`、リテラル同士の比べ（`'a'='A'`、`'a'='ａ'`、`'ア'='あ'`、`'1'='１'`）が、本物の MySQL に同じドライバでつないだ結果と同じ。`SET NAMES` の後は今までどおり。重なりのエラー（主キー、一意インデックス、複数の列、プレフィックスの索引、バイナリ、日時と DECIMAL、長い値、一時テーブル、主キーのない表、ALTER TABLE と CREATE UNIQUE INDEX）と INSERT IGNORE の警告が、番号、SQLSTATE、文で本物の MySQL のゴールデンと同じ。`ON DUPLICATE KEY UPDATE` と `REPLACE` の結果も同じ。Go のテスト（-race でも）、PHPUnit がベースラインと同じ。
- 実装後のレビュー（Fable）で直したこと: 重なりのエラーの文に書く値を、文を返すときにだけ作る（`ON DUPLICATE KEY UPDATE` と `REPLACE` は重なるたびにこのエラーを受け取るが、文は使わない。作るたびにセッションを 1 つ作っていた）。データベースを選んでいない接続の `@@collation_database` を `collation_server` にする（`docs/engine.md` の 90。エンジンが `utf8mb4_0900_bin` に決めていた）。
- 結果: (1) go-sql-driver で照合順序を伝えた 7 とおり（0900_ai_ci、general_ci、unicode_ci、unicode_520_ci、bin、utf8mb3_general_ci、latin1_swedish_ci）で、`@@collation_connection`、`@@character_set_connection`、`@@collation_server`、リテラル同士の比べが、本物の MySQL 8.0.46 に同じドライバでつないだ結果と同じになった（utf8mb3 は MySQL も utf8mb4_general_ci にする。latin1 だけは、MySQL は latin1、HeimDB は utf8mb4_0900_ai_ci）。`SET NAMES ... COLLATE` の後は今までどおり。(2) 重なりのエラーが、主キー、一意インデックス、複数の列、プレフィックスの索引、バイナリ（`\x00\xFF`）、ENUM、DATE、DATETIME と DECIMAL、64 バイトを超える値、一時テーブル、名前に記号のある表とインデックス、主キーのない表、ALTER TABLE ADD UNIQUE と CREATE UNIQUE INDEX、UPDATE で、番号、SQLSTATE、文が本物の MySQL のゴールデンと同じになった。INSERT IGNORE の警告も同じ（Level が Warning）。`ON DUPLICATE KEY UPDATE` と `REPLACE` の結果は変わらない。直しを 1 つずつ外すと、それぞれのテストが落ちた（12 とおり）。重なりのエラーの文を見ていたテスト 2 つ（主キーのない表、主キーの型）の期待を、MySQL の文にした。Go のテストは 470 件（-race でも成功）。PHPUnit は 26,475 件で、差は 35 件のまま一覧も同じ。接続の切断と panic は 0。
- 記録だけ: (a) HeimDB の挨拶は、vitess の定数の 33（utf8mb3_general_ci）を名乗る（MySQL 8.0 は 255）。サーバに合わせるクライアントは 33 を返し、HeimDB は utf8mb4_general_ci にする（MySQL に 33 を伝えたときと同じ）。(b) 重なりのエラーの値は 64 バイトまでで、MySQL は文字の途中でも切る（壊れた文字が残る）が、HeimDB は文字の境目で切る。(c) `DATETIME(6)` の列の値は、SELECT でも重なりのエラーでも、MySQL は列の桁まで 0 で埋め（`.120000`）、HeimDB は埋めない（`.12`。段階 90 の前から）。WordPress は小数の秒の列を使わない。(d) 主キーに DECIMAL の列を含む表は、HeimDB では作れない（前から）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- 重なりのエラー（1062）を MySQL と同じ文（`Duplicate entry '<値>' for key '<表>.<インデックス>'`、主キーは `<表>.PRIMARY`）と SQLSTATE `23000` にする。`UniqueKeyError` に、文に書く値とキーの名前を足し（`sql/errors.go` の `NewDuplicateEntryErr`。HeimDB の保存の層が渡す）、`CastSQLError` と、INSERT IGNORE の警告（`sql/rowexec/insert.go` の `warnOnIgnorableError`。MySQL と同じく Level を `Warning` に）で使う。Go のエラーの文（`Error()`）と `NewUniqueKeyErr` は変えない
  - 理由: 互換。重なりを `$wpdb->last_error` の `Duplicate entry` で見分けるプラグインがある。上流の文は `duplicate unique key given: [x]` で SQLSTATE が `HY000` だった。上流のテストの期待する Go の文と、`ON DUPLICATE KEY UPDATE` と `REPLACE` が使う既存の行（`Existing`）はそのまま。値の形（列の型の文字列を `-` でつなぐ、プレフィックスの索引はその文字数、64 バイトまで）は `internal/backend/editor.go` の `duplicateEntry`
- データベースを選んでいない接続の `@@collation_database`（`@@character_set_database`）を、`Collation_Default`（`utf8mb4_0900_bin`）ではなく `collation_server` にする（`sql/planbuilder/set.go` の `buildSysVar`）
  - 理由: 互換。MySQL は、既定のデータベースがなければ `collation_server` と同じ値にする。HeimDB は `collation_server` を `utf8mb4_0900_ai_ci` にした（段階 90）ので、`SHOW VARIABLES LIKE 'collation%'` が揃う
