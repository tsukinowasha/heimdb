# 段階 101〜110

[計画の開発ステップ](../plan.md#開発ステップ)の各段階の記録。

## 段階 101: 2 つのメタの条件と別のキーの並べ替えの JOIN の順を MySQL と同じにする

- 背景: 段階 100 の組の形で、API 用の索引の two_filters_t（`category = 'cat3'`、`featured` の `meta_value = '1'`、`event_date` で並べる）は GCE で 49.6 ms、MySQL 15.3 ms。HeimDB は category の点（2,000 行）から読み、記事ごとに event_date、featured、記事の順に引く（lookup が約 6,000 回）。本物の MySQL 8.0 の `EXPLAIN ANALYZE` は、category の後に featured を引いて 223 行に絞り、記事と event_date はその 223 行だけ引く（約 2,700 回）。手元でヒント（`JOIN_ORDER(wp_postmeta, mt1, mt2, wp_posts)`）で featured を先にすると、15.95 ms が 10.93 ms になり、結果は同じ。featured を `CAST(meta_value AS SIGNED) = '1'` で比べる two（段階 95）は、もう MySQL と同じ順。順を決める見積もりで、featured の条件で 1/9 に絞れることが効かず、event_date と同点になっているとみられる（推測。テストで確かめる）。WP_Query の meta_query で、条件 2 つと別のキーの並べ替えを組み合わせると、この形になる。lookup の 1 回ごとの手間（区間を作る処理 8%、区間がちょうどかの判定 5%）は、順を直した後に測り直す。Pebble の L0 を圧縮で空にしても 4〜6% だった。効く軸は性能。
- 方針: 計画を Go のテストで再現し、memo のコストと行数の見積もりを見て、同点になる場所を確かめてから直す。直すのは HeimDB の見積もり（`selectivity.go`、`coster.go`）を先に考え、エンジンを変えるなら `docs/engine.md` に書く。データ形式は変えない。
- 計画のレビュー（Fable）と再現で分かったこと: featured の Filter の割合は正しく 0.113 と見積もられていた（標本で数える）。同点は JOIN の出力の行数の見積もり（エンジンの `statsForRel`）から来る。Filter を通った子は値の種類の数を持たないので、大きい方の子の行数の 8 割を値の種類とみなし、出力は「小さい方の子の行数 ÷ 0.8」になる。category（187 行）と featured（231 行）の JOIN も、category と event_date（1,750 行）の JOIN も 233 行で、lookup JOIN のコストも同じになり、メモの中の並びの先の方（別名の番号で決まる）が選ばれていた。段階 95 の CAST の形が MySQL と同じ順だったのも、event_date が別名のない表で並びが逆になる巡り合わせで、見積もりで決まったのではない。直し方は、JOIN のキー（記事の ID）の値の種類の数で割ること。エンジンには差し替える口 `memo.JoinKeyDistinct`（既定は 0 で元のまま）だけを足し、HeimDB が表の統計の値の種類の数を返す。完了条件に、別名を入れ替えた形と、段階 95 の CAST の形の順の確かめを足した。
- 完了条件: two_filters_t が、API 用の索引でも標準の索引でも、MySQL と同じく featured を event_date より先に引く（計画のテスト。featured と event_date の別名を入れ替えた形と、段階 95 の CAST の形も）。featured が `'0'`（8/9 が当たる）のときの順は、本物の MySQL の `EXPLAIN` と同じ。two、two0、category、range_t の計画は変わらない。結果と並びは本物の MySQL のゴールデンと同じ。ページの文 352 種類の計画と結果を段階 99 と比べ、変わった計画を本物の MySQL の `EXPLAIN` と突き合わせる。手元の perfq で段階 99 と交互に測り、two_filters_t が速くなり、ほかが遅くならない。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。
- 結果: エンジンの `sql/memo/rel_props.go`（`JoinKeyDistinct`。元の見積もりより多いときだけ使い、そのときは 1 行未満にしない）、HeimDB の `selectivity.go`（`joinKeyDistinct`、`columnDistinct`）。内部 JOIN（lookup、ハッシュ、マージを含む）の、左と右の列の等号のキーについて、その列から始まるインデックスの先頭の列の値の種類の数（段階 80 の `tableDistinct`）を返す。外部 JOIN、semi、anti は対象にしない。two_filters_t は、API 用の索引で category → featured → 記事 → event_date の順（本物の MySQL 8.0.46 の `EXPLAIN` と同じ順）、標準の索引でも featured を event_date より先に引く。featured が `'0'`（見積もりは event_date と同じ 0.85）と、別名を入れ替えた形も、MySQL と同じく featured が先。ベンチの range（event_date の範囲の JOIN 3 本）も計画が変わり、2 本の範囲をそれぞれ読んでハッシュ JOIN でつなぐ形から、片側の範囲から記事ごとに引く lookup JOIN だけの形になった（MySQL は記事を索引だけで読み、記事ごとに 3 本を引く）。ほかの 7 つの文の計画は変わらない。ページの文 352 種類（計画の付いたもの 345）は、計画も結果も段階 99 と同じ。perfq の `check` で、9 つの組と前の形の range と two_filters_t が、標準の索引でも API 用の索引でも MySQL と同じ。手元（macOS）で段階 99 と交互に 2 回ずつ測った（組の時間の中央値、ms）。
    - API 用の索引: two_filters_t 17.6〜17.8 から 12.3〜12.4、range 134 から 51。ほかの 7 つは揺れの範囲（priority は 1 回目の計測で 5% 遅く見えたが、計画は同じで、測り直すと同じ）。
    - 標準の索引: two_filters_t 47.6〜48.0 から 32.7〜33.3、range 157〜160 から 59〜60。ほかは揺れの範囲。
  GCE（n2-standard-4）で MySQL 8.0.46、段階 99、段階 101 を比べた（`docs/bench.md` の「段階 101」。インスタンスを作り直したので段階 100 のときより全体に遅く、同じインスタンスの中で比べる）。4 vCPU、API 用の索引で two_filters_t 64.2 から 46.6 ms（MySQL 17.0）、range 507 から 183 ms（420）。標準の索引で two_filters_t 169 から 119（220）、range 581 から 208（779）。ほかの組は段階 99 と同じ。10 本同時の毎秒の組の数は、4 vCPU、API 用の索引で 17.6 から 27.2（MySQL 33.2）、標準の索引で 12.3 から 18.6（11.8）。1 vCPU では API 用の索引で 7.6 から 11.4（8.7）、標準の索引で 5.7 から 8.5（3.0）。遅くなった組はない。
  Go のテストは 507 件（`TestStage101MatchMySQL`、`TestStage101JoinOrder`）と、エンジンに 1 件（`TestJoinKeyDistinct`）。-race でも通り、エンジンの上流のテストも通る。直しを外すと、`'1'` と `'0'` の形（標準の索引と API 用の索引）と range の計画のテストが落ちる。別名を入れ替えた形と段階 95 の CAST の形は、直す前から（巡り合わせで）同じ順なので落ちない（守りとして残す）。ゴールデン（`stage101_golden.txt`）は計画によらず同じ。1 行未満にしない直しを外すと、エンジンのテストが落ちる。PHPUnit は 26,475 件で、本物の MySQL との差は 35 件のまま（段階 99 と同じ一覧）。互換のテスト集は、2 回とも思わぬ違いが 0（82 の観察、既知 4）。
- 実装後のレビュー（Fable）で直したこと: キーの列を IN の数件に絞った子と JOIN すると、値の種類の数で割った見積もりが 0 行に丸まり、その上の JOIN の順がどれも同点になる（直す前と後で計画の変わる文は見つからなかった）。値の種類の数で割ったときは 1 行未満にしない。エンジンのテストに、子が値の種類の数を持つ場合と空の場合を足した。
- 記録だけ: (a) 表全体の値の種類の数で割るので、条件がキーと独立だと仮定している（`wp_term_relationships` と `wp_term_taxonomy` の JOIN は見積もりが小さくなるが、ページの文の計画は変わらない）。(b) lookup の 1 回ごとの手間（区間を作る処理、区間がちょうどかの判定）は、GCE で測り直してから決める。(c) Pebble の L0 を圧縮で空にしても、手元で 4〜6%。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- JOIN の出力の行数の見積もりで割る値の種類の数を、差し替えられる関数 `memo.JoinKeyDistinct` から取る（`sql/memo/rel_props.go` の `statsForRel`。元の見積もりより多いときだけ使い、既定は 0 で元のまま）。HeimDB は、内部 JOIN のキーの列の値の種類の数を表の統計から返す関数に差し替える（`internal/backend/selectivity.go`）
  - 理由: 性能。元は、Filter を通った子は値の種類の数を持たないので、大きい方の子の行数の 8 割を値の種類とみなし、出力が小さい方の子の行数で決まった。meta_query の two_filters_t で、featured の `meta_value = '1'` で 1 割に絞るメタとの JOIN と、絞らない event_date のメタとの JOIN が同点になり、event_date を先に引いていた（MySQL は featured を先に引く。段階 101）。段階 83 と同じく、上流のメモリのエンジンの計画は変えない

## 段階 102: lookup JOIN の 1 回ごとの手間を減らす

- 背景: 段階 101 の後も、API 用の索引の two_filters_t は GCE で MySQL の 2.7 倍、two は 1.6 倍。どちらも MySQL と同じ順の計画で、lookup JOIN が記事ごとにメタを `(post_id, meta_key)` で引く（two_filters_t で 1 文に約 4,700 回）。手元のプロファイルでは、two_filters_t の CPU のうち、インデックスと本体の行の Pebble の検索（`Scan.Reset` と `Peek`）が 17% ずつで、これは引くたびに要る（MySQL も同じ）。ほかに、キーの値から区間を作る処理（`mergeIntervals`、`indexInterval`）が 9%、区間が範囲をちょうど表すかの判定（`exactIntervals`）が 6%、短い点かの判定（`shortPrefixPoints`）が 3%。区間、判定、短い点の確かめが、同じキーの値（post_id と `'featured'`）を下限と上限で別々に列の型へ変換し直す（`convertKey`。1 回の lookup で約 6 回）。ほかに、引くたびにインデックスの情報（`findKeyIndex`。表を作るときに `t.keys` に作ってあるのに、定義から作り直す）と、主キーを足した式（`extendedExprs`。範囲の条件と並べ替えにしか使わない）を作り、範囲が 1 つでも並べ替え（`sort.Slice`）をしていた。category は記事を主キーで引く `Peek` と cat3 の範囲を読む処理が大半で、この段階では変わらない。効く軸は性能。
- 方針: データ形式とエンジンは変えない。(1) 範囲が 1 つで、先頭から点（両端を含む同じ値）の列が続き、残りの列がすべての値の形（lookup JOIN が引く形）なら、点の値を列ごとに 1 回だけ変換して符号化し、区間、ちょうどかの判定、短い点かの判定を、その結果から決める（`pointLookup`）。変換できない値や、ほかの形は今までの経路。(2) `findKeyIndex` は `t.keys` から名前で探す。(3) 主キーを足した式は、範囲の条件か並べ替えが要るときだけ作る。(4) 区間が 1 つなら並べ替えない。
- 完了条件: `pointLookup` の結果（区間、ちょうどか、短い点か）が今までの経路と同じことを、単体テストで確かめる（整数、符号なし、文字列、プレフィックス長の列の短い値と長い値、日時、バイナリ、範囲外の値、NULL、点の後にすべての値の列、点でない列、複数の範囲）。ページの文 352 種類の計画と結果が段階 101 と同じ。段階 84〜101 のゴールデンが変わらない。手元の perfq で段階 101 と交互に測り、two_filters_t と two が速くなり、ほかが遅くならない。直しを外すとテストが落ちる（今までの経路と比べるテストは、`pointLookup` を壊すと落ちる）。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。
- 計画のレビュー（Fable）で変えたこと: 区間を作る条件（列の型に変換できる）と、ちょうどかの条件（値の Go の型が列の種類に合う。`exactKey`）は違う（文字列の列を数で引くと、区間は作れるが絞り直す）。go-mysql-server の lookup は、最初の 1 回だけ左の値をそのまま、2 回目からは変換した値を範囲に置くので、ちょうどかは元の値で見る（`exactKeyKind` を `exactKey` から分けた）。点は、両端が同じ Go の値のものだけ受ける（照合順序で同じ重みの違う文字列を比べずに済む）。短い点かは、文字列の文字の数がプレフィックス長より少ないかで決め、`shortPrefixPoints` の `ranged` が true と false の違い（すべての値のプレフィックス長の列）を保つ。NULL の点（`BelowNull`、`AboveNull`）と空の範囲は受けない。範囲を左の行ごとに書き換えて使い回すので、範囲を鍵に覚えない。テストに、ランダムな値で今までの経路と比べる形と、WordPress の形で `pointLookup` を通ることの確かめを入れた。
- 結果: `rows.go` の `pointLookup`（と `sameKey`）、`extended`（主キーを足した式を要るときだけ作る）、`mergeIntervals`（範囲が 1 つなら並べ替えない）、`indexes.go` の `findKeyIndex`（`t.keys` から探す）と `exactKeyKind`。データ形式とエンジンは変えない。ページの文 352 種類（計画の付いたもの 345）は、計画も結果も段階 101 と同じ。手元（macOS）で段階 101 と交互に、API 用の索引で 4 回ずつ測った（組の時間の中央値、ms）。two_filters_t 12.1 から 10.5（−14%）、two 12.7 から 11.2（−12%）、two0 23.2 から 20.1（−13%）、range 50.6 から 46.6（−8%）。ほかの 5 つは揺れの範囲（±4%）。標準の索引（2 回ずつ）は揺れの範囲で変わらない（`post_id` のインデックスで引くと 1 回に約 16 行を読むので、1 回ごとの手間の割合が小さい）。
  Go のテストは 509 件（`TestStage102PointLookup`、`TestStage102JoinTakesPointLookup`）。-race でも通る。`pointLookup` を 1 つずつ壊すと落ちる（ちょうどかで値の型を見ない、すべての値のプレフィックス長の列で短い点を落とさない、文字の数の境目、区間の上限、使わない、すべての値の後の点を受ける）。PHPUnit は 26,475 件で、本物の MySQL との差は 35 件のまま（段階 101 と同じ一覧）。互換のテスト集は、2 回とも思わぬ違いが 0（82 の観察、既知 4）。GCE（n2-standard-4）で MySQL 8.0.46、段階 101、段階 102 を比べた（`docs/bench.md` の「段階 102」）。4 vCPU、API 用の索引で two_filters_t 46.7 から 37.7 ms（MySQL 16.6）、two 48.7 から 39.1（21.2）、two0 84.9 から 67.7（31.6）、range 188 から 158（146）。ほかの組は同じ。標準の索引では lookup の多い組が 3〜4% 速い。10 本同時の毎秒の組の数は、4 vCPU、API 用の索引で 26.9 から 29.5（MySQL 33.7）、1 vCPU、API 用の索引で 11.3 から 12.5（8.8）。遅くなった組はない。プロファイルでいちばん大きいのは、本体の行を主キーで引く `RowReader.Peek`（10 本同時で 26%、category で 37%）。
- 実装後のレビュー（Fable）で足したこと: テストの値に、多バイトでちょうどプレフィックス長の文字列と、不正な UTF-8（符号化できなければ今までの経路）、照合順序で同じ重みの違う両端（受けない）を足した。
- 記録だけ: (a) バイナリのプレフィックス長の列は、短い点かを文字の数で見るが、符号化はバイト数で切る（多バイトの文字列で文字の数は短くバイト数は長い値を、ちょうどとみなす）。今までの経路も同じで、WordPress にはバイナリのプレフィックス長のインデックスはない。(b) 主キーの点（`pointKey` と `getPoint`）は変えていない（category の差の大半は、記事を主キーで引く `Peek` と cat3 の範囲を読む処理）。

## 段階 103: インデックスの走査のアロケーションを減らす

- 背景: 段階 102 の GCE のプロファイル（API 用の索引、4 vCPU、組の形）で、いちばん大きいのは本体の行を主キーで引く `RowReader.Peek`（10 本同時で 26%、category で 37%）。同じデータで Pebble の `SeekGE` だけを測ると 1 回 0.4〜0.8 µs で（キーが昇順で同じイテレータなら 0.4 µs。`Peek` は Pebble の昇順の最適化 TrySeekUsingNext がもう効く形）、HeimDB の `Peek` も手元で同じくらい。引く回数も MySQL と同じ（category の cat3 のメタは、key_value の索引に post_id がないので MySQL も本体を引く）なので、`Peek` そのものは減らせない。次に大きいのはアロケーションと GC で、`mallocgc` が 11〜14%。手元で GOGC を 100 から 400 にすると、10 本同時の毎秒の組の数が 195 から 225（+15%。1 本ずつの時間は同じで、メモリは 400 MB から 800 MB）。GCE のアロケーションの上位は、走査がエントリごとにエントリと値の写しを作る `store.Scan.Next`（15%。lookup JOIN でエントリから主キーを取るだけの `pkRowIter.fill` でも、全件の走査で値を復号するだけの `scanRowIter` でも写す）、逆順の走査がエントリごとに作業用のバッファを確保する `versionCursor.advance`（9%）、エントリから行を作る `coveredRow`（7%）、`pkRowIter.fill`（5%）。効く軸は性能（同時に流したときの件数）。
- 方針: データ形式とエンジンは変えない。(1) `store.Scan` に、写さずに返す `NextView` を足す（返したエントリと値は次の `Next`、`NextView`、`Reset`、`Close` まで使える）。返したカーソルを進めるのは次に呼ばれたとき。今の `Next` は `NextView` の結果を写して返す（`diff.go` と、関数に渡す走査は今のまま）。(2) `pkRowIter.fill` は `NextView` で読み、主キー（と covered のときのエントリの値）を、まとめて読む 1 回ごとに 1 つのバッファに写す。`scanRowIter` は `NextView` で読んで復号する（復号は文字列、バイト列、日時をすべて写す）。(3) 逆順の `versionCursor.advance` は、作業用のバッファをカーソルに持たせて使い回す。(4) 区間を移すたびの境界（`cursorBounds`）は、カーソルのバッファに作る（Pebble は `NewIter` と `SetBounds` で境界を写す）。
- 完了条件: `NextView` と写した値を返す前の実装（テストの中に残す）を、順方向と逆順、ブランチの重ね合わせ（上の層の削除の印、同じエントリの複数のバージョン、見えないバージョン）、区間を移す `Reset` でランダムに比べるプロパティテスト。`NextView` の値を持ち続ける呼び出し側がない（`fill` が写した主キーが次の読み込みで壊れない）ことのテスト。ページの文 352 種類の計画と結果が段階 102 と同じ。手元の perfq で段階 102 と交互に測り、10 本同時が増え、ほかが遅くならない（1 文あたりのアロケーションの数とバイト数も比べる）。直しを外すとテストが落ちる。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。GCE で段階 102 と MySQL と比べる。
- 計画のレビュー（Fable）で変えたこと: 返したエントリにいるカーソルは、返すときに覚え、次に呼ばれたときに進める（返したエントリは勝ったカーソルのバッファを指すので、先に進めると同じエントリの下の層のカーソルと比べられない）。`Reset` は覚えたカーソルを忘れる（LIMIT で途中まで読んで使い回しの置き場所に戻した走査を、ほかの検索が `Reset` してから読む）。`fill` は、読んだその場で主キーとエントリの値を写す（走査を読み終えると置き場所に戻り、同じ文で同じインデックスを引くほかの検索が、まだ使っていない主キーのあるうちにそれを使う）。Pebble は `NewIter` と `SetBounds` で境界を写すので、境界のバッファは 1 つでよい。テストに、読んでいる途中のランダムな位置での `Reset`、上の層が下の層と同じエントリを持つ形を足した。
- 結果: `store/layers.go` の `Scan.NextView`（`pending`）、逆順の `versionCursor.advance`（読んでいるエントリと値を、返すエントリと値のバッファにそのまま置く）、`cursorBounds`（カーソルのバッファ）、`backend/scan.go` の `intervalScan.next`（`NextView` を使う）、`rows.go` の `pkRowIter.keep`（1 回の fill の残りのエントリの数だけまとめて確保する。上限 64 KB）。データ形式とエンジンは変えない。ページの文 352 種類（計画の付いたもの 345）は、計画も結果も段階 102 と同じ。手元（macOS）で、統計を作り終えてから 1 つの組を 53 回流したときの 1 組あたりのアロケーションは、段階 102 と比べて list20 が 6.4 MB から 1.1 MB（−83%。`SQL_CALC_FOUND_ROWS` で数える 2 万件のエントリを写さない）、category 6.6 MB から 5.6 MB（−15%）、range 27.0 MB から 23.8 MB（−12%）、priority 45.9 MB から 42.2 MB（−8%）、two_filters_t 7.8 MB から 7.6 MB（−3%）、two は同じ。lookup JOIN が 1 回に 1 エントリを読む文では、アロケーションの大半は行の復号（文字列の写し）と、go-mysql-server が lookup ごとに作るもの（`LookupBuilder.GetLookup`、`StringType.Convert`、テーブルの反復子）で、この段階では変えない。手元で段階 102 と交互に 4 回ずつ測ると（API 用の索引、組の時間の中央値）、list20 が 3.1 から 2.5 ms（−18%）、ほかは ±2% の揺れの範囲。10 本同時の毎秒の組の数は、中央値で 196.5 から 202.6（+3%）。
  Go のテストは 511 件（`TestStage103NextView`、`TestStage103CoveredEntriesKept`）。-race でも通る。直しを 1 つずつ壊すと落ちる（`Reset` で覚えたカーソルを忘れない、返すときに進める、逆順で新しいエントリの前にバッファを空にしない、`fill` が写さない、足りないときに新しいバッファを作らない）。PHPUnit は 26,475 件で、本物の MySQL との差は 35 件のまま（段階 102 と同じ一覧）。互換のテスト集は、2 回とも思わぬ違いが 0（82 の観察、既知 4）。GCE（n2-standard-4）で MySQL 8.0.46、段階 102、段階 103 を比べた（`docs/bench.md` の「段階 103」）。速くなったのは list20 で、4 vCPU、API 用の索引で 11.4 から 8.2 ms（MySQL 11.7）。ほかの組は ±4% の揺れの範囲。10 本同時の毎秒の組の数は、4 vCPU、API 用の索引で 29.3 から 29.5（MySQL 32.9）、標準の索引で 18.5 から 19.1（11.4）。遅くなった組はない。10 本同時のプロファイルで GC の印付けは 3% で（`mallocgc` は 13.4% から 12.8%）、Linux の 4 vCPU ではアロケーションを減らしても時間はほとんど変わらない。いちばん大きいのは今も `RowReader.Peek`（26%）。
- 実装後のレビュー（Fable）で直したこと: `keep` は最初のエントリの大きさに残りのエントリの数を掛けて確保していたので、covered のエントリの値が長いと大きくなりすぎる（エントリの値は索引の列の元の値をすべて持つ。1 MB の値なら 4 GB）。1 度に確保するのを 64 KB までにした。テストに、エントリの大きさがまちまちで途中でバッファが足りなくなる形、1 回の fill が上限を超える形、同じ文で同じインデックスを 2 回引く形を足した。
- 記録だけ: (a) 走査のカーソルが進むときのエラー（Pebble の読み出しのエラー）は、そのエントリを返した次の呼び出しで返る（前は返す前）。返したエントリそのものは正しい。(b) GC の設定（GOGC）は、手元で 100 から 400 にすると 10 本同時が +15%（メモリは 2 倍）。運用の選び方なので変えない。(c) lookup JOIN のアロケーションの大半は go-mysql-server の側（lookup ごとに範囲と反復子を作る）。

## 段階 104: 標本で数える見積もりの手間を減らす

- 背景: 段階 103 の GCE のプロファイル（API 用の索引、4 vCPU、組の形）で、two_filters_t の CPU の 13% が計画（`Analyzer.Analyze`）で、そのうち 5.2% が `prefixSample.rows`（段階 84 の標本で数える見積もり）。標本（2 万行）の、インデックスの先頭の k 列の組のハッシュの並びから、同じハッシュの続きを 1 件ずつ数える（`meta_key = 'category'` は標本の約 1/16 で 1,000 件を超える）。JOIN の順の候補ごとに捨てる行の見積もり（`discardedSideCost`）から呼ばれる。range_t で 1.5%、category で 0.9%、10 本同時で 0.8%。手元で続きの終わりを二分探索で探すように変えて段階 103 と交互に 3 回ずつ測ると、two_filters_t が 10.44 から 9.34 ms（−11%）、two が 10.84 から 10.16 ms（−6%）、ほかと 10 本同時は揺れの範囲。効く軸は性能。
- 方針: データ形式とエンジンは変えない。`prefixSample.rows` は、同じハッシュの続きの終わりも二分探索で探す（数える件数は変わらないので、見積もりと計画は変わらない）。
- 完了条件: ランダムな、重複の多いハッシュの並びで、1 件ずつ数える前の数え方（テストの中に残す）と件数が同じことのプロパティテスト（並びの先頭、末尾、ない値、1 件だけの並び、空の並び、すべて同じ値の並び、`0` と `math.MaxUint64`）。ページの文 352 種類の計画と結果が段階 103 と同じ。段階 84〜101 のゴールデンが変わらない。手元の perfq で段階 103 と交互に測り、two_filters_t が速くなり、ほかが遅くならない。終わりの二分探索を壊すと（`>` を `>=` にする、`lo` を足し忘れる、探す長さを `len(hs)` にする）テストが落ちる（直しを外しても同じ件数を返すので落ちない）。Go のテストが -race でも通る。PHPUnit の差が 35 から増えない。互換のテスト集で、思わぬ違いが 0 のまま。GCE では、次の段階と一緒に比べる。
- 計画のレビュー（Fable）で変えたこと: 直しを外すとテストが落ちる、という条件は、同じ件数を返すのが目的なので満たせない。終わりの二分探索を壊すと落ちる、に直した。テストに、空の並び、すべて同じ値の並び、`0` と `math.MaxUint64` を足した（終わりを `h+1` の二分探索で探すと `math.MaxUint64` で桁あふれする）。`samplePrefixRows` を 2 回呼ぶ分（先頭の点を 2 回符号化する）はプロファイルに現れないので変えない。
- 結果: `statistics.go` の `prefixSample.rows` が、同じハッシュの続きの終わりを `sort.Search` で探す。データ形式とエンジンは変えない。ページの文 352 種類（計画の付いたもの 345）は、計画も結果も段階 103 と同じ。手元（macOS）で段階 103 と交互に 4 回ずつ測ると（API 用の索引、組の時間の中央値）、two_filters_t が 10.55 から 9.76 ms（−7%）、two が 11.06 から 10.52 ms（−5%）、ほかは揺れの範囲（category は回ごとに 7.0〜9.7 ms と揺れ、試作を測った 3 回では 6.92 と 6.77）。10 本同時の毎秒の組の数は、中央値で 178.8 と 177.7（揺れの範囲）。

## 段階 105: SQL とプロトコルのファズ

- 背景: 文の panic は段階 46 から回復し（1105 の `HeimDB: internal error`、その文の書き込みを取り消す）、vitess は接続のゴルーチンの panic を回復してその接続を閉じる。守りの外のゴルーチンの panic（プロセスが落ちる）、panic の後に残るロック、認証の前のパケットの読み違いを探す手段がなく、これまでの panic（`CONVERT ... USING`、`stats.Union`、`CALL heimdb_gc(1)`、準備した `LOAD DATA`）は PHPUnit などで偶然見つけていた。効く軸は安全性と堅牢性。
- 方針: Go の標準の fuzz で 2 つの対象を作る（`internal/backend/fuzz_test.go`、`fuzzpackets_test.go`）。worker ごとに、テストの中でサーバを `127.0.0.1:0` に立て、ゴールデンの文（1,522 本）を main に流して表と行をそろえる。入力は、WordPress と同じ管理者でないユーザー（パスワードなし、``GRANT ALL ON `wordpress@f`.*``）で、使い捨てのブランチ `wordpress@f` に、入力ごとに新しい接続で流す。入力の後にブランチを消して、準備の後の時刻から作り直す（1 件あたり約 30 ms）ので、どの入力も同じ状態から始まる。`FuzzQuery` はテキストの 1 文（種はゴールデンの文と、定数を境界の値に替えたバージョン。ふつうの go test では 40 本に 1 本に間引く）、`FuzzPackets` は手組みのクライアントで、認証の前に壊したハンドシェイクの応答を、認証の後に壊したコマンドを送る（準備した文の後の COM_STMT_EXECUTE の引数の型と値、COM_STMT_SEND_LONG_DATA、COM_FIELD_LIST、COM_CHANGE_USER など）。不具合とみなすのは、プロセスが落ちる、回復した panic（`HeimDB: internal error` の字と、ログのフック）、文と接続が切れる、20 秒を過ぎても終わらない（見張りのゴルーチンが入力を出してプロセスを落とす。Go の fuzz には入力 1 件の時間の上限がない）、入力の後に書き込みのロックが残る・つなげない・main に書けない。ブランチには文の実行時間の上限（3 秒）を掛け、上限で止まるだけの重い文は不具合にしない。メモリの上限は 1 GiB（食う入力は 1041 で止める）。自分の接続を切る `KILL` を含む入力は流さない。
- 計画のレビュー（Fable）で変えたこと: 実行時間の上限は main では SELECT と書き込みの文にしか効かず、接続ごとの `max_execution_time` は SELECT だけなので、上限を全文に効かせられるブランチで流す。入力ごとに新しい接続にし（`SET autocommit=0` や開いたトランザクションを次の入力に持ち越さない）、ロックを待つ時間を 2 秒にする（50 秒の待ちで偽の止まりにしない）。管理者でないユーザーで流し、`heimdb_*` の手続き、`SET GLOBAL`、他人の `KILL` を権限で拒否させる。入力 1 件の時間の上限は見張りで作る。panic の判定は番号（1105 はほかのエラーにも使う）でなく字とログで行う。種のゴールデンの文は複数行の文を続きの行まで取る。worker が OOM で落ちないよう、メモリの上限を掛ける。`FuzzPrepared` は go-sql-driver では引数の型を選べないので、生のクライアントの `FuzzPackets` に寄せた。
- 結果（見つけて直したもの。どれも文の panic の回復で 1105 になり、接続は保たれていた）: (1) 名前の空のシステム変数（`SELECT @@`、`SELECT @@session.`）で、vitess の `VarScope` が範囲の外を読む。エンジンの `sysVarScope`（`sql/planbuilder/set.go`）が先にエラーにする。(2) キーワードのすぐ後の空の文字列（`SELECT''`、`SELECT""`）で、vitess の構文解析器が選択の式の元の字を取るときに 1 文字の `'` を切り出す。HeimDB の構文解析の包み（`internal/backend/parser.go` の `recoverParsePanic`）が、vitess の構文解析器の panic を構文のエラーにする（この形は、MySQL では空の文字列を返すが、HeimDB はエラー。WordPress は送らない）。(3) 日時と NULL の `INTERVAL` の足し算と引き算（`'2024-01-01' + INTERVAL NULL DAY`、未定義のユーザー変数。`INSERT ... SELECT` の日付の計算で見つけた）で、`Interval.EvalDelta` の型付きの nil が NULL の確かめを抜けて `plus` が nil を読む。エンジン（`sql/expression/arithmetic.go`）で nil にしてから値にし、MySQL と同じく NULL を返す。HeimDB の側のロックの漏れ、止まる文、プロセスが落ちるものは見つからなかった。
- 記録だけ: (a) vitess（フォークしていない）の中で起き、vitess が回復してその接続を閉じるだけのもの 3 つ。認証の前の短いハンドシェイクの応答（`parseClientHandshakePacket` の `readNullString`）、空のコマンドのパケット（`handleNextCommand` の `data[0]`）、文の ID のない COM_STMT_RESET。どれも WordPress は送らず、プロセスとほかの接続に響かない（`vitessKnown` に載せ、ほかのものが出たら不具合として止まる）。認証の前のものは、つなげる人なら誰でもログにスタックを 1 回出させられる。(b) 行を送り始めた後のエラー（実行時間の上限で止めたものを含む）で vitess が接続を閉じるのは段階 46 の記録のとおり（-race で遅くなったときに当たった。その文を上限で止めた、つまり文の指標の 3024 が増えたときの切断は不具合にしない）。(c) 試験の仕組みが最初はストアの `DeleteBranch` を直接呼び、統計（`rowCounts`）を忘れず、入力ごとに約 260 KB 増えていた。`heimdb_branch_delete` は忘れるので、試験の仕組みの作り物だった（同じく忘れるようにした）。レプリカは、本番で消したブランチの統計を（そのブランチを読んでいれば）持ち続ける。読むことはほとんどないので、そのままにする。(d) テストのサーバは `WarmStats`、GC、記録の刈り込みを動かさないので、それらと入力の重なりは試していない。
  Go のテストは 514 件（`FuzzQuery`、`FuzzPackets`。513 件が通り、1 件は前からの飛ばし）。-race でも通る。エンジンの上流のテストも通る。直しを外すと（3 つの直し、`vitessKnown` を空にする）テストが落ちる。最後の流しは、手元（macOS、10 コア、4 worker ずつ）で `FuzzQuery` 1 時間と `FuzzPackets` 30 分を同時に流して何も出なかった（その後に -race で 5 分ずつ。試験の仕組みの停止を本番と同じく `Provider.Shutdown` を待つ順に直し、上限で止めた文の切断を見逃すようにしてから流し直して何も出なかった）。fuzz の 2 つの対象は、ふつうの go test で合わせて約 17 秒（準備が対象ごとに約 8 秒）。backend の -race は 10 分を超えるので、README の -race の行を CI と同じ `-timeout 30m` にした。PHPUnit は 26,475 件で、本物の MySQL との差は 35 件のまま（段階 104 と同じ一覧。panic のログは 0）。互換のテスト集は、2 回とも思わぬ違いが 0（82 の観察、既知 4）。
- 実装後のレビュー（Fable）で直したこと: 構文解析の回復が、HeimDB 自身の書き換え（`rewriteQuery`、`checkStatement` など）の panic まで構文のエラーにし、ファズから隠していた（vitess の呼び出しだけを包む）。入力の始めに、前の入力の確かめの後に起きた panic（切断の後片付けなど）を捨てていた（不具合にする。失敗で途中に終わった入力のものだけを捨てる）。上限の後の切断を、3 秒を過ぎたことだけで見逃していた（その文を上限で止めたときだけ）。準備の文が、`sql_mode` を設定した接続と別の接続で流れうる（1 本にした）。`vitessKnown` は vitess の行で決めるので、vitess を上げたら直すと書いた。

## 段階 106: 起動し直した直後の準備

- 足したもの: `heimdb_status` の `stats`（`building`、`ready`、表の一覧を読めなければ `failed`。`WarmStats` を呼ばなければ `off`）、`stats_ready_at`、`stats_build_duration`、`stats_tables`（`N built, M failed`）、`stats_error`。指標の `heimdb_stats_ready`（0 か 1）と `heimdb_stats_build_seconds`（作り終えてから出す）。`ready` は起動したときの 1 回が終わったことを表し、その後の作り直しでは戻さない。停止で途中でやめたら `building` のまま。待ち方は `docs/operations.md` の「起動し直した直後」。

## 段階 108: 長時間の負荷試験

- 背景: これまでの測りは数分で、何時間も動かしたときのメモリ、ディスク、GC、複製、ブランチの一巡の振る舞いを見ていなかった。効く軸は堅牢性。
- 方法（[`bench.md`](../bench.md) の段階 108、`scripts/soak/`）: GCE の 2 台で、WordPress のページを 8 要求/秒、毎分の書き込み、30 分ごとのブランチの一巡（作成、書き込み、マージ、削除、数え直しの検査）を 24 時間流した。保持期間 2 時間、GC 15 分ごと、毎時のバックアップ、途中でレプリカを 5 分止める。1 分ごとに指標、プロセスの RSS と fds、goroutine、ディスクを記録し、終わりに本番とレプリカのダンプ、AS OF、検査、起動し直し、バックアップを確かめた。手元の 40 分と GCE の 1 時間で台本を確かめてから流した。
- 完了条件: 後半の窓（18〜24 時間）と前半の窓（6〜12 時間）で、ディスク、live heap、RSS が幅に収まり、p50 と p99 が ±15% に収まる。5xx、panic、思わぬエラーがない。GC が毎回バージョンを消し、境界が保持期間に止まる。ブランチが 1 に戻る。レプリカが本番と同じ。数え直しが合う。起動し直して統計がそろう。
- 見つけて直したもの: 本番の live heap が 1 時間に約 3.6 MB 増え続けた。ハッシュ結合の索引を作る iterator（`hashLookupGeneratingIter`）が子を閉じず、右側の GROUP BY の途中結果のキャッシュが `MemoryManager` に残っていた。子を閉じる（上流の 0b37f3696 の取り込み。`docs/engine.md`）。WordPress 本体では `WP_User_Query` の `orderby=post_count` がこの形の文を出す。試験では `check.sql` が増やしていた。
- 結果: 24 時間は、メモリのほかはすべて完了条件を満たした（691,200 要求がすべて 200、48 回の一巡がすべて通る、GC は毎回約 8,400 バージョン、ダンプの違いは 0、起動し直して 2.05 秒で統計がそろう）。直したバージョンの 12 時間で、live heap が 86 MB で止まり、p99 の伸びも消えた。Go のテストは 519 件（`TestHashLookupChildClosed`。518 件が通り、1 件は前からの飛ばし）で、直しを外すとテストが落ちる。エンジンのテストも通る。PHPUnit は 26,475 件で、本物の MySQL との差は 35 件のまま（段階 107 と同じ一覧）、panic のログは 0。互換のテスト集は思わぬ違いが 0。
- 記録だけ: レプリカを止めている間は同期の待ちで書き込みが 10 秒止まり、非同期に切り替わる。止めて戻したレプリカは WAL を約 5 MB 余分に持つ。書き込みが少ないときの GC の境界の警告は、開いたトランザクションでなく最後のコミットで止まっている。mysqldump（MariaDB）の `optimizer_switch` のエラー。mysql 9.x のクライアントの `select $$` は 1105。相関サブクエリの数え直しは遅い（WordPress は出さない）。
- 計画のレビュー（Fable）で変えたこと: レプリカのための記録の保持を 2 時間にし（既定の 24 時間のままだと、ディスクが 24 時間伸び続ける）、レプリカにも同じ保持期間を付けた（GC は複製しない）。`-memory-limit` と `-cache-size` を決めて付けた（上限がないと RSS の幅が意味を持たない）。ディスクは 1 点でなく窓の中央値と傾きで比べ、`du` と `df` も取った（GC の後に空くのは compaction のとき）。GC の境界の古さ、ブランチの数、GC の失敗を完了条件に入れた。1 台では PHP が CPU を食うので WordPress と負荷を別の VM にし、読みを前の応答を待たない決まった間隔（8 要求/秒）にして、DB の時間を mu-plugin で要求ごとに取った。直す前の計画の確かめで、子を閉じても二重に閉じないこと、ほかに子を閉じない iterator がないことを確かめた。
- 実装後のレビュー（Fable）で直したこと: 台本では、起動し直しの時間に止める待ちが入っていた、傾きに負荷の後の標本が混ざっていた、0 の値を落としていた、エラーを番号ごとに出していなかった、ロケールで並びが変わる、などを直した。直しでは、`docs/engine.md` の行の位置と、WordPress 本体がこの形の文を出さないという書き方を直した。

## 段階 109: エンジンのメモリの残りをテストと指標で見つける

- 背景: 段階 108 の漏れ（ハッシュ結合の子を閉じない）は、エンジンで共有の `MemoryManager` に文の途中結果のキャッシュが残るもので、ヒープのプロファイルを取るまで見つからなかった。上流のエンジンのテストは文のたびにキャッシュの数が 0 に戻ることを確かめているが、HeimDB のテストは見ていなかった。効く軸は堅牢性。
- 方法: TCP のテストのサーバ（`serve`、`stopServer`）が止まるときに、エンジンのキャッシュの数が 0 であることを確かめる（KILL や切れた接続の片付けを 2 秒まで待つ）。ゴールデンの文は 1 つ流すたびに確かめ、増えた文を名前で出す。指標の `heimdb_engine_caches` を足し、PHPUnit と互換のテスト集を流した後に読む。
- 完了条件: Go のテストが確かめ付きで通り、確かめが段階 108 の直しを外すと落ちる。PHPUnit と互換のテスト集の後に `heimdb_engine_caches` が 0。PHPUnit の差は 35 件、互換のテスト集の思わぬ違いは 0。
- 見つけて直したもの: (1) 書き込みの文が途中でエラーになると（重複で止まる `INSERT ... SELECT ... WHERE 列 IN (SELECT ... GROUP BY ...)`）、文の計画の片付けが走らず、サブクエリのキャッシュが文ごとに残っていた。エラーのときに片付けだけを呼ぶ（`server/handler.go`。`docs/engine.md`）。(2) `MemoryManager` は一覧が空になるとキャッシュの番号を 0 に戻し、古い片付けが 2 回目に呼ばれると新しいキャッシュを一覧から消していた。番号を戻さない。(3) `DISTINCT` の片付けを 2 回呼んでいた。1 回にする。
- 結果: 今あるゴールデンの文と TCP のテストでは、ほかにキャッシュを残す文はなかった。PHPUnit（26,475 件）と互換のテスト集（2 回）の後の `heimdb_engine_caches` は 0。Go のテストは 522 件（`TestEngineCachesAfterStatements`、`TestMemoryManagerStaleDispose`、`TestDistinctDisposeOnce`。521 件が通り、1 件は前からの飛ばし）。3 つの直しと段階 108 の直しは、それぞれ外すとテストが落ちる。-race でも通る。エンジンのテストも通る。PHPUnit の差は 35 件のまま（段階 108 と同じ一覧）、panic のログは 0。互換のテスト集は 2 回とも思わぬ違いが 0。
- 記録だけ: 自分の context で文を流す経路（統計の温め、ユーザーの作成、差分、遅い文のログ）は共有の `MemoryManager` を使わないので、この確かめに出ない（どれもキャッシュを作る文ではない）。`FinalizeIters` がエラーになると、作った iterator を閉じない（DISTINCT と UNION は作るときにキャッシュを取る）が、テストとテスト集では起きなかった。
- 計画のレビュー（Fable）で変えたこと: 止めるときの確かめを、すぐでなく 2 秒まで待つ形にした（`Server.Close` は接続の片付けを待たない）。文ごとの確かめは 1 本の接続で順に流すゴールデンだけにした（ほかの接続の文も数える）。指標の値は `NewEngine` で Provider に渡した。書き込みの文が途中でエラーになる経路を、テストで試す候補にした。
- 実装後のレビュー（Fable）で直したこと: 書き込みの文のエラーで片付けが走らない形を、サブクエリのある文で試すように言われ、(1) を見つけた。iterator を閉じる形で直すと、時間の上限で止まった文の書き込みがコミットされた（`TestBranchTimeLimit` が落ちた）ので、閉じずに片付けだけを呼ぶ形にした（失敗した自動コミットの文は、前からセッションが取り消す）。いちばん外が `ExprCloserIter` でも片付けが届くようにした。`UNION DISTINCT` の計画も片付けを 2 回呼ぶことを、`docs/engine.md` に書いた。`Next` の中の panic では片付けを呼ばない（記録だけ）。テストの関数の名前を直した。段階 109 の項がなかった。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- `MemoryManager` のキャッシュの番号を、一覧が空になっても 0 に戻さない（`sql/memory.go` の `removeCache`）
  - 理由: 堅牢性。空になると番号を 0 に戻していたので、古いキャッシュの片付けが 2 回目に呼ばれると、同じ番号をもらった新しいキャッシュを一覧から消していた（キャッシュの数が少なく出て、メモリが足りないときの `Free` からも外れる）。番号は増やすだけにする（64 ビットなので尽きない）。2 回目の片付けは、`DISTINCT`（下の行）のほか、`UNION DISTINCT` の計画（`SetOp.Dispose` は片付けの一覧を消さずに全部呼ぶ）でも起きる
