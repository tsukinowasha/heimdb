# Stage 130: the effect of a backup on running queries

## Background

`CALL heimdb_backup()` takes a Pebble checkpoint while holding the store's write lock (`Store.Checkpoint` in `internal/store/backup.go`), so all writes wait while it runs. On the same filesystem as `-data` the checkpoint hard-links the data files; on another filesystem it copies them. An encrypted backup (`-backup-key`) writes the `.tar.gz.age` file after the checkpoint, without the lock. How much this affects the queries running at the time had not been measured.

## Plan

Measure only. Fix only a problem that gives wrong results on WordPress paths; record the rest.

1. Let `cmd/loadgen` run a statement on its own connection at fixed times, and split the page times into the pages that overlapped it and the others.
2. On the GCE instances of stage 126, measure the 95:5 load at a fixed rate with and without backups: to the data's filesystem, to a second disk, and encrypted; on `wpbench` and on `wpbench` grown to about 2 GB (1.9 GiB).
3. Record the results in `docs/bench.md`, and operating advice in `docs/operations.md`.

## Method

- `loadgen -side 'CALL heimdb_backup()' -side-first 15s -side-every 30s` runs the backups during the measured window. The result has each run (`side`), and the page time distributions of the pages that overlapped a run (`during_side_ms`) and of the others (`outside_side_ms`).
- `scripts/bench/load/run.sh K` runs the 4 cases on 2 data sizes, 2 runs each. `dbctl.sh make-seed` builds each data directory once (the large one with `wp_ballast`, a table no page reads), and every run starts HeimDB on a copy of it. `backup-agg.py` builds the table.
- `gce.sh` now gives the database instance a second disk, tags both instances and creates firewall rules for that tag only (SSH from IAP, and SSH and HeimDB between the two), and removes them on `delete`. SSH goes through IAP.
- GCE n2-standard-4 × 2 in Tokyo, HeimDB 0.3.0 (`main` at 6c197c7), 2026-11-21. The instances, the disk and the rules were deleted after the run.

## Tests

- `TestSide` (`cmd/loadgen`): a fake server holds every other statement back while the side statement runs. It checks the run times, that the pages are split into during and outside, and that the held-back pages are in "during".
- `go test -race ./cmd/loadgen/` passes.

## Results

The table is in "During a backup" in [`../bench.md`](../bench.md#during-a-backup).

- To the same filesystem: 13 ms (16 MiB) and 19 ms (1.9 GiB). The pages that overlap a backup are no slower than the others.
- To the second disk: 62 ms (16 MiB) and 11.7 s (1.9 GiB, about 170 MiB a second). For the 11.7 seconds, no page finished, reads included; afterwards the queue took about 10 seconds to clear.
- Encrypted: 99 ms (16 MiB) and 5.4 s (1.9 GiB). Nothing stops; the overlapping pages slow down (read p99 91 ms → 369 ms).
- No errors or disconnects in any run.

### Why reads wait

A goroutine dump (SIGQUIT) on the database instance, with a backup to the second disk running, an `INSERT` started after it, and a `SELECT` after that:

- The backup goroutine was in `vfs.CopyAcrossFS` under `Store.Checkpoint`, holding `writeMu`.
- The `INSERT` waited for `writeMu` in `Txn.Commit` → `updateWaits`. It had already taken an AUTO_INCREMENT value, so the counter was marked unsaved (`dirty`).
- The `SELECT` waited for `writeMu` in `Txn.Commit` → `flushAutoIncrements` → `Update`: a commit with no writes saves the unsaved counters, and waits for the lock to do so.

Pebble itself releases its mutex before copying (`checkpoint.go`), so reads would not wait without this.

One review:

## Only recorded

Added to "Other" in [`../differences.md`](../differences.md#other), as candidates for the next stage:

- A read-only transaction waits for the write lock while an AUTO_INCREMENT value is unsaved (WordPress: yes; latency only).
- With the Docker image, `-backup-dir` on its own volume is another mount point, so every backup is a full copy (hard links do not cross mount points).

The second fact also means the advice to put `-backup-dir` on the same filesystem as `-data` cannot be followed with the image as it is. `docs/operations.md` now says so.
