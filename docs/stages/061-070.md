## 段階 61: プラグインの `int` の AUTO_INCREMENT をブランチで分ける

- 背景: ブランチの AUTO_INCREMENT の番号帯（段階 6）は 64 ビットの列だけで、32 ビット以下の列は本番とブランチが同じ番号を使う（`autoIncrementRange`。`int unsigned` の上限 約 43 億に 10^10 の幅が入らない）。WordPress 本体の表はすべて `bigint(20)` だが、プラグインには `int` の表がある。手元で Redirection の形（`redirection_groups` と、それを `group_id` で指す `redirection_items`。どちらも `int`）を試した。(a) 本番だけが足したときは問題ない（マージの後、本番は続きから振る）。(b) 両側が同じ表に足すと、同じ ID が `added on both sides` の競合になり、`'branch'` の解決はできず（ワイルドカードの `'branch'` は黙って競合のまま残る）、`'parent'` を選ぶとブランチで足した行が捨てられる。(c) 本番がグループだけを足し、ブランチがグループとそれを指す項目を足すと、グループは競合（`'parent'` で解決）、項目は競合にならずに入り、項目が本番の別のグループを指した（エラーも警告もない）。手元にソースのある 62 本のうち、`int` の AUTO_INCREMENT の表を持つのは、Yoast SEO（`yoast_indexable`、`yoast_primary_term`。移行の仕組みが自動で作る `id`）、Redirection（4 表）、WP Mail SMTP（2 表）、W3 Total Cache（CDN のキュー）、WPML と WP Cerber（もともと使えない）。Yoast は記事の保存やページの表示のたびに `yoast_indexable` に行を足し、`yoast_indexable_hierarchy` と `yoast_seo_links` がその ID を指すので、ステージングの間に本番も動いていれば (b) と (c) がほぼ必ず起きる。Yoast の表は段階 60 でマージから外せるようになるが、Redirection のリダイレクトのように、マージしたい `int` の表のためにこの段階が要る。
- 方針: (1) `int`（符号の有無とも）の AUTO_INCREMENT の列にも番号帯を設ける。本番（main）は [1, 10^9)、ブランチ ID n（2 以上）は 10^9 + ((n - 2) mod 100) × 10^7 から 10^7 の幅（符号付きの上限 2,147,483,647 に収まる）。枠は 100 個を使い回すが、カウンタは枠の中の見えている行の最大値 + 1 から始めるので、前に同じ枠を使ったブランチの、マージ済みの行とは重ならない。重なるのは、ID が 100 違うブランチが同時に生きていて両方が同じ表に足したときだけで、そのときは今と同じく競合で止まる。一時テーブル（隠しブランチ）と、`tinyint`、`smallint`、`mediumint` は今のまま分けない（幅が足りない）。データ形式は変えない（変わるのは、これから振る番号だけ）。(2) 本番のカウンタは [1, 10^9) の中で動く。本番にすでに 10^9 以上の値がある表でも、本番が振る値は 10^9 未満なので重ならない。本番が 10^9 に届くと `ErrAutoIncrementExhausted`（MySQL は約 21 億まで振る。WordPress のプラグインの表では届かない前提で、記録だけ）。(3) バージョンを上げる前に作ったブランチは、次に番号を振るときに自分の枠から振る（保存したカウンタは帯の下限より小さいので使われない）。上げる前にすでに両側で同じ ID を足した行は、今と同じく競合。(4) ブランチの側を採れない競合（`Forbid`: 同じ ID の別の行、著者がいない記事）を黙って残さない。差分の行の `detail` にその理由を出し、ワイルドカードの `'branch'` が当たらずに残った競合は、マージのエラーに理由を添える（行を指定した `'branch'` は今もエラーになる）。(5) `docs/procedures.md`（番号帯）、`docs/plugins.md`（ブランチのマージで注意の要る表。`mediumint` 以下の AUTO_INCREMENT の表と、今回の前に作ったブランチ）、`scripts/plugin-check/check.py`（`mediumint` 以下の AUTO_INCREMENT の主キーを「ブランチのマージで競合しうる」として出す。Yoast のようにコードで作る表は見えないことを書く）、この文書の段階 6 の番号帯の説明を直す。
- 完了条件: 番号帯のテスト（`int`、`int unsigned`、`bigint`、`mediumint`、一時テーブル、main、枠の使い回しと、同じ枠の前のブランチのマージ済みの行の続きから振ること、上げる前のブランチの保存したカウンタ、明示した値、`ALTER TABLE` の書き直しの後のカウンタ）。Redirection の形で、両側が足しても競合にならず、マージの後に項目が正しいグループを指し、本番のカウンタが 10^9 未満で続く。`Forbid` の競合がワイルドカードの `'branch'` で残ったとき、差分とマージのエラーに理由が出る。直しを外すと対応するテストが落ちる。Go のテストが -race でも通る。PHPUnit の全テストで差が 43 から増えない。本物の WordPress（`scripts/wordpress`）に Yoast SEO と Redirection を入れ、ステージングと本番の両方で記事を作って編集し、リダイレクトを足してから差分とマージを流し、競合がなく、`yoast_indexable_hierarchy` と `yoast_seo_links` と `redirection_items` の参照が本番のマージの後も正しい行を指すことを確かめる。
- 結果: (1) `autoIncrementBand`（`table.go`）。`int` と `int unsigned` の列は、main が [1, 10^9)、ブランチ ID n が 10^9 + ((n - 2) mod 100) × 10^7 からの 10^7 の幅。カウンタ（`store.AutoIncrement`）は今までどおり、保存した値、帯の中の見えている行の最大値 + 1、帯の下限の大きい方から始めるので、枠を使い回したブランチは前のブランチのマージ済みの行の続きから振り、バージョンを上げる前のブランチの保存したカウンタ（帯の下限より小さい）は使わない。`ALTER TABLE` の書き直しも同じ帯を使う（`autoIncrementRange` を通る）。データ形式は変えていない。(2) ブランチの側を採れない競合（`Forbid`）が未解決で残ったとき、差分の `detail` に `only 'parent' can resolve this: <理由>` を足し（`rowDiff.forbidNote`。`'parent'` ## 段階 62: 組の表を片方だけ戻すときに知らせる

- 背景: 表を指定する復元（`heimdb_restore('main', T, 'wp_posts')`）は、記事を戻してもメタと分類を今のまま残す。消した記事はアイキャッチ、カスタムフィールド、カテゴリのない姿で戻り、後から作った記事のメタと分類は残り、中身をメタに持つ記事（Elementor、ACF）は題名だけが戻る。メタだけを戻すと逆向きに同じことが起きる。知らせていたのは、記事だけを戻すときに消える記事に残るコメントだけだった。
- 方針: 組（`posts` と `postmeta`、`posts` と `term_relationships`、`comments` と `commentmeta`、`users` と `usermeta`。接頭辞は自動で見分ける）の片方だけを戻すとき、時刻 T の後に親の行と子の行の両方が変わった ID を、戻す表の行の `detail` に出す（最初の 5 件と残りの数。最後に、当たった組の表をすべて加えた呼び出しを 1 つ。組ごとに出すと、片方を流しても揃わない）。片側だけが変わった ID は出さない。変わった行は `ChangedRowsSince` で拾い、ID の集合だけを持つ。`_edit_lock` と `_edit_last` は数えない。T の後にどちらかの表のテーブル ID が変わったときは比べず、そのことを出す。プレビューと復元の両方に出し、復元したときはログにも警告で出す（コメントの警告も出るようになる）。復元は止めない。戻す表を増やすこと、分類の件数の数え直し、プラグインの表どうしの組は作らない（文書に書く）。
- 完了条件: 記事だけを戻すとき、消した記事、後から作った記事、記事とメタの両方を編集した記事で警告が出て、メタだけを戻す逆向き、コメントとユーザーの組でも出る。記事だけの編集、`_edit_lock` だけの変化、変えて戻したメタ、両方の指定、既定の復元、`'*'` では出ない。書き直した表のときの文。プレビューと復元が同じ。判定を外すと落ちる。PHPUnit の差が 43 から増えない。本物の WordPress で、アイキャッチとカテゴリの付いた記事を消し、`wp_posts` だけを戻すと警告が出てアイキャッチのない姿で戻り、警告の呼び出しで両方を戻すとアイキャッチとカテゴリも戻る。
- 結果: `warnRestorePairs`（`restore.go`）。組の表（`restorePairs`）の片方だけを戻すとき、両側の変わった行の T と今の行を読み（同じ行と、編集のたびに変わるメタは飛ばす。下のレビューの直しを参照）、親の ID の集合の重なりを、戻す表の行の `detail` に組ごとに出し、最後に当たった組の表をすべて加えた呼び出しを 1 つ出す（組ごとに出すと、記事とメタ、記事と分類の両方が当たったとき、片方の呼び出しを流しても揃わないことが、本物の WordPress で分かった）。どちらかの表のテーブル ID が T と今で違えば、比べずにそのことを出す。復元したときは、`detail` のある行をログに警告で出す（コメントの警告も出るようになった）。`TestRestorePairedTables` で、消した記事、後から作った記事（6 件を超えて `and N more`）、記事とメタの両方の編集、メタだけを戻す逆向き、コメントとユーザーの組、書き直した親と子の表、復元の結果とログ、警告の呼び出しで戻すとメタと分類も戻ることと、記事だけの編集、`_edit_lock` と `_edit_last` だけの変化、変えて戻したメタ、両方の指定、既定の復元、`'*'` では出ないことを確かめた。判定（重なり、編集のロックの除外、同じ行の除外、テーブル ID の確かめ、表の一覧、ログ）をそれぞれ外すと落ちる。Go のテストは 387 件（-race とカーソルで読む設定でも成功）。PHPUnit の全テストは 43 で、段階 57 と同じテスト。接続の切断と panic は 0（1,303 本がすべて閉じた）。本物の WordPress（ローカルで作ったバイナリ、3336）で、アイキャッチ、カテゴリ、カスタムフィールドの付いた記事を消し、別の記事を作った後、`wp_posts` だけを戻すと、2 組の警告と 3 表を戻す呼び出しが出て、記事はアイキャッチとカテゴリのない姿で戻った。その呼び出しを流すと、アイキャッチ、カテゴリ、カスタムフィールドが戻り、後から作った記事のメタも消えた。データ形式は同じ。
- Fable のレビューで直したこと（高の指摘はなし）: (1) 公開済みの記事を保存すると WordPress が `_encloseme` と `_pingme` を足し、cron の ping が消すまで残るので、題名だけを直した記事も警告に出た。組の確かめでは、マージで飛ばす編集のロック（`merge.Policy.SkipPostmeta`）に加えて `_encloseme`、`_pingme`、`_trackbackme` を数えない（`restoreNoiseMeta`。マージは変えない）。(2) 戻す表の変わった行を組ごとに `ChangedRowsSince` で拾い直し、戻さない表の ID の集合も作っていた（310 万行のメタの大半が変わった後に記事だけを戻すと、確かめが復元より重い）。戻す表は計画で拾った主キー（`t.pks`）を `eachRestoreChange` で読み（写しだった `changedLinkIDs` をなくした）、戻さない表は集合を作らずに重なりだけを数える。(3) T と今の片方にしかない表も「rewritten」と書いていたので、「rewritten, created or dropped」にした。(4) マルチサイトのサブサイトの表は見ないことを文書に書いた。(5) テストに、`_encloseme` と `_pingme`、インデックスだけを足した `wp_posts`（テーブル ID が同じなので比べる）、親を 2 つ選んだときの呼び出し、コメントの警告のログ、組の片方の表がないサイト（`TestRestorePairMissingTable`）を足した。動きの変わらない分岐（何も戻さない表を先に飛ばす、選んだ表が計画にない）は外した。消す表（T の後に作った表）を飛ばす分岐も外し、文書どおり、作ったことを警告に出すようにした（2 回目のレビューの指摘。`TestRestorePairMissingTable`）。2 回目のレビューで記録だけにしたもの: 戻さない表の確かめは、その表の変わった行の主キーをメモリに持つので、上限が小さく、メタの大半が変わった後だと、記事だけの軽い復元が 1041 で止まりうる（文書に書いた）。戻す表に変化がないときの警告は結果に出ない（何も書かないので食い違わない）。T の後に作った記事が数えないメタ（`_edit_lock` など）だけを持てば、記事だけの復元で、そのメタが警告なしで残る（WordPress は記事のないメタを読まない）。直した後の Go のテストは 388 件（-race とカーソルで読む設定でも成功）。PHPUnit の全テストは 43 で、段階 57 と同じテスト。接続の切断と panic は 0（1,303 本がすべて閉じた）。
- バージョンを 0.2.14 にした（データ形式のバージョン 3 のまま。段階 62 を含む）。

## 段階 63: ブランチのユーザーに、自分のブランチの手続きを開ける（ホスティング側のお願い）

- 背景: `heimdb_*` の手続きは管理者（SUPER）だけが呼べるので、WordPress の管理画面から差分を見るには root でつなぐか、root を閉じ込めた別のサービスを作るしかなかった。root には `heimdb_branch_limit` の上限も効かない。差分は何も書かず、解決は自分のブランチの記録しか書かないのに、親を書き換えるマージと同じ壁の内側にあった。ブランチのユーザーは親を読めないので、競合の親の側の値が見えない。`CALL` は `LIMIT` で包めないので、行ごとの差分の量を呼び出し側で抑えられない（ホスティング側には 311 万行の `wp_postmeta` のサイトがある）。
- 方針: 起動フラグ `-branch-procedures`（既定はオフ）で、`heimdb_branch_diff`、`heimdb_branch_resolve`、`heimdb_changes`、`heimdb_restore_preview`、`heimdb_restore` を、接続中のデータベースの EXECUTE 権限で呼べるようにする。管理者でなければ、対象は接続中のデータベースのブランチだけで、main は拒否する。ブランチに `''` を渡すと接続中のブランチ（管理者も使える）。マージ、作成、削除、上限、マージから外す表は管理者だけのまま。ブランチのユーザーの解決は行の指定だけ（ハッシュがあり、値が変われば使われない）。解決の記録にユーザーと時刻を足し（省略できる項目。データ形式のバージョンは変えない）、ログにも出す。行ごとの差分に `resolved_by`、`resolved_at`、`conflict_values`（競合した列の両側の値）を最後に足し、開始と件数で区切る形（続きは `more` の行で知らせる）を足す。GRANT で手続きごとに開ける口は作らない。
- 完了条件: フラグがなければ今のまま。フラグがあれば、ブランチのユーザーが自分のブランチの 5 つを呼べ、別のブランチ、main、EXECUTE のないユーザー、管理者だけの手続き、ワイルドカードの解決は拒否する。記録したユーザーと時刻が差分に出る。記録の後に本番で値が変わると stale になりマージが拒否される。競合の両側の値とページ送り。ブランチのユーザーが呼んだ差分に実行時間の上限が効く。判定を外すと落ちる。PHPUnit の差が 43 から増えない。本物の WordPress で、ブランチだけの権限のユーザーが解決を記録し、管理者がマージできる。

## 段階 69: `SHOW INDEX ... WHERE` と `DO` を MySQL に合わせる

- 背景: 段階 68 で見つかった 2 つの差。(1) エンジンの `buildShowIndex`（`sql/planbuilder/show.go`）が `SHOW INDEX`（`SHOW KEYS`）の `WHERE`（vitess の `Show.ShowIndexFilterOpt`）を読まず、すべての索引を返していた。上位 100 の 11 本が `SHOW INDEX FROM t WHERE Key_name = 'x'` で索引の有無を確かめ、足すべき索引を足さず、ない索引を `DROP INDEX` してエラーになっていた（Smart Slider 3、SG Security、Google for WooCommerce の有効化。WooCommerce は `wp_comments` の索引を足さなかった）。上流の main も同じ。(2) vitess の構文解析が `DO` を知らず、WordPress 本体の `wpdb::check_connection()` の `DO 1` が構文エラーになり、WordPress がつなぎ直していた（UpdraftPlus と Duplicator はバックアップの途中で呼ぶ）。
- 方針: (1) ほかの `SHOW` と同じく、結果の列を小文字の名前でスコープに並べ、`WHERE` を `plan.Filter` で包む（エンジンの変更。docs/engine.md）。HeimDB の Sub_part を返す置き換え（`showIndexesWithSubPart`）は `Filter` の下でも効く。(2) 構文解析の包み（`parser.go`）で、文の先頭（空白とコメントの後）の語が `DO` なら `SELECT` にして解析し、解析した木の式に目印の別名を付ける（`rewriteDo`、`markDo`。`UNION` などは構文エラー）。実行の直前（`execBuilder`）に、目印の別名だけの射影を、射影を実行して読み切り OK を返す節（`doNode`）にする（`do.go`）。SELECT の結果をそのまま返す案は、`wpdb::query('DO 1')` の戻りや `mysql` クライアントの表示が MySQL と違うので採らない。(3) 段階 68 の比べる道具を `scripts/plugin-check/compare.sh`（MySQL は `docker-compose.mysql.yml` を重ねる）とシナリオ（`scenarios/`）としてリポジトリに入れる。Fable の計画レビューで、目印を文字列でなく解析した木に付けること、文の先頭の判定に既存の関数を使うこと、道具の出力を両側で揃えて終了コードを返すことにした。
- 完了条件: `SHOW INDEX ... WHERE` が本物の MySQL 8.0 と同じ行を返す（Sub_part も）。`DO` が OK を返し行を返さない（式の副問い合わせと実行時のエラーも）。Go のテスト（-race、カーソルで読む設定、記録を分ける設定）とエンジンのテストが通り、判定を外すと落ちる。PHPUnit の全テストで差が増えない。`compare.sh` で、Smart Slider 3 と SG Security の `DROP INDEX` と、UpdraftPlus の `DO 1` のエラーが HeimDB で出ない。
- 結果: `buildShowIndex` に `WHERE` を足した。`internal/backend/do.go`。最初は解析ルールで射影を `doNode` に置き換えたが、後のルールが中の射影に届かず、`DO (SELECT COUNT(*) FROM t)` の副問い合わせの列の位置が決まらなかったので、実行の直前に移した。列のない射影（`IN (SELECT 4)` の解析が作る）を `DO` と取り違えて、既存のテスト 2 本（`TestCoveringQueriesMatchMySQL`、`TestReview21UpdateRowNumbers`）が落ちたので、式が 1 つ以上の射影だけにした。`DO *` を拒否する判定は、表のない `SELECT *` としてエラーになり、テストで捕まえられないので入れない。テスト: `TestRewriteDo`、`TestDoStatement`、`TestShowIndexWhere`、エンジンの `TestInfoSchema` と `TestQueryErrors` に 4 本。`WHERE`、`doNode` への置き換え、語の境目、読み切り、`UNION` の判定のどれを外しても、テストが落ちる。 Go のテストは 389 件から 392 件（-race、`HEIMDB_TEST_CURSOR_MIN_ROWS=1`、`HEIMDB_TEST_LOG_CHUNK_BYTES=64` でも成功）。エンジンのテストは 53,231 件が通り（4 件増えた）、飛ばすのは 411 件のまま。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 65 と同じテスト（panic 0、接続 1,302 本をすべて閉じた。3336 で流した）。`compare.sh` で、UpdraftPlus（表ごとの行数も同じ）、Better Search Replace、Smart Slider 3 と SG Security の有効化は、HeimDB でだけエラーになった文が 0。WooCommerce は、主キーで拒否する `wc_product_attributes_lookup` の作成だけが HeimDB でだけのエラーとして出た（終了コード 1）。
- 記録だけ: `SHOW INDEX ... WHERE` の値の比較は大小文字を区別する（MySQL は `utf8mb3_tolower_ci` で区別しない。プラグインは作ったときと同じ名前で確かめる）。不明な列はエラー 1105（MySQL は 1054。ほかの文と同じ）。バイナリプロトコルの準備（COM_STMT_PREPARE）は vitess が HeimDB の構文解析より先に文を解析するので、`DO` は構文エラーのまま（文字列の `PREPARE s FROM 'DO 1'` は通る）。`DO 1 FROM t` のような MySQL では構文エラーの書き方も通り、`DO 1, * FROM t` のように行を返すものもある。集計（`DO MAX(1)`、`DO COUNT(*) FROM t`）や主キーの等号（`DO 1 FROM t WHERE id = 1`）の `DO` は、エンジンが結果を最大 1 行として返す経路が OK の結果を扱わないので、内部の型名を含むエラー 1105 になる（接続は切れない。`DO (SELECT COUNT(*) FROM t)` は通る）。`DO 1/0` は MySQL と同じく OK と警告。複数の文を送れる接続では、エンジンのログに残る文が書き換えた後の `SELECT` になる（mysqli は使わない）。目印の別名 `__heimdb_do__` の列だけの SELECT は `DO` になる（集計などは上と同じエラー）。Fable のコードレビューで、`do.go` のコメントの警告の記述の誤りと、`compare.sh` の MySQL 側がバックスラッシュをエスケープして出す（`-r` を付けた）ことを直した。

## 段階 70: 文字列、バイト列、日付を含む主キー

- 背景: 段階 68 で、文字列、日付、バイト列を含む主キーの表を作れず、WooCommerce（`wc_product_attributes_lookup` の `(product_id, product_or_parent_id, taxonomy, term_id)`）、Wordfence（`VARBINARY` の IP など）、WPForms Lite（`DATE` の主キー）、WP Reviews for Google が一部か全部を使えなかった。整数の主キーと 1 列の文字列の主キー（段階 38）にしか対応していなかった。
- 方針: 主キーの列に、整数、`CHAR` と `VARCHAR`（utf8mb4 と utf8mb3 の照合順序）、`BINARY` と `VARBINARY`、`DATE`、`DATETIME`、`TIMESTAMP`、`ENUM` を、どう組み合わせても使えるようにする。キーの形は「順序を保つ符号化」に書いた（既存の整数と 1 列の文字列のキーは変えない）。インデックスのエントリから主キーを取り出す処理（`pkOfEntry`）は、今までどおり、主キーが整数の列だけなら後ろから切り、そうでなければインデックスの列を前から読み飛ばす（日時は固定長だが、分けても速さの差をテストで捕まえられないので分けない）。主キーの点の読み出し（`exactKey`）にバイト列を足す（エンジンの文字列の判定はバイト列にも真になるので、その前に置く）。ブランチの差分は、主キーの列の名前に加えて型も比べる（キーの形が型で変わる）。差分と競合の表示は、既存の `jsonValue` で主キーの値を書く（整数と文字列の表示は変えない）。データ形式のバージョンを 4 に上げ（移す処理はなく、番号だけを書き換える）、記録の中身の形は 2 のまま。主キーのない表は今までどおり拒否する。`TEXT`、`BLOB`、`SET` などの主キーも拒否する。Fable の計画レビューで、`exactKey` のバイト列の扱い、`DATE` に時刻の付いた値はすでに正しく扱っていること（テストで確かめるだけ）、運用の文書（`docs/operations.md`）の上げる手順とレプリカの注意を足すこと、バージョンを上げる理由を「新しい形の表を古いバージョンで開かせない」と書くことにした。
- 完了条件: 主キーの符号化の順序が、値の順序（MySQL の比較）と一致する（プロパティテスト。空の値、`0x00`・`0x01`・`0xFF` を含むバイト列、ゼロの日付、大小文字だけ違う文字列を含む）。新しい形の主キーの表で、INSERT、主キーの点と範囲の読み出し、セカンダリインデックス、UPDATE、DELETE、重複のエラー、ブランチの差分とマージ、`AS OF` が動く（Go のテスト）。判定を外すと落ちる。Go のテスト（-race、カーソルで読む設定、記録を分ける設定）が通る。PHPUnit の全テストで差が増えない。`compare.sh` で、WooCommerce、Wordfence、WPForms Lite、WP Reviews for Google の主キーのエラーが HeimDB で出ない。
- 結果: `rowenc` の `AppendPKValue` を型ごとに分け（`PKType`）、`validateSchema` の判定を 1 つにした。計画から 2 つ足した。(1) `BINARY(n)`: `compare.sh` で、Wordfence の有効化が通ると、`BINARY(16)` の IP を主キーに含む表が 7 個あると分かった（`wfblockediplog` など）。エンジンは `BINARY(n)` の値を書くときに末尾を `0x00` で埋めて n バイトにそろえるので、そろえた値をキーにする。範囲の端の値はエンジンの変換で埋まるが、MySQL は短い値を埋めずに比べる（`k > 'ab'` は `'ab\0\0'` の行を含む）ので、短い値は区間に使わず条件で絞り直す（`convertKey`）。(2) `ENUM`: Wordfence の `wftrafficrates (eMin, IP, hitType)`。エンジンは値を番号（uint16）で持ち、番号で比べるので、整数と同じ形で入れる。差分と重複のエラーの行の名前は、`ENUM` を名前で、UTF-8 として読めないか制御文字（`BINARY` の末尾を埋めた `0x00` など）を含むバイト列を `0x` の 16 進で書く（生のバイトのままだと、`heimdb_branch_diff` が結果の文字列で 1105 になった）。`pkOfEntry` を日時の固定長で後ろから切る案は、前から読んでも結果が同じで、テストで捕まえられないので入れず、整数だけの主キーを後ろから切るまま。`ENUM` を区間に使わない判定も、エンジンの絞り込みと同じ結果になり捕まえられないので入れない。テスト: `TestMixedPKOrder`（rowenc。7 つの型と `BINARY`、`ENUM` を 1〜3 列で組み合わせ、順序と前方の一致を確かめる）、`TestMixedPrimaryKey`（WooCommerce、Wordfence 3 表、WPForms Lite、WP Reviews、WPML、日時の主キーの表で、読み書き、インデックス、重複、`AS OF`、差分とマージ、変更の一覧と復元）、`TestPrimaryKeyTypeDiffers`、`TestExactKeyBinary`、`TestNonIntegerPrimaryKeyRejected` を受け付ける側と拒否する側に分けた。変異（エントリの主キーを後ろから切る、`exactKey` のバイト列、主キーの型の比較、差分の書き方、`BINARY` の短い値、`BINARY` と `ENUM` を受けるか、`BLOB` を拒否するか、`PKType` の判定、バイト列の符号化、バイト列の `string` の値、重複のエラーの書き方、16 進）はどれもテストが落ちる。Go のテストは 392 件から 396 件（-race、`HEIMDB_TEST_CURSOR_MIN_ROWS=1`、`HEIMDB_TEST_LOG_CHUNK_BYTES=64` でも成功）。PHPUnit の全テストで、本物の MySQL との差は 43 件で段階 69 と同じテスト（panic 0、接続 1,302 本をすべて閉じた。3336 で流した）。`compare.sh` で、WooCommerce（商品、属性の絞り込み、注文）、Wordfence（有効化とスキャン）、WPForms Lite と WP Reviews for Google の有効化は、HeimDB でだけエラーになった文が 0。WPML 4.6.11 とアドオン 4 本は、有効化（`activate.sh` の `REQUIRES` に手元のディレクトリを渡せるようにした）で拒否した文が 0。`docs/plugins.md` は、使える 151 本、条件付き 1 本（WooCommerce の注文の全文検索）、使えない 2 本（主キーのない表の WP Cerber と Loginizer）。`check.py` の主キーの判定も合わせた。
- コードレビュー（Fable）で直したもの: (1) 日時の列の範囲で、定数を列の型に変換すると丸められる端（`DATE` の列に `'2026-10-20 10:00:00'`、`DATETIME` の列に秒より細かい値）を、エンジンが丸めた値のまま区間の端にし、MySQL なら返す行を落としていた（`d < '2026-10-20 10:00:00'` が `2026-10-20` の行を落とす。セカンダリインデックスにも前からあった）。エンジンの範囲の組み立て（`costed_index_scan.go` の `timeKeyRounds`）で、丸められる端を含む側に広げる（`<` を `<=` に。列の値はどれも列の精度なので、条件に合う行は範囲に入り、広げた分は残した条件で落とす）。HeimDB の `convertKey` も、丸められる日時の値を区間に使わない（`exactKey` と、範囲の端を読む解析のルールにあった同じ判定をまとめた）。(2) 照合順序を書かない `ALTER TABLE ... - 記録だけ: `'0000-00-00'` と `'0000-01-01'` の日付は同じキーになる（エンジンがどちらも Go のゼロの時刻にする。主キーでない列の比べ方と同じ）。`TIMESTAMP` のキーは UNIX 秒なので、接続の時間帯によらない。主キーに NULL を入れると明示的なエラー。主キーでない列と同じエンジンの差として、`CONCAT` に `DATE` の列を渡すと時刻が付き（`'0000-00-00'` は `0000-01-01 00:00:00`）、`GROUP_CONCAT` に `ENUM` の列を渡すと番号になり、`ENUM` の列を文字列の定数と比べると番号で比べる（MySQL は文字列で比べる。`h > 'a'`）。`BINARY(n)` の列を、末尾を `CHAR(0)` で埋めた文字列の式と比べると等しくならない（MySQL は等しい）。重複のエラーの値は、`DATE` にも `00:00:00` が付き、`ENUM` は番号（列の型を見ない）、`TIMESTAMP` は UTC（MySQL は接続の時間帯）。差分の行の名前で、`VARBINARY` の文字列の `0xFF` とバイトの 0xFF は同じに書く。JOIN のインデックスの検索のキーは、エンジンが列の型に変換する（`BINARY(n)` は末尾を埋め、`DATE` は時刻を切る）ので、MySQL より広く一致する（`checkLookupKeys` が包むのは整数の列だけ。WordPress は使わない）。

### エンジンの変更

[`docs/engine.md`](../engine.md#変更の一覧) の変更の一覧の、この段階の行の全文（変更、理由）。

- 日時の列の範囲で、定数を列の型に変換すると丸められる（`DATE` の列に時刻の付いた値、`DATETIME` の列に秒より細かい値）なら、`<` と `>` を `<=` と `>=` に、`<>` を NULL でない全体にし、`NOT IN` ではその値を除かない（`sql/analyzer/costed_index_scan.go` の `timeKeyRounds`。範囲の組み立ての `sql.MySQLIndexBuilder` は変えない）
  - 理由: 不具合。範囲の組み立ては値を列の型に変換して丸めた値を端にするが、MySQL は丸めずに比べるので、`d < '2026-10-20 10:00:00'` が `DATE` の `2026-10-20` の行を落としていた（上流の main も同じ）。列の値はどれも列の精度なので、丸めた値を含めば条件に合う行は範囲に入る。広げた分は、残した条件で落とす（列の型と違う型の定数との比較は `PreciseComparison` が偽で、条件をいつも残す）。テストを `enginetest/queries/script_queries.go` に足した
